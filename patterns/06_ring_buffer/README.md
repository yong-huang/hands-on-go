# 06 · Ring Buffer：固定数组 + head/tail 取模回绕

> 环形缓冲区（Ring Buffer / 循环队列）用**固定大小数组**和 **head/tail 两个指针**实现 FIFO 队列：指针走到数组末尾就取模回绕到开头，复用已读出的空间，无需动态分配、无数据搬移、读写均 O(1)。读完本篇，你能写出一个完整 Go 实现，把回绕、判满、判空变成看得见的指针数值。

## Background

用普通切片做队列，读出头部元素后只有两种选择：要么 `s = s[1:]`——底层数组越切越长，前面的内存再也用不上；要么把剩余元素整体前移搬移——每读一个元素就要搬 O(n) 个。日志、音视频这类高频读写的队列里，两条路的浪费都会持续累积。

环形缓冲区的答案是让指针"转圈"：前进改为取模回绕 `tail = (tail + 1) % cap`，读写都在同一个固定数组里进行，两个操作都严格 O(1)，数组创建后既不扩容也不搬移。

代价是实现细节变多了：首尾相接之后，"满"和"空"的判别、回绕的边界、满时的语义（拒绝还是覆盖）都成了必须想清楚的问题——也是手写时出错最集中的三处。

## What

Ring Buffer（环形缓冲区/循环队列）是一种用固定大小数组实现的 FIFO（First In First Out，先进先出）队列：head 与 tail 两个下标沿数组取模回绕（用 `%` 运算越过末尾后回到 0），读写过程不搬移任何数据。

可以把数组想象成一条环形传送带：head 是取餐口，tail 是放餐口，两个口各自沿带子转圈前进，用过的带面自动回收复用。但和真实传送带不同的是，带子长度固定，且两个口可能停在同一个位置——重叠时究竟是空带还是满带，必须靠一个计数器（或牺牲一个格子）来说明。

| 部件 | 职责 | 关键约定 |
|---|---|---|
| `head` | 指向下一个**读出**的位置 | 用 `% cap` 回绕 |
| `tail` | 指向下一个**写入**的位置 | 用 `% cap` 回绕 |
| `count` | 当前元素数量 | 负责区分"满"和"空"——否则 `head == tail` 时两种状态无法区分 |

## When to Use

这一节给出判断依据：固定内存预算、头尾顺序访问，是它适用的共同前提。

- **生产者-消费者之间垫缓冲时**：一端写入、一端读取，内存预算固定，需要严格 O(1) 的入队出队。
- **日志环/指标采样时**：只关心最近 N 条，满后用覆盖语义挤掉最旧数据，内存永不增长。
- **音视频流/内核缓冲这类恒速流转的场景时**：数据按固定节奏流过缓冲区，数组复用恰好匹配。

何时不用：

- 需要随机访问中间元素或动态扩容：切片才是自然选择，环形缓冲只暴露头尾。
- 元素量不可预估且一条都不能丢：固定容量会拒绝写入，需要可扩容的队列结构。
- 多生产者/多消费者并发：本文实现非线程安全，并发方案复杂（见 Q&A），生产代码通常直接用 channel。

同类方案对比：

| 方案 | 与 Ring Buffer 的差异 | 什么时候选它 |
|---|---|---|
| 切片队列 `s[1:]` | 写法简单；底层数组持续增长，前面内存浪费 | 偶尔用一下的短队列 |
| 搬移式队列 | 逻辑最直观；每次读要搬移剩余元素，O(n) | 队列极短且读频极低 |
| Go channel | ring buffer 加锁与阻塞语义的开箱即用版 | 生产代码里的并发队列 |

三个关键观察：`Write(50)` 后 **tail 从 4 回绕到 0**；写满时 `head == tail == 2` 却是"满"；满后再写指针**一动不动**，返回 `ErrFull`。

实现的全部状态在五个字段里。这段在做什么：声明固定数组与 head/tail/count 三个控制字段，数组创建后大小不变：

```go
type RingBuffer struct {
    buf   []int // 底层数组（固定大小，创建后不变）
    head  int   // 下一个读出的位置
    tail  int   // 下一个写入的位置
    count int   // 当前元素数量
    cap   int   // 最大容量
}
```

`count` 是本实现的关键设计：只用 head/tail 无法区分满和空，加一个计数器是最直接的方案。

## How It Works

机制的主线是：**读走 head，写走 tail，推进都取模，count 仲裁满空**。

### Write：先判满，写 tail，取模回绕

```go
func (rb *RingBuffer) Write(val int) error {
    if rb.IsFull() { // count == cap
        return ErrFull
    }
    rb.buf[rb.tail] = val
    rb.tail = (rb.tail + 1) % rb.cap // 回绕
    rb.count++
    return nil
}
```

本实现是**拒绝语义**：满时返回 `ErrFull`，不覆盖旧数据（何时该用哪种语义见 Q&A）。

输出第 3 步 `Write(70)` 写入 `buf[1]` 后 tail 落回 2——你在输出里看到的 `head=2 tail=2 len=5` 满状态，物理数组此时是 `[60 70 30 40 50]`，逻辑序却是 `30 40 50 60 70`，回绕让两者不再相同。

### Read：先判空，读 head，取模回绕

```go
func (rb *RingBuffer) Read() (int, bool) {
    if rb.IsEmpty() { // count == 0
        return 0, false
    }
    val := rb.buf[rb.head]
    rb.head = (rb.head + 1) % rb.cap // 回绕
    rb.count--
    return val, true
}
```

`Show()` 按逻辑序打印：第 i 个元素是 `buf[(head+i)%cap]`——取元素同样要取模。所以满状态打印 `[30 40 50 60 70]`，而物理数组里是 `idx0=60, idx1=70, idx2=30...`。

输出第 6 步的 FIFO 验证（写入 100, 200, 300，读出 100 200 300）就是 head 沿逻辑序逐格前进的结果。

### 与 Go channel 的关系

`chan int` 的缓冲就是 `runtime.hchan.buf` 这个 ring buffer，在此之上加了锁（并发安全）、`sendq`/`recvq` 等待队列（阻塞/唤醒语义）和 select 支持。缓冲 channel 满时发送者阻塞——等价于这里返回 `ErrFull` 的"暂停"变成了挂起。

### 关键字段一览

| 字段/表达式 | 含义 | 为什么重要 |
|---|---|---|
| `head` | 下一个读出的下标 | 回绕后逻辑序 ≠ 物理序 |
| `tail` | 下一个写入的下标 | 满时 `tail == head`，但含义是"写不进" |
| `count` | 当前元素个数 | 判满 `count==cap`、判空 `count==0`，消除歧义 |
| `(tail+1) % cap` | 回绕推进 | 手写时漏 `%` 会越界；漏判满会覆盖未读数据 |

## Pitfalls & Q&A

以下条目都来自手写实现时的真实失误，每条按现象、原因、解法展开。

### 踩坑清单

- **满/空歧义**。现象：`head == tail` 时分不清是空还是满，读写行为错乱。原因：两个指针重合对应两种状态，对称性破坏不了。解法：方案 A 加 `count` 字段（本实现，多 4/8 字节）；方案 B 浪费一个槽位——判满 `(tail+1)%cap == head`、判空 `head == tail`，代价是有效容量只剩 cap-1。
- **漏取模**。现象：回绕一次后立即数组越界 panic。原因：`tail++` 写成不取模，指针越过末尾。解法：所有推进一律 `(i+1) % cap`，包括 `Show()` 里按逻辑序取元素。
- **覆盖与拒绝混淆**。现象：该报错的场景悄悄丢了数据，或该循环覆盖的场景写满即失败。原因：动手前没确认语义要求。解法：先问清满时是 return error 还是前移 head，再写代码。
- **cap 为 0**。现象：`NewRingBuffer(0)` 后第一次操作 panic。原因：`% 0` 除零。解法：构造函数前置校验容量。
- **并发使用未加锁**。现象：多 goroutine 同时读写时数据竞争。原因：本实现非线程安全。解法：外层加锁；能否做 lock-free 变体见下方 Q&A。

### 深入问答

**Q：为什么读写都要取模？不取模会怎样？**
A：见上文 Write/Read 两节的 `(i+1)%cap`——指针到末尾后必须回到 0 才能复用已读空间；不取模则要么越界 panic，要么被迫整体搬移数据退化成 O(n)。

**Q：满时应该拒绝写入还是覆盖最旧的数据？**
A：看场景。有界队列/背压场景（下游处理不过来时让上游暂停的机制）必须拒绝——返回 error 或阻塞，丢数据不可接受；日志环、监控采样等只关心最近 N 条的场景用覆盖语义——写 tail 的同时把 head 前移一格，本质是用 O(1) 换掉最旧元素。

手写前先确认语义要求。

**Q：能做 lock-free（无锁）的环形缓冲吗？**
A：单生产者单消费者（SPSC）可用 CAS（compare-and-swap，原子比较并交换）+ atomic 去掉锁；多生产者/多消费者（MPMC）要保证先占位再写槽的顺序，复杂度高很多，通常直接用 channel。
