# 01 · LRU Cache：map + 双向链表实现 O(1) 淘汰

> LRU（Least Recently Used，最久未使用）是一种缓存淘汰策略：容量满时淘汰最久未被访问的条目，且 `Get`/`Put` 都必须是常数时间 O(1)。读完本篇，你能用 `container/list` + `map` 写出一个完整可运行的 LRU 缓存，并从真实输出看清每一次淘汰与移动。

## Background

缓存（用一块小而快的存储挡在慢速存储前面，把读过的数据暂存起来）容量总是有限的，写入新条目前必须先腾位置。任何容量受限的缓存都绕不开同一个问题：**淘汰谁**。

最直接的两个做法是随机淘汰和 FIFO（First In First Out，先入先出，按写入顺序淘汰最早的条目）。它们在一种典型场景下撞墙：某条数据正被密集反复读取，仅因为它写入得早，FIFO 会率先把它淘汰；随机淘汰也有同样的概率选中它。结果是刚删掉的数据马上又要从慢速存储重新加载一遍。

观察到的规律是时间局部性——刚被访问过的数据，短时间内很可能再次被访问。据此自然想到按"最久未被访问"来淘汰。但工程上还有两条硬性要求同时成立，这让数据结构的选择变得不平凡：

- `Get`/`Put` 都是 O(1)（常数时间，耗时与缓存中的条目数无关）：查找必须靠哈希表；
- O(1) 内维护"谁最久没用"：顺序必须靠链表，且删除任一节点不能遍历找前驱，所以必须是双向链表。

## What

LRU（Least Recently Used，最久未使用）是一种按访问新鲜度淘汰条目的缓存策略：容量满时，把最久没有被访问过的条目删掉。它不是一种新发明的数据类型，而是两种基础结构的组合——哈希表加双向链表。

可以把整个结构想象成一条排队队伍：谁被用到，谁就立刻站到队首；队伍超员时，队尾的人离场。map 是点名册——报上 key 就能直接定位到队伍里的那个人；链表是队伍本身，记录谁最靠前。但和真实队伍不同的是，这里"移到队首"是纯指针摘接，不需要本人真的走过去，所以这一步也是 O(1)。

| 部件 | 职责 | 关键约定 |
|---|---|---|
| `map[int]*list.Element` | 按 key 一跳找到节点 | 存的是链表节点指针，不是值 |
| 双向链表 `*list.List` | 维护使用顺序 | Front=MRU（Most Recently Used，最近使用），Back=LRU（最久未使用） |

于是每个操作都拆成两半：命中或写入把节点移到链表头；容量满时把尾部节点从链表 `Remove`、再从 map 里 `delete`——两步都是 O(1)。

## When to Use

这一节给出判断依据：什么活儿适合交给 LRU，什么情况下它反而多余。

- **给进程内热点数据加内存缓存时**：API 服务反复读取同一批配置、会话或用户资料，内存装不下全部条目，只能保留一部分，且访问有明显热点。
- **给慢速存储垫一层容量受限的缓存时**：例如数据库查询结果、磁盘文件元数据，命中（要读的数据恰好在缓存里）就免去一次慢速访问。
- **需要"最近 N 个"语义的记录场景**：比如只关心最近访问过的 key 集合，与"最久未使用即淘汰"天然对应。

何时不用：

- 数据量小到全部装得下：直接用 map，淘汰逻辑纯属多余。
- 访问模式接近均匀随机：没有时间局部性可用，LRU 相比随机淘汰没有优势。
- "最近"不等于"常用"：条目价值取决于频率而非新鲜度时，按频率淘汰更合适，见 [02_lfu_cache](../02_lfu_cache/)。
- 多 goroutine 并发读写：本文实现非并发安全，需要分片加锁的方案，见 [20_concurrent_lru](../20_concurrent_lru/)。

同类方案对比：

| 方案 | 与 LRU 的差异 | 什么时候选它 |
|---|---|---|
| 不设淘汰的 `map` | 无容量管理，内存随 key 数增长 | 数据量小且可控 |
| FIFO | 只看写入顺序，读操作不影响顺序 | 条目写一次读一次、新老更替稳定 |
| 随机淘汰 | 不维护任何顺序，实现最简单 | 对命中率无要求、想省维护成本 |
| LFU | 按访问频率而非最近性淘汰 | 热点集合长期稳定 |

```text
1. Put:
  Put(1,10)    Cache: [1:10]
  Put(2,20)    Cache: [2:20] [1:10]
  Put(3,30)    Cache: [3:30] [2:20] [1:10]

2. 淘汰:
  Put(4,40) → 淘汰key=1    Cache: [4:40] [3:30] [2:20]

3. Get:
  Get(2)=20 (命中)    Cache: [2:20] [4:40] [3:30]
  Get(4)=40 (命中)    Cache: [4:40] [2:20] [3:30]
  Get(1)=0 (未命中)    Cache: [4:40] [2:20] [3:30]

4. 随机测试:
  Cache: [1:78] [4:9] [2:43]
```

注意第 3 步的细节：`Get(2)` 命中后 `[2:20]` 立刻跳到输出序列的最前面；`Get(4)` 命中后又把 `[4:40]` 提到最前。**每次读都会改变顺序**——这正是 LRU 与 FIFO 的分水岭：FIFO 的读操作不改变顺序。

实现只有两个结构体加两个方法。先看数据结构定义，这段在做什么：声明条目 `entry` 与缓存主体 `LRUCache`，map 存 key 到链表节点的指针，链表维护使用顺序：

```go
type entry struct{ key, value int }

type LRUCache struct {
    cap   int
    m     map[int]*list.Element // key → 链表节点指针
    order *list.List            // 双向链表：Front=MRU, Back=LRU
}
```

`container/list` 是标准库提供的双向链表。`entry` 里必须存 `key`：淘汰尾部时要从节点反查 key 才能删除 map 里的映射，这是最容易漏的一点。

## How It Works

机制围绕一条主线展开：**map 定位，链表定序**。每个操作的两半分别由两个结构承担。

### 两个结构如何分工

| 需求 | 哈希表 | 双向链表 | 组合 |
|------|--------|----------|------|
| O(1) 查找 | ✅ map[key] | ❌ 需遍历 | map 查 |
| O(1) 移到最前 | 无序 | ✅ MoveToFront | 链表移 |
| O(1) 插入 | ✅ | ✅ PushFront | 两者都做 |
| O(1) 删最旧 | ❌ 无序 | ✅ Remove(Back) | 链表删 + map 删 |

你在输出里看到的 `Cache: [2:20] [4:40] [3:30]`，就是链表从 Front 到 Back 的遍历结果——最左侧是 MRU，最右侧是下一个将被淘汰的 LRU。

### Get：命中即移动

```go
func (c *LRUCache) Get(key int) (int, bool) {
    if e, ok := c.m[key]; ok {
        c.order.MoveToFront(e) // 标记为最近使用
        return e.Value.(*entry).value, true
    }
    return 0, false
}
```

哈希查找 O(1)，`MoveToFront` 是纯指针摘链/重挂，也是 O(1)。输出里 `Get(2)=20 (命中)` 之后 `[2:20]` 跳到队头，就来自 `MoveToFront` 这一行。未命中返回 `(0, false)`，调用方靠 `ok` 区分"存的值就是 0"和"不存在"。

`e.Value.(*entry)` 是类型断言（从 `any` 接口值里取回具体类型）：`list.Element` 的 `Value` 字段类型是 `any`，每次读写都要断言一次。

### Put：三步走

```go
func (c *LRUCache) Put(key, value int) {
    if e, ok := c.m[key]; ok {          // 1. 已存在：更新值 + 移到头
        e.Value.(*entry).value = value
        c.order.MoveToFront(e)
        return
    }
    if c.order.Len() >= c.cap {         // 2. 容量满：淘汰尾部
        b := c.order.Back()
        c.order.Remove(b)
        delete(c.m, b.Value.(*entry).key)
    }
    e := c.order.PushFront(&entry{key, value}) // 3. 头插并登记 map
    c.m[key] = e
}
```

输出第 2 步的 `Put(4,40) → 淘汰key=1` 走的是第 2 分支：key=1 位于链表尾（Back，最久未使用），`Remove(b)` 把它摘出链表，`delete(c.m, 1)` 抹掉映射，两步都 O(1)。

**更新已有 key 不算新容量**：直接改值 + 移到头就返回，不触发淘汰（输出第 4 步随机测试里大量走这条路径）。

### 关键字段一览

| 字段/操作 | 含义 | 为什么重要 |
|---|---|---|
| `m map[int]*list.Element` | key → 节点 | 存的是**指针**，才能 O(1) 拿到节点去 MoveToFront/Remove |
| `order *list.List` | 双向链表 | 方向约定：Front=MRU、Back=LRU，实现前要先说清 |
| `entry.key` | 节点反存 key | 淘汰时 `delete(c.m, key)` 全靠它 |
| `e.Value.(*entry)` | 类型断言 | `list.Element.Value` 是 `any`，每次读写都要断言 |
| `MoveToFront` | 摘链 + 头插 | O(1) 的前提是节点已有 `Prev` 指针——单向链表做不到 |

## Pitfalls & Q&A

以下条目都来自手写实现时的真实失误，每条按现象、原因、解法展开。

### 踩坑清单

- **entry 忘存 key**。现象：淘汰后 map 里残留已删节点的映射，之后 Get 已淘汰 key 会命中脏数据，缓存"越删越脏"。原因：链表节点只能反查 value，没有 key 就无法 `delete` map。解法：`entry` 同时存 key，淘汰时用它删映射。
- **更新已有 key 误走淘汰分支**。现象：Put 一个已存在的 key 也会挤掉别的条目。原因：先判断容量、后判断存在性，顺序反了。解法：先查存在性，命中就更新值 + MoveToFront 后直接 return。
- **Get 只查不动**。现象：缓存行为退化成 FIFO，热数据被误淘汰。原因：命中后没有 MoveToFront，链表顺序只剩写入顺序。解法：命中即移动，这一行不能省。
- **cap ≤ 0 未防护**。现象：传入 cap ≤ 0 时代码不报错，行为没有定义。原因：练手题约束通常给定 `1 ≤ capacity`，生产实现必须自己兜底。解法：构造函数里显式校验并拒绝非法容量。
- **并发使用未加锁**。现象：多 goroutine 下 map 并发读写 panic，或链表结构损坏。原因：本实现非并发安全，且 Get 内含 MoveToFront 写操作，不能只加读写锁 RWMutex（允许多个读者或一个写者的锁）的读锁。解法：整体加 `sync.Mutex`；高并发改用分 shard（把缓存拆成多个独立加锁的小缓存），见 [20_concurrent_lru](../20_concurrent_lru/)。
- **数据图与演示序列脱节**。现象：改动 main 的演示序列后，`viz.py` 生成的统计对不上。原因：其统计来自固定演示序列（Put=4、Get=3、Evict=1、命中 2/未命中 1）。解法：改动后重新运行 `viz.py` 生成数据图。

### 深入问答

**Q：为什么必须双向链表，单向链表行不行？**
A：`MoveToFront` 和 `Remove` 都要修改节点**前驱**的后继指针。单向链表找前驱要从头遍历，O(n)；双向链表节点自带 `Prev`，O(1) 完成。

手写时最容易错的地方是摘链要同时接好 `prev.next` 和 `next.prev` 四根指针（`container/list` 已封装好，手写版要自己防漏）。

**Q：Get/Put 的 O(1) 分别由哪个结构承担？**
A：见上文 How It Works 的分工表——查找归 map，移动与插入归链表，淘汰是链表删 + map 删两步。

**Q：手写还有哪些实现取舍要注意？**
A：哨兵头尾节点（不存业务数据的占位节点）能把"空缓存/单节点"的边界统一成同一套指针逻辑；不设哨兵，则每个操作都要特判空表。

**Q：边界条件怎么验证？**
A：cap=1 时每次 Put 不同 key 都淘汰唯一旧元素；重复 Put 同一 key 不应增加链表长度、不应触发淘汰；Get 已淘汰 key 返回 miss 且不改变链表。演示第 2、3 步覆盖了淘汰与 miss。
