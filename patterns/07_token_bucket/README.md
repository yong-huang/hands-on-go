# 07 · Token Bucket 令牌桶限流器：恒速补充、桶封顶、按需消费

> 令牌桶（Token Bucket）是最经典的限流算法，Nginx 的 `limit_req`、`golang.org/x/time/rate` 都基于它：允许短时突发流量（burst），同时保证长期平均速率不超过阈值。读完本篇，你能用 Go 从零实现一个线程安全的令牌桶，并用 100 个并发请求实测验证。

## Background

限流（rate limiting，控制单位时间内通过的请求数）是后端的常规需求：API 网关、数据库保护、防爬策略都要精确控制请求速率，否则一次突发就能把下游打垮。

更早的两类做法各有短板：固定窗口计数（把时间切成固定窗口，每窗口计数一个上限）在窗口边界可能出现 2 倍突发——前一个窗口末尾和后一个窗口开头的请求加起来远超阈值；滑动窗口更平滑，但内存开销大。而很多场景（如开放 API）要的是"平时匀速、短时能扛突发"。

令牌桶用一个模型同时满足这两点：系统以恒定速率往桶里放令牌，每个请求取走 1 个令牌才能通过——桶里攒下的令牌就是突发余量，桶空了就拒绝。本文的实现是一个可运行的 Go 版本：100 个 goroutine 并发抢一个桶、顺序请求观察令牌缓慢恢复、`-race` 验证并发安全。

## What

令牌桶是一种限流算法：以恒定速率向容量有限的桶中补充令牌，请求取到令牌才放行。它由四个要素组成，速率与容量两个参数定一切：

| 要素 | 含义 | 类比 |
|------|------|------|
| `tokens` | 当前可用令牌数（`float64`，支持分数令牌） | 桶里的水 |
| `rate` | 每秒补充的令牌数 | 水龙头流速 |
| `burst` | 桶的最大容量 | 桶的容积 |
| `last` | 上次补充时刻 | 计时起点 |

可以把令牌桶想象成一个接在恒速水龙头下的水桶：水龙头以 `rate` 的流速滴水，桶最多装 `burst`（多余的溢出丢弃），每个请求来取一杯水（1 个令牌），取不到就被拒。

但和真实水桶不同的是，这里的水不按秒实时注入，而是在下次请求到达时一次性"补账"（惰性结算，见 How It Works）；且只按整杯取用，不足 1 个令牌时哪怕有 0.9 个也不放行。

核心公式：`tokens += rate × elapsed`，但不超过 `burst`。`rate` 决定长期平均速率，`burst` 决定突发容忍度。

## When to Use

这一节给出判断依据：是否需要"平均限速 + 突发容忍"的组合，决定令牌桶是否合适。

- **API 网关/服务出入口限流时**：保护下游不被突发流量打垮，同时允许客户端短时的小突发不被误杀。
- **数据库保护/防爬策略时**：给每秒查询数（QPS）设上限，超速请求直接拒绝，把攻击性流量挡在门外。
- **对外开放 API 配额时**：向调用方承诺"长期平均 X 次/秒、最多突发 Y 个"，令牌桶的语义正好一一对应。

何时不用：

- 要求输出严格平滑、不允许任何突发：漏桶（Leaky Bucket——以恒定速率处理请求的另一类限流算法）更合适。
- 多实例部署：单机桶只保护一个进程，需要分布式限流方案（见 Q&A）。
- 只需要粗略的总量控制：固定窗口计数几行代码就够，不必引入浮点令牌与锁。

同类方案对比：

| 方案 | 与令牌桶的差异 | 什么时候选它 |
|---|---|---|
| 固定窗口计数 | 实现最简单；窗口边界可能出现 2 倍突发 | 精度要求低 |
| 滑动窗口 | 更平滑无边界效应；内存开销更大 | 不接受边界突发的统计场景 |
| 漏桶 | 恒定速率输出，不允许突发 | 流量整形/削峰填谷 |

## Quick Start

前置条件：只需安装 Go 工具链，代码无第三方依赖。两条命令分别跑并发演示与数据竞争检测：

```bash
cd patterns/07_token_bucket
go run token_bucket.go        # 并发演示 + 顺序演示
go run -race token_bucket.go  # 数据竞争检测（应无 WARNING）
```

并发演示预期输出（节选，goroutine 编号每次不同，但合计恒定）：

```text
Config: rate=10 tokens/sec, burst=20

  [goroutine 02] ALLOWED
  [goroutine 50] REJECTED (no tokens)
  ...
Results: 20 allowed, 80 rejected (total=100)

Remaining tokens: 0.00
```

顺序演示（rate=2/s、burst=5、每 200ms 一个请求，节选）：

```text
  Request  1: ALLOWED (tokens=4.00)
  Request  7: ALLOWED (tokens=0.42)
  Request  8: REJECTED (tokens=0.82)   ← 打印的是请求后余额，0.82 < 1 所以本轮被拒
  Request  9: ALLOWED (tokens=0.22)    ← 200ms 又补了 0.4 个，攒够 1 个再取
```

桶初始装满 20 个令牌，100 个 goroutine 几乎同时到达，恰好放行 20 个；之后每次请求间隔 200ms 只补充 `2 × 0.2 = 0.4` 个令牌，令牌数在 1 上下波动——放行与拒绝交替出现。`-race` 模式下没有 WARNING，即并发安全验证通过。

## How It Works

机制的主线是：**不做定时器，每次请求在锁内"先补充、再取 1 个"**。

### refill：按时间差惰性补充

```go
func (tb *TokenBucket) refill() {
    now := time.Now()
    elapsed := now.Sub(tb.last).Seconds()
    if elapsed > 0 {
        tb.tokens += tb.rate * elapsed
        if tb.tokens > tb.burst {
            tb.tokens = tb.burst   // 桶满截断：闲置再久也只补到 burst
        }
        tb.last = now
    }
}
```

惰性计算（把计算推迟到真正需要结果的时刻）的思想：把"随时间的连续补充"推迟到"下一次请求时结算"。好处是无常驻线程、闲置零开销；代价是久置后首个请求会一次性结算到 `burst` 封顶——这正是突发的来源，不是 bug。`elapsed > 0` 的判断防止时钟回拨（系统时间被调到过去）或同刻重复结算。

### Allow：加锁 → 补充 → 取令牌

```go
func (tb *TokenBucket) Allow() bool {
    tb.mu.Lock()
    defer tb.mu.Unlock()
    tb.refill()           // 先按时间差补充
    if tb.tokens >= 1 {   // 有整令牌才放行
        tb.tokens--
        return true
    }
    return false          // 令牌不足，拒绝
}
```

输出里 `Request 8: REJECTED (tokens=0.82)` 对应的就是 `tokens >= 1` 不成立：余额不足 1 个整令牌，拒绝但余额保留，等下轮补充。

### 并发安全：为什么必须加锁

不加锁时两个 goroutine 可能都读到 `tokens=1`、各自减 1，出现负余额——放行了 2 个请求却只扣了 1 个令牌。

`Mutex`（互斥锁，同一时刻只允许一个 goroutine 进入临界区——即这段"补充+消费"代码）保证 `refill() + 消费` 是原子的（操作不可分割，中间状态不会被并发看到）；`go run -race` 可验证无数据竞争（多个 goroutine 同时读写同一变量且没有同步）。

### 关键字段一览

| 字段/设计 | 为什么这样写 |
|---|---|
| `tokens float64` | 支持分数令牌：rate=0.5 表示 2 秒攒 1 个；不足 1 时不能取 |
| `last time.Time` | 惰性补充的计时锚点；只在 elapsed>0 时推进，防重复结算 |
| `burst` 截断 | `min(tokens, burst)` 丢弃多余令牌，保证突发上限=burst 而非无限累积 |
| 初始装满 | `NewTokenBucket` 中 `tokens: burst`，允许冷启动即享满额突发 |
| `mu` 锁粒度 | 锁住"补充+判断+消费"整个临界区，而不是只锁 `tokens--` |

## Pitfalls & Q&A

以下条目都来自实现与调试中的真实困惑，每条按现象、原因、解法展开。

### 踩坑清单

- **误读 REJECTED 后的余额**。现象：看到 `REJECTED (tokens=0.82)` 以为余额被扣成负数。原因：打印发生在 `Allow()` 返回之后，是**消费后余额**；0.82 < 1 才是拒绝的原因。解法：按"打印值小于 1 即本轮被拒"理解输出。
- **把 last 不推进当 bug**。现象：elapsed ≤ 0 时补充看似"没生效"。原因：这是防时钟回拨/同刻重复结算的保护，不是缺陷。解法：只在 elapsed>0 时推进 `last`，测试里用足够大的间隔。
- **把"允许突发"当成"无限突发"**。现象：闲置后突发请求全部放行，下游被打挂。原因：补充后忘了 `min(tokens, burst)` 截断，令牌无限累积。解法：保留桶满截断；想更平滑就调小 burst 或改漏桶。
- **单机桶用于多实例部署**。现象：每台机器各有限流配额，全局限流形同虚设。原因：`mu` 只保护单进程内存态。解法：改用分布式限流（见下方 Q&A）。

### 深入问答

**Q：为什么"懒补充"而不是起一个定时器？**
A：定时器方案有空闲开销、精度受 tick（定时器最小触发间隔）限制，还有 goroutine 生命周期问题；lazy 方案在每次 `Allow()` 时按 `now-last` 一次性结算，无常驻线程、数学上精确、闲置零开销。

`golang.org/x/time/rate` 用的就是同样的思路。

**Q：突发流量是怎么"冒出来"的？上限在哪？**
A：桶初始装满 burst 个；闲置期间令牌持续累积（封顶 burst）。突发到来时先消费存量，最多 burst 个请求立即通过，之后只能按 rate 补一个过一个。

**Q：令牌桶 vs 漏桶？**
A：令牌桶控制**平均速率、允许突发**（输入侧整形，输出速率取决于请求到达）；漏桶以**恒定速率**处理请求（输出侧平滑，不允许突发）。API 网关多用令牌桶，流量整形/削峰填谷用漏桶。

**Q：单机令牌桶怎么扩展到分布式？**
A：常见方案：Redis + Lua 脚本把"补充+判断+扣减"做成原子操作（或 INCR+EXPIRE 计数窗口）；或集中式 Token Server 统一发牌。代价是网络延迟影响精度、Redis 需高可用。
