# 05 · Bloom Filter：位数组 + k 个哈希的"可能存在"判定

> Bloom Filter（布隆过滤器）是一种**空间高效的概率型数据结构**，回答"这个元素可能见过吗"：**绝不漏报**（Add 过的元素查询一定返回 true），但**可能误报**（没加过的元素也可能返回 true）。读完本篇，你能用 Go 实现它（FNV-1a 双重哈希），并实测误判率与理论公式的差距。

## Background

缓存穿透是这类问题的典型场景：恶意请求一个数据库里根本不存在的 key，缓存永远不命中，每次都打到数据库。常规防御是在缓存前放一个精确集合（HashSet——把元素原样存进内存的结构）记录"所有存在的 key"，查询返回 false 就直接拒绝。

痛点出在内存：HashSet 要存元素本身，元素量大或元素很长时开销随之膨胀。防御场景恰好又不需要精确答案——偶尔误放行（假阳性：把不存在的判为可能存在）可以接受，错杀（假阴性：把存在的判为不存在）绝不允许。

Bloom Filter 为这个权衡而生：**只存"指纹"不存元素本身**——一个 10000 位的位数组（1.25 KB）就能以约 1% 的误判率容纳 1000 个任意长度的字符串。代价同样明确：不能删除元素、不能枚举内容、误判率随填充度上升。

## What

Bloom Filter 是一种概率型集合成员判定结构（允许以一定概率给错答案，换取极小空间）：用位数组（每个 bit 只有 0/1 的数组）加 k 个哈希函数回答"元素可能存在吗"，以可能误报为代价换取远小于精确集合的内存。

可以把位数组想象成一块共享白板：每个元素来了，都用 k 支不同的笔在 k 个格子里打勾；查询就是检查 k 个格子是否全有勾。但和真实白板不同的是，这里的勾只打不擦，也没有人记录每个勾是谁画的——这正是误报无法消除、删除做不到的根源。

Add 和查询走同一条 `hash(item) → k 个位数组索引` 的路径，判定规则只有两条：

| 查询时看到的 k 个位 | 结论 | 原因 |
|---|---|---|
| 任一位为 0 | **一定不存在** | 那个位从没被置过 1 |
| 全为 1 | **可能存在** | 可能都是别人置的 |

## When to Use

这一节给出判断依据：能否容忍小概率误报、是否需要删除，决定它是否合适。

- **防缓存穿透时**：在缓存前记录"所有存在的 key"，查询返回 false 直接拒绝，挡住对不存在 key 的请求；放行的请求再交给后端核实。
- **海量去重时**：需要判断"某个元素是否处理过"，元素总量大到精确集合装不下。
- **黑名单/垃圾邮件预筛时**：先快速筛掉"一定不在名单里"的请求，缩小精确检查的范围。

何时不用：

- 需要精确答案：任何误报都不可接受时，用 HashSet。
- 需要删除元素或枚举内容：本文结构不支持，删除要换 Counting Bloom Filter（空间代价见 Q&A）。
- 元素量小：HashSet 的内存完全可承受，概率结构不值得引入。

同类方案对比：

| 方案 | 与 Bloom Filter 的差异 | 什么时候选它 |
|---|---|---|
| HashSet | 精确、支持删除与枚举；存元素本身，内存大 | 数据量小或要求零误报 |
| Counting Bloom Filter | 每位变计数器，支持删除；空间约涨 4 倍 | 需要从过滤器中移除元素 |
| Bloom 预筛 + 后端确认 | 拦"一定不存在"，放行的仍需后端核实 | 误报可容忍的防护层（上文场景 1） |

## Quick Start

前置条件：只需安装 Go 工具链，代码无第三方依赖。运行：

```bash
cd patterns/05_bloom_filter
go run bloom_filter.go
```

预期输出（节选，误判率数值每次运行基本一致，大规模测试的实测值会小幅波动）：

```text
=== Bloom Filter Demo ===

Filter: size=10000 bits, numHashes=7

--- Adding items ---
  Add("apple") ... Add("elderberry")        # 5 个已存在元素全部 MayContain=true

--- Query non-existing items (false positive test) ---
  MayContain("grape") = false ...           # 10 个未加入元素全部 false

=== Large-Scale False Positive Test ===
Added: 10000 items, Filter bits: 100000, Hash functions: 7
False positives: 432 / 10000 = 4.32%
Estimated FP rate (formula): 0.8194%

=== Hash Function Count Trade-off ===
  k= 1  bits=100000  actual FP=9.08%  estimated FP=9.52%
  k= 3  bits=100000  actual FP=3.39%  estimated FP=1.74%
  k= 7  bits=100000  actual FP=4.36%  estimated FP=0.82%
```

注意最后两段：**实测误判率（4.32%）明显高于公式估计（0.82%）**——本实现用双重哈希 `h1 + i*h2`，k 个索引彼此相关而非独立，理论公式"k 个独立哈希"的前提不严格成立。这个偏差本身就是本文要讲清的知识点。

实现分两层：位打包和哈希索引。这段在做什么：用 `[]uint64` 打包位（每个 uint64 存 64 个 bit，内存只有 `[]bool` 的 1/8），置位与检查都是 O(1) 位运算：

```go
type BloomFilter struct {
    bitArray  []uint64 // 位数组，每个 uint64 存 64 个 bit
    size      uint     // 总位数 m
    numHashes uint     // 哈希函数数量 k
    count     uint     // 已添加元素数 n
}
```

```go
func (bf *BloomFilter) setBit(pos uint) { bf.bitArray[pos/64] |= 1 << (pos % 64) }
func (bf *BloomFilter) getBit(pos uint) bool { return bf.bitArray[pos/64]&(1<<(pos%64)) != 0 }
```

`pos/64` 定位到哪个 uint64 字，`pos%64` 定位到字内哪一位，两处写反是最常见的手写失误。

## How It Works

机制的主线是：**k 个哈希位共同作证，位只置 1 不清零**。Add 和查询是同一条路径的两个方向。

### 双重哈希：2 次哈希生成 k 个索引

```go
h1 := fnvHash(item, 0)       // FNV-1a，种子 0
h2 := fnvHash(item, 0xBEEF)  // 同一算法，不同种子
indices[i] = (h1 + i*h2) % bf.size
```

FNV-1a 是一种快速的非加密哈希算法；种子（seed）是拼进哈希输入的一段固定数据，用来让同一元素产出不同哈希值。相比调用 k 个独立哈希函数，只需 2 次哈希计算，k 个索引由线性组合生成（Kirsch–Mitzenmacher 方案——用 2 次哈希模拟 k 个哈希的经典技巧）。

副作用见 Quick Start 的实测：索引相关性推高实际误判率。

### Add 与 MayContain：同一枚硬币的两面

```go
func (bf *BloomFilter) Add(item string) {
    for _, pos := range bf.hash(item) { bf.setBit(pos) }  // k 个位全置 1
    bf.count++
}
func (bf *BloomFilter) MayContain(item string) bool {
    for _, pos := range bf.hash(item) {
        if !bf.getBit(pos) { return false }  // 任一 0 → 一定不存在
    }
    return true                              // 全 1 → 可能存在（可能误报）
}
```

**不会漏判的根因**：位只从 0 变 1、永不清零，所以 Add 过的元素 k 个位永远保持为 1。**会误判的根因**：其它元素的哈希可能恰好覆盖了查询元素的 k 个位，查询者无从区分"我置的 1"和"别人置的 1"。

输出前两段正是两面：Add 过的 5 个元素全部 `MayContain=true`，未加入的 10 个元素全部 `false`。

### 误判率公式与实测偏差

理论误判率 `FP = (1 - e^(-kn/m))^k`，最优参数 `m = -n·ln(p)/ln(2)²`、`k = (m/n)·ln 2`。本实现固定 `m = 10n`、k=7（接近 n=1000、p≈1% 的理论最优组合 m≈9585、k≈7）。

实测却偏差明显：插入满 10000 元素后实际误判 4.32%，公式只给 0.82%——双重哈希的索引相关性是主因，此外哈希把 seed 拼进输入再 FNV（`fmt.Fprintf(h, "%s%d", item, seed)`）也非严格独立。

k 折中实验里实际误判在 3~9% 波动、k=3 附近最好，同样偏离了"公式最优点 k=7"。

### 关键字段一览

| 字段/函数 | 含义 | 为什么重要 |
|---|---|---|
| `bitArray []uint64` | 打包位数组 | 空间 1/8 于 `[]bool`；`pos/64` 定字、`pos%64` 定位 |
| `size (m)` | 总位数，代码取 `10n` | 决定误判率下限；太小则位很快被占满 |
| `numHashes (k)` | 哈希个数 | 太少漏置位误判高，太多占满位数组误判也高 |
| `count (n)` | 已添加元素数 | `FalsePositiveRate()` 用 n/m/k 估当前误判率 |
| `hash()` | 双重哈希生成 k 索引 | 相关性使实际 FP 高于理论值（见上文公式一节） |

## Pitfalls & Q&A

以下条目都来自手写实现时的真实失误，每条按现象、原因、解法展开。

### 踩坑清单

- **位打包的 `pos/64` 与 `pos%64` 写反**。现象：置位后查询时灵时不灵，位越界 panic。原因：把"定字"和"定字内偏移"两个运算弄混。解法：`pos/64` 选中 uint64 字，`pos%64` 选中字内位，固定记法。
- **h1/h2 忘用不同种子**。现象：k 个索引退化为重复值，误判率暴涨。原因：`fnvHash(item, 0)` 与 `fnvHash(item, 0xBEEF)` 全靠 seed 区分，两次同参哈希得到同一组索引。解法：h1/h2 必须用不同种子。
- **误判率照公式报**。现象：压测结论与线上表现对不上。原因：双重哈希实现下实测可能是公式估计的数倍（实测 4.32% vs 公式 0.82%），公式前提是独立哈希。解法：压测后再给结论，并注明实现方式。
- **`m = n*10` 是硬编码默认，k=0 才自动算 k**。现象：换了目标误判率，误判率却不达标。原因：m 不会随目标 p 自动调整。解法：换目标误判率需自己按公式改 m。

### 深入问答

**Q：为什么会有误判，却永远不会漏判？**
A：见上文 Add 与 MayContain 一节——判断依据是"k 个哈希位是否全为 1"，位只置 1 不清零给出了不漏判的保证，1 的来源不可区分造成了误判。

**Q：为什么不能删除元素？怎么解决？**
A：删除需要把位清 0，但一个位可能被多个元素共享，清 0 会让别人被"漏判"。变体 Counting Bloom Filter 把每个位换成计数器，删除时减 1，代价是空间从 1 bit/位涨到 4 bit 左右。

**Q：m 和 k 怎么选？**
A：给定预期元素数 n 和目标误判率 p：`m = -n·ln(p)/ln(2)²`、`k = (m/n)·ln 2`。n=10000、p=1% 时 m≈95851 bits（约 12 KB）、k≈7。本实现简化为 m=10n、k=7。

**Q：空间优势有多大？**
A：存 100 万个 URL，HashSet（存字符串）约 50~100 MB，Bloom Filter（p=1%）约 1.2 MB——50~100 倍的差距，因为只存位指纹、不存元素本身。
