# 03 · Read4K：跨调用缓冲管理的 4K 读取管线

> 底层 API `Read4(buf4)` 每次最多读 4 个字符，要在其上实现任意长度 n 的 `Read(buf, n)`——一次没读完的字符必须缓存到下次调用。读完本篇，你能写出这个跨调用缓冲 Reader 的完整 Go 实现，并从演示输出看清"源 → 分块填充 → 缓冲 → 逐块处理 → 计数聚合"管线的每一步。

## Background

操作系统和标准库的分块读（底层按固定大小的块搬运数据，而不是按需求数量）是这类问题的缩影：底层永远按块搬——比如 4096 字节的页缓冲，调用方要的却是任意长度的 n。经典练手题 LeetCode 157/158 "Read N Characters" 把块大小缩到 4 字节，得到最小可推演的模型 `Read4`。

两者的差额不会消失，只会堆积：一次 `Read(3)` 实际会拿到 4 字节，多出的 1 字节如果随手丢弃，下次调用就永久少了 1 字节。单次调用可以读完即弃；一旦上层会连续多次调用（流式读取），状态就必须跨调用存活。

所以实现要同时满足两条硬要求：

- **跨调用状态保持**：多读的字节存在实例字段里，而不是函数局部变量；
- **EOF（End Of File，文件结束）边界处理**：读到文件尾时停机，且不重复读、不多读。

## What

这个模式的产物是一个跨调用的缓冲 Reader：一种把固定块底层读取与任意长度上层请求衔接起来的读取器。

它的全部逻辑是一条 4 字节 mini 管线——`Read4` 把数据分块灌进 `buf[4]`，`Read` 优先消费缓冲区剩余（`pos < size`），不够才再调 `Read4` 补充，最后把复制字节数 `total` 聚合返回。

可以把 Reader 想象成一只容量 4 升的水桶挂在每抽必满 4 升的水泵下：要打任意数量的水，优先舀桶里剩的，桶空了才让水泵再抽。但和真实水桶不同的是，这只桶再抽水时是整桶覆盖——没喝完就被覆盖等于把水倒掉（数据丢失），所以"先喝完再抽"是硬规则。

`buf/pos/size/eof` 四个状态全部挂在结构体上，跨调用共享；管线的五个环节——源、分块填充、缓冲、逐块处理、计数聚合——分别由底层源、`Read4`、`buf`、循环复制、`total` 承担。

## When to Use

这一节给出判断依据：什么时候需要自己搭这层缓冲，什么时候标准库现成实现更合适。

- **封装流式读取器时**：在按固定块吐数的底层接口（文件、网络、设备）之上，给调用方提供"要多少给多少"的按需读取。
- **逐字节消费协议数据时**：消息边界与块边界不一致，需要把块到达的数据拆成任意长度的片段。
- **理解或复刻标准库缓冲层时**：`bufio.Reader` 一类的实现用的正是"先吃缓存、再向底层要新块"的同一套思路。

何时不用：

- 一次性读整个对象：`os.ReadFile`、`io.ReadAll` 直接返回完整数据，不必手写状态机。
- 底层接口本身已按需读取：再垫一层缓冲只增加复杂度，没有收益。
- 生产代码优先用 `bufio`（标准库的带缓冲 IO 包）：手写版的价值在理解机制，不在替代标准库。

同类方案对比：

| 方案 | 与手写 Reader 的差异 | 什么时候选它 |
|---|---|---|
| `io.ReadAll` / 一次性读入 | 简单，但整个对象进内存 | 数据量小、一次用完 |
| `bufio.Reader` | 同一套块缓冲思路的标准库实现 | 生产代码直接使用 |
| 裸块读（如 `Read4` 直连） | 无缓冲层，残字节直接丢失 | 块大小恰好等于请求大小 |

## Quick Start

前置条件：只需安装 Go 工具链，代码无第三方依赖。运行：

```bash
cd patterns/03_read4k

```

预期输出（实测，`fileData` 共 45 字节）：

```text
=== Read4K → Read N Characters ===

测试 1: 单次 Read(5)
  读取 5 字节: "Hello"

测试 2: 多次 Read(3)
  第1次 Read(3): 3 字节 → "Hel"
  第2次 Read(3): 3 字节 → "lo,"
  第3次 Read(3): 3 字节 → " Wo"
  第4次 Read(3): 3 字节 → "rld"
  第5次 Read(3): 3 字节 → "! T"

测试 3: Read(100) 超过文件长度
  读取 45 字节: "Hello, World! This is a test file for Read4K."

测试 4: 文件读完后再 Read(5)
  读取 0 字节（应为 0）
```

测试 2 每次 `Read(3)` 都精确接住上次缓存的残字节，5 次拼出连续 15 字节；测试 3 请求 100 只返回 45；测试 4 在 `eof` 置位后返回 0。

实现的核心是一个状态容器。这段在做什么：把 `buf/pos/size/eof` 四个字段挂在 `Reader` 结构体上，让下一次 `Read` 接着上次的进度走：

```go
type Reader struct {
    buf  [4]byte // 内部缓冲区
    pos  int     // buf 中下一个要读的字节
    size int     // buf 中有效字节数（Read4 的返回值）
    eof  bool    // 文件是否读完
}
```

单调用版本（LC157）读完即弃，不需要任何字段；多调用版本（LC158）必须保存这组状态——这就是两个版本的本质分界。

## How It Works

机制围绕 `Read` 的一次调用展开：先吃缓存，再补货，循环到读够或读不到为止。

### Read：先吃缓存，再补货

```go
func (r *Reader) Read(buf []byte, n int) int {
    total := 0
    for total < n {
        if r.pos < r.size { // 1. 缓冲区有剩余，直接复制
            buf[total] = r.buf[r.pos]
            r.pos++
            total++
            continue
        }
        if r.eof { // 2. 文件已读完，退出
            break
        }
        r.size = Read4(r.buf[:]) // 3. 补货
        r.pos = 0
        if r.size == 0 { // 4. 补到 0 字节 = EOF
            r.eof = true
            break
        }
    }
    return total
}
```

循环四步的顺序不能换：**必须先检查 `pos < size` 再决定是否调 `Read4`**。`Read(3)` 时 `Read4` 一次灌 4 字节，第 4 字节留在 `buf` 里等下次——这就是"少读不丢字"的关键。你在测试 2 看到的五次连续输出，每一次都由"先吃缓存、再补货"的顺序保证。

### eof 与逐次对照

`Read4` 返回 0 是文件结束的唯一证据：置 `eof = true` 后，后续所有 `Read` 直接短路返回 0，不再碰 `Read4`。测试 2 的逐次管线对照：

| 调用 | 返回 | 缓冲区动作 |
|---|---|---|
| `Read(3)` #1 | `"Hel"` | `Read4` 灌入 `"Hell"`，取 3 剩 1（`"l"` 留在 buf） |
| `Read(3)` #2 | `"lo,"` | 先吃缓存 `"l"`，再 `Read4` 灌 `"o, W"`，取 `"o,"` 剩 `"W"` |
| `Read(3)` #3 | `" Wo"` | 先吃缓存 `"W"`，再 `Read4` 补充 |
| `Read(3)` #4 | `"rld"` | 同上 |
| `Read(3)` #5 | `"! T"` | 同上，缓存链始终连续 |

### 关键字段一览

| 字段/语句 | 含义 | 为什么重要 |
|---|---|---|
| `buf [4]byte` | 内部块缓冲 | 存放 `Read4` 多读的残字节，跨调用不丢 |
| `pos` | buf 内读游标 | `pos < size` 判定"还有缓存可吃" |
| `size` | buf 有效字节数 | 来自 `Read4` 返回值；为 0 即 EOF 证据 |
| `eof` | 结束标志 | 置位后短路返回 0，防重复读 |

## Pitfalls & Q&A

以下条目都来自实现与测试中的真实失误，每条按现象、原因、解法展开。

### 踩坑清单

- **顺序颠倒丢数据**。现象：测试 2 从第 2 次调用起输出断流、内容跳变。原因：先调 `Read4` 再检查缓存，残字节被新块整块覆盖，且覆盖是静默发生的。解法：保持"先吃缓存（`pos < size`）、再补货"的判断顺序。
- **忘置 eof 导致死循环**。现象：文件读完后调用不返回、CPU 空转。原因：`Read4` 返回 0 后若不 `break`，`pos == size` 恒成立，循环既复制不了也退出不了。解法：`size == 0` 即置 `eof = true` 并 `break`。
- **假设返回值一定是 n**。现象：请求 100 字节却拿到 45，调用方按 n 处理读到脏数据。原因：`n` 超过文件长度时靠 `size == 0 → eof → break` 兜底，返回实际字节数（实测 45）。解法：调用方按返回值取数据，不假设读满。
- **值接收者陷阱**。现象：每次 `Read` 行为都像第一次调用，缓存永远传不下去。原因：`Read` 用了值接收者，方法操作的是状态副本。解法：使用指针接收者 `*Reader`，让状态落在原结构体上。

### 深入问答

**Q：多调用版本和单调用版本的本质区别是什么？**
A：见上文 Quick Start 的状态容器——把 `buf/pos/size/eof` 从函数作用域提升到结构体作用域，多调用版本就自然成立。

**Q：为什么 `pos < size` 的检查必须在调 `Read4` 之前？**
A：见上文踩坑第一条——`Read4` 是整块覆盖式写入，先补货会静默覆盖未消费的字节。

**Q：`Read(100)` 但文件只有 45 字节，返回什么？为什么不会多读？**
A：返回 45（实测）。循环里 `Read4` 返回 0 时置 `eof` 并 `break`，`total` 停在真实读取数；eof 之后即使再调 `Read` 也直接返回 0，不会重读。

**Q：真实系统里 `Read4` 对应什么？为什么是 4 字节/4096 字节？**
A：对应内核页缓存与标准库的 `bufio` 分块读。块大小是系统调用的摊销单位——把每次调用的固定开销分摊到一大块数据上，4096 正是一个内存页；练习用 4 字节是为了让"缓存残字节"的边界在几步之内就能人肉验证。
