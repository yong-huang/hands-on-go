# 08 · 缓存一致性：两种坏例复现与恰好失效的最终策略

> cache-aside 的写路径怎么删缓存才算对？本篇用编排式复现拆掉两个流行答案：
> 先删后更让旧值驻留整个 TTL；先更后删（失效不拿锁）留一个"回填晚于失效"的窄窗口。
> 最终策略——更库 + 失效与回填共用同一把 per-key 锁 + TTL 兜底——10 万次读写交错零脏读。

## Background

实验 07 的读路径有了"恰好一次回源"，写路径还悬着：数据库更新之后，缓存里的旧值
什么时候删、按什么顺序删？拍脑袋的答案有两个，都很流行——先删缓存再更库
（"让缓存立刻空掉"），或先更库再删缓存（"先保数据再清缓存"）。

两个答案都有坏例，且坏例都源于同一个结构：回填（读 miss 后把结果写回缓存）与
失效（写路径删缓存）是两个互不知晓的并发行为。只要它们能交错，旧值就能在失效的
眼皮底下溜回缓存——然后驻留整个 TTL。这类"旧数据在缓存里活得好好的"的状态，
对余额、库存类数据就是事故。

## What

写路径三个候选策略，差异全在失效与回填的相对顺序上：

| 策略 | 写侧动作 | 坏例 | 窗口 |
|---|---|---|---|
| 先删后更 | DEL → 更库 | 并发回源在 DEL 后、更库前读走旧值并回填 | 整个 TTL |
| 先更后删（无锁） | 更库 → DEL | 在途回填把 DEL 之前读到的旧值写回 | 窄，但必然被踩中 |
| 最终策略 | 更库 → 锁内失效 | 无（交错被锁序钉死） | 0 |

可以把失效与回填想成两个都在动黑板的人：失效者擦黑板、回填者往上写旧答案。
不协调就永远可能"擦完又被写上"。最终策略让他们共用同一支粉笔盒的钥匙
（per-key 互斥锁）：拿不到钥匙的人先等着，黑板状态因此只有两种合法序列——
先写后擦（擦掉旧答案）或先擦后写（写的是新答案），旧答案无处驻留。

脏读的判定基准也要说清：失效是一个过程（拿锁、DEL、解锁），db 更新到失效完成
之间存在**最终一致窗口**，窗口内的旧读是 cache-aside 的契约内行为。可断言的
承诺是"失效完成之后，旧值不再可读"——本篇的零脏读断言建立在这个基准上。

## When to Use

- **读多写少 + 可容忍秒级滞后**的数据：cache-aside + 最终策略，一致性成本最低
- **写后立刻要读新值**的路径（read-your-writes）：失效后该用户的下一次读要么
  短路缓存、要么等失效完成——最终策略的锁恰好提供了这个同步点
- **永远不该用缓存的**：多写者强一致数据（账户余额的写路径本身）——缓存解决
  读扩展，不解决写一致

| 方案 | 一致性承诺 | 复杂度 | 适用 |
|---|---|---|---|
| 不缓存 | 线性一致 | 零 | 写多读少 |
| 先更后删 + 锁内失效（本篇） | 失效完成后不旧 | 一把锁 | 读多写少的绝大多数 |
| 双写（更新缓存而非删除） | 差（并发写互相覆盖） | 高且易错 | 不推荐 |

```bash
cd web/08_cache_consistency
go run .
go test -race -count=3 .
```

真实输出（`go run .`；第 3 步含 10 万次读写交错，约 10 秒）：

```text
== 第 1 步：先删后更——旧值回填，驻留整个 TTL ==
  库已是 101，缓存命中 100（写入发生在 DEL 之后的回填）
  下一个读者仍命中 100——旧值将驻留整个 TTL（1m0s）
== 第 2 步：先更后删（无锁）——回填发生在失效之后的窄窗口 ==
  更库+DEL 都已完成，缓存命中 200（回填晚了 DEL 一步）
  下一个读者仍命中 200——窄窗口，但真实流量下必然被踩中
== 第 3 步：最终策略——10 万次读写交错，脏读必须为 0 ==
  读 100000 次（命中 99533/回源 471），写 500 次，脏读 0
  ⇒ 失效与回填共用一把锁后，两种交错都被顺序钉死；TTL 只是兜底，不再被依赖。
```

测试验收（`-race` 连跑 3 轮全绿，含 goleak 门禁）：

```text

```

诚实预期：两个坏例用 sleep 编排出确定的交错时序（教学手法，与实验 04 的

测试跑 2 万次交错，演示跑满 10 万。

## How It Works

### 坏例一：先删后更，旧值回填无人拦截

时序：读者 miss → 回源读到旧值 100 →（写者此刻完成 DEL 与更库）→ 读者把 100
回填进缓存。写者的 DEL 发生在回填之前，等于白删；更库又改变不了已经读走的旧值。
结果：缓存里是 100，数据库是 101，差一个 TTL 的距离。DEL 得越早，留给它拦的
回填越多——"先删"在结构上就是把门打开。

### 坏例二：先更后删，失效追不上在途回填

时序：读者 miss 回源（慢，已读走 200）→ 写者更库 201 并 DEL（此刻缓存为空，
DEL 空挥）→ 读者的回填把 200 写进缓存。写者的两个动作都完成了，旧值照样进门——
因为失效不知道有一个回填正在飞行。窗口很窄，但读路径的 QPS 乘以运行时长，
窄窗口在真实流量下是必然而非偶然。

### 最终策略：失效与回填共用一把 per-key 锁

`InvalidateLocked` 与 `GetOrLoad` 的回填段使用同一把 per-key 互斥锁，交错只剩
两种合法序列：失效先拿锁，DEL 后回填读到必是新值；回填先拿锁，在途回填先落地、
失效随后删掉它。锁序把"擦黑板"与"写黑板"排成全序，旧值无处驻留。
TTL 降级为兜底，正常情况下永远等不到出场。

### 脏读判定：失效承诺，而非写完成承诺

判定基准是写者的 `invalidated` 版本号——每次失效完成后推进。读者在读开始时采样
r0，读到比 r0 更老的值才算脏。db 更新到失效完成之间的旧读属于 cache-aside 的
最终一致窗口（契约内），强行把它们算成脏读，任何缓存策略都拿不到零——
这也是"缓存永远给不了线性一致"的具体形状。

## Pitfalls & Q&A

- **用"双写"代替删除**：现象是并发写时缓存与数据库各自为政，顺序错乱。
  原因：更新缓存与更新数据库是两个独立写，无全序。解法：写路径只失效（DEL），
  让下一次读回源重建——删除是幂等的，更新不是
- **失效不拿回填的锁**：现象是压测下偶发旧值驻留（本篇坏例二）。
  原因：失效与回填互不知晓。解法：`InvalidateLocked`，同一把 per-key 锁
- **脏读判定取 db 版本**：现象是"零脏读"永远测不出来，满屏误报。
  原因：失效窗口内的旧读是契约内行为。解法：以失效完成的版本号为判定基准
- **坏例靠压测碰运气**：现象是复现不了就不存在。原因：窄窗口在低并发下难自然出现。
  解法：编排式复现（sleep 摆出交错），机制课与实验课的手法同源

**Q：TTL 还需要吗？失效锁不是已经关闭窗口了吗？**
A：需要，但角色变了。锁保证"失效后旧值不复活"；TTL 防的是锁之外的意外——
进程崩溃在回填与失效之间、Redis 与数据库时钟漂移、以及未来某个程序员写出的
一条没走锁的 SET。兜底不参与正确性，但它的存在让正确性不必完美。

**Q：写后立刻读自己的数据（read-your-writes）怎么办？**
A：三个常见解法，按成本递增：失效完成后该用户的下一次读强制回源（按用户维度
短路缓存）；写路径把版本号写进用户会话，读时比对；或者对该用户禁用缓存数秒。
最终策略的失效锁天然是一个同步点，方案一几乎免费。

**Q：多实例部署下，per-key 锁只在单进程内有效？**
A：对——它协调的是本进程的回填与失效。多实例时 A 实例的回填可能与 B 实例的
失效交错，窗口重新打开。工业解法是 pub/sub 广播失效或版本化 key（旧版本自然
过期）；marklet 单实例，边界在实验 19 的 Compose 阶段重新审视。

**Q：为什么演示里命中 99533 次、回源只有 471 次？**
A：500 次写失效后，第一个读者回源重建，其余 499 个写周期里的读者都命中同一份
缓存——这正是缓存的经济学：失效的代价由下一次读一次性偿还，而不是每次写都
让所有读者穿透。
