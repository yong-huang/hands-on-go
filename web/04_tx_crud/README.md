# 04 · 事务与 CRUD 接线：丢更新、守恒与事务边界

> marklet 数据层与 HTTP 层就此接通：同一业务（把余额减 1）三种写法的并发对照——
> 无事务读-改-写 100 次减法丢 90 次、事务版与原子 UPDATE 版精确归零；启动即迁移，CRUD 全链路集成测试。

## Background

顺序执行时，"先读余额、减 1、再写回"从没出过错——单线程里读写之间隔多久都无所谓。
两个请求并发时问题显形：它们可能读到同一个旧值，各自算好结果再先后写回，
后一个写覆盖前一个写——减了 100 次、余额只降 10，90 次减法凭空消失。

这类错误叫丢更新（lost update）：不报错、不留日志，账面看起来永远合理，
是余额、库存、配额这类守恒业务（总量不许凭空增减）最隐蔽的敌人。数据库为此提供
事务（transaction，多条语句捆成"要么全做、要么全没做"的单元）与隔离级别
（并发事务互相可见程度的等级）；简单场合，一条原子 UPDATE 就够。

## What

事务是"多条语句的整体原子性 + 受控的相互可见性"。本篇用同一个业务对比三种写法：

| 写法 | 读与写的关系 | 并发结果（实测） |
|---|---|---|
| 无事务读-改-写 | 两条独立语句，中间有业务窗口 | 丢 90 次 |
| `WithTx` + BEGIN IMMEDIATE | 整个读-改-写持写锁串行 | 精确归零 |
| 原子 `UPDATE n = n - 1` | 单语句自带原子性 | 精确归零 |

可以把 BEGIN IMMEDIATE 想成会议室预订：进门就把整间房锁上，别人在你出来前进不来；
默认的 BEGIN（deferred，延迟取锁）则是先在门口听会，轮到自己才抢话筒——抢不到时
你基于的讨论早已过时。但和会议室不同的是，锁只保护"房间里的事"，提交后的一致性
仍要靠唯一约束、对账这些数据库之外的手段。

## When to Use

- **守恒型写操作**：转账、扣库存、配额扣减——差一次都是事故，必须事务或原子语句
- **启动时的结构迁移**：迁移器把 DDL（建表类语句）和版本记录捆进一个事务，接进服务启动序列
- **handler 的多条写**：一条请求要改多张表时，事务边界就是 handler 的边界

何时不用：单条语句能表达的自增自减（`n = n - 1` 自带原子性，包事务是白锁）；纯只读查询。

| 方案 | 正确性 | 吞吐 | 适用 |
|---|---|---|---|
| 无事务读-改-写 | ❌ 丢更新 | 最高 | 不适用守恒业务 |
| BEGIN IMMEDIATE + 读-改-写 | ✅ | 中（写串行） | 需读出后复杂决策 |
| 原子 UPDATE | ✅ | 高 | 能用单语句表达的全部场景 |

## How It Works

### 丢更新的机制：窗口里的过期值

`decrementRacy` 三步走：`SELECT n` 读出余额、`time.Sleep` 模拟业务处理窗口、
`UPDATE ... SET n = <算好的值>` 整体写回。10 个 goroutine 同时读到 100、各自算出 99 写回——
最终一百次减法只生效十次，输出里丢掉的 90 次就是被覆盖的写。

丢更新的危险在于它**不报错**：每次写都成功返回，只是基于过期值。检测它的唯一办法
就是本篇这样的守恒断言——期望值和实际值对不上，丢失才显形。

### BEGIN IMMEDIATE：SQLite 把写事务整体串行

DSN 里的 `_txlock=immediate` 让 `BeginTx` 产出 `BEGIN IMMEDIATE`：事务一开始就取写锁，
配合 busy_timeout（实验 02 的排队机制）天然排队，读-改-写作为整体被串行化，
中间窗口不再有人插得进来。

对照隔离级别：SQLite 的这一模式等效 SERIALIZABLE（串行化，事务像排队执行）；
PostgreSQL 默认 READ COMMITTED（只保证读到已提交的数据），无事务实验照样丢、
事务版也救不了（PG 不锁读），要 `SELECT ... FOR UPDATE`——实验 05 原样重跑本实验。

### WithTx：事务边界住在一个函数里

```go
tx, err := db.BeginTx(ctx, nil)
defer tx.Rollback()   // Commit 后是空操作；panic 时兜底回滚
if err := fn(tx); err != nil {
    return err         // 业务错误 → 已回滚
}
return tx.Commit()
```

`defer Rollback` 不是冗余：测试 `TestWithTxRecoversPanic` 断言 panic 时也不留悬挂事务——
否则未决事务随连接回池，下一个借用者踩进半截事务。事务边界的安放：单语句写直进直出；
跨语句写在 store 层；跨多表才提到 handler 层。

### 启动即迁移 + CRUD 接线

`startServer` 的次序就是验收③：`Migrate()` 返回后才 `srv.Serve(ln)`——第一个请求进来时
表一定已经在。路由侧用 `{id}` 路径参数（`r.PathValue("id")` 取值），语义约定：
参数坏是 400、资源不存在是 404、成功改删是 204——集成测试逐条断言。

## Pitfalls & Q&A

- **指望 busy_timeout 救无事务读-改-写**：现象是照样丢更新。原因：它只给单条语句
  排队，两条语句之间的业务窗口它管不着（第 1 步实录）。解法：事务或原子语句
- **删掉 defer Rollback**：fn panic 后连接带悬挂事务回池，借用者踩进半截事务。解法：`defer tx.Rollback()` 永远保留
- **_txlock=immediate 开全局**：纯读事务也开始排队等写锁，读吞吐受损。解法：本篇规模无所谓；读多写少再按读写拆两个连接配置
- **并发实验之间忘记重置余额**：现象是"守恒"碰巧成立或全错。原因：第二步从第一步
  的残留值减起。解法：每组实验前显式 `UPDATE counters SET n = ?` 重置（本篇实现）

**Q：事务版和原子版，实际项目选哪个？**
A：能用原子语句表达的业务（自增自减、带条件的批量更新）首选原子版——没有窗口
就无须锁，吞吐也最高。需要"读出来做复杂决策再写"（风控、跨表校验）才上事务。

**Q：事务里的 time.Sleep 是不是作弊？**
A：它把真实业务里本来就存在的处理时间（网络调用、计算、校验）显式化并拉宽到
肉眼可见。窗口不是实验造出来的，是业务自带的——实验只是让它必然被踩中。

**Q：PostgreSQL 上这个实验会有什么不同？**
A：无事务版照样丢；事务版在默认 READ COMMITTED 下**也丢**——PG 不锁普通读，两个事务
都能读到同一个旧值。解法是 `SELECT ... FOR UPDATE`（行锁）或 SERIALIZABLE，实验 05 重跑。

**Q：删一个不存在的书签为什么返回 404 而不是 200？**
A：REST（HTTP 接口设计的通行风格）语义里 404 表达"目标资源不存在"，客户端据此区分
"删成功"与"本来就没有"；200 会让重试无法察觉资源早已消失。参数非法是 400，两者不可混用。
