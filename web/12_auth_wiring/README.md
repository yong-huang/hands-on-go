# 12 · 全站认证打通：身份贯穿到每一行数据

> 阶段三收官：令牌里的用户 ID 贯穿到 SQL 的 WHERE 子句——每条查询都带 owner 过滤，
> 用户 A 对用户 B 的书签 GET/PUT/DELETE 全部 404（与"真不存在"同响应，不泄露存在性）。
> 注册→登录→建→查→改→删全链路集成测试，未登录与伪造令牌全量 401。

## Background

实验 09-11 各自成立：密码哈希可靠、令牌可验证、入口有防线。但身份停在
`context` 里就断了——数据层不知道"当前用户"，任何持有效令牌的用户都能读写
所有书签。这类漏洞叫 IDOR（不安全的直接对象引用：URL 里的对象 id 被换成
别人的），OWASP 最常见缺陷之一。

它太容易写出：`GET /bookmarks/42` → `SELECT * FROM bookmarks WHERE id = 42`
——查询没错，错在少了 `AND owner_id = 当前用户`。修复位置在 SQL 而非 handler
里查后比对：比对会漏（缓存、批量、新端点），WHERE 不会。

## What

marklet 的数据模型长出归属：users 表（argon2id PHC 落库）+ bookmarks.owner_id
（外键指向 users）。路由分两组：公开组（注册/登录/healthz，豁免认证）与受保护组
（书签 CRUD，Bearer 必过，用户 ID 从令牌的 sub 声明来）。

可以把 owner 过滤想成酒店房卡：令牌验出"你是 1608 房的客人"，房卡系统里
开 1608 的锁天经地义；拿它开 1609 的锁，门不会说"这是别人的房间"（403），
只会说"开不了"（404）——你甚至不知道那间房存不存在。泄露存在性本身
就是信息（攻击者可据此枚举资源），所以 404 是唯一正确的拒绝方式。

| 请求 | 身份 | 结果 |
|---|---|---|
| GET /bookmarks/42（自己的） | alice | 200 |
| GET /bookmarks/42（别人的） | mallory | 404（不泄露存在） |
| GET /bookmarks/42（未登录） | — | 401 |
| GET /bookmarks（列表） | alice | 只有 alice 的书签 |

## When to Use

- **多用户数据的任何读取**：列表、详情、导出——owner 过滤必须是查询的一部分
- **写路径同样适用**：UPDATE/DELETE 的 WHERE 里带 owner，越权写与越权读一起关死
- **安全测试的必查项**：用两个账号互测对方资源，断言 404——这是每个数据端点
  上线前的固定动作（本篇测试就是模板）

何时不用：单用户系统（无"别人"可言）；平台管理端（管理员跨用户操作是另一套
显式授权模型，不是省略过滤的理由）。

| 防御位置 | 可靠性 | 失效场景 |
|---|---|---|
| SQL WHERE（本篇） | 高——遗漏即查不到数据 | 无（缺了功能就不完整） |
| handler 查后比对 | 低——新端点容易忘 | 缓存、批量、重构 |
| 前端隐藏入口 | 零——改 URL 即绕过 | 一切场景 |

## How It Works

### 身份的旅程：从令牌到 WHERE 子句

登录签发的 JWT 里，`sub` 是用户 id（不是用户名——id 不可变、可做外键）。
Bearer 验签后把 id 放进 `r.Context()`，handler 取出传给 store，
store 写进 SQL 的 `$2`。身份三次"翻译"（令牌 → context → SQL 参数），
每一环都有测试钉住。

### owner 过滤的两种查询形态

列表用 `WHERE owner_id = $1`，天然只回自己的。单条用 `WHERE id = $1 AND
owner_id = $2`——不是"先查出再校验"，而是让数据库直接回答"对你是否存在"。
UPDATE/DELETE 同理，`RowsAffected` 为 0 即"不属于你"，统一 404。

### 404 与 403 的分界

403 告诉攻击者"资源存在但你权限不够"——枚举 id 就能画出资源地图；
404 把两种失败折叠成一个响应，攻击者拿到的是零信息。代价是合法用户拼错 id
时也看到 404（本来也该看到 404）。唯一例外的暴露面是响应时间差，
marklet 的数据量下不构成信号。

## Pitfalls & Q&A

- **owner 从请求参数来**：现象是任何人改 `owner_id` 字段就能把书签写进别人名下。
  原因：客户端可篡改一切输入。解法：owner 只取自令牌（context），请求体里的
  owner 字段一律忽略
- **新端点忘带 owner 过滤**：现象是老端点安全、新加的搜索/统计接口越权。
  原因：过滤靠人肉记忆。解法：数据访问层统一收口（所有函数签名必须带 owner
  参数），code review 按"每个查询有没有 owner"过一遍
- **越权返回 403**：现象是攻击者枚举出全部资源 id。原因：403 泄露存在性。
  解法：统一 404，测试断言两种"不存在"响应逐字相同
- **清库顺序错**：现象是首次跑测试报"relation does not exist"（本篇实录）。
  原因：DELETE 跑在建表之前。解法：EnsureSchema 先行，清库在后

**Q：管理员需要跨用户看数据怎么办？**
A：显式建模，而非偷懒省略过滤。owner 过滤的函数族旁边提供 `ForAdmin` 变体，
入口用独立的管理员认证中间件 + 审计日志。隐式的"没有过滤"和显式的"授权绕过"
在代码审计里是两个世界。

**Q：JWT 的 sub 用用户名不是更可读吗？**
A：用户名可能改名（id 不可变）、可能大小写歧义、且作为字符串参与索引成本高。
数字 id 做主键与外键，用户名只是登录凭证——sub 与数据库在这个细节上对齐。

**Q：这是阶段三收官，marklet 现在算安全了吗？**
A：防住了凭证泄露（argon2id）、令牌伪造（HS256+白名单）、越权（owner 过滤）
三类。尚未覆盖：暴力登录（实验 16 限流）、传输窃听（实验 19 TLS）、注入
（已参数化）。安全是过程不是状态——清单见实验 20。

**Q：测试里为什么每用例清库而不是每测试建新库？**
A：建库成本（连接系统库 + CREATE DATABASE）远高于清两行数据，且清理动作本身
就是一套"数据可重建"的演练。容器库的隔离粒度用数据库（实验 06 的教训），
用例的隔离粒度用数据清理。
