# 07 · Redis 缓存层：防击穿的恰好一次回源与空值防穿透

> marklet 的 GET 热点路径接入 Redis（cache-aside）：命中直接回、未命中回源回填。
> 两个经典事故的实测对照：1000 并发查同一冷 key 回源恰好 1 次（per-key 互斥 + 锁内重查），
> 查不存在的 key 两波并发回源也止步于 1（空值缓存 + 滑动续期）；命中率实测 100%。

## Background

实验 04 的 CRUD 每个请求都打到数据库。热点数据（同一批书签被反复读）让 99% 的请求
做着重复的磁盘查询——缓存的动机朴素直接：把读过的答案放在更快的介质里，下次直接用。

但缓存一上，两类事故如影随形。击穿（thundering herd）：热点 key 过期或冷启动的瞬间，
上千并发同时发现缓存为空、同时回源，数据库被打出一道尖峰；穿透（penetration）：
请求查的 key 根本不存在，缓存永远不可能命中，每次请求都完整穿透到数据库——
攻击者只需随机拼 URL 就能让缓存形同虚设。

解法都藏在"回源那一刻"的并发控制里：同 key 的并发请求只放一个去回源（其余共享结果），
不存在的答案也缓存起来（让后续请求在缓存层终结）。

## What

cache-aside 是读缓存的通行模式：先查缓存，命中直接返回；未命中则回源（查数据库），
把结果写入缓存并设 TTL（存活期），下次同类请求就是命中。marklet 的实现签名是
`GetOrLoad(ctx, key, ttl, load)`——读路径的全部逻辑封装在这一个方法里。

可以把缓存想成前台接线员：能答的直接答（命中）；答不上来的去问后屋专家（回源），
问完把答案记在小本子上（回填）。击穿是"一百个人同时涌进来问同一个问题"——
恰好一次的机制让第一个人去问、其余九十九个等他回来抄答案。穿透则是"问一个
根本不存在的人"——小本子上也要记一笔"查无此人"（空值缓存），否则每次都白跑后屋。

| 事故 | 触发条件 | 解法 | 实测结果 |
|---|---|---|---|
| 击穿 | 热点 key 失效瞬间的并发回源 | per-key 互斥 + 锁内重查 | 1000 并发回源 1 次 |
| 穿透 | 查询不存在的 key | 空值缓存（短 TTL + 滑动续期） | 第二波回源 0 次 |

## When to Use

- **读多写少的热点数据**：书签详情、用户主页——命中率是唯一重要的指标
- **回源昂贵**的读路径：聚合查询、上游 API 调用——回源一次的成本远超一次缓存读
- **需要削峰**的冷启动：服务重启后缓存全空，恰好一次回源保证数据库只承受一轮真实查询

何时不用：写后即读的一致性敏感路径（读到旧数据不可接受时，缓存是负担）；
命中率注定低下的一次性访问（每次都 miss，白白多一跳）。

| 方案 | 一致性 | 吞吐 | 适用 |
|---|---|---|---|
| 直连数据库 | 强 | 低 | 写后即读 |
| cache-aside（本篇） | 最终一致（TTL 窗口） | 高 | 读多写少 |
| 读写穿透（write-through） | 较强 | 高 | 写也要过缓存的场景 |

## How It Works

### 恰好一次回源：per-key 互斥 + 锁内重查

未命中路径的全部并发控制在一个临界区里：先取该 key 专属的互斥锁，锁内**再查一次**
缓存，命中就返回；仍未命中才回源、回填、解锁。正确性来自锁的 happens-before：
前任的回填发生在它释放锁之前，后任的重查必然命中——回源次数 =1 靠的是锁的顺序保证。

这正是 singleflight（同一 key 的并发调用合并为一次执行，concurrency/09 手写过其
WaitGroup 版）要解决的问题。WaitGroup 版只合并"同时在飞"的请求，回填前的读配
结束后的进入会漏网（本篇实测踩中）；互斥锁版阻塞等价于无限大合并窗口，
"恰好一次"从概率变成保证。

### 空值缓存与滑动续期

回源返回 ErrNotFound 时，往缓存写入空值标记并设短 TTL——后续同 key 请求在缓存层
拿到标记、直接得到"不存在"，穿透被终结。

标记的 TTL 有个反直觉的设计：**命中即续期**（滑动过期）。固定 TTL 会输给足够慢的
查询队列——串行重查 200 个请求要数秒，2 秒的标记在队列尾部之前就过期了，穿透在
波尾重新露头（本篇实测踩中）。滑动续期让"被持续查询的不存在"持续生效，
风暴平息后 2 秒自然过期。

### 命中率是缓存的验收指标

hits/misses/loads 三个原子计数器贯穿全部演示。回源失败（非 NotFound）不缓存——
一次上游抖动不该被放大成整个 TTL 的"假装不存在"（`TestLoaderErrorNotCached` 断言）。

## Pitfalls & Q&A

- **用 WaitGroup 版 singleflight 防击穿**：现象是压测下回源次数偶尔为 2。
  原因：它只合并同时在飞的请求，窄窗口漏网（本篇实测）。解法：per-key 锁 +
  锁内重查，阻塞换确定性
- **锁内重查漏掉**：现象是互斥锁下仍有多把回源。原因：进锁前只查一次，
  排队期间的回填没被看见。解法：拿到锁之后**再**查一次（double-check 的位置
  在临界区内，不在临界区外）
- **空值标记用固定 TTL**：现象是穿透在慢查询队列的尾部露头（本篇实测）。
  原因：TTL 跑不赢串行重查的时长。解法：命中即滑动续期
- **Redis 故障被当成未命中**：现象是 Redis 挂掉时回源被打爆。原因：连接错误与
  key 不存在走了同一条 miss 路径。解法：`redis.Nil` 才是未命中，其余错误原样上抛

**Q：per-key 锁表会不会内存泄漏？**
A：锁数量等于历史冷 key 数，不淘汰确实会涨。生产化路径：按 key 哈希分片成
固定数量的锁（牺牲无关 key 之间的并行度换内存上界），或用带淘汰的并发 map。
marklet 的书签 key 空间有限，演示规模不淘汰，边界写在代码注释里。

**Q：为什么不用 x/sync/singleflight 现成库？**
A：机制课上过（concurrency/09），本篇的增量是"缓存回源恰好一次"这个工程保证——
x/sync 版的合并窗口恰好是它的边界。库仍在接口后面，需要非阻塞语义时随时可换。

**Q：空值缓存为什么用 2 秒而不是 30 秒？**
A：空值缓存的代价是"后来真的存在了"的数据迟到——攻击者伪造的 key 30 秒不痛，
正常用户刚创建的资源查不到 30 秒很痛。滑动续期已保证高峰期不穿透，
TTL 只需要覆盖"无人在 2 秒内再次问起"的冷却期。

**Q：命中率 100% 是不是太理想？**
A：演示预热后只读已预热的 key，100% 是构造出来的上限。真实服务看的是稳态命中率
（90% 上下即健康），跌落通常意味着 TTL 过短、容量淘汰或访问模式变化——
这正是把命中率做成指标导出的原因（实验 14 接入 Prometheus 文本格式）。
