# 18 · 优雅停机与任务排空：零丢失与可审计的停机时序

> 实验 01 的停机只管 HTTP；marklet 现在还有队列里的任务。编排器四阶段——
> 摘流量 → HTTP 收尾 → 队列排空 → 关依赖——50 个在途任务零丢失对账通过；
> 排空超时则剩余任务进死信、强制退出路径留痕；每阶段带毫秒时间戳，时序可审计。

## Background

后台任务（实验 17）让"进程退出"从一句话变成一部剧：HTTP 层停了，队列里还有
47 个任务、4 个 worker 手里各攥着一个做到一半——此时退出，这些任务人间蒸发；
不退出，卡死的任务会让进程永远退不出去。

更隐蔽的是顺序问题。依赖连接（DB/Redis）如果在排空之前关掉，排空期间的每个
任务都报连接错误；readyz 如果最后才摘，停机的几秒里负载均衡还在派发新请求。
每一步都对、顺序错了，结果还是灾难——而顺序错误在故障时才暴露，平时不可见。

## What

编排器（orchestrator）把停机固化为四个阶段，每阶段带相对毫秒的时间戳写入
PhaseLog，停机全过程像时间线一样可回放：

| 阶段 | 动作 | 为什么在这个位置 |
|---|---|---|
| ① 摘流量 | readyz → 503 | LB 的轮询周期是秒级，必须最早执行 |
| ② HTTP 收尾 | Shutdown 等在途请求 | 已受理的请求不该被抛弃 |
| ③ 队列排空 | 期限内做完，超时进死信 | 排空期间还要写库，依赖必须活着 |
| ④ 关依赖 | DB/Redis 连接关闭 | 最后一步，之后进程可退出 |

可以把排空想成航班截载：先停值机（摘流量），再等已过安检的旅客登机
（HTTP 在途），然后清点候机厅（队列），没赶上的旅客记入改签名单（死信），
最后撤桥（关依赖）。但与航班不同的是，"清点候机厅"有时间上限——
飞机不能为无限迟到的人等待，超时者记录后按计划起飞。

## When to Use

- **任何带后台任务的常驻服务**：只要队列里有任务，`os.Exit` 就是数据丢失
- **滚动发布的每一轮**：新旧实例交接的窗口，排空质量直接决定用户可见的错误数
- **停机演练**：把"重启安全吗"变成可断言的测试（本篇测试即模板）

何时不用：无状态纯计算服务（实验 01 的 HTTP 停机已足够）；任务可以随便丢的
场景（缓存预热一类）。

| 停机方式 | 在途任务 | 可审计 | 适用 |
|---|---|---|---|
| 直接退出 | 全部丢失 | 无 | 不适用有队列服务 |
| 只等 HTTP（实验 01） | 队列任务丢失 | 部分 | 无后台任务 |
| 四阶段编排（本篇） | 排空或死信 | 全程时间线 | marklet |

## Quick Start

前置条件：Go ≥ 1.21；无外部依赖。运行：

```bash
cd web/18_graceful_drain
go run .
go test -race -count=3 .
```

```text

    [   0ms] ② HTTP Shutdown 完成：在途请求已收尾

    [ 271ms] ③ 队列排空完成：processed=50 dead=0
    [ 271ms] ④ 依赖连接已关闭：进程可退出

== 第 4 步：排空超时——卡死任务进死信，强制退出有日志 ==
```

测试验收（`-race` 连跑 3 轮全绿，含 goleak 门禁）：

```text

```

诚实预期：排空完成时间随机器波动（271ms ≈ 50 任务 ÷ 4 并发 × 20ms 的理论值）；
超时路径里 worker 手里卡死的任务不进死信——它仍在执行中，强杀会弄脏状态
（见 Q&A）。

## How It Works

### 排空的语义：close 之后 range 会消费完存量

worker 的消费循环是 `for j := range p.queue`——`close(p.queue)` 之后，
range 会把缓冲存量全部取完才退出。这是 Go channel 的原生语义："关店门、
服务完排队的客人"。Drain 关队列、等 wg 归零，期限内排空是确定性事件。

### 超时路径：恰好一次的死信

排空超时后置 abort 旗标：workers 把取到的任务直接送死信，编排器同时把
队列存量逐个送死信。两路接收同一 channel，每任务恰好交付/记录一次。
worker 手里在执行的任务无法强取，留在原地自然结束——保数据不保时间。

### PhaseLog：把顺序变成断言

四阶段各打一行 `[毫秒] 阶段描述`。测试断言三件事：行数正确、时间戳单调
不减、阶段编号 ①→④ 严格递增、第一行必须是 readyz 摘除。"停机顺序对不对"
从口口相传的约定变成一条可执行的断言——重构停机逻辑时，测试会拦住任何
顺序调整。

## Pitfalls & Q&A

- **select 双通道消费**：现象是停机后队列里剩下一大半任务没跑（本篇实测
  processed=6/50）。原因：quit 关闭后 select 在两个就绪分支间随机选择，
  workers 随机退出。解法：`for range` 消费存量，quit 改为"closed 标志 +
  close 队列"
- **依赖先于排空关闭**：现象是排空期间任务全部报连接错误。原因：连接关闭
  排在了队列处理之前。解法：阶段④固定在最后（PhaseLog 断言）
- **死信双计**：现象是超时后死信数量大于队列存量。原因：编排器与 workers
  各自记了一份。解法：channel 的恰好一次交付——两路都是接收者，天然不重
- **超时后强杀 worker**：现象是任务做到一半的状态损坏。原因：强杀无法
  回滚已写的副作用。解法：让任务留在 worker 里自然结束，死信只记队列存量

**Q：超时后 worker 手里那个任务算丢了？**
A：算"未决"——仍在执行，结果未知。彻底方案是任务状态机 + 启动时把
running 重置为 pending 重跑，代价是任务必须幂等（marklet 的抓取天然幂等），
状态机在实验 19 落地。

**Q：为什么 drain 期限 5 秒而不是"无限等"？**
A：无限等 = 进程永不退出 = 编排器（如 systemd/K8s）发 SIGKILL 强杀，
那比有计划的死信更糟。期限是"业务能容忍的最大收尾时间"的显式化——
marklet 取 5 秒，超时部分靠死信留下线索。

**Q：readyz 摘除后，已经在飞的 HTTP 请求呢？**
A：②的 Shutdown 等它们收尾（实验 01 的语义）。若在途请求也超时，
Shutdown 返回 DeadlineExceeded，编排器记录后继续——HTTP 层的失败
不影响任务层的排空，两层各自独立收尾。

**Q：四阶段和 K8s 的 terminationGracePeriodSeconds 怎么对应？**
A：K8s 发 SIGTERM 后给宽限期（默认 30s），到期 SIGKILL。编排器总耗时必须
小于宽限期（③的 5 秒是主要预算）。实验 19 的 compose 显式配 stop_grace_period。
