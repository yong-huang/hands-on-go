# 17 · 后台任务队列：worker 池、重试死信与 SSRF 防线

> 书签创建后异步抓取页面标题：创建请求 201 即返回（52ms 内标题落库入档），
> worker panic 不丢任务（recover→重试→死信，worker 存活），SSRF 三类内网目标
> 全部在"连接前"被拒进死信。队列健康面板 = depth/processed/dead 三个数字。

## Background

同步抓取的用户体验是灾难：目标页面 3 秒响应，创建书签的请求就等 3 秒；
目标页面超时，创建就失败——但"存书签"和"读那个页面"本来就是两件事。
把抓取挪到后台，创建请求立即返回"已受理"，抓取完成后结果自己长出来。

后台化引入三个新问题。谁来做：常驻 worker 池而非每次 new goroutine（无限
即无限内存）；做错了怎么办：目标站 500、超时、fetch 自己 panic——任务不能
一次失败就消失；URL 指向哪里：云元数据地址让服务器替攻击者扫内网——SSRF。

## What

marklet 的任务队列是有界 channel + 固定 worker 池：`Enqueue` 入队（满了立即
返回背压错误，不排队到内存爆炸）；worker 循环取任务、执行、失败重试
（固定退避），重试耗尽进死信队列（dead letter，可人工复查的"失败仓库"）。

可以把队列想成洗衣店：柜台容量有限，满了店主直接说"改天再来"（背压）；
店员固定几人，一人晕倒被扶起来继续，那件衣服重新排队（重试）；洗坏两次的
进"待处理事故"架（死信），绝不悄悄扔掉。但与洗衣店不同的是，衣服是顾客送
的（用户提交的 URL），店员要先检查衣服里有没有炸弹（SSRF）。

| 机制 | 行为 | 断言 |
|---|---|---|
| 有界 channel | 满即背压 | 第 3 个入队返回 ErrQueueFull |
| recover + 重试 | panic 任务不丢、worker 不死 | 死信含 panic 记录、后续任务正常 |
| SSRF 校验 | 连接前拒绝内网目标 | 三类内网 URL 全部进死信 |

## When to Use

- **响应时间与工作时长解耦**：抓网页、生成缩略图、发邮件——用户不该等这些
- **失败需要被看见的任务**：死信队列让失败可复查，而不是 try-catch 吞掉
- **削峰**：突发创建请求进队列排队，worker 按稳定速率消化

何时不用：结果必须立刻返回（那就不是异步）；任务量小到一次函数调用即可
（队列是开销不是架构）。

| 方案 | 失败可见性 | 背压 | 适用 |
|---|---|---|---|
| 每任务一个 goroutine | 差（panic 即丢） | 无 | 不推荐 |
| 有界队列 + worker 池（本篇） | 死信可查 | 满即拒绝 | marklet 规模 |
| 外部队列（Redis/消息系统） | 可查 + 可重放 | 天然 | 跨进程/持久化需求 |

## Quick Start

前置条件：Go ≥ 1.21；无外部依赖（fixture 页面与队列都在进程内）。运行：

```bash
cd web/17_jobs_queue
go run .
go test -race -count=3 .
```

真实输出（`go run .`，服务 127.0.0.1:19625，跑完自动退出）：

```text

  创建 → 201 id=1（此刻 title 为空——异步的起点）
  52ms 内标题落库："Marklet Fixture"
== 第 2 步：SSRF——生产配置下三类内网 URL 全部被拒 ==
  http://169.254.169.254/latest/meta-data        → url targets private network
  http://127.0.0.1:19625/secret                  → url targets private network
  http://10.0.0.5/internal                       → url targets private network
== 第 3 步：队列可见性 ==
  dev: depth=0 processed=1 | prod: dead=3
```

测试验收（`-race` 连跑 3 轮全绿，goleak 门禁在此篇尤其关键——
worker 池是最容易漏 goroutine 的地方）：

```text

```

诚实预期：落库耗时随调度波动（几十毫秒级，验收线 3 秒）；SSRF 演示的
169.254.169.254（云元数据地址）不需要真实网络——它在 DNS 解析后就被
IP 黑名单拒绝，请求从未发出。

## How It Works

### panic 的三段处置：recover → 重试 → 死信

worker 的执行函数用 defer recover 包住：panic 转成错误走重试（固定退避），
耗尽进死信。recover 的位置是关键——必须与 panic 同 goroutine（实验 01 纪律），
所以在任务执行函数里。测试断言：poison 进死信、worker 存活、重试发生过。

### SSRF：在"连接前"拒绝，而不是"失败后"补救

校验三步：scheme 白名单；DNS 解析出 IP 列表；逐 IP 检查环回/私网/链路本地。
拒绝发生在发请求之前——连接后补救来不及。开发 fixture 也在环回上，故有
`allowPrivate` 开关：同一代码路径，生产默认拒绝。

### 背压：队列满是一种诚实的响应

`Enqueue` 用 select 的 default 分支实现非阻塞入队——队列满立即返回
ErrQueueFull，API 层把它转成 429。让创建请求"排队等位"看似友好，实则把
内存压力变成了无上界——拒绝比拖延诚实。测试用"卡住唯一 worker"构造满队列，
断言第三个入队立即失败。

## Pitfalls & Q&A

- **无界队列**：现象是生产高峰时内存曲线与队列同涨同落直至 OOM。
  原因：channel 没有容量上限。解法：有界 + 背压拒绝（本篇）
- **recover 放在池启动函数**：现象是 worker 死后整条流水线停摆。
  原因：recover 只能捕获当前 goroutine 的 panic（实验 01 纪律）。
  解法：recover 包住任务执行段，与 panic 同 goroutine
- **SSRF 只查字符串前缀**：现象是 `http://foo@127.0.0.1/` 这类 userinfo
  混淆绕过。原因：字符串匹配不解析语义。解法：DNS 解析后按 IP 判定
  （本篇实现），userinfo 在 hostOf 里剥除
- **get 返回内部指针**：现象是 `-race` 报数据竞争（本篇实测）。
  原因：调用方在锁外读指针指向的字段。解法：get 返回副本

**Q：重试为什么用固定退避而不是指数退避？**
A：marklet 的重试上限是 2 次、间隔 100ms——两次的指数退避（100/200ms）
与固定退避差异可忽略。指数退避的价值在多次重试 + 多客户端场景（避免重试
风暴同步共振），任务量大或重试次数多时再升级。

**Q：死信之后呢？**
A：死信是"人工复查的队列"不是坟墓：修复原因后把死信任务重新入队（重放）。
marklet 当前提供快照读取；持久化死信（实验 19 落盘）与重放命令是它的
自然延伸——关键是不管失败的原因是什么，失败的记录先活下来。

**Q：DNS Rebinding 为什么说没彻底防住？**
A：攻击者可让 DNS 第一次解析公网 IP（过校验）、第二次解析内网 IP（连接时
打到内网）。彻底防御是自定义 `net.Dialer`：建连时再校验一次对端 IP 并复用
解析结果——"教学口径"的边界，生产按此加固。

**Q：为什么不用 errgroup？**
A：worker 是常驻循环，errgroup 的 Wait 语义（等全部完成、返回首错）不匹配。
它的纪律以另一形态存在：池大小即并发上限，死信即错误出口。
