# 16 · Redis 滑动窗口限流：边界、滑动与四件套联动验收 ⛓️

> 阶段四收官：Redis ZSET 滑动窗口限流（Lua 原子）——100 请求/10s，第 101 起
> 429 且带精确到请求的 Retry-After；窗口滑过即恢复（无固定窗口的 2× 突刺）。
> 观测四件套协同验收：被限流请求的 request_id 同时出现在日志、指标、trace 三处。

## Background

实验 12 之后 marklet 有了认证，但还没有"礼貌拒绝"的能力：暴力登录、爬虫、
失控的客户端都能无限制地打满资源。限流（rate limiting）是服务的礼貌边界——
超过承受能力的请求被明确拒绝（429），而不是拖垮所有人。

限流的常见起点是固定窗口计数（每分钟一桶，数到 100 就拒），但它有边界突刺：
两个桶的交界处可放行 2×limit 的请求（前桶末尾 100 + 后桶开头 100）。滑动窗口
（sliding window）记录每次请求的时间戳，判定时数"最近 N 毫秒内"的数量——
边界连续，没有突刺。

## What

ZSET（有序集合，成员带分数、可按分数范围操作）是 Redis 上实现滑动窗口的
标准结构：成员=每次请求（时间戳 ms 为分数），判定时清出窗口外旧成员、
数窗口内数量。四步操作（清旧、计数、写入、续期）用 Lua 脚本一次执行——
Redis 单线程跑 Lua 期间不插入其他命令，原子性无需显式锁。

可以把滑动窗口想成地铁闸机的"最近 1 分钟 3 次"规则：判定看的是你过去
60 秒的刷卡记录（滚动），不是"这个自然分钟刷了几次"（固定）。所以
"10:59:58 刷一次、11:00:01 刷一次"不会被算成同一分钟的三次。

| 机制 | 行为 |
|---|---|
| ZREMRANGEBYSCORE | 清出窗口外的旧时间戳 |
| ZCARD | 窗口内请求数 |
| ZADD + PEXPIRE | 记录本次请求并给 key 设生存期（无请求时自动清理） |
| Lua | 四步原子执行 |

## When to Use

- **按用户/API key 限流**：维度天然存在于认证信息里（本篇按 X-User-Id）
- **需要精确 Retry-After**：窗口内最老请求离开的时间可以算出来，客户端据此退避
- **多实例共享额度**：计数在 Redis——所有实例看到同一个窗口（本地计数做不到）

何时不用：只需要粗粒度保护（每进程令牌桶即可，见 patterns/07）；
Redis 不可用时 fail-open 还是 fail-close 需要先行决策——本篇选择上抛错误。

| 算法 | 突刺 | 内存 | 精度 |
|---|---|---|---|
| 固定窗口（INCR+EXPIRE） | 有（交界 2×） | O(1) | 粗 |
| 滑动窗口（ZSET，本篇） | 无 | O(窗口内请求数) | 精确到请求 |
| 令牌桶 | 平滑但突发可配 | O(1) | 按速率 |

## How It Works

### Lua 原子性：不用锁的并发正确

清旧、计数、写入、续期若是四次独立命令，两个并发请求可能都读到 n=99、
都写入、都放行——超发。Lua 脚本在 Redis 单线程里整段执行，期间任何其他
命令都不会插入：并发请求被自然串行化，"检查再写入"的竞态从结构上不存在。
这正是实验 04 事务思想的 Redis 形态：把多步操作变成一个不可分割的单元。

### Retry-After：精确到最老的那一次请求

被限流时，窗口内最老请求的分数（时间戳）就是"什么时候能腾出位置"的答案：
`oldest_score + window - now`。客户端拿到的不是"等满 10 秒"的粗暴值，
而是精确的退避建议——HTTP 的 Retry-After 是秒精度，向上取整。

### 四件套联动：一个 request_id 串起三处

被限流时三件事同时发生：日志记 WARN（logger 预注 request_id）、指标
`rate_limited_total{user}` 加一、span 打 `ratelimit.exceeded=true` 属性。
联动测试逐一断言三处——实验 13/14/15 的观测件第一次作为整体工作。

### 中间件顺序：注入者在外

RequestID 必须包在限流中间件外面——限流的日志要写 request_id，而 logger
是 RequestID 注入的。本篇实测踩中：顺序写反后日志缓冲全空（限流用了全局
默认 logger）。与实验 13 的教训同源：谁依赖注入，谁就在内层。

## Pitfalls & Q&A

- **固定窗口的边界突刺**：现象是压测在桶交界处瞬间放行 2×limit。
  解法：ZSET 滑动窗口（本篇）或令牌桶
- **Lua 里忘记续期**：现象是冷 key 永久驻留 Redis。原因：只有 ZADD 没有
  PEXPIRE。解法：脚本内对数据 key 与序列 key 同时 PEXPIRE
- **成员不唯一**：现象是同毫秒的两个请求互相覆盖（ZSET 成员唯一）。
  解法：成员 = 时间戳 + 服务端 INCR 序列（本篇实现）
- **Redis 故障静默放行**：现象是 Redis 挂掉后限流形同虚设（fail-open）。
  原因：错误被吞掉。解法：上抛并 503——限流器坏了应该显式失败，
  策略（open/close）要作为配置决策而非默认行为

**Q：窗口内的请求数会撑爆 Redis 吗？**
A：内存 = 窗口内请求数 × 每成员约 60 字节。100 req/10s 的用户约 60KB/窗口；
限流本身会把超额请求挡在窗口外，所以 ZSET 大小天然有界（≤limit 个成员）。

**Q：为什么按用户而不是按 IP 限流？**
A：IP 是设备的属性不是人的属性——NAT 后一个 IP 是一栋楼，IPv6 下一个人
有 2^64 个地址。认证后的用户标识稳定且与业务对齐；未认证流量的 IP 限流
通常放在更外层的网关上做。

**Q：分布式部署时锁不锁本地计数？**
A：不锁——计数本来就在 Redis（共享），多实例天然共享同一个窗口，
这正是"计数放 Redis"相对于本地计数的核心优势（实验 05 换 PG 的同款理由）。

**Q：和实验 14 的指标、15 的 trace 具体怎么分工？**
A：限流器是第一个"四件套齐全"的业务组件：日志记录个案（哪个请求被限），
指标暴露趋势（限流率是否在涨——可能是攻击或配额太小），trace 保留现场
（该请求的完整上下文），限流器自身是执行者。观测不是装饰，是限流可运营的前提。
