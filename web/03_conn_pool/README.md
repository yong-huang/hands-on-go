# 03 · 连接池调参：MaxOpen / MaxIdle / MaxLifetime 实测

> database/sql（Go 标准库的数据库访问层）自带连接池，三个旋钮拧错档位代价惊人：
> 实测里"不限连接数"的默认思路吞吐垫底、p99 最差；`Open=4 Idle=4` 拿到 4 倍吞吐；
> 写负载上池开得越大吞吐越低。WaitCount（池的排队账本）让每一次排队都可对账。

## Background

没有连接池的做法是每个请求新建一条数据库连接：打开文件、执行 PRAGMA、用完即关，
成本按请求数线性付；另一极端是全服务共用一条手写全局连接：零成本，但所有请求串行排队。

两者之间需要缓冲层，这就是连接池（connection pool，预建并复用数据库连接的组件）。
Go 的 database/sql 内置了池，但默认参数针对网络数据库设计——在 SQLite 这种
"连接极便宜、单写者"的本地库上，默认档位的真实成本只有实测才看得清。

调参不能拍脑袋的另一面是"必须可观测"：排队有没有、等多久，都有账可查。
本篇的测量方法（DBStats——连接池的运行时统计——对账，加 p50/p99 百分位延迟：
p50 是单请求耗时的中位数，p99 表示 99% 的请求快于此值）比结论本身更值得带走。

## What

连接池是一条"取用 → 使用 → 归还"的循环：请求来时从池里拿一条空闲连接；
没有空闲且未达上限就新建；达到上限就在队列里等；用完归还，池决定留闲还是关闭。

可以把池想成共享单车停车场：MaxOpen 是车位总数（没车位就排队），MaxIdle 是打烊后
留几辆备用（留少了下个人得去车店取新车），MaxLifetime 是车辆报废年限。
但和单车不同的是，数据库连接有读写之分——SQLite 单写者（同一时刻只允许一个写连接），
写连接加再多也无益。

池的行为全部记在 DBStats（连接池的运行时统计）里：

| 字段 | 含义 |
|---|---|
| `WaitCount` | 累计有多少次取用排队等待过（只增不减，看增量） |
| `WaitDuration` | 累计等待总时长 |
| `OpenConnections` | 当前连接总数（含在途与空闲） |
| `MaxIdleClosed` / `MaxLifetimeClosed` | 因留闲上限/寿命到期被关闭的连接数 |

## When to Use

- **给服务定池参数**：实验 02 的 Store 上线前就该回答"MaxOpen 设几"——本篇给出测量方法
- **排查"延迟随并发飙升"**：先看 WaitCount 与 p99，判断瓶颈在池队列、写锁还是业务
- **容量评估**：池上限就是并发上限，压测容量规划从池参数开始

何时不用：单 goroutine 顺序访问（无排队可言，默认参数即可）；一次性 CLI 查询
（连接用一次就退，池没有复用机会）。

| 配置 | 行为 | 适用 |
|---|---|---|
| 不设池 | 每请求新建连接 | 原型 |
| 默认池（Open 不限，Idle=2） | 无排队但有连接翻新 | 网络库的保守起点 |
| 调优池（Open=4 Idle=4，本篇） | 有界复用，零翻新 | SQLite 实测最优 |

## How It Works

### 取用-归还循环与 WaitCount 账本

一次 `stmt.QueryContext` 内部先向池取连接：有空闲直接用；无空闲且未达 MaxOpen 就新建；
已达上限就进队列，这次等待在 `WaitCount` 记一笔。它只增不减，对账取实验前后的差值：
上限 2、并发 50 时 2000 个请求里 1998 个排过队；上限不限则一笔都没有。

### 为什么默认配置反而垫底

默认档（Open 不限，Idle=2）零排队，却是五组里吞吐最低、p99 最差的：50 个并发各自拿连接，
用完只留 2 条、48 条被关，下一轮再重开——新连接要重开文件、重跑 PRAGMA（毫秒级），
这笔"连接翻新"成本全落在少数请求上。连接翻新（churn，连接被反复关闭重建）是默认档的真成本。

调优档 `Open=4 Idle=4` 的算术：连接总量有界且用完全部留闲，翻新归零；
代价是排队把 p50 从 6µs 抬到 68µs——用可预期的微秒级排队换 4 倍吞吐，稳赚。

### 写负载：单写者面前池失灵

WAL（预写日志，实验 02 的并发前提）只保证读写不互斥，写与写仍是单写者串行。
池从 2 开到 8，写吞吐 14139/s 跌到 6128/s：更多连接同时抢同一把写锁，竞争开销倒贴。
瓶颈不在池时，调池只是给瓶颈添乱——先定位瓶颈，再谈调参。

## Pitfalls & Q&A

- **"池越大越快"**：现象是写负载池开大吞吐反降（本篇第 3 步实录）。
  原因：单写者下大池加剧锁竞争。解法：先分清读写瓶颈，写池给小、读池按需
- **MaxIdle 远小于 MaxOpen**：现象是零排队但 p99 毫秒级尖刺。原因：用完即弃触发
  连接翻新。解法：MaxIdle=MaxOpen（本篇调优档），让上限内的连接全部留闲
- **只看 p50 调参**：现象是 p50 最小的默认配置吞吐反而最低。原因：翻新成本集中在
  少数请求，均值被稀释。解法：p99 与吞吐双指标入档
- **WaitCount 不做差**：现象是两组实验读数混在一起无从对账。原因：它只增不减。
  解法：实验前后各读一次 `db.Stats()` 取增量（本篇读实验各组独立库文件，天然不串账）

**Q：池上限到底怎么选？**
A：从目标反推：目标吞吐 × 单请求耗时 ≈ 需要的并发连接数。SQLite 读池 4~8、
写池 1~2 是合理起点，之后用本篇方法实测修正——参数是测出来的，不是背出来的。

**Q：MaxLifetime 对本地 SQLite 有意义吗？**
A：不如对网络数据库（连接会被防火墙/负载均衡掐死）刚需，但仍有两用：让 PRAGMA
配置变更生效（每条新连接才执行）、让池定期换血以暴露连接级问题。测试断言见
`TestLifetimeRecycles`。

**Q：为什么 p99 比平均值先报警？**
A：翻新、排队这些成本集中在少数请求上（毫秒级），而海量正常请求只有微秒级——
平均值被稀释得毫无感觉，p99 直接暴露尾巴。容量与延迟的 SLO（服务等级目标）
几乎都定义在 p99 上，原因就在这。

**Q：和 patterns/12 的手写连接池什么关系？**
A：那边讲机制（空闲队列 + 信号量 + 健康检查），本篇用标准库池讲调参与观测，互为印证——
手写池的信号量超限即快速失败，标准库改为阻塞等待，并用 DBStats 把每次等待记了账。
