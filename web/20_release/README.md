# 20 · CI 与压测：五步门禁、基线入档与发布清单 🏁

> 收官：五步本地 CI（fmt/vet/race/build/摘要，goleak 内嵌于测试）全绿；
> 100 并发 × 60 秒压测基线入档——171.5 万请求、100% 成功、28,589 req/s、p99=25.5ms；
> 压测还抓到并修掉了一个真 bug（压测工具自身未读干 body 导致连接裸奔），
> 前后对比 41% → 100% 全程入档。marklet 毕业。

## Background

20 篇实验堆出来的能力，怎么保证下一次改动不把它弄坏？答案是两道自动化闸门。
CI（continuous integration，提交即自动执行的质量门禁）把实验 01-18 的全部纪律
固化成脚本：格式、静态检查、带竞态检测的测试、可构建——任何一条红了就不许合并。

第二道是性能基线：服务"现在多快"必须有一个可对比的锚点，否则每次发布都是
开盲盒。压测（loadtest）以固定并发与时长打真实服务，产出成功率与延迟分位数——
这次压测还当场抓到一个真 bug（见下），修完的前后对比自然入档。

## What

marklet 的 CI 是一个五步脚本，每步失败即整体失败（exit 1）：

| 步骤 | 命令 | 拦什么 |
|---|---|---|
| 1 gofmt -l | 格式清单非空即失败 | 手写格式的随意性 |
| 2 go vet | 静态检查零告警 | 可静态发现的缺陷 |
| 3 go test -race ./... | 全部测试（含 goleak 门禁） | 逻辑错误 + 数据竞争 + goroutine 泄漏 |
| 4 go build ./... | 全部可执行 | 编译损坏 |
| 5 摘要 | fail 标志汇总 | 前四步任何失败传播为整体失败 |

压测工具 `loadtest`：并发 worker 循环打目标 URL 至时长耗尽，输出总数、
成功率、吞吐与 p50/p95/p99。发布清单（RELEASE_CHECKLIST.md）把自动化
覆盖不到的部分（密钥管理、回滚兼容性、发布窗口）显式列为人工项。

## When to Use

- **每次提交**：ci.sh 五步是提交前的最后动作（也是 CI 平台的第一道门）
- **每次发布**：压测基线对比 + RELEASE_CHECKLIST 逐项过
- **性能调查的起点**：基线漂移即报警，实验 14 的指标面板是实时版

何时不用：原型期（先跑通再谈门禁）；一次性实验分支（ci 全量约 1 分钟，
按需跑子集）。

| 门禁 | 自动化程度 | 拦截时机 |
|---|---|---|
| 五步 CI | 全自动 | 提交前 |
| 压测基线 | 半自动（需起栈） | 发布前 |
| 发布清单 | 人工 | 发布中 |

## Quick Start

前置条件：Go ≥ 1.21；压测需要目标服务在跑（本篇用实验 19 的容器化 app）。
运行：

```bash
cd web/20_release/scripts && ./ci.sh
cd ../19_docker_deploy && docker compose up -d && cd ../20_release
go run ./loadtest -url http://127.0.0.1:8080/healthz -concurrency 100 -duration 60s
```

CI 真实输出（节选）：

```text
=== 3/5 go test -race（含 goleak 门禁）===
ok  	marklet/17_jobs_queue	9.671s
ok  	marklet/18_graceful_drain	9.327s
ok  	marklet/19_docker_deploy	7.047s
=== 5/5 摘要 ===
CI 全绿
```

压测基线（100 并发 × 60s，打容器化 app 的 /healthz；实测入档）：

```text
总请求=1715335 失败=0 成功率=100.000% 吞吐=28589 req/s
p50=1.442291ms p95=13.299083ms p99=25.482208ms max=125.958ms
```

压测抓到真 bug 的前后对比（同一目标、同一参数）：

```text
修复前（压测工具未读干 body）：总请求=68401 失败=… 成功率=41.198% 吞吐=1140 req/s
  首错采样: Get "http://127.0.0.1:8080/healthz": dial tcp 127.0.0.1:8080:
  connect: can't assign requested address
  （5 秒后 netstat 实测 8080 相关 TIME_WAIT 16226 条）
修复后（io.Copy(io.Discard, resp.Body) 再 Close）：成功率=100.000% 吞吐=28589 req/s
```

诚实预期：吞吐与延迟绝对值随机器波动（本机为 M 系列笔记本直连回环），
基线的意义是相对对比；首版压测的 41% 成功率是压测工具自己的 bug 而非服务
的问题——对照组实验（原生直连同样 39%）排除了 Docker 转发层嫌疑后，
定位到客户端连接裸奔。

## How It Works

### 压测抓到的真 bug：未读干的 body 让连接裸奔

首错采样给出线索：`can't assign requested address`——macOS 环回临时端口
耗尽（EADDRNOTAVAIL）。5 秒压测后实测 16,226 条 TIME_WAIT：每请求新建
连接、用完即弃。

对照组三步收敛：换直连目标仍 39%（排除转发层）；拨号探针显示复用正常；
嫌疑落到压测工具——`Body.Close()` 前未读干 body，连接被丢弃。
修复一行 `io.Copy(io.Discard, resp.Body)`：吞吐 25 倍，成功率 41% → 100%。

教训的一般形状：**看起来是服务的问题，先证明不是客户端的问题**——
对照组实验 + 首错采样，两件武器都比猜测便宜。

### 五步门禁的边界与黑名单

goleak 在每包的 TestMain 里（实验 17 的 worker 池、13 的日志中间件都靠它拦过
泄漏）。CI 拦的是"可自动判定的回归"；发布清单（RELEASE_CHECKLIST.md）里的
密钥管理、回滚兼容、窗口值守是自动化够不到的决策项——清单的价值是让
"忘了检查"变成"检查了没通过"。

### 基线的入档格式

本次入档：1715335 请求 / 100% / 28589 req/s / p50 1.4ms p95 13.3ms p99 25.5ms。
下次发布的 loadtest 输出与它逐项对比：成功率跌、p99 劣化 1.5 倍、吞吐掉三成
——任一命中即回归，先查再发。数字本身不重要，**有数字且可对比**才重要。

## Pitfalls & Q&A

- **压测工具未读干 body**：现象是大量 EADDRNOTAVAIL + TIME_WAIT 堆积
  （本篇实录）。原因：连接被丢弃重建。解法：`io.Copy(io.Discard, resp.Body)`
  后再 Close
- **CI 只在本地跑**：现象是"我本地全绿"与远端红。

  解法：脚本即 CI 的 definition（同一条 ci.sh 两边跑）
- **基线只记一次**：现象是半年后没人知道基线是什么机器什么参数。
  解法：入档时带机器口径、参数与日期（本篇：M 系列笔记本、100×60s、回环直连）
- **失败不采样**：现象是只有失败率没有失败原因，排查全靠猜。
  解法：首错采样一行代码（本篇实现）

**Q：为什么压测打 /healthz 而不是业务端点？**
A：先测"纯服务能力"（无依赖路径的上限），再测"带依赖路径"（含 PG 的真实
画像）——两层结论不同：前者定位服务与网络，后者定位存储。本篇基线是前者；
带上 PG 的版本作为发布前的补充口径（切换 -url 即可）。

**Q：100 并发是"真实流量"吗？**
A：不是，它是校准过的合成负载——价值不在模拟真实，而在**可复现的对比**。
真实流量的画像来自实验 14 的指标（path 维度的真实分布）。两者互补：
合成压测管回归，真实指标管容量。

**Q：CI 为什么不用 -count=3？**
A：全量 16 包 × 3 轮 ≈ 3 分钟，提交前每次跑太重。本地开发用 -count=1 快速
反馈，发布前手动加跑 -count=3（本系列各篇 README 的验收口径）。节奏分层
是 CI 设计的一部分，不是偷懒。

**Q：marklet 二十篇毕业了，下一步是什么？**
A：把 20 篇的清单当索引读第二遍：每篇的 Pitfalls & Q&A 是踩过的坑，
发布清单是上线动作表。后续自然续篇是 K8s、消息队列、读写分离——但地基
（并发纪律、观测三件套、安全四层、停机编排）已压在测试与清单里，拆不掉。
