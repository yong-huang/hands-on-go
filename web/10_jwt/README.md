# 10 · JWT：签发、验证与三个陷阱的复现

> JWT（JSON Web Token）是无状态令牌：payload 谁都能读、签名改不得、过期自动拒。
> 本篇把三个经典陷阱逐个撞一遍——过期令牌、篡改 payload、alg=none——全部被拒；
> 刷新流程同时暴露无状态的真实边界：旧令牌在过期前永远有效，吊销无门。

## Background

实验 09 的会话方案有个天然的规模问题：会话状态存在 Redis 里，每个服务的每次请求
都要问一次 Redis"这个 SID 是谁"。跨服务调用（A 服务验完 B 服务不认识）或 Redis
抖动时，认证成为单点。

JWT 的思路是把身份信息直接装进令牌：payload 里写好"我是 alice，几点过期"，
再用只有服务端知道的密钥对它做 HMAC 签名。服务端验证签名即可信任 payload，
不需要查任何存储——无状态，天生跨服务。代价同样清晰：令牌发出去就收不回来，
"登出"与"踢人"在纯 JWT 世界里没有位置。

## What

JWT 是三段 base64 字符串，用点连接：header（算法声明）、payload（声明集合，
sub= subject 即用户、exp= 过期时间戳）、signature（对前两段的 HMAC-SHA256）。
签发即"算签名"，验证即"重算签名并比对 + 检查过期"。

可以把 JWT 想成塑封的访客证：信息印在证上谁都能看（不是加密），但覆膜工艺
（签名）让涂改必留痕迹；保安只看证不打电话核实（无状态），证上印着有效期。
但和访客证不同的是——塑封证丢了可以挂失作废，JWT 没有"挂失"这个动作，
有效期前谁捡到谁能用。

| 机制 | 会话（实验 09） | JWT（本篇） |
|---|---|---|
| 服务端状态 | Redis 一个 key | 无 |
| 吊销/登出 | 删 key，即时 | 无（等过期或建黑名单） |
| 跨服务 | 各服务共享会话存储 | 任何持密钥者自验 |
| 典型失败 | 存储抖动即认证瘫痪 | 密钥泄露即全网沦陷 |

## When to Use

- **跨服务的身份传递**：签发一次，各服务持同一密钥（或公钥）自验，不回源
- **短时效授权**：15 分钟寿命的 API 令牌，过期即自然失效，无需清理任务
- **移动端/第三方 API**：客户端不便维护 Cookie，Bearer 头 + 令牌更直接

何时不用：需要"登出即失效、封号即下线"的业务——会话的一行 DEL 在 JWT 世界
要靠黑名单模拟，而黑名单就是状态，等于绕回会话。

## How It Works

### 验证即重算：签名是唯一信任锚

`Parse` 用同一密钥对 header.payload 重算 HMAC，与第三段比对——一致说明这两段
自签发以来一个字节都没动过。payload 是 base64 不是加密：演示里直接解码出了
sub/exp，所以 JWT 绝不能放敏感数据；也正因可读，签名的职责就是让篡改必被察觉。

### 三个陷阱与各自的闸门

过期：exp 声明由库在 `Parse` 时自动比对当前时间，过期即错。篡改：payload
改一个字符，重算签名对不上。alg=none：攻击者把 header 的算法改成"不签名"，
防线是 `WithValidMethods([]string{"HS256"})` 算法白名单，白名单外一律先拒。

golang-jwt 默认也拒绝 none（要 `UnsafeAllowNoneSignatureType` 才能签），
白名单是第二道锁——测试里两个解析器都撞了一遍。

### 刷新：续命容易，吊销无门

`Refresh` 验证旧令牌后签发新令牌——纯算术，不查任何存储。也正因此，旧令牌
在它自己的 exp 之前始终可用（演示第 3 步实测）：刷新没有作废旧令牌的能力，
它只是"提前换发"。需要"登出即失效"时，工程答案是短 TTL + 刷新令牌轮换，
或者退回实验 09 的会话——选型的分水岭是吊销是不是硬需求。

## Pitfalls & Q&A

- **解析器不设算法白名单**：现象是攻击者用自选算法的令牌通过验证（算法混淆攻击）。
  原因：库按 header 的 alg 字段选验证算法。解法：`WithValidMethods` 钉死 HS256
- **payload 里放敏感数据**：现象是"加密传输"的错觉被一行 base64 解码击碎。
  原因：JWT 只签名不加密。解法：只放身份与过期时间，敏感数据留在服务端
- **密钥硬编码进仓库**：现象是密钥随代码泄露，任何人可自签令牌。
  解法：密钥走配置/密钥管理（本篇的 Secret 是演示值，长度 32 字节是底线）
- **把 JWT 当会话用**：现象是"登出后令牌还能用"被当成 bug 追查。
  原因：无状态没有吊销。解法：明确选型——要吊销用会话，要跨服务用 JWT

**Q：HS256 和 RS256 怎么选？**
A：HS256 对称密钥，签发方与验证方共享一个密钥——验证方多一个，泄露面多一分。
RS256 非对称，私钥签发、公钥验证——第三方服务只拿公钥，验得了但造不了令牌。
marklet 单体服务用 HS256 足够；对外发令牌的授权中心应选 RS256。

**Q：弱密钥的爆破有多容易？**
A：HS256 的验证是本地 HMAC 运算，攻击者拿到一个真实令牌就能离线穷举密钥——
每秒可试百万级。纯数字密钥几秒沦陷，"marklet" 这类词秒破。32 字节随机
（本篇演示密钥的长度）意味着 2^256 的空间，穷举失去意义。

**Q：刷新令牌（refresh token）和访问令牌为什么分开？**
A：把长寿命令牌放在请求里频繁传输，泄露概率高；分成"15 分钟访问令牌 +
7 天刷新令牌（只在刷新端点出现）"，泄露面收窄到最常暴露的那部分。
本篇为聚焦陷阱没有拆分，marklet 的完整认证栈在实验 12 汇合。

**Q：alg=none 曾经真的能打吗？**
A：能。历史上多个主流库默认接受 none 算法（"签名可选"的宽松设计），
导致攻击者把算法改成 none、删掉签名即可伪造任意身份。这也是"算法白名单"
成为每个 JWT 库安全清单第一条的原因——库默认安全是底线，白名单是保险。
