# 05 · Interface 底层实现：eface、itab 与 nil 陷阱

> 接口是 Go 抽象的核心，但"接口变量里装了什么"常被想当然：为什么装了 nil 指针的接口不等于 nil？类型断言到底比较了什么？本篇用 `unsafe` 读出接口的两字布局，用 `reflect` 取类型名与方法集，划清"何时能用 unsafe、何时不能"的分界线。

## Background

用接口的人常撞上两个意外：

- 函数里明明构造的是 nil 指针错误，装进 `error` 返回后，调用方的 `err != nil` 判断却为真，进了错误处理
- 参数都写成 `interface{}` 的函数，调用一密性能就掉

在理解布局之前，多数人把接口变量当"魔法盒子"：行为对了不深究，出问题就背规则，比如"别返回 nil 指针"。但断言、方法调用、nil 比较各有一套规则，靠背记很快对不上号。

这些行为出自同一个结构：接口变量就是两个指针字。这个布局已稳定十余年、属于承重结构，可以谨慎地读出来验证——只把接口变量当 `[2]uintptr`（两个地址宽的数组）读两个字的地址，绝不解引用内部字段（字段名随版本可能变），类型名与方法集交给 `reflect`（官方反射 API）。

## What

**定义**：接口变量是一个"类型描述 + 数据"的两字容器——空接口 `interface{}` 是 `{ _type, data }`（类型信息指针 + 数据指针）；带方法的接口是 `{ itab, data }`，itab 打包了接口类型、具体类型与方法表。

**心智模型**：可以把接口变量想象成一张寄存小票：左栏写"东西是什么类型"，右栏写"东西放在哪"。但和单个指针不同的是，两栏要同时看——nil 判定要求两栏全空，只空右栏（数据指针）不算 nil。

`_type`/itab 按"类型"或"接口×具体类型"组合全局唯一缓存，接口只存指向它们的指针；data 指向装箱后的数据副本（值类型装接口时拷贝一份存入）。

## When to Use

什么时候需要按"两字布局"来思考接口：

- 在设计错误返回、可空依赖注入时——预判"装了 nil 指针的接口不等于 nil"什么时候触发
- 在写泛化容器、序列化入口（收 `interface{}` 参数）时——评估装箱与分配代价，决定收值还是收指针
- 在解释类型断言、type switch 的行为时——知道比较发生在哪个字段，语义不再靠猜

什么时候不用：

- 类型在编译期就能确定时，直接用具体类型或泛型，省掉装箱与一次间接
- 需要读类型信息时走 `reflect` 官方 API，不要按内存布局硬读

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 具体接口类型（如 `error`） | 编译期检查方法集 | 明确的抽象边界 |
| `interface{}` / `any` | 无约束，任何值都能装 | 序列化入口、极简签名 |
| 泛型（type parameter） | 编译期实例化，无装箱 | 容器、算法对类型参数化 |
| `reflect` 动态检查 | 运行时取类型与方法，较慢 | 类型在编译期完全未知 |


## How It Works

按演示顺序展开：eface → iface 与 itab → 装箱 → 断言与 nil 陷阱。

### 空接口 eface = { _type, data }

`efaceWords` 把接口变量当 `[2]uintptr` 读出两个字。`_type` 指向类型信息，进程内全局唯一；`data` 指向数据。

int、string、*Point 的 `_type` 地址各不相同，而两个 int 装箱的接口共享同一份——这就是"接口只保存类型指针"的直接证据。输出前两行里 `e1(int 42)` 与 `e4(int 99)` 的 type 地址相同（`0x102767a40`），正是这一点。

### 带方法接口 iface = { itab, data }

带方法接口的第一字是 itab 指针。itab 展开为三件事：接口类型（inter）、具体类型、方法表——`Speaker`×`main.Dog` 的方法表是 `[Bite, Speak]`。

runtime 按（接口, 具体类型）组合对 itab 做全局缓存：`s1`/`s3` 同为 Dog 共用 0x…058，`s2` 是 Cat 用 0x…078。方法调用就是查一次方法表，这也是接口调用比直接调用慢的原因。

本实验的 Dog/Cat 都是零大小结构体，装箱的值没有数据可存，`data` 一律指向 runtime 的 `zerobase` 哨兵地址——输出里 s1/s3 的 data 相同、itab 相同，s2 的 data 相同、itab 不同，正是"类型有别、值共享"的直观体现。

### data 指针的装箱语义

值类型装接口会"装箱"：`x := 5; ex := interface{}(x)` 后 `ex.data=0x…7e8` 与 `&x=0x…0d0` 不同——接口里是拷贝，改 `x=100` 后 `ex` 仍是 5。

指针类型则直存：`ey := interface{}(yp)` 的 `data` 就是 `yp` 本身，不再拷贝。

### 类型断言与 nil 陷阱

断言 `e.(int)` 本质是拿 `_type` 与目标类型比较，匹配才取 data；type switch 是语法糖（`switch v := s.(type)` 命中 Dog 后可调 `Speak()`）。

输出最后一行 `e.(int) → 42, ok=true（_type 匹配 int）` 就是这条比较的成功分支。

nil 陷阱：装了 nil 指针的接口 `_type` 非空、`data` 为 0，所以 `e == nil` 为 false——对应输出里的 `e == nil ? false` 与 `eface._type=0x1027735a0 data=0x0` 两行：第一字有类型、只有第二字是 0。

只有两字全 0 的接口才是真 nil；判断"接口里的值是否为 nil"，必须先断言出具体类型再比较。

### 字段速查

| 字段/概念 | 含义 | 为什么重要 |
|---|---|---|
| `_type` | 空接口第一字：类型信息指针 | 全局唯一；断言就是比较它 |
| `itab` | 带方法接口第一字 | 按（接口, 具体类型）全局缓存；含方法表 |
| `data` | 第二字：数据指针 | 值类型指向副本，指针类型存原指针 |
| 装箱 | 值类型 → 副本 | 每次装接口都可能分配，热路径要留意 |
| 两字全 0 | 真 nil 接口 | 只看 data 或只看 _type 都会误判 |

## Pitfalls & Q&A

踩坑记录，每条 = 现象 + 原因 + 解法：

- **err == nil 误判**。现象：函数返回 `*MyErr` 类型的 nil，装进 error 接口后 `err != nil` 为真。原因：`_type` 非空，接口不是真 nil。解法：要么返回接口类型本身，要么先断言再判。
- **图省事把参数都写成 `interface{}`**。原因：值类型每次传参都装箱拷贝，热路径额外分配，且丧失编译期类型检查。解法：用具体类型或泛型，确实要泛化时优先收指针。
- **业务代码依赖 unsafe 布局**。原因：两字布局稳定，但 itab/_type 内部字段随版本可能变。解法：两字读法只当学习手段，业务代码走 `reflect`。

深入问答：

**Q：类型断言为什么快？**
A：断言只比较接口第一字（_type 或 itab）与目标类型是否匹配，匹配则取出 data——一次指针比较加一次取值，不涉及反射；type switch 是它的语法糖。

**Q：把大结构体传给 interface{} 参数有什么代价？**
A：值类型会装箱拷贝（可能堆分配），热路径建议传指针——指针装接口时 data 直存原指针，不再拷贝。
