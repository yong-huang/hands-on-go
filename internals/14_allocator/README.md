# 14 · 内存分配器：mcache / mcentral / mheap 三级结构

> Go 的堆分配走三级结构：处理器本地的缓存无锁现取，未命中才逐级上溯到带锁的中央缓存与全局页堆，大对象（>32KB）直接绕过前两级。这套结构背下来不难，但"凭什么说它快"需要证据。本实验用三类对象的堆地址分布与 `HeapInuse` 增量把三条路径拍出来，读完你将握有一条可复现的证据链。

## Background

堆分配是 Go 程序最频繁的操作之一，每秒可能发生几十万次。分配动作本身只是"找一块合适大小的内存"，难点在并发：多个执行流同时伸手要内存，谁说了算？

早期通用分配器的做法是一把全局锁管所有分配，多核并发下锁竞争成为瓶颈。TCMalloc（Google 开源的线程缓存分配器，C/C++ 服务广泛使用）引入"线程本地缓存"思想，把锁从热路径上拿掉。

Go 的分配器沿用同一思想，把"线程本地缓存"的归属从线程改成 P（processor，调度器授给线程的逻辑处理器，同一时刻只执行一个 goroutine），落地成一套三级结构（下一节拆解各层）。

理解这层结构之后，很多现象才有解释：`sync.Pool`（标准库提供的临时对象复用池）为什么快、为什么小对象要多小有多小才好、为什么大对象分配天然贵。本实验不满足于背诵结构，而是用地址分布把三条路径实测出来。

## What

Go 的内存分配器是一种按对象大小分诊的三级分配网：用 67 个 size class（把任意对象大小向上取整到的固定尺寸档位，如 16B、32B、…、32KB）统一尺寸，再用三级缓存逐级供货。

三个部件各司其职：

| 层级 | 锁 | 角色 |
|:---|:---|:---|
| mcache | 无（每 P 一份） | 热路径现拿，计数器加减 |
| mcentral | 有（每 size class 一个） | 跨 P 借还 span |
| mheap | 全局 | 页堆协调，缺页向 OS 要内存 |

其中 span（一组同 size class 的连续内存页组成的供货单元）是 mcentral 与 mheap 之间的交换单位；OS 即操作系统。

心智模型一句话：分配请求按大小分诊——<16B 无指针走 tiny（微对象合并）路径；16B~32KB 按 size class 从本 P 的 mcache 无锁拿，miss 才加锁上溯 mcentral、mheap；>32KB 直通 mheap 独占 span。

可以把三级网想象成公司领办公用品：工位抽屉随手拿、不用排队；抽屉空了去部门库房登记借一盒；库房也没有就找总部仓库；特大件设备不值得走这套流程，直接找总部。

但和公司不同的是：这里所有"借还"由运行时自动完成，尺寸按固定档位取整而非按需裁剪，mcache 的归属跟着 P 走而不是跟着线程走。

## When to Use

这层知识在你"决定内存策略"的时候派上用场。三个典型场景：

- **写高并发服务的热路径**：知道小对象分配在多数情况下无锁且近乎免费，可以放心使用局部临时对象，不必过度池化
- **排查大对象带来的卡顿**：>32KB 的对象直通 mheap、绕过两级缓存，天然更贵——拼接大 buffer 之类操作应优先复用或切块
- **定位 `sync.Pool` 的角色**：它是在分配网之上再加一层对象复用，理解三级结构后才判断得出这层复用省掉的是哪一段成本

何时不用：常规业务代码让分配器自己干活即可，"背结构"不等于处处手动优化；先用性能剖析证明分配确实是热点，再针对热点路径动手。

拿到内存的几种方式对比：

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 直接堆分配 | 走三级分配网，代码最简单 | 默认选择，热点证明贵了再优化 |
| 值语义留栈 | 不进堆，无回收成本（见逃逸分析） | 对象生命周期不出函数时 |
| `sync.Pool` | 进程内复用临时对象，减少分配次数 | 高频创建又随即丢弃的临时对象 |
| 自建对象池 | 手工管理生命周期，控制粒度最细 | 少数确定且稳定的场景，维护成本高 |

## Quick Start

前置条件：安装 Go（本实验在 Go 1.26.5 下实测），进入实验目录即可运行，运行 demo 只需 Go；重画数据图需 Python 3 与 matplotlib（pip install matplotlib）。

```bash
cd internals/14_allocator
go run main.go          # 文本演示：tiny/small/large 三组地址分布
go run main.go -json    # 输出 JSON 快照
python3 viz.py          # 重新生成实测数据图
```

预期输出（节选，地址与增量数值每次运行不同，看模式）：

```text
========== A. tiny：24 个 1B 对象 ==========
   相对首个对象偏移(bytes)：[0 1 2 3 4 53 54 55 ... 71]
   → 5/24 落在头一个 16B 块里（tiny allocator 合并分配）

========== B. small：64B 对象 ==========
   排序后相邻地址间隔：[64 64 64 64 64 64 64 64 64 64] ...
   → 间隔基本是 64B（size class）的倍数；HeapInuse +8192 B

========== C. large：48KB 对象 ==========
   相邻地址间隔(bytes)：[49152 49152 49152]
   页内偏移（期望对齐到页首，≈0）：[0 0 0 0]
   → 每个大对象独占一个 span；HeapInuse +196608 B
```

两个要点帮你校准预期：

- 三段输出分别对应 tiny、small、large 三条路径，地址数值每次运行不同，稳定的是**模式**：挤块、间隔规律（small 是 64B 的倍数；large 是 48KB 的倍数、页对齐——无其他 span 插入时恰为 49152）、独占页对齐
- `HeapInuse`（`runtime.MemStats` 中"正在使用的堆 span 字节数"计数器）的增量只在触发新 span 分配时才有参考价值

第三段输出里的 `+196608 B` 恰好等于 4×49152——4 个 48KB 对象分毫不差地各占一条 span。下一节逐条解释这些数字从哪来。

## How It Works

按对象大小从小到大拆解三条路径，每条都对上 Quick Start 输出里的一段。

### tiny：<16B 无指针小对象合并进 16B 块

`<16B 且不含指针`的对象走 tiny allocator（微对象分配器）：多个对象挤进同一个 16B 块，分配调用次数≈块数而不是对象数。这就是输出 A 段。

实测 24 个 1B 对象的偏移只跨约 72 B——本例偏移 `[0..4] + [53..71]` 分两簇（**簇形每次运行不同**，不变的规律是"挤进极少数 16B 块"）。

含指针字段的对象不走 tiny，直接进对应 size class——GC 需要精确指针对齐（回收器扫描对象时依赖指针落在对齐位置上），混装会破坏这一前提。

### small：size class 的 64B 平铺

256 个 64B 对象排序后相邻间隔**全部是 64**——同 class 的对象在 span 里按固定步长紧凑平铺，地址天然 64 对齐，CPU 缓存友好。这就是输出 B 段，也是 size class 的直接证据。

档位设计本身是取舍：任意大小向上取整到 67 个固定档位（16B、32B、…、32KB），碎片可控、对齐免费、复用简单。`HeapInuse` 增量（本例 +8192 B）只在触发新 span 分配时才有参考价值，每次运行不同。

### large：直通 mheap，独占 span、页对齐

4 个 48KB 对象相邻间隔全部 **49152（=48KB）**，`地址 & 0xfff == 0` 全部成立——每个大对象独占一条 span、页对齐，绕过 mcache/mcentral 两级缓存。`HeapInuse` +196608 B = 4×49152，分毫不差。这就是输出 C 段。

### 路径判别总表

| 路径 | 条件 | 机制 | 实测证据 |
|:---|:---|:---|:---|
| tiny | <16B 且无指针 | 合并进 16B 块 | 24×1B 只跨 ~72B |
| small | 16B~32KB | mcache 无锁现取 | 间隔恒 64B |
| large | >32KB | 直通 mheap | 间隔=48KB、页对齐、+196608 B |

三条路径的设计取舍可以压缩成一句话：**无锁优先，代价逐级上升，绝不让热路径碰锁**。

## Pitfalls & Q&A

踩坑清单，每条按"现象 → 原因 → 解法"展开：

- **地址间隔算出来乱糟糟**：现象是间隔忽大忽小没有规律；原因是分配顺序和地址顺序不一致；解法是先排序再算相邻间隔
- **「大对象间隔≈64KB」的直觉是错的**：现象是拿 64KB 预测 48KB 对象的间隔而落空；原因是 large 路径独占 span，间隔等于对象大小（跨度即 span 大小）；解法是按"间隔=对象大小"预期，并加验页对齐
- **tiny 实验失败**：现象是 24 个对象没有挤进少数 16B 块；原因是对象带了指针字段，直接进了 16B size class；解法是确认被测对象不含指针
- **MemStats 读数不可靠**：现象是单次绝对值忽上忽下；原因是堆里本就有其他活动；解法是前后各读一次取增量
- **HeapInuse 不涨误判为没分配**：现象是明明分配了、增量却为 0；原因是 mheap 里常有空闲 span 直接复用，不必新申请；解法是地址间隔才是可靠证据

深入问答：

**Q：Go 的小对象分配为什么快？**
A：三级结构把锁从热路径上拿掉了——每个 P 的 mcache 私有，拿对象只是内存读写；只有 miss 才加锁上溯 mcentral、mheap。TCMalloc 同款思想。

**Q：size class 为什么需要？**
A：把任意大小向上取整到 67 个固定档位，同 class 的 span 按固定步长平铺对象（实测 64B 对象间隔恒 64），碎片可控、对齐免费、复用简单。机制细节见 How It Works 的 small 一节。
