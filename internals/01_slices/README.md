# 01 · Slice 底层实现：三字段头、共享与扩容分离

> slice 是 Go 里"看起来像数组、用起来像动态数组"的核心类型。本篇用 `unsafe` 读出 slice 的真实内存布局，把"函数内 append 外面看不到""两个切片改一个、另一个跟着变"这两类陷阱，变成看得见的地址与数值。

## Background

写 Go 的第一年通常会撞上两个意外：

- 把切片传给函数，在函数内 `append`（向切片尾部追加元素的内建函数），函数外看不到新元素
- 从一个切片再切出另一个，改其中一个的内容，另一个也跟着变

在此之前，多数人把切片当成"会自动变长的数组"来用：行为对了不深究，行为怪了就用 `copy` 再拷一份绕过去。这种做法在代码量小时可行；一旦要在过滤、去重、批量解析这类函数之间传递切片，"到底谁和谁共享数据"就只能靠逐条背规则回答。

背规则很快会失效，因为规则本身就是内存结构的推论。Go 运行时（负责内存分配与调度的运行时库）把切片实现成"一小份描述信息 + 一块独立数据"，上面的两类意外都是这个结构的自然结果。

这份布局是官方承诺的稳定结构（不随版本变化），因此可以借助 `unsafe`（绕过类型检查、直接按内存布局读写的标准库包）把真实地址打印出来，对每条规则做实证——比背结论可靠。

## What

**定义**：slice（切片）是一种数组视图类型——变量本身只持有一个三字段头，元素数据永远存放在另一块底层数组（真正存元素的那段连续内存）里。

```go
type sliceHeader struct {
    Data uintptr // 底层数组起始地址
    Len  int     // 有效元素个数
    Cap  int     // 到底层数组末尾的可用容量
}
```

这段在做什么：用 `uintptr`（能装下一个内存地址的整数类型）复刻 `runtime.slice` 的字段排布，配合 `unsafe` 就能读出任意切片的真实头部。

**心智模型**：可以把切片想象成贴在一卷胶片上的取景框——框子本身很轻（三个字段共 24 字节），挪动框子（切片表达式 `s[a:b]`）只是改指针偏移和 Len/Cap，不搬动照片。但和取景框不同的是，两个框子可以同时框住同一段胶片：重叠区域里的元素天然共享，改一处另一处立刻可见。

## When to Use

什么时候需要按"头部 + 底层数组"来思考切片：

- 在写会修改切片的库函数（过滤、去重、截断、追加）时——判断该用返回值回传新切片，还是原地写入共享内存
- 在做零拷贝数据处理（从大 buffer 切子视图解析、网络包分片）时——用切片表达式避免成块复制
- 在排查"数据被莫名改掉"的问题时——打印 Data 地址即可判断两个变量是否指向同一块内存

什么时候不用：

- 数据量小、逻辑简单时，直接 `copy` 复制一份，比推理共享关系更省事
- 需要键值语义、按键随机存取时用 map，切片表达不了这种关系

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| slice 共享视图 | 切片表达式零拷贝，多个视图共享内存 | 大 buffer 上反复取子区间 |
| `copy` 全量复制 | 每次复制 O(n)，换来完全隔离 | 数据小、要安全交给别人修改 |
| 三索引切片 `s[lo:hi:hi]` | 主动把 cap 限到 hi，append 必然分离 | 只想给出视图，杜绝共享写入 |
| 定长数组 `[N]T` | 值类型，赋值即整块复制 | 长度编译期已知（如 `[32]byte` 摘要） |

## Quick Start

前置条件：本机安装 Go 即可（扩容数值以 go1.26 实测为准）。

```bash
cd internals/01_slices
go run main.go          # 文本演示：结构 → 扩容 → 共享 → 分离
go run main.go -json    # 输出 JSON 状态快照（地址/容量数值）
```

预期输出（节选，地址每次运行不同）：

```text
original                     data=0x...e190  len=5   cap=10
sliceA = original[1:4]       data=0x...e198  len=3   cap=9
地址关系：sliceA 偏移 original 8 字节，sliceB 偏移 16 字节
-- 修改 sliceA[0]（即 original[1]）--
修改后: sliceA[0]=999  sliceB[0]=21  original[1]=999
sliceA 扩容后: len=10 cap=18 data=0x...8000
data 地址: 0x...e198 -> 0x...8000  true
```

输出按"读头部 → 改共享元素 → 扩容对比"推进。每一步"在看什么"都写在 `main.go` 的注释里；`-json` 快照给出与文本演示一致的机器可读数值。

## How It Works

按程序演示顺序展开：头部 → 切片表达式 → 共享 → 扩容分离。

### 头部与 make 语义

`var s []int` 时三个字段全为 0；`make([]int, 2, 4)` 分配容量 4 的底层数组，但 Len 只开放前 2 个。slice 本质是一个"数组视图"——它自己不持有数据。

你在输出里看到的 `original data=0x...e190 len=5 cap=10`，就是读这个头的结果；`len(s)` 是 O(1)（与长度无关的常数时间）读头，不是遍历。

### 切片表达式：偏移而不复制

`s[lo:hi]` 不复制数据：新视图的 Data = 原 Data 加偏移、len = hi-lo、cap 减 lo。所以 `original[1:4]` 与 `original[2:5]` 相对 `original` 分别只偏移 8 字节和 16 字节——对应输出里的"地址关系"一行。

### 共享：重叠窗口内的元素

`original`（cap=10）切出 `sliceA=original[1:4]`、`sliceB=original[2:5]`。把 `sliceA[0]`（即 `original[1]`）改为 999 后，`original[1]` 一并变为 999。

`sliceB[0]` 看的是 `original[2]`，仍是 21。

你在输出里看到的 `修改后: sliceA[0]=999 sliceB[0]=21 original[1]=999`，就来自这里的重叠窗口共享——不重叠的元素互不影响。

### 扩容：growslice 的两步

`growslice`（runtime/slice.go 里的扩容函数）先按规则算目标容量：

- 所需容量超过 2×cap 时，直接按所需容量分配
- 否则 cap < 256 翻倍；cap ≥ 256 按 `(cap+3*256)/4` 递增（约 1.25 倍）

第二步再按元素大小向上对齐到 size class（mallocgc 的内存规格档位）。实测对比（go1.26）：cap 512 估算 832、实际 848；cap 2048 估算 2752、实际 3072——差值就是对齐的贡献。

### 分离：append 超容量后换新数组

`sliceA` 扩容前 len=3、cap=9，连续追加 7 个元素触发扩容：分配新数组（cap 9→18）并拷贝旧数据。

输出里 `data 地址: 0x...e198 -> 0x...8000 true` 就是新旧地址不相等的判定结果；而 original 与 sliceB 的地址不变、仍指向旧数组——"切片后 append 会悄悄分离"。

### 字段速查

| 字段/表达式 | 含义 | 为什么重要 |
|---|---|---|
| `Data uintptr` | 底层数组起始地址 | 偏移它就实现了"零拷贝切片" |
| `Len` | 有效元素个数 | `len(s)` 是 O(1) 读头，不是遍历 |
| `Cap` | 到数组末尾的容量 | 决定 append 是否触发扩容/分离 |
| `s[lo:hi]` | 视图：data+lo，len=hi-lo，cap 减 lo | 第三个参数 `s[lo:hi:cap]` 可主动限 cap 防共享 |

## Pitfalls & Q&A

踩坑记录，每条 = 现象 + 原因 + 解法：

- **对比不出扩容前后的地址差异**。原因：记录地址的取值时机在 append 之后，读到的已是新值。解法：源码先把 `ha.Data` 拷进局部变量 `oldAddr`，再触发 append。
- **JSON 快照里的地址是十进制**。原因：`uintptr` 序列化成 JSON 时按整数打印。解法：在 Go 侧用 `fmt.Sprintf("0x%x", ...)` 格式化成十六进制再输出。
- **按公式估算 cap 会偏小**。现象：cap 512 估算 832、实测 848。原因：实际 cap 是"规则 + size class 对齐"的结果。解法：程序把估算与实际并排打印，以实测为准。
- **容量内的 append 会写进共享数组的尾部空位**。现象：`go run main.go -json` 里 `original` 的第 5 个元素被 sliceA 的 append 覆盖成 100。原因：sliceA 的 cap 延伸到 original 数组的空余位置，append 在原数组上就地写入——这是比"分离"更隐蔽的别名写入（两个变量名指向同一块内存）。解法：需要隔离时用三索引切片限制 cap。

深入问答：

**Q：slice 作为参数传递，函数内 append 为什么有时外面看不到？**
A：传的是 24 字节头的值拷贝。函数内 append 若在原 cap 内，写入的是同一底层数组（len 不变时外面看不见新元素，但按索引能读到）；若触发扩容则换新数组，完全不影响外面。

**Q：怎么安全地把切片交给别人修改而不影响自己？**
A：`append(s[:0:0], s...)` 或显式 `make + copy` 强制换底层数组；反之想保持共享就别触发扩容。

**Q：为什么可以用 unsafe 读 slice 内部？map 也可以吗？**
A：sliceHeader 布局是官方承诺的稳定结构，unsafe 读取仅适合学习；map 的 `hmap` 无此承诺且运行时故意不暴露，不应硬编码（见 [02_map](../02_map/)）。
