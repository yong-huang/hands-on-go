# 25 · defer 底层实现与性能：LIFO 收拢、立即求值、几乎白送的开销

> defer 是 Go 的延迟调用关键字：注册的函数在宿主函数退出前执行。读完本篇，你能用真实输出回答三个问题——它按什么顺序执行、参数何时求值、每次使用付多少代价。

## Background

写资源型代码（锁、文件、网络连接）的第一原则是"谁申请谁释放"。没有语言机制帮忙时，最常见的写法是在函数末尾手动调用释放函数：开头 `mu.Lock()`，结尾 `mu.Unlock()`。

手动释放有两个死角。一是提前 `return`：函数有多个出口时，每个出口前都得记得补释放，漏一处资源就泄漏。二是 panic（运行时异常，会沿调用栈向上传播、中断正常流程）——末尾的释放语句会被整段跳过。

```go
mu.Lock()
if err := do(); err != nil {
    return // 漏掉 mu.Unlock()：这把锁再也放不回去
}
mu.Unlock()
```

Go 为此把"登记释放动作"做成了语言级机制：在申请处登记，函数退出时保证执行，异常路径也不例外。它如何做到、代价多大，正是本篇要拆解的内容。

## What

**定义**：defer 是一种延迟调用语句——`defer f(x)` 在书写处把 f 和参数 x 立即求值并存好，推迟到宿主函数返回前执行。

**心智模型**：可以把 defer 的登记过程想象成往一摞盘子上叠盘子——最后叠上去的最先被拿走（LIFO，Last-In First-Out，后进先出）。但和真实盘子不同的是：每只盘子放上去的瞬间就刻好了字（参数立即求值成快照），而且函数返回前必须把整摞搬完。

**机制一句话**：defer 语句只是"注册"——依序进栈、参数当场求值；`return` 先把返回值写进返回槽（存放返回值的变量），然后栈按 LIFO 出栈，此刻才允许改写命名返回值（在函数签名里给返回值起名字的写法，如 `(ret int)`），出栈完毕函数才真正返回。

## When to Use

### 典型场景

- 成对资源的释放：拿到锁、打开文件或连接后立刻 `defer Close()`，提前 return 与 panic 路径都不漏。
- 逆序收尾：先开连接、再开锁、再开文件的场景，释放天然要反着收，defer 的 LIFO 正好匹配依赖关系。
- 返回值最后修正：命名返回值 + defer 改写返回槽，配合 recover（在 defer 中捕获 panic 的内置函数）把 panic 转成错误返回。

### 何时不用

- 热循环体内：每轮 defer 会退化为 heap defer（运行期在堆上组织 defer 链表的慢速实现），且资源积压到整个函数返回才释放。
- 对纳秒级延迟极端敏感、且函数没有提前 return 也没有 panic 风险的极热函数：手动释放实测略快，数字见 How It Works。

### 同类方案对比

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| defer | 语言级注册，panic 路径也执行；open-coded defer（编译器直接在函数返回点展开的零链表实现，详见 How It Works）单次开销约 1ns | 绝大多数成对资源释放，默认选择 |
| 函数末尾手动释放 | 实测略快（4.40 vs 4.97 ns/op），但每个提前 return 都要补释放 | 无多出口、确定不会 panic 的极热函数 |
| 循环体内 defer | 退化为 heap defer，句柄积压到函数返回 | 不要这样用——把循环体抽成小函数，defer 放函数内 |

## How It Works

### LIFO：后开先关

登记顺序 1→2→3→4→5，返回时打印顺序 5→4→3→2→1，严格逆序。你在输出里看到的 5→4→3→2→1，就来自"注册进栈、return 后出栈"这条机制。这也是"开连接→开锁→开文件，释放天然反着收"的根据：先申请的资源后释放，依赖关系不会乱。

### 参数立即求值 = 快照语义

`mark()` 在 `defer` 语句出现的那一刻就执行（log 立即拼满 5 条），真正打印发生在函数返回时。

所以 `defer f(x)` 存进栈的是 x 的**快照**（求值结果的一份副本），不是执行时才去读；想延迟读变量得包一层闭包 `defer func(){ f(x) }()`——闭包是捕获了外层变量的函数值，执行时才读变量本身。`defer file.Close()` 捕获的是"当前那个 file"，也是同一语义。

### return 不是原子操作：命名返回值可被 defer 改写

`return x` 实际分三步：把 x 写入返回槽 → 执行 LIFO 的 defer → 真正返回。命名返回值 `func f() (ret int)` 的 ret 就是返回槽本身，defer 改它有效；匿名返回值在 return 时已拷出，defer 改局部变量改不到返回值。

main.go 没演示这段，用最小程序单独验证过（go1.26）：

```go
func anonymous() int { x := 1; defer func(){ x++ }(); return x }  // 返回 1
func named() (ret int) { ret = 1; defer func(){ ret++ }(); return } // 返回 2
```

### open-coded defer：为什么"几乎白送"

Go 1.14+ 绝大多数 defer 走 open-coded（编译器直接在函数返回点内联展开要执行的代码）：带条件判断哪个 defer 触发，没有堆上链表、没有运行期遍历，开销 ≈ 一个分支判断。

只有 defer 出现在 for 循环里（动态数量）、或与 panic/recover 交互等边界场景，才退回慢速的 heap defer（运行期走 `deferproc`/`deferreturn` 两个运行时函数注册与执行）。

实测对照（500 万次循环，mu.Lock + Unlock）：机器空闲时 defer 额外开销约 1.09–1.13x；首次编译/高负载时会飘到 1.4x 以上——数据漂移，但结论稳定：这点代价换"异常路径也一定解锁"是值得的。

对照输出里的 `4.97 vs 4.40 ns/op`，就来自这条 open-coded 路径。

### 关键语义速查

| 写法 | 语义 | 为什么重要 |
|---|---|---|
| `defer f(x)` | x 在注册那一刻求值并快照 | "以为读的是最终值"这类 bug 的根源 |
| `defer func(){ f(x) }()` | 执行时才读 x | 想要"最终值"就包这层闭包 |
| 命名返回值 `(ret int)` | defer 可改写返回槽 | 实测 1 → 2，配合 recover 改错误码常用 |
| 匿名返回值 | 已拷出的副本，改不到 | 与上一行对比是经典易错点 |
| `defer p.Close()` | p 是注册时拷贝的指针值 | 之后 `p = nil` 不影响 defer 已捕获的指针 |

## Pitfalls & Q&A

**坑 1：把"逆序"当成绝对顺序。** 现象：登记写 5→1，执行却打出 1→5，表面像违背了语义。原因：逆序是相对登记顺序而言的，登记 1→5 才会执行 5→1。解法：判断执行顺序前，先确认登记顺序。

**坑 2：把输出第一行当成第一条 defer。** 现象：首行"函数体先打这行"先于全部"执行"行出现。原因：函数体内的语句按书写顺序先执行，defer 注册的函数体要到返回时才跑。解法：读输出时跳过函数体打印的行，从"执行(5)"开始看。

**坑 3：热循环里写 defer。** 现象：循环大了句柄耗尽、性能明显下降。原因：defer 绑定的是函数而不是循环轮次——资源积压到整个函数返回才释放，同时退化为 heap defer。解法：把循环体抽成小函数，defer 放函数内，每轮返回即释放。

**坑 4：benchmark defer 时连着 panic。** 现象：测出的开销远大于 1.1x。原因：open-coded defer 只在无 panic 路径展开，panic 才走的 `deferproc` 链是另一套实现。解法：基准代码避开 panic 路径，或明确注明测的是 heap defer。

**坑 5：拿单次 ns/op 当结论。** 现象：多次运行比值在 1.09–1.54x 之间波动。原因：编译缓存、机器负载都会影响绝对值。解法：结论看比值不看绝对值，多跑几轮取稳定区间。

**Q：手动释放性能更好，为什么还坚持用 defer？**
正确性优先——提前 return 和 panic 路径只有 defer 能保证解锁。百万 QPS（每秒请求数）的 handler（请求处理函数）里一次 defer ≈ 每请求 1ns，无感；真正的热循环才值得手动管理。

执行顺序、求值时机、返回值改写与开销数字均已在 How It Works 给出实测证据，此处不再重复。
