# 04 · String 底层实现：只读两字段头与共享拷贝

> string 是最熟悉的类型，但三个问题常被想当然：它底层长什么样？`s[a:b]` 真的不拷贝吗？为什么和 `[]byte` 互转总会分配内存？本篇用 `unsafe` 读出真实地址，把这三件事变成看得见的数字。

## Background

用 string 的人常撞上三个意外：

- `len(s)` 对中文给出的数字比"字符数"大
- 按下标切片，切出来的子串是乱码
- 循环里反复 `string(b)` / `[]byte(s)` 转换，性能骤降

在理解内存表示之前，多数人把 string 当"字符数组"：按直觉数长度、按位置取子串。Go 源码默认按 UTF-8 编码存字节，一个汉字占多个字节，而 string 记录的是字节数——直觉与实现从这里开始错位。

互转变慢、切片变乱码，这些行为的根源是同一个结构：string 变量本身只是一小份只读描述信息，字节内容存在别处。string 头是官方承诺的稳定布局（`reflect.StringHeader` 承载，与 slice 一样、与 map/channel 不同），这正是能用 `unsafe` 直接读头验证的前提。

## What

**定义**：string 是只读字节序列类型——变量只持有一个两字段头：`Data`（指向只读字节数组）与 `Len`（字节数，不是字符数），共 16 字节，比 slice 头少一个 cap 字段。

```go
type stringHeader struct {
    Data uintptr // 指向只读字节数组
    Len  int     // 字节数（不是字符数）
}
```

这段在做什么：复刻 `reflect.StringHeader` 的字段排布，配合 `unsafe` 读出任意 string 的真实头部地址。

**心智模型**：可以把 string 头想象成一张借阅卡——卡上只写"书在哪、共几页"，书（字节数据）锁在别处且不可涂改。但和 slice 视图不同的是，卡上没有容量（cap）栏，也没有任何"原地写"的口子：任何修改都意味着分配一块新内存。

同为 "hello"，字面量的数据在 rodata（编译期只读数据区），运行时构造的落在堆/栈——内容相同也各存一份，地址每次运行都不同，但"来自不同区域"这件事永远成立。

## When to Use

什么时候需要按"两字段头 + 只读字节"来思考 string：

- 在写文本解析、协议拆包（按边界切字段、找子串）时——判断该按字节切还是按 rune（Unicode 码点，`range` 遍历的单位）切
- 在性能敏感路径（序列化、日志拼接、高频 `[]byte`↔`string`）时——知道每次转换是一次 O(n)（与长度成比例）的分配，决定缓存结果还是换 Builder
- 在排查中文乱码、长度对不上时——先确认 `len` 数的是字节，再谈别的

什么时候不用：

- 缓冲区需要原地修改时，直接用 `[]byte`，避免来回转换
- 少量片段一次性拼接时，直接用 `+` 连接即可，无需额外工具

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| string | 只读、切片零拷贝、可比较相等 | 文本字面量、map 的键、不需修改 |
| `[]byte` | 可写，支持共享与 append | 需要原地修改的字节缓冲 |
| `strings.Builder` | 累积拼接，最后一次性转 string | 循环里拼接大量片段 |
| `[]rune` | 每字符一个码点，可按字符下标改 | 需要按"字符"位置操作文本 |

## Quick Start

前置条件：本机安装 Go 即可，无其他依赖。

```bash
cd internals/04_string
go run main.go          # 文本演示：头 → 切片共享 → 双向转换 → 不可变
go run main.go -json    # 输出 JSON 地址快照（供程序化读取）
```

预期输出（节选，地址每次运行不同）：

```text
  字面量     "hello"              data=0x10273b8b7 len=5
  运行时构造  "hello"              data=0x161455510048 len=5
  s   = "gopher"  data=0x10273b9e3 len=6
  sub = "ophe"    data=0x10273b9e4 len=4
  偏移：sub.data - s.data = 1 字节（不拷贝，只移动指针）
  两者不同 → 发生拷贝（true）
```

每一步"在看什么"都写在 `main.go` 注释里；`-json` 快照给出一致的地址与 copied 字段。

## How It Works

按演示顺序展开：头与区域 → 切片共享 → 双向转换 → 编译期不可变。

### 两字段头与数据所在区域

比 slice 少一个 cap。字面量被编译器放进只读数据区（rodata）；运行时用 `string([]byte{'h','e','l','l','o'})` 拼出的 string，数据落在堆/栈。

你在输出里看到的前两行——同为 "hello" 的两个字面量与运行时构造——就是这两个头并排的样子：结构相同（len=5），内存区域不同，各存一份数据。

### 字符串切片共享底层字节数组

`s := "gopher"; sub := s[1:5]` 不复制字节：新头只是 `str + 1`、`len = 4`。实测 `sub.data - s.data = 1` 字节，即输出里的"偏移：sub.data - s.data = 1 字节"一行。

没有 cap 意味着 slice 那种"容量内 append 写穿共享数组"的隐患在 string 上不存在；共享的代价是谁都不能原地修改。

### string 与 []byte 双向转换都拷贝

string 只读、[]byte 可写，语义冲突使两者不能共用内存：两个方向各分配、各拷贝一次。实测 `0x…8b7 → 0x…068` 与 `0x…078 → 0x…07a`；改可写方后只读方打印不变——两份数据。

输出里 `两者不同 → 发生拷贝（true）` 就是转换前后 Data 地址不相等的判定结果。

### 不可变由编译期强制

`lit[0] = 'a'` 直接编译失败（`cannot assign to lit[0]`）：只读是语法层拦截的保证，任何"可变"诉求都只能先拷贝成 `[]byte`。

### 字段速查

| 字段/表达式 | 含义 | 为什么重要 |
|---|---|---|
| `str uintptr` | 只读字节数组起始地址 | 切片 = 指针加偏移，零拷贝 |
| `len int` | 字节数 | 中文一个字符 3 字节；字节边界切片可能切碎字符 |
| `s[a:b]` | 新头：str+偏移、len 重算 | 零拷贝共享只读数据 |
| `[]byte(s)` / `string(b)` | 各拷贝一次 | 每次转换一次内存分配，O(n) |

## Pitfalls & Q&A

踩坑记录，每条 = 现象 + 原因 + 解法：

- **len 是字节数不是字符数**。现象：对中文切片切出乱码。原因：按字节边界切片可能把多字节字符拦腰切断。解法：遍历用 `for _, r := range s`（按 rune 逐字符）。
- **高频 string↔[]byte 转换成为分配大户**。原因：每次转换一次内存分配。解法：拼接场景改用 `strings.Builder`，一次构造一次拷贝。
- **对 map/channel 照搬 unsafe 读法**。原因：hmap/hchan 是内部结构且随版本变动。解法：读内部状态要走 reflect 等官方 API，不要按偏移读。
- **试图背具体地址**。原因：地址每次运行都不同。解法：结论看"是否相等/偏移多少"，别背具体地址值。

深入问答：

**Q：怎么安全地读 string 内部？map 也可以吗？**
A：string/slice 头是官方承诺布局，unsafe 读取仅适合学习；map 的 hmap 非稳定契约（Go 1.24 起已换 Swiss Table），硬读只能得到垃圾。
