# 24 · 闭包与函数捕获：闭包抓的是「引用」，不是一个拷贝

> Go 闭包捕获变量是**引用捕获**——共享同一份变量存储（下文称"盒子"），不是值快照。这个语义导致两个经典现象：循环里起 goroutine 捕获 `&i` 时所有协程共享同一个盒子（经典 bug），以及被捕获变量被迫逃逸到堆（变量改在堆内存分配）。
>
> 本实验用 `unsafe.Pointer(&i)` 把"共享 vs 独立"量化成**唯一地址数**（1 个 vs 5 个），再用 `go build -gcflags=-m` 看编译器的逃逸供词。读完你将能解释并修复循环捕获 bug，并预判闭包的堆分配。

## Background

写并发 Go 时几乎人人踩过这个坑：循环里起 5 个 goroutine（Go 的轻量协程），每个都打印循环变量，结果输出全是终止值。

根源在于闭包捕获的永远是变量本身（引用），不是创建那一刻的值——闭包和外部代码共享同一个盒子，`x = 99` 之后闭包读到的是 99，不是 10。

这个语义直接推出两个后果。其一，被捕获的变量可能比创建它的栈帧（函数运行时占用的栈区域）活得久——goroutine 还在跑，函数已返回，栈上无处安放，编译器只能把它 moved to heap（移到堆分配）。

其二，循环变量若声明在循环外，整个循环只有这一个盒子，所有闭包共享。程序演示三件事：循环捕获的地址塌缩成 1 个、参数传值修复后变回 5 个、引用捕获让闭包看到外层的后续修改。

## What

**定义**：闭包（closure，引用了外部变量的函数值）在 Go 里是一个 `funcval{fn 指令指针, env 捕获变量引用}` 结构：函数体只有一份，被捕获的变量变成堆上的"盒子"，闭包里存的只是盒子的引用。捕获语义因此是引用捕获——闭包与外部代码读写同一份变量。

**心智模型**：可以把被捕获变量想象成一块公共白板：闭包存的不是白板内容的照片（值快照），而是白板的门牌号（地址引用）。5 个闭包都存 `&i`，等于 5 个人记的是同一个门牌。

但和"拍照快照"不同的是：引用捕获会看到后续修改——外层 `x=99` 后闭包读到 99，而快照永远停在拍摄那一刻。Quick Start 输出的两个"唯一地址数"（1 与 5），就是"共享"与"独立"两种情形的判据。

## When to Use

这套知识在三类时刻派上用场：

- 写延迟执行的代码（goroutine、defer 内的闭包、回调与事件处理器）时：先想清楚捕获的是引用还是拷贝
- 排查"goroutine 读到循环变量终止值"类 bug 时：用唯一地址数验证共享，再用传参修复
- 做性能分析时：闭包密集路径出现分配热点，先查被捕获变量是否逃逸上堆

什么时候不用：

- 只在函数内即时调用、不跨生命周期的匿名函数，按普通函数理解即可，无需纠结捕获
- 需要快照语义时别依赖捕获，直接显式传参——语义即文档
- Go 1.22+ 的 `:=` 循环变量已每迭代一份，循环内 `:=` 声明的新代码无需手动修复；但循环外声明仍要警惕

同类写法对比：

| 写法 | 差异 | 什么时候选它 |
|---|---|---|
| `go func(j int){…}(i)` 传参拷贝 | 每迭代一份独立变量，语义显式 | 循环起 goroutine 的标准修复 |
| 循环体内 `i := i` 遮蔽拷贝 | 每迭代新变量，改动最小 | 老代码快速修补 |
| 依赖 Go 1.22+ `:=` 新语义 | 每迭代一个新变量，零改动 | 新代码默认；老代码迁移需确认声明位置 |

## How It Works

### 闭包 = funcval{指令指针, 捕获变量引用}

编译器把 `func(){ return x }` 编译成一个普通函数（指令指针）加一个 `funcval` 结构头，被捕获的变量不在结构里复制一份，而是以**引用**（地址）挂在环境里。

所以闭包和外部代码看到的是同一个盒子：`get := func() int { return x }` 创建时 `x=10`，随后外层 `x=99`，调用 `get()` 返回 **99**。

两个闭包捕获同一个 `v`，`&v` 地址相等判定为 **true**——与 Quick Start 第 3 段输出一致。

### 经典坑：循环变量只有一个盒子

`var i int; for i = 0; i < 5; i++`——变量声明在循环外，整个循环只有这一个盒子。每个 goroutine 存下的都是 `&i`，等它们真正被调度执行时 `i` 已自增到 5。

于是 5 份地址全部相同、读到的全是终止值 `[5 5 5 5 5]`——Quick Start 第 1 段的"唯一 1 个"就来自这里。若调度交错，也可能读到 `[3 5 5 5 5]` 这类中途值，这正是数据竞态（多 goroutine 无同步地读写同一变量）的现场。

**Go 1.22 语义变更**：`:=` 在循环内声明的变量（range 与三段式 for 都算）已改为**每迭代一个新变量**，"全部看到终止值"的经典现象在 `:=` 写法下不复存在。

但坑没有消失——**声明在循环外**（`var i int; for i = 0; …`）或手动改写循环变量时仍是同一个盒子，老代码迁移时这是真实雷区。本实验特意用"循环外声明"复现经典坑。

### 修复：参数传值，各自持有一份

`go func(j int) { … }(i)` 把 `i` 的当前值**拷贝**进本迭代的 `j`，5 个 goroutine 各拿一份。

实测 5 个地址互不相同（相邻常差 `0x800`，每次运行会变），读到的值正是各自的 `[0 1 2 3 4]`——对应 Quick Start 第 2 段的"唯一 5 个"。

等价写法还有循环体内 `i := i` 遮蔽拷贝（内层同名变量遮住外层），或直接依赖 Go 1.22+ 的新语义，取舍见 When to Use 的对比表。配图由 viz.py 生成（需 Python 3 + matplotlib），文本数据用 `go run main.go -json` 即可复现。

### 逃逸到堆是结果，不是选择

闭包体可能比创建它的栈帧活得久：goroutine 还在跑，外层函数已经返回，栈帧随之销毁——`&i` 无处可搁。编译器的选择只有一个：`moved to heap`。

本实验的供词是 `i`、`wg`、`mu`、`next` 全部上堆（`captureFixed` 里被捕获的 `wg` 同样上堆）——正是配套诊断命令列出的那几行。逃逸意味着每次这样的闭包创建都伴随堆分配，闭包密集的代码路径就是分配热点。

### 关键表达式速查

| 表达式 | 含义 | 为什么重要 |
|---|---|---|
| `func() { … &i }` | 闭包捕获变量引用 | 与外层共享同一盒子，看到后续修改 |
| `go func(j int){…}(i)` | 参数传值拷贝 | 每迭代一份独立变量，是标准修复 |
| `unsafe.Pointer(&i)` | 读变量的真实地址 | 把"共享 vs 独立"量化成唯一地址数 |
| `go build -gcflags=-m` | 逃逸分析诊断 | `moved to heap: i` = 这轮多了一次堆分配 |

## Pitfalls & Q&A

### 踩坑清单

- **并发往共享 slice append 会丢更新**：偶发只记下 3-4 个地址，早期差点误判成"栈复用"
  - 原因：5 个 goroutine 同时 `append` 同一切片，数据竞争丢更新
  - 解法：每个 goroutine 写自己的槽位（`slots[j]=…`），数字才稳定——这本身就是一个小竞态教训
- **别跨 goroutine 打印地址拼顺序**：靠打印顺序判断"共享"时而失灵
  - 原因：多个 goroutine 各自打印 `&i`，到达顺序随机
  - 解法：判断"共享"只能靠唯一地址数，不能靠排列
- **`-m` 诊断不要 grep 全量**：输出被闭包逐行展开淹没，抓不到重点
  - 原因：`go build -gcflags=-m` 完整输出非常长
  - 解法：聚焦 `moved to heap` + 变量名即可；`-m -m` 才能看到 cost 预算（见实验 23）
- **`sync.WaitGroup` 也会被捕获上堆**：偶发 deadlock（死锁，各方可永久互相等待）
  - 原因：`wg` 同样 `moved to heap`，迭代共享并乱序 `Done` 时序错乱
  - 解法：收尾只在循环外 `wg.Wait()` 一次

### 深入问答

**Q：Go 闭包捕获的是值还是引用？**
A：变量本身（引用捕获），机制与证据见上文 funcval 一节；想拍快照必须显式传参拷贝。

**Q：循环里起 goroutine 打印循环变量，为什么全是最后一个值？**
A：变量声明在循环外，整个循环共享一个盒子，执行时 `i` 已是终止值；修复三选一（传参 / `i := i` / Go 1.22+ 语义），见上文"经典坑"与"修复"两节。
