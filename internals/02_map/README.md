# 02 · Map 底层实现：tophash 预筛、溢出链与负载因子扩容

> map 是 Go 里"用起来最简单、内部最复杂"的容器，且不可 `unsafe` 直读。本篇用纯 Go 结构复刻经典 hmap/bmap 设计（Go 1.23 及更早），把哈希定位、冲突、扩容整条路径变成看得见的打印。

## Background

用 map 的人迟早会问三个问题：为什么遍历无序？什么时候扩容？哈希冲突怎么解决？这些行为的答案全在运行时的哈希表布局里，但 Go 不让你直接看。

早期探究这块的常见做法是用 `unsafe` 硬读运行时的 map 结构——本实验旧版代码就试过，结果读到的只是哈希种子的随机字节。

原因在于：map 的布局不是官方承诺的稳定结构（与 slice/string 不同），Go 1.24 起内部实现已改用 Swiss Table（一种用 1 字节控制位加分组扫描加速查找的哈希表设计），硬编码字段偏移注定随版本失效。

出路是不碰内存、改用纯 Go 结构复刻经典 hmap/bmap 设计：字段与行为对齐 Go 1.23 及更早的真实运行时，既能打印每一步，又不依赖脆弱的内部布局。

## What

**定义**：map 是一种哈希表容器——对 key 计算哈希，用哈希低位选定桶数组里的一个桶，桶内最多放 8 个键值对；桶满了挂溢出桶，密度超过阈值就整体扩容翻倍。

复刻用的两个核心结构：`hmap`（顶层表头，记录元素数与桶数组）和 `bmap`（桶，存 8 个槽位的键值对），代码见 How It Works。

**心智模型**：可以把一个桶想象成一排 8 格的储物格，每格门上贴一张 1 字节的摘要标签（tophash，即 key 哈希的高 8 位）——找东西先扫标签，标签对上才开格核对。但和储物格不同的是，桶满了不会换大柜，而是在尾部再挂一节新柜子（溢出桶），最坏时退化成一条长链。

## When to Use

什么时候值得按"桶 + tophash + 溢出链"来理解 map：

- 在写读多写少的共享缓存、判断要不要加锁或分片时——先要知道 map 扩容搬多少数据、并发写为什么直接崩溃
- 在排查"遍历顺序每次都不同"的问题时——运行时会随机化遍历起点，防止业务依赖顺序，这不是 bug
- 在做性能选型（键查找用 map 还是别的结构）时——了解冲突链与负载因子的代价，选型才有依据

什么时候不用：

- 键就是 0..n 的连续整数、数据量小时，直接用 slice 按下标存取，比哈希更快更省内存
- 只需判断"存在与否"且元素极少时，线性扫描一个 slice 往往足够

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| `map[K]V` | 均摊 O(1) 查找，自动扩容 | 键值语义、键稀疏 |
| slice + 线性扫描 | O(n) 但常数极小 | 元素只有几十个 |
| `sync.RWMutex` + map | 读写锁串行化访问 | 并发读写同一份 map |
| 分片 map（多个小 map 各配锁） | 写热点分散到多把锁 | 高并发写下争用明显 |

## How It Works

按查找路径展开：结构 → 定位 → 预筛 → 溢出链 → 扩容。

### 顶层 hmap 与桶 bmap

```go
type hmap struct {
    count   int      // 元素总数
    B       int      // 桶数 = 1 << B
    buckets []*bmap  // 桶数组
}
type bmap struct {
    tophash [8]uint8 // 每个 key 哈希的高 8 位，用于快速预筛
    keys    [8]string
    vals    [8]string
    used    int
    next    *bmap    // 溢出桶：桶满后挂到链表尾部
}
```

这段在做什么：用两个纯 Go 结构体复刻真实运行时的表头与桶。每桶最多 8 个键值对（与真实运行时一致），`len(m)` 读的就是 count。

### 哈希定位：低 B 位找桶、高 8 位做 tophash

```go
func (m *hmap) bucketIdx(h uint32) int { return int(h) & (len(m.buckets) - 1) }
func tophashOf(h uint32) uint8        { return uint8(h >> 24) } // 哈希高 8 位
```

这段在做什么：第一行用位与算桶下标——桶数恒为 2 的幂，`hash & (2^B - 1)` 等价于取模但更快；第二行取哈希高 8 位做预筛标签。演示用固定种子 0x9e3779b9 的 FNV-1a 哈希（一种简单的迭代异或哈希算法），每次运行结果一致、便于讲解。

你在输出里看到的 `"hello" hash=0x21793a17 tophash(高8位)=0x21 桶下标(低2位)=3`，就是这两个函数的结果。

### tophash 预筛

桶内查找逐槽比较 tophash：比较一个 uint8 远比比较字符串便宜，标签不等直接跳过该槽，相等才开格比对完整 key。全部不中就沿 `next` 走溢出桶。

### 冲突解决：溢出桶链

桶满后新建溢出桶挂到 `next` 链尾。m3 从 3000 个候选 key 挑出 12 个落在同一桶（B=4，16 桶，不会触发扩容）：前 8 个填满主桶，第 9 个触发输出里的"桶 4 已满"，剩下 4 个进溢出桶——一条最坏退化为链表的长链。

viz.py 画的实测分布印证两个 map 的差别：m2 扩容后 15 个 key 摊在 4 个桶（负载 3.75）；m3 的 12 个 key 全挤在桶 #4（含溢出链），其余 15 桶全空——冲突的影响一眼可见。

### 扩容：负载因子阈值 6.5

```go
if float64(m.count+1)/float64(m.bucketCount()) > 6.5 { m.grow() }
```

这段在做什么：负载因子（元素数除以桶数）超过 6.5 就 grow——桶数翻倍（B+1）并把旧元素全部重新哈希。m2 插到第 14 个触发扩容，重哈希 13 个元素到 4 个桶，对应输出里的"触发扩容"与"[状态] 插入 15 个 key"两行。

真实运行时为避免一次性停顿，采用渐进式搬迁（每次操作搬一小部分）；模拟版做全量重哈希，只为把过程看得完整。

### 字段速查

| 字段 | 含义 | 为什么重要 |
|---|---|---|
| `count` | 元素总数 | `len(m)` 的来源；负载因子的分子 |
| `B` | 桶数的对数 | 桶数恒为 2 的幂，下标用 `& (2^B-1)` 算 |
| `tophash[8]` | 每槽 key 哈希高 8 位 | 1 字节整型预筛，挡住绝大多数字符串比较 |
| `next *bmap` | 溢出桶指针 | 冲突的兜底手段，链越长查找越慢 |
| 负载因子 | count / 桶数 | 超过 6.5 触发扩容，平衡空间利用率与链长 |

## Pitfalls & Q&A

踩坑记录，每条 = 现象 + 原因 + 解法：

- **`unsafe` 硬读 map 得到随机字节**。现象：读出的字段值每次运行都变。原因：map 内部布局非稳定契约，读到的是随机哈希种子；Go 1.24 起 hmap/bmap 已不存在（换成 Swiss Table）。解法：用纯 Go 模拟或走官方 API，不要按偏移读内存。
- **桶下标每次运行全变，讲解无法复现**。原因：真实运行时哈希种子随机。解法：演示代码用固定种子（0x9e3779b9）的确定性哈希。
- **JSON 里 tophash 读不到数值**。现象：`-json` 输出的 tophash 是一串 base64。原因：JSON 序列化把 `[]uint8` 编码成 base64。解法：字段改用 `[]int` 输出。
- **模拟版全量重哈希被当成运行时行为**。原因：真实运行时扩容是渐进式搬迁，模拟版为观察做了全量重哈希。解法：讲清差异，别把模拟实现等同于运行时。

深入问答：

**Q：为什么桶数设计成 2 的幂？**
A：桶下标 = `hash & (2^B - 1)`，位与替代取模，扩容 B+1 即桶数翻倍，两件事都因 2 的幂而成立。

**Q：并发读写 map 会发生什么？为什么 runtime 宁可崩溃也不返回脏数据？**
A：hmap 里有 flags 位标记"有 goroutine 正在写"，并发读写会直接 `fatal error: concurrent map read and map write`（不可 recover）。

因为 map 无锁，并发写会破坏溢出链/计数，宁可崩溃也不返回脏数据；需要并发就用 `sync.RWMutex` 包一层或分片（见 patterns/10）。
