# 12 · sync.Once：done 原子位快路径 + Mutex 慢路径

> `sync.Once` 是标准库里最小的同步原语：一个 1 字节的 `atomic.Bool` 加一个 `Mutex`。本篇用 `unsafe` 读出 done 字段、用毫秒级延时对比，回答三个问题：并发 100 个调用为什么 f 只跑一次、抢不到锁的人为什么要等 f 跑完、`done.Store(true)` 为什么必须放在 f 返回之后。实测环境 go1.26.5。

## Background

"初始化一次"的代码到处都是：单例（全局唯一实例）、配置加载、连接建立。并发调用时，手写方案是双重检查锁（先无锁查一次标志，未命中再加锁、锁内再查一次）。

手写双重检查几乎必错，错的姿势还各不相同：有人忘掉锁内的二次检查，有人把 `Store` 放错位置，还有人用 CAS 写出只保证"执行一次"、不保证"别人等它执行完"的残缺版本。

`sync.Once` 用两个小字段把这件事彻底做对：done 原子位加 Mutex。理解它的结构，等于理解 Go 并发里最典型的两个手段——双重检查与 release 语义。

## What

`sync.Once` 是一个保证"恰好执行一次"的同步原语：内部一个 `done atomic.Bool`（1 字节的原子布尔标志）做快路径判据，一个 `Mutex` 做慢路径串行化，两者合起来保证所有 `Do(f)` 返回时 f 已经结束。

可以把 Once 想象成开业前的门店：第一个到的员工拿钥匙进门布置（执行 f），后来的人排在门外等；门一开（done=true），之后的人推门就进（快路径）。但和真实门店不同的是，"门开"标志的翻转被严格安排在布置完成之后——看到门开的人，保证能看到全部布置好的成果。

心智模型一句话：`Do` 每次都先做一次原子 `done.Load()`（快路径——无锁无等待直达返回）；只有读到 0 才进慢路径抢 mutex，抢到的人二次检查后执行 f，**f 返回之后**才 `done.Store(true)`——置位顺序就是语义本身。

## When to Use

**在初始化单例、加载配置、建立连接这类"恰好一次"的逻辑时**。多个 goroutine 同时触发初始化，Once 保证不重复也不读到半成品。

**在惰性初始化（第一次用到才初始化）时**。初始化昂贵且不一定被用到，快路径的 0 开销让"每次先 Do 一下"没有负担。

何时不用：

- 初始化便宜且程序必然用到时，直接用包级变量初始化，更简单直白。
- f 失败需要重试时——Once 的语义是"跑过就算"，失败也会被记住。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| `sync.Once` | 原子位 + Mutex，恰好一次且等待完成 | 并发下的惰性初始化 |
| 包级变量初始化 | 程序启动时执行，天然一次 | 初始化便宜且必然用到 |
| 手写双重检查 | 顺序自己守，容易错 | 需要定制语义（如失败重试） |

## How It Works

### 结构：done 刻意放在最前面

```go
type Once struct {
    _    noCopy      // 零宽占位，禁止拷贝
    done atomic.Bool // 首个有效字段，1 字节，热路径只读它
    m    Mutex       // 慢路径串行化
}
```

`done` 放最前是性能工程：快路径 `if !o.done.Load()` 会被内联到每个调用点，首字段意味着更紧凑的指令。实验里 `readDone` 直接把 `*Once` 按 `*atomic.Bool` 解读——正因为 done 位于偏移 0（noCopy 是零宽字段），且只读保持原子性。

### 并发首次调用的时间线

慢路径 `doSlow` 三步：`m.Lock()` → 再查一次 `done`（双重检查，锁外等锁的人可能已经有人跑完）→ `f()` 返回后才 `Store(true)`。

实测 f 睡 30ms 时，4 个慢路径调用者平均等 28.9 ms——等待的终点是"f 已结束"，而不是"done 已置位"，这两个时刻差一次 `Store`。

Quick Start 输出第 2 段就是这条时间线：0ms 处 f 开始且 done=false，31ms 处 f 结束、此刻才置位，之后快路径调用只花 0.00 ms。

### 内存屏障：看到 done=1 就看到 f 的全部副作用

`done.Store(true)` 是 release-store（发布式写入，保证它之前的所有写对后续读者可见）：f 里写的 `result=42` 对 acquire-load（获取式读取，保证其后的读不早于它）的读者全部可见。

exp3 实测：16 个 goroutine 在 Do 返回后读 result，16/16 看到 42，即输出第 3 段。反过来，f 内部读 done 必然是 false——置位还没发生，这正是"release 在 f 之后"的活证据。

### 关键字段与语句

| 字段/语句 | 含义 | 为什么重要 |
|---|---|---|
| `done atomic.Bool` | "f 已跑完"标志 | 快路径判据；1 字节就有屏障效果 |
| `m Mutex` | 慢路径互斥锁 | 保证"所有 Do 返回时 f 已结束" |
| `if !o.done.Load()` | 快路径 | 内联在每个调用点，零锁零等待 |
| `f(); o.done.Store(true)` | 顺序不可换 | 换了就丢失 release 语义 + 完成语义 |

## Pitfalls & Q&A

坑清单：

- **CAS 是错误实现**。现象：用 `if o.done.CompareAndSwap(false, true) { f() }` 后，第二个并发调用者在 f 没跑完时直接返回。原因：CAS 只保证"执行一次"，不保证别人等它执行完。解法：mutex 不可省，用标准库。
- **读 done 用了反射**。现象：读到过期值或引入额外开销。解法：直接 `(*atomic.Bool)(unsafe.Pointer(o)).Load()` 最贴近标准库且原子（依赖 done 在偏移 0，仅限学习用途）。
- **并发测量不看观测窗口**。现象：慢路径等待远低于预期的 ~29ms。原因：并发者抢在 f 前面到达，走的是另一条时间线。解法：实验用 `time.Sleep(2ms)` 先让 f 进临界区再测。
- **`Once` 被按值拷贝**。现象：`go vet` 报拷贝告警。原因：结构体含 `noCopy`（零宽的防拷贝标记）字段。解法：传参一律用 `*sync.Once`。

**Q：done.Store(true) 放在 f() 之前会怎样？**
A：两个层面都坏：语义上"Do 返回时 f 未结束"；内存模型上丢失 release——其他 goroutine 看到 done=1 时，f 写入的变量可能还没对它们可见（16/16 看到副作用的保证消失）。

**Q：双重检查（抢到锁后再查 done）可以省吗？**
A：不能。抢到锁之前可能有别的 goroutine 已经在锁内跑完 f 并置位；不二次检查会跑两次 f。
