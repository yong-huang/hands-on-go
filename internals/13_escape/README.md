# 13 · 逃逸分析：编译器到底把变量放栈还是放堆

> Go 变量放栈还是放堆，不由程序员声明决定，而由**逃逸分析**（编译器判断指针会不会"逃出"当前作用域的静态分析）判定：逃出则上堆，否则留在栈帧里、不给垃圾回收（GC）添负担。麻烦在于编译器提示与运行时实测有时"打架"。本实验用 8 个场景双管齐下：读完你将能用编译器开关与运行时计数互相印证，准确判断每个变量落在哪。

## Background

一个 Go 变量只有两种可能的归宿：栈（stack，函数调用时随栈帧自动分配、函数返回即整体回收的内存区）或堆（heap，由运行时统一管理、事后需要回收善后的内存区）。两者的成本天差地别。

栈分配几乎免费：栈帧（一次函数调用在栈上占据的连续内存块）可以复用，函数返回即回收。堆分配则要调用运行时的 `newobject`（按类型大小在堆上划出内存的内部函数），事后还得由 GC（垃圾回收）处理。

写热路径代码（程序中被高频执行的核心代码段）时，"这个变量上没上堆"直接决定性能上限——堆分配得越多，GC 的回收负担越重。

在没有便捷查证手段时，开发者靠背规则推断：返回局部指针就上堆、局部变量就留栈。痛点在于规则背了也不准——编译器会顺手做内联（inlining，把被调函数的代码直接展开进调用者）和栈上化（把本该上堆的对象改放到栈上）等优化，同一行代码在不同上下文里结论会变。

于是 Go 把这件事做成编译器内置的判定，并提供 `-gcflags=-m` 开关逐行查看结论，再用运行时计数器实测验证。

## What

逃逸分析（escape analysis）是一种编译期静态分析（不运行程序、直接检查代码得出结论的分析方法）：它判定变量的生命周期是否会超出当前栈帧——超出则分配到堆，否则留在栈上。

心智模型一句话：判据是"指针逃多远"。

- 上堆：返回局部指针、闭包（引用了外部函数局部变量的函数值）捕获变量、超过栈帧容量的超大对象、存进包级变量后全局可达、接口值装箱（把具体值连同类型信息打包成 interface）后转手逃出
- 留栈：值不出函数、只读传指针（编译器标注 `p does not escape`）、按值返回小对象

可以把栈想象成办公桌桌面——东西随手放、用完随手清，几乎零成本；把堆想象成仓库——放进去要登记，还得定期有人来清运。

但和真实仓库不同的是，Go 编译器会先替你判断"这件东西离开桌面后还有没有人用"，只在必要时才入仓；判断本身不会报错，放错方向的代价只体现在性能上。

## When to Use

逃逸分析在每次编译时自动运行，"用"它指的是主动查证与优化。三个典型场景：

- **压降 GC 开销**：性能画像显示堆分配频繁、GC 占比高时，逐个排查热路径上的分配点，把本可留栈的对象改造成值传递或复用
- **读懂指针语义的代价**：代码评审中看到函数返回 `*T`，判断这次返回是否真的引发堆分配，还是编译器已经把它按在栈上
- **验证优化是否生效**：把大对象拼接改成 `sync.Pool`（缓存临时对象供复用的并发池）或分片处理后，用运行时计数确认分配确实归零

何时不用：一次性脚本、只在启动时跑一遍的初始化逻辑，上堆成本可以忽略，不值得花时间优化；逃逸上堆也不是错误，而是"省心换性能"的正常权衡。

同类查证手段对比：

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| `go build -gcflags=-m` | 编译期静态判定，逐行提示 | 快速定位"哪一行"可能上堆 |
| `MemStats.TotalAlloc` 增量 | 运行时实测分配字节 | 与编译器提示"打架"时，以它为准 |
| pprof heap profile（标准库自带的堆分配采样剖析） | 带调用栈的采样视图 | 宏观找出分配热点函数 |
| 基准测试的 allocs/op | 每次操作的分配次数统计 | 量化优化前后的对比 |

## Quick Start

前置条件：安装 Go（本实验在 Go 1.26.5 下实测）；如需重画数据图另需 Python 3 与 matplotlib（pip install matplotlib）。

```bash
cd internals/13_escape
go run main.go                      # 文本演示：8 场景 × 20 万次调用的 TotalAlloc 增量
go run main.go -json                # 输出 JSON 快照
go build -gcflags=-m main.go        # 编译器逐行的分配决策（与实测对照）
python3 viz.py                      # 重新生成实测数据图
```

两个要点帮你校准预期：

- 8 个场景分成泾渭分明的两组——4 个逃逸场景的增量线性上涨，4 个栈上场景稳定为 `+0 B`
- `TotalAlloc`（`runtime.MemStats` 里"程序启动以来累计堆分配字节"的计数器，只增不减的毛账）在这里量的是分配频率，不是当前占用

第三条命令是编译器视角：`-gcflags=-m` 逐行打印每个变量的分配决策，例如 `moved to heap: x`、`escapes to heap`。拿它与上面的实测对照，会发现一处著名的"打架"——下一节解释原因。

## How It Works

按"先看逃逸组、再看栈上组、最后解释反直觉"的顺序拆解 8 个场景，每一步都与 Quick Start 的输出对上号。

### 逃逸组：每次调用都是一次堆分配

4 个场景实测线性上涨：返回局部变量指针每次 8 B（×20 万 = 1.6 MB）、闭包捕获每次 16 B（+3.2 MB）、64KB 大对象每次 65536 B（累计约 **13.1 GB**）、包级变量可达 +1.6 MB。

你在输出里看到的 `+1600000 B`，就来自"每次 8 B × 20 万次"这条账。

### 栈上组：零分配

纯局部使用、只读指针调用（编译器标注 `p does not escape`）、按值返回小对象，20 万次调用 `TotalAlloc` 全部 +0 B。这是"栈上才是零成本"的实证：不产生任何垃圾，不给 GC 添任何工作。对应输出里稳定不变的四个 `+0 B`。

### 反直觉：interface 装箱 ≠ 堆分配

编译器对 `makeIface` 明确打了 `[16]int{...} escapes to heap`，但运行时 +0 B——这就是输出表的第 5 行。

原因：接口值是"类型指针 + 数据"两个字段，当装箱对象**没逃出调用者栈帧**（本实验里立即被类型断言消费）时，编译器把装箱数据放在调用者帧上——根本没有 newobject。

所以 `-m` 说的是"这个值需要存储介质"，栈还是堆的**最终分派**由它逃多远决定。只有接口值被存出去/传出去（动态派生逃逸），才真上堆。编译器提示是线索，不是判决书。

### 内联会收窄逃逸面

所有场景函数都标了 `//go:noinline`（指示编译器禁止内联该函数的指令）。初版没标时，返回局部指针的场景被内联（inlining，把被调函数的代码直接展开进调用者）进测量函数，指针只在调用者帧内存活，硬生生变回栈上——5 个"逃逸"几乎全是 0。

这不是 bug，是编译器在帮你省内存；但要测"场景本身"就得先禁内联。反过来看，内联本身就是一种逃逸优化。

### 判定对照表

下表是 8 个场景"编译器说"与"运行时做"的全量对照：

| 场景 | 编译器判定（-m） | 运行时（20 万次） |
|:---|:---|:---|
| 返回局部变量指针 | `moved to heap: x` | +1.6 MB |
| 闭包捕获 | `func literal escapes to heap` | +3.2 MB |
| 大对象 (64KB) | `&[8192]int64{} escapes to heap` | +13.1 GB |
| 包级变量可达 | `moved to heap: x` | +1.6 MB |
| interface 装箱（直接消费） | `[16]int{...} escapes to heap` | **+0 B**（装箱留在调用者帧） |
| 纯局部使用 / 只读指针 / 按值小对象 | 无提示 / `p does not escape` | +0 B |

## Pitfalls & Q&A

踩坑清单，每条按"现象 → 原因 → 解法"展开：

- **`-m` 与运行时"打架"**：现象是编译器说 `escapes to heap`、实测却是 0；原因是接口装箱数据没逃出调用者帧、被栈上化了；解法是先查接口数据是否真逃出调用者帧，最终以 `TotalAlloc` 实测为准
- **内联毁掉测量**：现象是"明明返回指针却 0 分配"；原因是场景函数被内联进调用者，逃逸面全变；解法是给场景函数加 `//go:noinline` 再测
- **把 `TotalAlloc` 当占用看**：现象是数值大到离谱（如 13.1 GB）；原因是它是只增不减的累计毛账；解法是用"涨不涨"判断分配频率，看当前占用改用 `HeapAlloc`
- **闭包捕获误判**：现象是以为闭包捕获必上堆；原因是闭包本身不逃逸时，被捕获变量可以留栈（配合内联常常成立）；解法是按"逃逸链"整体看，而非单点判断
- **超大临时数组拖垮热路径**：现象是 64KB 数组每次调用一次堆分配、累计 13.1 GB；原因是超过栈帧容量的对象强制上堆；解法是改 `sync.Pool` 复用，或按值小片处理

深入问答：

**Q：逃逸上堆对性能到底意味着什么？**
A：栈分配≈零成本（复用栈帧、无 GC 负担）；堆分配每次 newobject 且给 GC 添活。热路径上消灭逃逸的常见手段是值传递、预分配容量和 `sync.Pool` 复用。

**Q：`TotalAlloc` 和 `HeapAlloc` 有什么区别？**
A：`TotalAlloc` 累计历史堆分配字节，只增不减，适合看分配频率；`HeapAlloc` 是当前堆上活对象的字节，看占用。测"逃逸了没有"用前者。

**Q：编译器提示与实测冲突时信谁？**
A：信实测。`-m` 的输出是"需要存储介质"的线索，最终分配位置由逃逸距离决定——机制见 How It Works 的"interface 装箱"一节。
