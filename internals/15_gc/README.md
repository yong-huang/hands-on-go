# 15 · GC 三色标记与写屏障：并发变异为什么不能裸奔

> Go 的 GC（垃圾回收）大部分标记工作与业务代码并行跑，而标记进行中指针还在被修改——怎么保证活对象不被误收？答案是三色抽象与写屏障。本实验用最简标记-清扫仿真复现"无写屏障丢对象"的事故，再在 200 万节点图上量出真实停顿与回收量。读完你将能说清停顿发生在哪里、为什么与堆大小基本无关。

## Background

GC（garbage collection，垃圾回收——运行时自动找出并回收不再使用的堆对象的机制）的第一步是找出"哪些对象还活着"。做法叫标记：从根对象（栈上局部变量与包级全局变量里的现存引用）出发，顺着引用把能到达的对象都登记为存活。

早期 GC 的做法是暂停一切再标记：所有业务代码停住，回收器独占运行。痛点有二——业务被硬生生打断；堆越大要登记的对象越多，停顿随之变长。对延迟敏感的服务，这是硬伤。

Go 的解法是让标记与业务并发跑：goroutine（Go 的轻量执行单元）照常执行。危险随之而来——扫描进行中代码还在改指针，刚登记完的对象可能又指到没登记的对象上，处理不当会把活对象误判为垃圾，留下悬垂引用（指向已回收内存、访问即出错的指针）。三色抽象与写屏障就是为堵住这个漏洞而生的。

## What

Go 的 GC 采用并发标记-清扫（并发地"标记"出活对象，再"清扫"回收死对象）。三色抽象把标记进度编码进对象的三种颜色状态；写屏障（编译器插在每次堆指针写入处的一小段代码）负责并发期的安全。

三种颜色是标记的最小完备描述：

| 颜色 | 含义 | 结局 |
|:---|:---|:---|
| 白 | 还没确认可达 | 清扫阶段被回收（即"垃圾"） |
| 灰 | 已知可达，子指针还没扫完 | 排在灰色工作队列里等扫描 |
| 黑 | 扫描完成，确认存活 | 绝对不回收 |

灰色工作队列（待扫描对象的待办列表）驱动整个过程。

心智模型一句话：标记就是"灰→黑"的推进——从灰色队列取出对象变黑、把它的白色子对象染灰；全程靠写屏障堵住唯一漏洞"黑→白"，标记结束仍白的对象交给清扫回收。

可以把标记想象成流调（追踪感染者的接触链排查）：已问完话的贴黑标、排上待问名单的贴灰标、还没查到的暂按白标处理；每问完一个人，就把他新供出的接触者拉进名单。

但和流调不同的是，这里的人随时会在"问完之后"又结交新朋友——黑指向白正是唯一的漏查通道；写屏障强制"每次结交当场登记"，才守住不漏。

## When to Use

这套机制知识在"服务出现可疑停顿或内存异常"的时候派上用场。三个典型场景：

- **排查周期性毫秒级停顿**：服务监控出现规律性毛刺时，先确认是不是 GC 停顿，再谈优化
- **排查内存泄漏**：堆对象只涨不降时，观察清扫回收量是否失效、是谁一直被标记为存活
- **调 GC 参数之前**：改 `GOGC`（控制 GC 触发时机的环境变量，默认 100 表示堆增长到上轮存活数据的 2 倍才触发）或压缩分配频率前，先建立"看见每轮 GC"的观测手段，避免盲调

何时不用：一次性脚本、分配量本来就小的工具程序，GC 不是瓶颈时调优收益趋零；先观测证明 GC 有问题，再动手。

观察 GC 的几种手段对比：

| 手段 | 差异 | 什么时候选它 |
|:---|:---|:---|
| `runtime.GC()` + `MemStats` 前后差值 | 主动触发、受控对比 | 实验里精确量化回收量 |
| `GODEBUG=gctrace=1` | 运行时逐轮打印轨迹 | 长跑进程看逐轮行为 |
| pprof heap profile | 采样活对象的引用来源 | 找"谁在持有内存" |
| execution tracer | 时间线视图 | 分析停顿与并发的时序关系 |

```text
========== 1. 三色标记：写屏障的救场 ==========
   对象：root→A→B，标记进行中 B 新增指向 C 的引用
   有写屏障 : 幸存 = [root A B C]（C 被染灰救下），标记步数=4
   无写屏障 : 幸存 = [A B root]（C 丢失被误回收！），标记步数=3

```

两个要点帮你校准预期：

- 第 1 段是自研三色仿真的逐帧对照：同一场景，有无写屏障的幸存集合差一个 C

注意第 1 段里"无写屏障"一行的步数是 3、幸存少一个——C 就是那个被误收的对象。下一节逐帧解释这个事故怎么发生、怎么被救。

## How It Works

按"状态机怎么转 → 漏洞在哪 → 真实运行时怎么量"的顺序展开。

### 三色不变式：多标浪费，少标就崩

标记就是"灰→黑"的推进：灰色队列耗尽、无白可染时标记结束；随后把所有仍白的对象清扫掉。多标一点只是浪费，少标一点就崩——**三色不变式**（不允许黑→白的边存在）是底线。

### 并发变异的危险与写屏障

仿真把事故逐帧跑了一遍：对象图 root→A→B，标记进行中 B（已黑）新增指向 C（仍白）的引用——

- **无写屏障**：标记结束 C 还是白的 → 被清扫回收，但 B 还指着它 → 悬垂引用，业务访问直接崩溃。实测幸存 `[A B root]`，标记步数 3——就是你在输出里看到的"丢失"一行
- **有写屏障**：堆写入的瞬间把新指向的白对象染灰 → 进灰色队列 → 扫成黑。实测幸存 `[root A B C]`，标记步数 4

一个仿真细节：变异必须发生在 B **扫描完之后**（其 refs 不会再被扫），否则无屏障时 C 也会在扫 B 时被顺手染灰，复现不出事故。真实并发场景里变异随时发生，无从保证"扫描前"，所以屏障不可省。

### 真实 GC：停顿两段与清扫回收

200 万节点的指针图上连跑 6 轮 `runtime.GC()`，每两轮把图减半：停顿 0.10~0.45 ms（STW 时间，数值随机器漂移），`HeapObjects` 从 2000231 回落到 230。

停顿为什么这么短？STW（stop-the-world，暂停所有业务代码的同步点）只出现在标记开始（开启写屏障、扫描根对象）和标记终止（重扫、关屏障）两个小段，标记主体与清扫都与业务并发。回收量是清扫的战果（并发进行，不进停顿）——"回收了多少"和"停了多久"是两个独立指标，垃圾多才贵。

### 关键概念速查表

| 概念 | 含义 | 为什么重要 |
|:---|:---|:---|
| 白/灰/黑 | 待定 / 待扫 / 确认存活 | 标记进度的最小完备描述 |
| 灰色工作队列 | 待扫描对象列表 | 队列空 = 标记结束 |
| 写屏障（WB） | 堆写入时把新指向的白对象染灰 | 堵住"黑→白"，并发标记的地基 |
| STW | 标记起止两段短暂暂停 | 停顿毫秒级且与堆大小基本无关 |
| `MemStats.HeapObjects` | 堆活对象计数 | 量化清扫回收效果 |

## Pitfalls & Q&A

踩坑清单，每条按"现象 → 原因 → 解法"展开：

- **仿真复现不出事故**：现象是无屏障分支对象也幸存；原因是变异放在了对象扫描之前，C 被顺手染灰；解法是让变异发生在对象扫描完之后
- **把 `GCStats.Pause` 当"标记耗时"**：现象是标签夸大了停顿含义；原因是 `Pause` 只覆盖 STW 段；解法是标签诚实写"停顿"，别写"标记耗时"
- **看不见垃圾量**：现象是不知道一轮 GC 到底收了多少；原因是缺前后对照；解法是 `runtime.GC()` 手动拉一轮，配合 `MemStats.HeapObjects` 前后差值
- **图被提前回收、量出空壳**：现象是 200 万节点图没产生工作量；原因是根里没有引用，图整体成了垃圾；解法是把图挂进 `[]*obj` 保活
- **停顿序列没有对比度**：现象是 6 轮数值平铺无规律；原因是堆规模不变；解法是每两轮把图减半，制造"大→小→大"的压力变化

深入问答：

**Q：怎么在代码里观察 GC 行为？**
A：`runtime.GC()` 手动触发一轮；`runtime.ReadMemStats` 前后取 `HeapObjects`/`NumGC`/`PauseTotalNs` 差值；`GODEBUG=gctrace=1` 看逐轮轨迹。先能"看见"，再谈调优。
