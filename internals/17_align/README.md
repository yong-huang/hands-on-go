# 17 · 内存对齐与 struct 优化：只改声明顺序，省下 1/3 内存

> 同一组字段，`{int8, int64, int8}` 顺序排出来 24 字节，换成 `{int64, int8, int8}` 只要 16 字节——逻辑一字未改，只动了**声明顺序**。本实验用 `unsafe.Sizeof / Alignof / Offsetof` 把三个结构体的逐字段偏移与填充（padding）打印出来，看清对齐规则落在内存里的真实位置，并给出能直接落地的字段排序口诀。

## Background

CPU 按字长（一次内存访问读取的固定宽度，64 位平台通常 8 字节）对齐地访问内存最快，不少架构上不对齐的访问会变慢甚至出错，所以 Go 编译器会在字段之间和结构体尾部**悄悄插入填充字节**。

填充不可见、不报错，唯一的痕迹是 `unsafe.Sizeof` 大于字段字节和：badOrder 三个字段 1+8+1=10 字节，`Sizeof` 却是 24。只看代码完全发现不了这 14 字节去了哪。

填充还会随对象数量放大：100 万元素的 `[]badOrder` 比 `[]goodOrder` 多吃约 8 MB 内存，每个缓存行（CPU 缓存与内存之间一次搬运的数据块，通常 64B）装的对象也更少。

这种浪费完全由声明顺序决定，code review 时肉眼很难看出来，值得用一次实验把规则看穿。

## What

内存对齐是一种数据布局约束：编译器把每个字段的偏移（字段起始地址相对结构体首地址的距离）安排在其对齐值的倍数上，安排不下就用填充字节占位。

心智模型一句话：每个字段的偏移必须是它自身对齐值的倍数，放不下就垫填充——`int8` 插在 `int64` 前面会把 8 对齐位顶走 7 字节；把 8B 大字段放最前、小字段收尾，填充就只剩尾部补齐。同一组字段（内容同为 10B）的两种排法，结果就是 24B vs 16B。

可以把内存想象成一排连续编号的储物柜，`int64` 这类 8B 大件只肯放进 8 的倍数号柜，放不进去就宁可空着几个柜位。

但和储物柜不同的是：这里"放不下"不会失败，而是默默垫空位再继续，成本不报错、只在总量里体现；且柜位宽度由字段类型决定，跟声明者写什么顺序无关。

## When to Use

对齐意识在"定义会被批量存放的结构体"时最有价值。三个典型场景：

- **定义缓存或大切片的元素类型**：`[]T` 里每个元素都复制一遍填充，百万级元素下 8B 的差距就是 8 MB
- **内存占用超标需要瘦身**：堆内存剖析显示偏高时，检查高频 struct 是否在交"顺序税"
- **写新 struct 时顺手做对**：按"大字段在前、小字段收尾"声明，零成本避免返工

何时不用：单个、少量、一次性的对象差 8B 无关痛痒；结构体的字节布局被外部依赖（二进制协议、与 C 交互的共享内存）时不能随意重排，先确认兼容性。

三种排查手段对比：

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 按"大前小后"口诀手动重排 | 零依赖，写时就做对 | 新增 struct 的预防 |
| `go vet` 的 fieldalignment | 自动报出可优化顺序 | 存量代码批量排查 |
| `unsafe` 三件套逐字段核对 | 精确到每个偏移的填充 | 定位"填充到底垫在哪" |

## Quick Start

前置条件：安装 Go（实测于 go1.26.5），进入实验目录即可运行，无第三方依赖。

```bash
cd internals/17_align
go run main.go          # 文本演示：三个结构体的偏移与 pad
go run main.go -json    # 输出 JSON 快照，供 viz.py 画数据图
```

预期输出（节选；偏移与大小由编译器和平台 ABI（应用二进制接口，约定二进制层面布局的规范，下文详述）决定，64 位平台结果一致，实测于 go1.26.5）：

```text
== badOrder(a int8, b int64, c int8) : 大小=24 对齐=8
     a  int8      偏移=0  (pad=0)
     b  int64     偏移=8  (pad=7)
     c  int8      偏移=16 (pad=0)

== goodOrder(b int64, a int8, c int8) : 大小=16 对齐=8
     b  int64     偏移=0  (pad=0)
     a  int8      偏移=8  (pad=0)
     c  int8      偏移=9  (pad=0)

== mixed(p *int, f float64, b bool, s string) : 大小=40 对齐=8
     p  *int      偏移=0  (pad=0)
     f  float64   偏移=8  (pad=0)
     b  bool      偏移=16 (pad=0)
     s  string    偏移=24 (pad=7)
```

两个要点帮你校准预期：

- badOrder 与 goodOrder 字段内容完全相同（10B），差的 8B 全部是填充——对比两段的 `pad` 列即可看出填充垫在哪
- mixed 里 `s string` 前面的 `pad=7` 是下一个重点：16B 的 string 为什么不等在偏移 17

ABI（应用二进制接口，编译器约定的二进制层面布局与调用规范）在所有 64 位平台上都要求 8 字节对齐，所以这些数字可以直接当布局图读。下一节逐字段拆解。

## How It Works

先立规则，再按 badOrder → goodOrder → mixed 的顺序逐个对账。

### 两条对齐规则

- **字段规则**：每个字段的偏移必须是它自身对齐值的倍数（`int64`→8 的倍数，`int8`→任意位置）
- **整体规则**：结构体总大小是最大成员对齐值的倍数——这是为了保证 `[]T` 数组里每个元素的首地址都对齐

### badOrder：int8 插队的代价

`a int8` 占了偏移 0，`b int64` 要求 8 的倍数，只能从偏移 8 开始——中间硬塞 7 字节填充（输出里的 `pad=7` 就是它）；`c` 结束于 17，尾部再补 7 字节凑到 8 的倍数。10B 的内容膨胀成 24B。

### goodOrder：填充挤到尾部

`b int64` 先占 0~8，两个 `int8` 自然贴在 @8、@9，字段到 10 就结束了；尾部补 6 字节凑成 16。**同样的字段，顺序对了填充只剩尾部一处**。

### mixed：大小与对齐是两回事

`string` 的 `Sizeof` 是 16（指针+长度），但 `Alignof` 只有 8——大小和对齐是两个维度。`b bool` 结束于 17，16B 的 `s` 仍要等 8 的倍数，于是前面垫 7B、尾部刚好齐平。

指针/`string`/`slice`/map 在 64 位平台都是 8 对齐。

### 三结构体对账表

| 结构体 | 字段顺序 | 字段内容 | 间填充 | 尾填充 | 总大小 |
|:---|:---|:---:|:---:|:---:|:---:|
| badOrder | a int8 → b int64 → c int8 | 10B | 7B（a、b 之间） | 7B | **24B** |
| goodOrder | b int64 → a int8 → c int8 | 10B | 0 | 6B | **16B** |
| mixed | p *int → f float64 → b bool → s string | 33B | 7B（b、s 之间） | 0 | **40B** |

### 工具箱与优化口诀

| 工具 | 含义 | 用法 |
|:---|:---|:---|
| `unsafe.Sizeof(x)` | 变量总字节数（含填充） | 传**值**或解引用，别传指针变量 |
| `unsafe.Alignof(x)` | 对齐值 | 决定字段能落在哪些偏移上 |
| `unsafe.Offsetof(s.f)` | 字段偏移 | 与"上一字段偏移+大小"的差就是填充 |

口诀四条（批量场景才值得折腾，单对象 8B 无关痛痒）：

1. **大字段放前，小字段收尾**：8B 字段先占对齐位，小字段自然贴上去
2. **别让小字段插队**：`int8` 垫在 `int64` 前 = 白送 7B 间填充；插队排布是 24B，大字段在前是 16B
3. **批量才显著**：100 万个元素差 8 MB；slice-of-struct（元素为结构体的切片）的紧凑度直接影响缓存命中
4. **工具兜底**：`go vet` 的 `fieldalignment`（`golang.org/x/tools/go/analysis/passes/fieldalignment`）能自动报出可优化的顺序

## Pitfalls & Q&A

踩坑清单，每条按"现象 → 原因 → 解法"展开：

- **`unsafe.Sizeof(ptr)` 永远是 8**：现象是想量结构体大小却得到 8；原因是传入的是指针变量，量的是指针本身；解法是传值或用 `unsafe.Sizeof(*ptr)` 解引用
- **大小算成 10**：现象是字段字节和与 `Sizeof` 对不上；原因是漏了填充；解法是按"偏移+大小"逐字段推算——badOrder 的 24 = 10B 内容 + 中间 7B + 尾部 7B
- **预测字段位置失灵**：现象是以为 `string`（16B）会占更多对齐位；原因是把大小和对齐混为一谈，`string` 的 Alignof 是 8；解法是对齐值只看成员类型，不看你写的顺序
- **画逐字节栅格图溢出**：现象是 matplotlib 导出成超大图；原因是 x 用"数据单位"后范围未固定；解法是手动 `set_xlim/set_ylim` 固定范围，避免 `bbox_inches='tight'` 拉爆

深入问答：对齐是什么、为什么换序省 8B、总大小为何取最大对齐值的倍数、string 的对齐值、如何发现浪费——这些常见疑问已分别在 How It Works 的两条规则、三个结构体拆解与工具箱中展开，不再重复。
