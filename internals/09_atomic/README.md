# 09 · Atomic 原子操作：CAS 重试循环与 release/acquire 内存屏障

> 用三组可复现的数据讲清原子操作：非原子 `c++` 丢失约 90% 的更新、CAS 靠重试做到 160 万次精确无一丢失、release/acquire 握手 20000 轮脏读 0 次。原子操作不是"加了锁的变量"，而是硬件直接支持的不可分割指令。读完你将掌握无锁计数、CAS 重试与跨 goroutine 可见性顺序的正确写法。

## Background

多个 goroutine 共享一个计数器时，常规解法是用互斥锁把"读-改-写"包成临界区。这能保证正确，但每次操作都要走加锁/解锁路径，竞争者互相阻塞。

更隐蔽的问题是 `c++` 本身：它看着是一行代码，实际是"读-改-写"三步。多个 goroutine 读到同一个旧值后各自 +1，只有最后一次写回生效——不加任何同步时更新会大量丢失，而这是 `-race` 可检测的数据竞争（多个 goroutine 并发读写同一内存且无同步）。

第三个痛点是顺序：跨 goroutine 的普通读写会被编译器/CPU 重排，"先写数据、再置就绪标志"的意图可能失效，读者看到标志却读到旧数据。CPU 的回应是直接提供不可分割指令与屏障语义，Go 的 `sync/atomic` 包把它们封装成了标准 API。

## What

原子操作是硬件直接支持的不可分割内存读写指令：要么整体发生、要么没发生，中间状态对外不可见。它不是"加了锁的变量"——没有加锁路径、没有等待队列，提供的是单个机器字的不可分割性加内存屏障。

可以把 CAS（compare-and-swap，比较旧值符合预期才写入新值的原子指令）想象成 git 提交前"先 pull 再 push"：基于旧值算好新值，提交时发现已被别人更新就失败，重读再来一轮；但和 git 不同的是，"比较与写入"由同一条 CPU 指令完成，中间不可能被插入。

心智模型一句话：CAS 把"读-改-写"压缩成一条不可分割的 CPU 指令——比较旧值，一致才写入；不一致说明被人抢先，重读新值再来一轮。不加锁、不阻塞，用重试换正确。

## When to Use

**在写并发计数器或统计指标时**。`atomic.AddInt64` 一行完成精确累加，是计数器的标准姿势。

**在实现无锁结构、自旋锁、双检单例时**。CAS 失败重试是这些结构的通用骨架，正确性可以自己推导。

**在跨 goroutine 传递"就绪"标志时**。`Store`/`Load` 自带的屏障保证标志背后关联的数据先于标志可见。

何时不用：

- 竞争极高且临界区不短时，CAS 重试会空转烧 CPU（本实验 160 万次递增伴随约 300 万次失败），不如让等待者休眠的锁。
- 要保证多个变量的一致性时，单个原子操作管不了，需要锁或更大的临界区。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| `atomic.Add/Load/Store` | 一条指令，无阻塞 | 单个机器字的计数、标志位 |
| `atomic.CAS` 循环 | 失败重试，乐观并发 | 无锁数据结构、自旋锁 |
| `sync.Mutex` | 竞争高时等待者休眠 | 临界区较长、多变量一致性 |
| channel | 传递数据所有权 | 生产者-消费者、需要关闭/超时语义 |

## Quick Start

前置条件：已安装 Go；`python3 viz.py` 需 Python 3 与 matplotlib（可选，仅影响画图）。`go run -race` 会运行内置的数据竞争检测器，是检验本实验的统一工具。

```bash
cd internals/09_atomic
go run main.go          # 文本演示：丢更新对比 → CAS 循环 → 屏障握手
go run main.go -json    # 输出 JSON 数据（exp1/exp2/exp3）
go run -race main.go    # 在非原子版本报告数据竞争（原子版无告警）
python3 viz.py          # 绘制期望/非原子/原子计数对比数据图
```

预期输出（节选，非原子结果与重试次数每次运行不同）：

```text
期望值              : 1600000
非原子  c++         : 180391    （丢了 1419609）
原子    AddInt64    : 1600000    （精确）
CAS 无锁计数: 1600000（精确）  CAS 失败重试 3075779 次
自旋锁保护计数: 1600000（精确，临界区不长，自旋比休眠划算）
release/acquire 握手 20000 轮，消费者读到脏数据 0 次
```

每一步"在看什么"都写在 `main.go` 的注释里；`-json` 快照给出与文本演示一致的机器可读数值。

核心的 CAS 重试循环（这段在做什么：`Load` 旧值，`CompareAndSwap` 成功即完成一次递增，失败说明别人抢先改了旧值，记一次重试、重读再来）：

```go
for {
    old := atomic.LoadInt64(&v)
    if atomic.CompareAndSwapInt64(&v, old, old+1) {
        break
    }
    atomic.AddInt64(&retries, 1) // 失败：别人抢先改了 old
}
```

## How It Works

### 丢更新的根因：非原子读-改-写

16 个 goroutine 各自 `++` 十万次，期望 1600000，实测非原子版只落地十几万（丢失约 90%）。用 `go run -race` 运行会在 `c++` 处报告数据竞争——丢更新不是玄学，是可检测的竞争。

Quick Start 输出的前三行就是这组对比：期望 1600000、非原子 180391（丢 1419609）、`AddInt64` 精确命中。注意非原子结果每次运行都不同——唯一稳定的是"必然丢失"。

### CAS 重试循环：乐观并发

实测 160 万次递增背后是约 300 万次 CAS 失败重试（每次运行不同）。高竞争下重试代价可见，但全程无阻塞。输出里"CAS 失败重试 3075779 次"这一行，就是 Quick Start 那段循环里 `retries` 的最终读数。

同一套路还能拼出自旋锁（用忙等抢锁的锁实现）：拿锁 = `CAS(0→1)` 成功，放锁 = `Store(0)`，失败路径加 `runtime.Gosched()`（让出一次调度，避免饿死其他 goroutine）。输出里"自旋锁保护计数: 1600000"说明这条路同样精确。

### release/acquire 内存屏障

生产者先写 `data = 42` 再 `Store ready=1`：`Store` 是 release 屏障——之前的写入必须先对外可见。消费者轮询 `Load ready==1` 再读 data：`Load` 是 acquire 屏障——之后的读取不得提前。

一送一收，"写 data happens-before（先行发生，效果保证对另一个操作可见）读 data"。实测 20000 轮握手脏读 0 次，即输出最后一行。若 `ready` 换成普通变量，编译器/CPU 有权重排，消费者可能读到 0。

### arm64 上的真实指令

原子操作在 arm64 编译为带屏障语义的单条指令：`AddInt64 → LDADDAL`（自带 acquire+release）、`CAS → LDAXR + STLXR` 独占对、`Load → LDAR`、`Store → STLR`。所以 Go 的原子操作无需手写栅栏指令。

### 关键 API 与指令

| API / 指令 | 含义 | 为什么重要 |
|---|---|---|
| `atomic.AddInt64` | 原子读-改-写 | 硬件保证不可分割，计数器正确姿势 |
| `atomic.CompareAndSwapInt64` | 比较并交换（一条指令） | 全部无锁结构的基石 |
| `atomic.StoreInt32` / `LoadInt32` | release / acquire 屏障 | 建立跨 goroutine 的 happens-before |
| `retries` 计数 | CAS 失败次数（实测 ~300 万） | 乐观并发的代价标尺 |
| `LDAXR + STLXR` | arm64 独占加载/存储对 | CAS 的真实硬件形态 |

## Pitfalls & Q&A

坑清单：

- **非原子丢更新不可复现**。现象：每次跑丢的数都不同。原因：竞争 interleaving（交错执行顺序）随机。解法：显式打印"期望值"对比，否则容易误判"差不多对了"。
- **CAS 重试在高竞争下空转烧 CPU**。现象：结果精确但 CPU 占用高。原因：失败者立刻重试，互相踩踏。解法：掂量临界区长度；自旋锁失败路径务必 `runtime.Gosched()`，避免饿死其他 goroutine。
- **屏障实验的 `data` 是普通变量**。现象：把 `ready` 也改成普通读写后，消费者可能读到 0 且 `-race` 报竞争。原因：顺序全靠原子 `ready` 提供，普通读写可被重排。解法：保持标志位用原子 `Store`/`Load`。
- **重试次数每次运行不同**。原因：竞争强度随调度抖动。解法：稳定的是"精确结果 + 重试机制"，不是具体数字。

**Q：CAS 能实现锁吗？什么时候比 Mutex 划算？**
A：能。拿锁 = `CAS(0→1)`，放锁 = `Store(0)`，失败自旋重试，失败路径加 `Gosched()` 防饿死。临界区极短时自旋比休眠切换划算——本实验自旋锁版本同样精确计数 1600000。

**Q：为什么说原子操作不是"加了锁的变量"？**
A：它是硬件直接支持的不可分割指令（arm64 上映射为 `LDADDAL` 等单条指令），没有加锁/解锁路径，也没有等待队列。它提供单字不可分割性与 release/acquire 屏障；多个变量之间的一致性仍然要靠锁或更大的临界区。
