# 03 · Channel 底层实现：带锁环形队列 hchan

> channel 是 Go 协程通信的核心原语，底层 hchan 不在公开 API 里且字段随版本漂移，但核心设计十几年没变：一个带锁的环形队列。本篇用纯 Go 结构复刻它，把 sendx/recvx 两个游标的推进、阻塞与回绕逐步打印，最后用真实 channel 对照验证。

## Background

用 channel 的人迟早会撞上这些问题：向已关闭的 channel 发送会怎样？无缓冲和带缓冲差在哪？发送方什么时候卡住？这些行为的答案都能从"环形队列 + 两个游标"推出来，但 Go 不让你直接看内部。

外部观察 channel 的官方入口只有 `len()` 和 `cap()`，分别对应 hchan 的 `qcount` / `dataqsiz`；更深的内部状态读不到。

hchan（channel 的运行时结构体）不在公开 API 里，字段布局随版本演进（Go 1.24 起运行时大规模重构），`unsafe` 硬读极易读到垃圾字段。

好在 hchan 的核心设计十几年没变过。本实验按简化后的结构用纯 Go 模拟，把每一步游标推进打印出来，再用真实 channel 交叉验证行为一致。

## What

**定义**：channel 是由带锁环形队列实现的消息通道——一个固定容量的环形数组做缓冲，配两个只增不回绕的游标（sendx 指向下一个写入位置、recvx 指向下一个读取位置），加收发两个等待队列和一把互斥锁。

**心智模型**：可以把带缓冲 channel 想象成一条环形传送带：sendx 是投放口、recvx 是取货口，两个口都只往前走，走到头由掩码计算绕回开头。但和普通环形缓冲区不同的是，满了不报错而是发送方阻塞、空了是接收方阻塞；cap=0 时干脆没有传送带，收发双方直接交接（rendezvous，会合式同步）。

## When to Use

什么时候值得按"环 + 游标 + 等待队列"来理解 channel：

- 在写生产者-消费者管道、worker pool 任务分发时——判断缓冲开多大、阻塞点落在谁身上
- 在设计"传数据还是传同步信号"时——选无缓冲（发送即完成交接）还是带缓冲（发送只保证入队）
- 在排查 goroutine 卡在收发的问题时——按环满、环空、nil channel 三种阻塞情形逐一排除

什么时候不用：

- 只是保护一段共享数据、没有消息传递语义时，`sync.Mutex` 加共享变量更直接
- 传播取消/超时信号时，用 `context`（标准库的上下文传递机制）更清晰

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 无缓冲 channel | 收发双方会合，数据不经缓冲 | 需要"发送完成即已被接收"的同步语义 |
| 带缓冲 channel | 环未满时发送立即返回 | 生产消费速率不均、允许削峰 |
| `sync.Mutex` + 共享变量 | 只保护临界区，无消息语义 | 多个 goroutine 读写同一份数据 |
| `context.Done()` | 关闭即广播的单次信号 | 传播取消或超时 |

前置条件：本机安装 Go 即可，无其他依赖。

go run main.go          # 文本演示：环形队列 → 阻塞 → 回绕 → close → 无缓冲 → 真实对照

## How It Works

按演示顺序展开：结构 → 游标推进与回绕 → 阻塞与交接 → close 语义。

### hchan 结构与环形队列

```go
type hchan struct {
    qcount   uint  // 队列中元素个数（对应 len(ch)）
    dataqsiz uint  // 环形队列容量（对应 cap(ch)）
    buf      []int // 环形队列底层数组（简化：元素为 int）
    sendx    uint  // 发送游标：下一个写入的位置（只增不回绕）
    recvx    uint  // 接收游标：下一个读取的位置（只增不回绕）
    closed   bool  // 是否已 close
    blocked  uint  // 被阻塞方数量（简化"等待队列"）
}
```

这段在做什么：复刻真实 hchan 的核心字段。真实 runtime 还有 `recvq`/`sendq` 两个等待队列和一把 `lock`，模拟版用 `blocked` 计数简化；语义不变：阻塞的 goroutine（Go 的轻量级线程）挂进队列，被对端唤醒。

### sendx/recvx 推进与掩码回绕

```go
func (ch *hchan) mask(n uint) uint { return n & (ch.dataqsiz - 1) }
```

这段在做什么：游标只增不回绕，落槽时用 `& (size-1)` 掩码映射到环下标。演示对 cap=4 的环发送 {10,20,30,40} 填满（sendx=4），接收 2 个腾出槽 0/1 后再发 500/600：sendx 4→5→6，掩码后正好落回槽 0/槽 1——槽位被循环复用，qcount 回到 4。

你在输出里看到的 `发送 40 → 写入环槽3` 与 `发送 500 → 写入环槽0`，就是游标过掩码的结果：前者 sendx=3、写入后变 4；后者 sendx=4，掩码 4&3=0，正好绕回槽 0。

### 满则阻塞、空则阻塞与直接交接

环满时发送方阻塞（快照里 blocked=1，值暂存 pending）；环空时接收方阻塞。但若队空却已有等待方，则直接交接、不占环。

无缓冲 channel（cap=0）没有环：send(42) 因无接收方阻塞，recv 到来时数据经 pending 直接递过去，sendx/recvx 永远为 0——这就是"直接交接"的极端形式。

### close 之后的语义

close 置位后：接收先把 buf 里的残留数据读完（30、40、500、600 依次读出，recvx 追到 6），读空后再接收返回零值 `ok=false`；再发送直接 panic。

演示特意按"close → 读光残留 → 空收 → send"分步执行，避免"已关闭"判定短路吞掉残留数据。输出里 `关闭 channel → closed=true；buf 里残留的数据仍可读出` 对应这一段的起点。

### 字段速查

| 字段/表达式 | 含义 | 为什么重要 |
|---|---|---|
| `qcount` | 队列中元素数 | `len(ch)` 的来源，收发各增减 1 |
| `dataqsiz` | 环容量 | `cap(ch)` 的来源；满/空判定的基准 |
| `sendx` / `recvx` | 写/读游标 | 只增不回绕，落槽靠掩码 |
| `& (dataqsiz-1)` | 掩码映射 | 游标 → 环下标；容量是 2 的幂才成立 |
| `blocked` / 等待队列 | 被阻塞方 | 阻塞语义与唤醒的载体 |

## Pitfalls & Q&A

踩坑记录，每条 = 现象 + 原因 + 解法：

- **`unsafe` 硬读 hchan 读到垃圾字段**。原因：hchan 不在公开 API 里且字段随版本漂移。解法：学习内部状态只用纯 Go 结构模拟，行为用真实 channel 交叉验证。
- **拿 sendx/recvx 直接当数组下标用**。现象：下标越界。原因：它们是单调递增游标，不回绕。解法：必须过 `&(dataqsiz-1)` 掩码再落槽。
- **close 后的接收顺序写反，残留数据被吞**。原因：close 的接收语义有顺序——先读光残留，再判"已关闭且空 → 返回零值"，判定在前会短路。解法：按"读残留 → 判关闭"的顺序实现与使用。
- **用 `len(ch)` 做同步判断**。原因：`len(ch)` 只是某一瞬间的 qcount，并发场景下读到的值随时可能过期。解法：不要用它做同步，同步语义交给收发本身。

深入问答：

**Q：sendx/recvx 会不会回绕或溢出？**
A：它们只递增、不回绕，落槽时用 `& (cap-1)` 掩码映射到环上（要求容量是 2 的幂）。游标本身是 uint，工程生命周期内不会溢出。

**Q：向 nil channel、已关闭的 channel 收发分别会怎样？**
A：nil channel 收发永久阻塞；已关闭的 channel 接收先读光残留数据再返回零值 `ok=false`，发送直接 panic，close 已关闭的 channel 也 panic。

**Q：无缓冲 channel 的发送何时返回？**
A：必须有接收方就绪才直接交接（rendezvous），数据不经过缓冲；它保证的是"传递完成"这一同步语义，而带缓冲 channel 只保证"已放入队列"。
