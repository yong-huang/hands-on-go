# 18 · GMP 调度模型：本地 runq、全局兜底与 work stealing

> Go 能撑起百万并发，靠的不是百万条 OS 线程，而是 **G（goroutine）+ M（OS 线程）+ P（处理器）** 三层调度。排队与补位由三条朴素规则决定：**本地队列优先、全局队列兜底、work stealing 均衡**；再加上一条保命规则——G 阻塞在 syscall 时，M 与 P 分离移交。本实验写一个迷你调度器把前三条规则原样建模，用 42 条真实调度事件看 steal 和全局队列什么时候登场。

## Background

如果一条 goroutine（Go 的轻量执行单元，自带栈与任务体）对应一条 OS 线程，百万并发就是百万线程——内核调度开销与栈内存都会先崩。线程这条路走不通，是整个问题的起点。

Go 的做法是把"任务"（G）与"执行流"（M，即 OS 线程，内核调度的基本单位）解耦，中间插入数量受限的 P（处理器，调度资源，`GOMAXPROCS` 个——GOMAXPROCS 是控制 P 数量的运行时配置）：M 必须占到一个 P 才能跑 G，G 只在 P 的队列里挪动。

收益立竿见影：**G 的切换 ≈ 出队 + 入队**，全程用户态（不陷入内核的普通执行状态）、没有系统调用；而线程切换要陷入内核、保存并恢复内核调度上下文。G 怎么排队、谁先谁后、谁闲着帮忙，就由接下来的三条队列规则加一条保命规则决定。

## What

GMP 是 Go 运行时的三层调度模型：G（goroutine，任务+栈）、M（machine，OS 线程）、P（processor，持本地队列的调度资源）三者配合，把海量 G 分摊到少量 M 上执行。

心智模型一句话：主路径上，新 G 进发起者 P 的本地 runq（run queue，待运行 G 的队列，无锁、最快）；本地空了先查全局 runq（带锁、公平兜底），全局也空就偷最忙邻居的（负载均衡）。

另有一条保命规则：一旦 G 阻塞在 syscall（系统调用，进入内核执行的操作），runtime 就把 P 从这个 M 身上分离、移交给空闲 M。

可以把 GMP 想象成一间车间：G 是工单，M 是工人，P 是工位——工人必须占到一个工位才能干活；工单先堆在自己工位的格子架（本地队列）里，架子空了去中央仓库（全局队列）领，仓库也没有就去邻居工位匀几件（偷）。

但和车间不同的是：工位可以脱离卡死的工人整体搬家（handoff 移交），工人陷入长等待时工位绝不陪绑；而且工位数量是刻意限定的（`GOMAXPROCS`），它决定并行度，与工单数量无关。

## When to Use

这套模型在"推断调度行为、解释并发性能"的时候派上用场。三个典型场景：

- **估算并发容量**：goroutine 可以开到百万级，真正的约束是 M 数量与阻塞 syscall 的占比——下单量级前先想清楚哪个环节会卡住 M
- **设置 `GOMAXPROCS`**：它控制的是 P 的数量（并行度上限），不是 goroutine 数量；容器里核数变化时对应调整
- **解释长尾延迟**：负载不均时靠 steal 补位、大量 G 阻塞在 syscall 时靠 handoff 保住 P，两类延迟的来源不同

何时不用：普通业务代码接触不到调度细节，也不需要手动干预；本实验是确定性模拟，它的比例数字（如 71%）不能外推到真实 runtime 的统计。

并发执行模型的对比：

| 方案 | 差异 | 什么时候选它 |
|:---|:---|:---|
| 一任务一线程 | 模型直白，线程数随并发爆炸 | 并发量小、依赖线程局部生态时 |
| 线程池 | 固定线程跑任务队列，控制线程数 | 任务粒度粗、数量可控时 |
| 单线程事件循环 | 无锁无切换，但吃不满多核 | IO 密集且可异步化时 |
| M:N（GMP 一类） | 任务与线程解耦，切换在用户态 | 海量轻量任务、多核并行时 |

## Quick Start

前置条件：安装 Go，进入实验目录即可运行，运行 demo 只需 Go；重画数据图需 Python 3 与 matplotlib（pip install matplotlib）。本实验是确定性模拟（P 固定 4 个、12 个 G 负载故意不均——3 个重 G 各 8 个任务全挤在 P0），每次运行结果相同。

```bash
cd internals/18_gmp
go run main.go          # 文本演示：调度统计 + JSON 快照 + 结论
go run main.go -json    # 只输出 JSON 快照（供 viz.py 画图）
python3 viz.py          # 重新生成实测数据图
```

预期输出（节选，每次运行结果相同——本实验是确定性模拟，不含随机数与地址）：

```text
== 调度结果：12 个 G（负载不均），11 步 =====
   local 取（局部性）  : 30
   global 取（公平）  : 2
   steal 取（负载均衡）: 10
   比例 local:global:steal = 30:2:10
```

JSON 快照里有全部 42 条调度事件（`step`/`p`/`g`/`src`）。例如第 5 步：`p1` 与 `p2` 本地已空，从全局队列取走 G0、G1——正是 P0 在第 1 步队满时溢出到全局的两个重 G。

两个要点帮你校准预期：30:2:10 的比例说明本地队列是主线、全局是低频兜底、steal 在轻任务耗尽后集中发生；每条事件都带来源标注，可以逐条核对下一节的机制。

## How It Works

按"统计总览 → 三级水位逐级展开 → syscall 保命规则"的顺序拆解，每一步都对上 Quick Start 的数字。

### 三级水位：本地 → 全局 → steal

不均衡负载（P=4，12 个 G，3 个 8 任务重 G 挤在 P0）下的实测分布：

| 来源 | 含义 | 次数 | 占比 |
|:---|:---|:---:|:---:|
| local | 从自己的本地队列取（局部性） | 30 | 71% |
| global | 本地空/溢出后取全局（公平） | 2 | 5% |
| steal | 偷别人队列（负载均衡） | 10 | 24% |

71% 的调度走本地队列——这是**本实验这种不均衡负载下的实测值**，不是真实 runtime 的统计比例；但它说明的机制是真实的：本地队列不碰全局锁、不跨核，CPU 缓存友好，天然是主线。

### 全局队列：公平的安全网

本地队列有容量上限（模拟里 `LOCAL_CAP=3`；真实 runtime 每 P 的 runq 上限是 256）。满了就把**队头一半**溢到全局队列（FIFO，先进先出），保证先来的 G 不会被无限推迟；任何 P 本地空时先来全局取。

你在 JSON 快照第 5 步看到的 `global` 取 G0、G1，就来自 P0 第 1 步队满时的这次队头溢出。真实 runtime 还有一道保险：每 61 次调度 tick（调度循环的步数计数，`schedtick%61 == 0`）强制查一次全局，用概率防饿死。

### work stealing：闲 P 自动补位

全局也空时，P 去偷别人的本地队列。模拟里挑**最忙**的邻居、取它队尾一个；真实 runtime 是随机试 4 个受害者、一次性**偷走其队头的一半**——传一批而不是传一个，摊薄 stealing（工作窃取）的成本。

注意实测里 10 次 steal 全部发生在第 7 步之后：轻 G 跑完、本地队列见底，闲 P 才开始从仍剩重 G 的 P0/P1 身上分活。不均衡是常态——`go` 语句创建的 G 都挤在发起者的 P 上，steal 让闲 P 自动补位。

### syscall 阻塞：M 与 P 分离 handoff

这是模拟没有建模、但真实 GMP 必须有的一条：G 阻塞在 syscall 里时，M 陪着 G 陷入内核等待；`sysmon`（runtime 的后台监控线程）发现后把 **P 从该 M 身上分离**（handoff，移交），移交给空闲 M 继续跑别的 G。

syscall 返回后，M 尝试拿回一个 P；拿不到就把 G 放进全局 runq，自己睡眠。

这条规则补全了 P 的价值：任务队列从线程上解耦之后，线程数与并行度解绑，阻塞的 M 不影响 P 继续调度，M 本身也可被复用。"工位"（P）永远不会陪一个卡死的"工人"（M）闲置。

### 关键常量与字段

| 常量/字段 | 值 | 为什么重要 |
|:---|:---|:---|
| `P` | 4 | 处理器数，对应真实 `GOMAXPROCS` |
| `NS` | 12 | 并发 G 数；`done` 计数以它为终止条件 |
| `LOCAL_CAP` | 3 | 本地队列容量，超了队头溢到全局（真实 runq 上限 256） |
| `event{Step,P,G,Src}` | — | 每步调度事件，`-json` 快照的原子单位 |
| `bySrc` | map | local/global/steal 计数，数据图直接吃它 |

## Pitfalls & Q&A

踩坑清单（全部来自本实验真实踩过），每条按"现象 → 原因 → 解法"展开：

- **调度器死循环**：现象是跑满 10 万步上限才停；原因是终止条件写成 `done < NS*ST`（任务总数），而 `done` 数的是"完成多少个 G"；解法是**循环边界 = 计数单位**，命名别混
- **队列空了却收不了尾**：现象是队列已空、`done` 不达标；原因是同一 G 在多个队列存在副本，被重复 decrement（递减计数）；解法是保证每 G 恰一份，不变量立刻成立
- **复现不出 steal**：现象是 10 次 steal 一次没出现；原因是重 G 分散在 4 个 P 上，人人都忙、没人偷；解法是把 3 个重 G 挤到 P0，先造出不均衡场景
- **全局队列形同虚设**：现象是全程只有 local 取；原因是缺少进入条件；解法是只有本地队满溢出才进 global——公平兜底不是免费来的
- **模拟与真实混淆**：现象是按模拟数值推断真实 runtime；原因是简化实现与真实源码有差距（模拟打印"1/64 概率查全局"是口误，真实是 `schedtick%61 == 0`，约 1/61；模拟偷队尾、真实偷队头一半）；解法是以 How It Works 各节的"真实 runtime"描述为准

深入问答：为什么非要加一层 P、goroutine 切换为什么便宜、全局队列何时被查、steal 偷多少、syscall 阻塞后 P 和 M 的去向——这些常见疑问已分别在 What 的三层定义与 How It Works 的四小节中展开，不再重复。
