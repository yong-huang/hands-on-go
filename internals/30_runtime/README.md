# 30 · 最小 Go 运行时模拟：GMP 调度器 + 两级分配器 + 标记清扫 GC

> 不碰真实 runtime 源码里的指针位运算和汇编，而是把三大件的核心机制"翻译"成 200 行可读 Go 代码：M 用真 goroutine 扮演，P 带本地队列，G 是带状态（runnable/running/done）的闭包任务；分配器走 mcache→mcentral→arena 两级；GC 是简化版标记-清扫。跑 12 个任务、1200 次分配，完整验证"调度、分配、回收"能一起工作。

## Background

分别学完调度（GMP——Go 调度模型的三要素：G 任务、M 机器线程、P 逻辑处理器）、分配器（size class，按字节数分档的分配规格）、GC（三色标记——标记阶段以白/灰/黑三色推进的经典算法）之后，知识点是散的：调度器怎么和内存分配器协作？GC 触发时分配器在干什么？

直接读真实 runtime 源码门槛很高：满屏指针位运算和汇编。而机制本身，用一个"玩具 runtime"就能对上接口——**M 从队列取 G 执行，G 里调 alloc，完成数过阈值就触发 GC**。核心机制一小时就能讲清楚，还能跑出真实数字。

本实验就是这个玩具：200 行可读 Go 代码，把三大件放进同一个程序里协作。

## What

**定义**：这是一个最小 Go 运行时模拟器——用普通 Go 代码复刻 runtime 三大件（GMP 调度器、两级内存分配器、标记-清扫 GC）的核心协作机制，供观测与验证。

**心智模型**：可以把内存分配链路想象成领物资——工位抽屉（mcache，每 P 私有的无锁快取）→ 部门仓库（mcentral，按尺寸等级加锁的中央池）→ 总仓向供应商进货（mheap/arena 向操作系统要内存）。

但和真实仓储不同的是：抽屉完全无锁、人人专属，而且"回收员"（GC）会定期把没人用的物资收走重新上架。

**机制一句话**：分配永远先走每 P 无锁的 mcache，不够才去按 class 加锁的 mcentral 补一批，内存最终来自 mheap/arena 向 OS 预取。

`runtime.MemStats`（runtime 的内存统计结构）的四个关键字段就是这条链路的四个观测点：`TotalAlloc` 只增不减（累计计数）、`HeapAlloc` 当前存活、`HeapSys` 向 OS 要的堆总量、`Sys` 进程预留总内存。

## When to Use

### 典型场景

- 学完 GMP/size class/三色标记后做整合验证：确认三大件在同一个程序里如何协作、接口怎么对上。
- 诊断内存指标前建立心智模型：读 `MemStats` 做线上内存分析时，先弄懂字段背后的分配层级。
- 理解并发程序的可观测性边界：为什么"统计稳定、时序浮动"，为什么不能对并发输出做逐字断言。

### 何时不用

- 需要实现级精确行为时：模拟删掉了抢占细节、指针位运算与汇编，结论不能直接套到真实 runtime 的数值上。
- 线上问题诊断：直接用真实 `runtime` 指标与 pprof，玩具模拟不参与生产。

### 同类方案对比

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 读真实 runtime 源码 | 精确但门槛高（位运算、汇编） | 需要实现级结论 |
| 玩具模拟（本实验） | 机制等价、代码可读，细节有简化 | 建立三大件协作的全景 |
| MemStats/pprof 实测 | 观测真实行为，但不给机制 | 线上诊断与验证 |

## Quick Start


预期输出（节选；**窃取次数与回收字节数随调度时序浮动**）：

```text
  GMP=4  任务=12  完成=12  窃取=6  本地队列峰值=2
== 分配器 + GC ===========
  分配=1200  回收对象批=3  GC 次数=3  存活字节=120  回收字节=13976  根对象=15
```

## How It Works

### 调度器 = 队列 + 窃取 + 让出

本地队列空时先看全局队列，再随机偷别的 P 的本地队列尾；都空就小睡让步（模拟 sysmon——真实 runtime 的后台监控线程）。任务按 `taskCount%3` 分流——约 1/3 进全局队列，其余轮询进各 P 本地队列，这样跨 P 窃取才有机会发生。

真实 runtime 的 `runqsteal` 会偷走一半且从尾部拿——属主从头消费、小偷从尾拿走，天然减少竞争；本实验简化为偷一个，机制相同。

用 `go run main.go -json` 输出的事件序列可以按时间画出 4 个 M 的调度泳道（viz.py 生成，每次运行的窃取时刻都不同）：哪个 M 在执行 G、哪次取任务是窃取成功、哪段在等队列。

### 分配器 = 两级缓存降锁争

每 P 一个无锁 mcache 快取（free list，串起可复用内存块的空闲链表），空了才拿 mcentral 的锁补一批 8 个：把"每次分配都加锁"变成"每 8 次才加一次锁"。

真实 runtime 的三级层级就是这个套路：mcache 让绝大多数分配零锁；mcentral 按 size class 全局管理、每 class 一把锁；mheap 管页级内存、向 OS 缺页——本实验的 arena 预建对象池对应 mheap 批量要内存那一步。

微小对象另有 tiny allocator 合并分配，大对象（>32KB）直接走 mheap。

### GC = 标记可达、清扫其余

完成数每越过阈值 4/8/12 触发一次（用 `lastGC` 去重，防多个 M 并发重复触发）。

从 roots（GC 扫描起点：全局变量、各 goroutine 栈上的变量）出发 DFS（深度优先搜索）标记所有可达对象，未标记的当场退回 central 的 free list。

3 次 GC 后仅 15 个根对象存活——对应输出里的 `GC 次数=3  根对象=15`。

真实 Go 的触发条件本质相同：`HeapAlloc` 涨到上次存活堆的 GOGC 比例（默认 100% 即翻倍）就收，外加 2 分钟强制 GC 与 `runtime.GC()` 手动触发。

### 为什么能一直分配不撑爆池

池总共只有 184 个对象（5 类：8/16/32/64/128 B，各 64/48/32/24/16 个），靠 GC 在跑批中途回收才能支撑 1200 次 alloc——"分配→用→丢→GC 回收→再分配"闭环成立。

这也解释了 MemStats 里 `TotalAlloc`（累计 1200 次）远大于 `HeapAlloc`（存活 120 B）的日常现象：前者是吞吐计数，后者是当前存活水位。

### 关键字段速查

| 字段/结构 | 含义 | 为什么重要 |
|---|---|---|
| `Scheduler.global` / `P.local` | 全局队列 / P 本地队列 | 多级队列分摊锁；全进全局就没有"窃取" |
| `steals` | 窃取计数（实测 5~7，浮动） | 负载不均衡被自动修复的证据 |
| `mcache.free[c]` | 每 P 每 class 的无锁快取 | 命中即分配，不加锁 |
| `mcentral.free[c]` + `sync.Mutex` | 每 class 一把锁的中央池 | refill 批量 8，摊薄锁成本 |
| `allocs` / `liveBytes` | 累计分配 / 当前存活 | 对应 `TotalAlloc` / `HeapAlloc` 口径 |
| `lastGC` | 上次触发的完成数 | 防止多个 M 在同一阈值重复触发 GC |

## Pitfalls & Q&A

**坑 1：用 Python 的命名实参语法。** 现象：`spawnWorkers(allocs=1200, ...)` 编译报语法错误。原因：Go 不支持关键字实参。解法：按位置传参，或传配置结构体。

**坑 2：对 map 元素取地址。** 现象：`&map[id]` 编译报错。原因：Go 不允许对 map 元素取址（元素可能随扩容搬移）。解法：事件收集改成 `events []*[]Mev` 存指针切片。

**坑 3：任务全进全局队列。** 现象：steals 等于任务数、本地队列峰值恒 0，"窃取"名存实亡。原因：没有本地队列就没有负载不均衡可修复。解法：约 1/3 任务直接塞本地队列，制造不均衡。

**坑 4：GC 阈值用 `done%4==0` 裸判断。** 现象：同一阈值被触发多次 GC。原因：多个 M 并发到达同一完成数，各自满足条件。解法：记 `lastGC` 去重。

**坑 5：根对象没活到最后。** 现象：最终存活数不是预期的 15 个。原因："保留根"和"丢弃"逻辑存在并发读写竞争。解法：共享计数 + mutex 保护。

**Q：`TotalAlloc`、`HeapAlloc`、`HeapSys`、`Sys` 到底各数什么？**
`TotalAlloc` 是累计分配字节数，只增不减，用来算吞吐。

`HeapAlloc` 是当前存活堆字节（约等于 runtime 里 `heap_live`），GC 就看它涨没涨过 `HeapSys` 的 GOGC 比例。

`HeapSys` 是向 OS 申请的堆总量（含已归还但未归还 OS 的）；`Sys` 是进程从 OS 预留的全部内存，堆之外还有栈、元数据等。

**Q：为什么窃取次数每次运行不一样？**
M 是真 goroutine，被 OS 线程以不确定的节奏调度，谁先跑空本地队列、谁抢到锁都随时间序浮动——这正是并发程序"统计稳定、时序浮动"的典型表现，也是不能对并发输出做逐字断言的原因。

**Q：模拟的"完成数过阈值"触发和真实 Go 的 GC 触发一样吗？**
模拟用完成数当水位；真实 Go 用 `HeapAlloc` 相对上次存活堆的比例（GOGC，默认 100% 即翻倍）触发，外加 2 分钟强制 GC 和 `runtime.GC()` 手动触发——本质相同：堆涨到"再不收就浪费"的水位就收。

三大件的公共设计主题是"分摊"：调度用多级队列分摊锁，分配用两级缓存分摊锁，GC 用标记分摊"知道谁活着"的成本；工作窃取让负载不均衡自动修复，池内 184 个对象靠 GC 周转撑起 1200 次分配。
