# 06 · 数组与 slice：值内联与 24 字节 header 的内存布局对比

> "数组和 slice 到底差在哪"是 Go 初学者最常困惑的问题之一：为什么数组赋值/传参会拷走整份数据，而 slice 却能"引用式"地共享？本篇用 `unsafe.Sizeof` 与 `reflect.SliceHeader` 打印两者的运行时内存布局，把答案变成看得见的字节数与地址。

## Background

写 Go 时两类问题高频出现：

- 把大数组传给函数，以为只传了个"引用"，实际发生了整份拷贝
- 以为切片赋值出来的是独立副本，改一个、另一个跟着变

在此之前的直觉多半来自别的语言：C 里数组名会退化成指针，动态语言里数组赋值就是引用——两套直觉搬到 Go 各对一半，于是在"什么时候拷贝、什么时候共享"上反复踩错。

这些行为的根源在内存表示：数组与切片的变量"本体"里装的东西根本不同。两者的布局是语言规范层面的稳定结构，所以可以放心用 `unsafe` 直接读出真实布局验证，并顺带对比两者作为函数参数的传递代价。

## What

**定义**：数组 `[N]T` 是值类型——N 个元素直接内联（平铺存放）在变量占用的内存里；slice 是结构体式的视图——变量本身只有 `{Data, Len, Cap}` 三个字段共 24 字节，元素数据在 Data 指向的底层数组上。

**心智模型**：数组变量就是数据本身，slice 变量只是数据的"取景框"——框住 `[5]int` 时，数组本体 40 字节、框子只有 24 字节。

但和数组不同的是，框子赋值/传参只拷 24 字节，且两个框子可以框住同一块底层数据：`a[1:4]` 的框子只比 `a[:]` 的 data 前进 8 字节（1 个元素）。

## When to Use

什么时候需要按"值内联 vs header"来做选择与排查：

- 在选集合的底层表示时——长度编译期已知（采样缓冲、`[32]byte` 摘要）用数组，需要变长就用切片
- 在写接收集合参数的函数时——预判按值传数组的整份拷贝代价，与传切片的共享副作用
- 在排查"改了一个另一个也变了""函数内改动外泄"的问题时——先判断是值拷贝还是共享底层数组

什么时候不用：

- 长度需要运行期增长时直接用切片，数组表达不了
- 只是想避免大数组拷贝时，传 `*[N]T` 或切片即可，不必坚持数组

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| `[N]T` 数组 | 值语义，赋值/传参整份拷贝，长度是类型的一部分 | 定长小数据、需要拷贝隔离 |
| `[]T` 切片 | 24 字节 header 加共享底层数组 | 变长集合、大 buffer 传参 |
| `*[N]T` 数组指针 | 只传地址，保留定长与内联 | 大数组的零拷贝传参 |
| `make + copy` 全量复制 | O(n) 拷贝换来完全隔离 | 要切片语义但要独立副本 |

## Quick Start

```bash
cd internals/06_array_vs_slice
go run main.go          # 文本演示：数组内联 → slice header → 传参 → 切片窗口
go run main.go -json    # 输出 JSON 状态快照（机器可读的地址/字节数值）
```

预期输出（节选，地址每次运行不同）：

```text
sizeof(arr) = 40 字节（5 个元素直接放在变量里，没有指针）
&arr[0] = 0x…eb8  value=1
&arr[1] = 0x…ec0  value=2        ← 相邻元素间隔 8 字节
&arr     = 0x…eb8（== &arr[0]，数组名就是首元素地址）
sizeof(sl) = 24 字节（只有 header 的三个字段）
&sl     = 0x…f10   Data    = 0x…ee0   Len=5  Cap=5
函数内 &a = 0x…db8（按值传入 → 拷贝整 40 字节）
函数内 &s = 0x…db8（只拷 24 字节 header），s.Data = 0x…ee0（与外面共享底层数组）
sB = a[1:4]   Data=0x…008  Len=3  Cap=4
偏移 = Data(sB) - Data(sA) = 8 字节（= 1 个元素）
```

## How It Works

按演示顺序展开：数组内联 → slice header → 传参代价 → 切片窗口。

### 数组是内联的连续"值"

`[5]int` 的 5 个元素直接平铺在变量占用的内存里，`unsafe.Sizeof` 得到 40 字节（5 × 8，无任何指针层）。程序逐个打印 `&arr[0]` 到 `&arr[4]`，地址间距正好 8 字节。

输出里 `&arr = 0x…eb8（== &arr[0]，数组名就是首元素地址）` 验证了数组没有 header：它就是一块连续内存本身。

### slice 是 { Data, Len, Cap } 结构体

slice 变量本身只有 3 个字段共 24 字节：`Data`（指向底层数组的指针）、`Len`（元素个数）、`Cap`（容量上限）。

程序读出字段并验证 `&sl != Data`——header 变量里没有数据，真正的 5 个 int 躺在 `Data = 0x…ee0` 指向的底层数组上，对应输出里的 `&sl = 0x…f10 Data = 0x…ee0 Len=5 Cap=5` 一行。

### 传参：全量拷贝 vs 只拷 header

`copyArr` 按值接 `[5]int`，函数内 `&a` 与调用方不同（整份 40 字节的拷贝）；`copySl` 按值接 `[]int`，函数内 `&s` 同样不同，但 `s.Data` 与调用方相同——只拷了 24 字节 header，底层数组共享。

所以函数内 `s[i] = x` 对调用方可见，而修改 `arr[i]` 不影响外界——输出里"函数内 &a / 函数内 &s"两行就是这对地址的对照。

### 切片产生新 header，只移动指针

`sA := a[:]` 与 `sB := a[1:4]` 是两个独立的 header，但 `Data(sB) - Data(sA) = 8` 字节——切片只是把 Data 指针挪了一个元素、重算 Len=3/Cap=4，不复制数据。

随后 `sB[0] = 99`，`sA` 变成 `[1 99 3 4 5]`（即 `a[1]` 被改）：两个取景框框住同一块内存，这就是内存别名（多个变量名指向同一块内存）。输出最后两行——偏移 8 字节与"改后 sA/sB 同步变化"——就是它的实证。

### 字段速查

| 字段/表达式 | 含义 | 为什么重要 |
|---|---|---|
| `unsafe.Sizeof(arr)` | 数组变量占的字节数 = N×元素大小 | 证明元素内联、无指针层（40 = 5×8） |
| `SliceHeader.Data` | 底层数组起始地址 | `&sl != Data` 直接证明"header 里没有数据" |
| `SliceHeader.Len/Cap` | 元素数 / 容量上限 | `a[1:4]` 后 len=3、cap=4（cap 从偏移处数到数组尾） |
| `&arr` vs `&arr[0]` | 数组名即首元素地址 | 传参时整份拷贝的根源 |
| `Data(sB)-Data(sA)` | 切片偏移（本例 8B） | 偏移 ≠ 拷贝：窗口移动，数据不动 |

## Pitfalls & Q&A

踩坑记录，每条 = 现象 + 原因 + 解法：

- **把子切片当独立副本**。现象：`sB := a[1:4]` 后 `sB[0] = 99` 连 `a` 一起变。原因：两个 header 共享同一底层数组。解法：要真拷贝用 `append([]int(nil), s...)` 或 `make + copy`。
- **函数内改 slice 元素"意外"影响调用方**。原因：传 slice 共享底层数组，`s[i] = x` 对外生效，和数组按值传递的直觉完全相反。解法：明确函数契约——改元素生效，还是只读并返回新切片。
- **误以为 slice 传参总是引用语义**。现象：函数内 append 超过 cap 后，扩容结果没有反映回调用方。原因：header 本身按值拷贝，append 换了新底层数组。解法：函数显式返回新 slice。
- **生产代码依赖 `reflect.SliceHeader`**。原因：Data 指针不能脱离 GC（垃圾回收）长期持有，unsafe 依赖脆弱。解法：只当学习手段，业务代码走常规 API。

深入问答：

**Q：`sB := a[1:4]` 之后 sB 的 len 和 cap 各是多少？为什么？**
A：len=3（4-1），cap=4（cap(a)-1=5-1）。新 header 的 data 只前进 1×8=8 字节，窗口从 a[1] 框到数组末尾，所以 cap 是"从偏移处数到尾"。

**Q：数组名是指针吗？**
A：不是。`&arr == &arr[0]` 只是数值上等于首元素地址；数组是纯值类型，赋值/传参发生整份拷贝，这与 C 里"数组名退化为指针"完全不同。
