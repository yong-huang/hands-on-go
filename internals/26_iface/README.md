# 26 · interface 动态派发开销：贵的是挡住优化，不是多查一次表

> 接口调用到底贵在哪？本实验对同一个方法用七种调用方式计时：直接（可内联）、直接 noinline、接口派发、类型断言、type switch，外加一组"常数方法"放大对照。读完本篇，你能用实测数字和 objdump 汇编分清两笔账——寻址的账（≈1.05x）与被挡住的优化的账（1.5~1.7x）。

## Background

"面向接口编程"是 Go 的日常写法，但接口方法调用比直接调用慢多少、慢在哪，流传的答案两极：有人说"一次间接寻址而已，忽略不计"，有人说"动态派发是性能杀手"。

两种说法都会造成实际损失。信前者的人会在热路径（执行最频繁、对性能最敏感的代码段）上随手引入接口；信后者的人到处绕开接口、复制具体类型的代码，却可能优化不到点上。

这个实验不背结论，直接测，再用汇编对照验证——因为新版本编译器（go1.26 起）会自动改写部分接口调用点，教科书结论需要重新校准。

## What

**定义**：interface（接口）是 Go 的一组方法签名约定；动态派发（dynamic dispatch）指"调用哪个实现"推迟到运行时才确定——通过接口值调用方法就是最常见的派发场景。

**心智模型**：可以把接口值想象成"名片 + 地址"的组合：名片（itab，接口方法表，记录具体类型每个接口方法的函数指针）印着"会哪些方法、各在第几格"，地址（data 指针）指向真实数据。调用方法 = 按方法序号翻到对应格、取出函数指针再间接 CALL（调用目标存在寄存器里，运行时才确定）。

但和真实名片不同的是：名片不是每次现做的——(接口类型, 具体类型) 组合的 itab 生成一次、全局缓存复用；而且编译器一旦能证明"这张名片只有一个人用"，会把间接调用改写成守卫比对 + 内联方法体（内联指编译器把被调函数体直接展开到调用处；这个改写叫去虚化，见 How It Works）。

## When to Use

### 典型场景

- 定义函数参数与依赖注入：handler 依赖 `io.Reader` 这类接口参数，测试时可以替换假实现，调用点自动获得多态能力。
- 多实现分派：同一抽象（存储后端、编码器等）有多个实现，运行时按配置选择，接口是语言级方案。
- 热循环的优化决策：循环里的接口调用若成为瓶颈，先测再改——优先考虑"剥壳"（用类型断言把接口值还原为具体类型，如 `v, ok := x.(T)`），而不是全盘放弃接口。

### 何时不用

- 类型唯一、也无替换需求时：直接用具体类型，调用点可内联 + 常量折叠（编译期把常量计算直接算出结果），实测 0.76 vs 1.15 ns/op。
- 微基准测量纳秒级差异时：接口调用点的汇编形态受编译器版本影响很大，别拿教科书路径直接下结论。

### 同类方案对比

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 直接调用具体类型 | 编译期定死目标，可内联 + 常量折叠 | 类型唯一、无替换需求 |
| 接口 + itab 派发 | 运行时间接 CALL，与 noinline 直接调用实测 ≈1.05x | 需要多实现或依赖替换 |
| 类型断言 / type switch 剥壳 | 一次类型比对换回内联空间，实测 0.90 ns/op | 热循环内的接口调用 |
| 编译器去虚化（go1.26 起） | 自动改写：守卫比对 + 内联，无需改代码 | 唯一实现可被证明的调用点 |

## Quick Start

前置条件：go1.26 及以上（去虚化行为以 go1.26.5 实测为准）；viz.py 重新画图另需 Python 3 与 matplotlib（只跑 go run main.go 无需）。运行：

```bash
cd internals/26_iface
go run main.go          # 七组对照计时 + 解释
go run main.go -json    # 机器可读快照（七组数值 + 三个比值）
python3 viz.py          # 重新生成实测数据图表与汇编对照面板
```

三组对照各司其职：**noinline 直接调用**（禁止内联的对照组）隔离出"纯派发成本"；**类型断言/type switch** 演示"把接口剥回具体类型"的实价；**常数方法对照**（`ConstVal` 永远返回 42）放大"优化视野"的差异。

预期输出（go1.26.5 实测，一次典型运行）：

```text
  调用方式                 ns/op
  direct(内联)                   0.76
  direct noinline              1.10
  interface itab               1.15
  type-assert+直接               0.90
  type-switch                  1.12

  常数方法对照：
  direct const(折叠)             0.65  （循环被常量折叠删掉）
  iface const(挡死)              0.90  （itab 每次真调）
  差距 1.4x —— 这就是接口隐藏的代价：挡住编译器的优化眼
```

数值每次运行都在浮动（`direct` 多轮观察到 0.68~1.08；机器负载高时出现过 `ifaceConst=5.58` 的离群值）。`ns/op` 是每次操作的平均耗时（纳秒）。

判断看比值与趋势：`iface/directNI` 稳定 ≈1.0x，`iface/direct` 约 1.5~1.7x，`const` 对照稳定 ≈1.4x。

## How It Works

### 接口值的运行时表示：iface{tab, data}

`var c Calc = s` 之后，`c` 是两个字：类型描述符信息在 `tab`（*runtime.itab*），数据指针在 `data`（这里指向 `*Sampler`）。

itab 由 `(接口类型, 具体类型)` 二元组唯一确定：编译期能确定的直接生成在只读段（二进制中不可写的数据区），运行时才遇到的由 runtime 计算并全局缓存。

本实验二进制里能看到 `go:itab.*main.Sampler,main.Calc` 这样的符号——所以"查表"不是每次哈希查找，是读已经备好的方法槽。

### 教科书路径：itab.fun[i] 间接寻址

未被去虚化的接口调用编译成三步：取 `tab`、按下标取 `tab.fun[i]`、间接 CALL。与直接调用的差别一目了然：直接调用在链接期就定死目标（`CALL main.(*Sampler).CalcNI(SB)`），接口调用是 `CALL AX`（目标在寄存器里，运行时才知道）。

一次间接寻址 + 一次不可预测的间接跳转，量级就是一两纳秒——这就是 `iface` 与 `directNI` 几乎同价（≈1.05x）的原因。

### 本机实测汇编：go1.26 devirtualization 改写了调用点

`go tool objdump` 实拍（go1.26.5/arm64）三处调用点：

- direct 闭包 `run.func1`：`Calc` 被内联后整个循环体只剩"读参数、算 `31*x`、写 sink"（sink 是防止编译器删掉无用计算而写入的落地变量），连 CALL 都没有；
- `run` 本体：只有 7 组 `CALL main.bench(SB)` 和 map/json 调用——`CALL AX` 一行都找不到；
- iface 闭包 `run.func3`：编译器把 `c.Calc(i)` 改写成"读 itab → 和静态 itab 地址 `CMP` → 失配才 `panicdottypeI`，命中则执行**内联的方法体**"——用一次比对守卫换掉间接 CALL，这就是去虚化（devirtualization）。

你在输出里看到的 `interface itab 1.15`，就是这条"守卫 + 内联"路径的实测价：比 noinline 基线 1.10 略高，差在守卫比对与栈帧序言（函数入口保存现场的开销）。

推论：`Calc`/`ConstVal` 两个符号已被内联删除，`objdump` 里根本查不到——查不到符号 ≠ 编译错了，往往正是优化生效。当编译器**无法**证明唯一实现时（接口值来自函数参数、多个实现类型），才会回落到上一节的真派发路径。

### 七个数字怎么读

| 调用方式 | ns/op | 汇编里实际发生什么 |
|:---|:---:|:---|
| direct(内联) | 0.76 | 方法体内联，闭包只剩读写 sink |
| direct noinline | 1.10 | `CALL CalcNI`：真调用的基线 |
| interface itab | 1.15 | devirt 守卫 + 内联方法体（含栈帧序言） |
| type-assert+直接 | 0.90 | 断言守卫 + 直接调用 |
| type-switch | 1.12 | switch 分派 + 直接调用 |
| direct const(折叠) | 0.65 | 常量折叠：循环被删，只剩 store 42 |
| iface const | 0.90 | 守卫 + 折叠后的 store 42 + 栈帧开销 |

两个修正要诚实标注：

- 程序打印说 iface const 是"itab 每次真调"，但汇编显示常量 42 **仍然被折叠**进了闭包——0.65→0.90 的差值主要是栈帧序言加守卫比对，不是"没折叠"；
- "接口比直接慢 1.1x"的说法不准确：相对 noinline 直接调用是 ≈1.05x，相对可内联直接调用是 ≈1.5~1.7x，差价对应的就是被守卫/栈帧吃掉的优化红利。

剥壳（断言/type switch）后 0.90~1.12，与真派发同量级，但给编译器留出了内联空间。

### 关键符号速查

| 字段/符号 | 含义 | 为什么重要 |
|:---|:---|:---|
| `itab.fun[i]` | 方法槽表（变长数组） | 接口调用的寻址目标，`i` 是方法在接口里的序号 |
| `itab.inter / _type` | 接口类型 / 具体类型描述符 | 二元组唯一确定一个 itab，全局缓存复用 |
| `go:itab.X,Y` 符号 | 链接期生成的 itab 只读数据 | 能在 `go tool nm` 里看到；也是 devirt 守卫比对的地址 |
| `runtime.panicdottypeI` | 接口断言失败 panic | 汇编里出现它 = 这里有个 itab 比对守卫 |

## Pitfalls & Q&A

**坑 1：用函数值/泛型包装被测调用。** 现象：五种写法的 ns/op 全被拉平，什么都测不出。原因：`bench(fn)` 的 `fn` 本身是间接调用，把各写法的差异抹掉了。解法：每组必须手写闭包循环。

**坑 2：省掉 noinline 对照组。** 现象：测出的"派发成本"虚高。原因：没有禁止内联的基线，"派发成本"和"内联收益"混进同一个数字。解法：保留 direct noinline 作为真调用基线。

**坑 3：把 objdump 查不到符号当成编译出错。** 现象：汇编里搜不到 `Calc`/`ConstVal`。原因：符号已被内联删除；另外 `objdump -s` 的正则要转义 `(`、`)`、`*`。解法：先怀疑优化生效，改用调用点外围符号定位。

**坑 4：拿教科书派发路径直接读新版本汇编。** 现象：go1.26 下找不到 `CALL AX`。原因：去虚化把本实验三个接口调用点全部改写成守卫 + 内联。解法：先跑一遍程序确认调用点形态，再对照汇编，不套旧结论。

**坑 5：轻信单次微基准。** 现象：同机多次运行绝对值可差 ±15%，甚至出现离群值。原因：机器负载、代码布局都影响纳秒级数字。解法：固定看比值与趋势，多跑几轮，跑之前别让 IDE/浏览器抢核。

**Q：接口调用比直接调用慢多少？慢在哪？**
账分两笔记：寻址的账很小——`itab.fun[i]` 一两次访存，相对 noinline 直接调用 ≈1.05x。

优化的账才是大头——接口调用点对编译器是不透明调用，内联、常量折叠等局部优化被终止，相对可内联的直接调用差 1.5~1.7x。go1.26 的去虚化正在把第二笔账也慢慢抹平：能证明唯一实现时，接口调用退化成"一次比对 + 原地展开"。

**Q：怎么消除接口调用的开销？**
热循环里"剥壳"——用类型断言或 type switch 把接口变回具体类型（实测 0.90 ns/op），编译器就能内联小方法。go1.26 已对能证明唯一实现的调用点自动去虚化（本实验汇编可见守卫 + 内联体），但多实现场景仍走真派发。

结论：业务代码放心面向接口，热路径用断言剥壳，其余交给编译器。

常数方法 0.65→0.90 的折叠疑案已在 How It Works 的"七个数字怎么读"一节给出汇编证据；微基准的测量纪律见上方坑 1 与坑 5。
