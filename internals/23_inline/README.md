# 23 · 内联优化：编译器怎么决定把函数"抄"进调用点

> 内联（inlining，把小函数的函数体直接拷进调用点的编译器优化）是 Go 编译器默认开启的：省掉 call 的压栈/传参/返回。但编译器只内联"够便宜"的函数——判定标准是一条 **80 分的成本预算**。
>
> 本实验让编译器自己供词（`-gcflags=-m` 的 `can inline` / `cannot inline` + cost 值），再用三组对照（小函数 / 大函数 / 常数函数）量出内联到底值多少：**~1.1x、~1.0x、~4.3x**——第三组差距最大，才是内联的真正价值所在。

## Background

函数调用有真实开销：参数入栈/寄存器、call/ret（调用与返回指令）、返回值搬运。内联把被调函数体拷贝到调用点，这笔开销直接消失。

更重要的是它打开了跨过程优化的窗口——调用点周围的常量折叠（编译期把可算的式子直接算掉）、循环变换、逃逸分析（判断变量该分配在栈还是堆的分析）突然能"看穿"函数边界。但内联不是免费的：函数体会被复制到每一个调用点（二进制膨胀），profile（性能剖析数据）也难以归属到原函数。

所以编译器用成本模型挑三拣四。本实验做两组对照回答两个问题：**编译器凭什么收/拒**（用 `-gcflags=-m` 看诊断），以及**内联到底值多少**（用 `//go:noinline` 手动拆掉内联做计时对照）。

## What

**定义**：内联是编译器的一种自动优化：把被调函数的函数体直接拷贝到调用点，用一次"抄写"换掉一次函数调用。判定标准是成本预算——编译器给每个函数体算一个 cost（近似目标指令量的加权估算值），低于 80 就拷贝。

**心智模型**：可以把编译器想象成一个挑剔的抄写员：扫描每个调用点，给被调函数算 cost——**低于 80 预算就把函数体抄进调用点**（诊断输出 `inlining call to …`），随后常量折叠、逃逸分析在调用点上下文里看得更远。

超预算（cost 186 > 80）、`//go:noinline` 标记、`defer` 这类硬规则，则保持真调用。

但和人类抄写员不同的是：它的判定完全可复现——`go build -gcflags=-m` 能让编译器逐函数打印决策理由，不需要猜。

## When to Use

这套知识在三类时刻派上用场：

- 写热点路径上的小函数（取值器、薄封装、中转层）时：知道它们大概率被内联，放心封装而不用担心调用开销
- 做微基准或优化验证时：用 `//go:noinline` 拆出"无内联"对照组，量化优化到底来自哪一步
- 排查二进制膨胀、profile 里函数"消失"时：内联是常见原因，`//go:noinline` 是正规的调优开关

什么时候不用：

- 不必为了"凑预算"手动拆碎大函数——预算判定交给编译器，先用诊断确认再动手
- 大函数别指望内联提速：函数体本身占满运行时间，call 占比趋近于 0
- 别把"没被内联"直接当性能问题：先看 profile 与比值，再回头读诊断

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 依赖编译器自动内联 | 零代码改动，预算内自动生效 | 默认方式，绝大多数场景 |
| 手动复制代码展开 | 无 call 开销，但双份维护、易失同步 | 极少数确认的热点，且先量化再动 |
| `//go:noinline` 显式禁用 | 强制保持真调用 | 对照实验、保住 profile 归属、抑制二进制膨胀 |

## Quick Start

前置条件：仓库根目录下装有 Go 即可，无其他依赖。

```bash
cd internals/23_inline
go run main.go                          # 文本演示：三组 内联 vs noinline 计时对照
go run main.go -json                    # 输出 JSON 快照（ns/op 与比值）
go build -gcflags=-m main.go            # 看编译器报 can inline / inlining call to
go build -a -gcflags="-m -m" main.go    # -m -m 才报 cannot inline 的完整原因
```

编译器诊断节选（go1.26.5，诊断行是确定的；注意单层 `-m` 只报 `can`，`cannot` 的原因要 `-m -m`）：

```text
./main.go:65:6: can inline constForty
./main.go:37:6: can inline smallSum8
./main.go:43:6: can inline bigLoop
./main.go:74:19: inlining call to smallSum8
./main.go:92:16: inlining call to bigLoop
./main.go:40:6: cannot inline smallSum8NI: marked go:noinline
./main.go:70:6: cannot inline benchSmall: function too complex: cost 186 exceeds budget 80
```

计时对照节选（某次运行的 `-json` 输出；**ns/op 每次运行、每台机器都不同，看比值与趋势**）：

```json
{
  "smallInlineNs": 0.577, "smallNoinlNs": 0.660, "smallRatio": 1.14,
  "bigNs": 1.504, "bigNoinlNs": 1.515, "bigRatio": 1.01,
  "cfInlineNs": 0.221, "cfNoinlNs": 0.946, "cfRatio": 4.28
}
```

读数先看三个 Ratio：~1.14 / ~1.01 / ~4.28 对应小函数、大函数、常数函数三档。数值随机器/运行漂移（±15% 量级），稳定的是三档比值——下文按这三档逐一拆解。

## How It Works

### 成本预算 80：编译器的斤两秤

内联成本是对函数体 AST（抽象语法树，源码的树状表示）的一次加权估算（近似目标代码指令量），预算 80。本实验各函数的实测 cost：

| 函数 | `-m -m` 诊断 | 结论 |
|---|---|---|
| `constForty` | `can inline … with cost 2` | 极便宜，白送 |
| `smallSum8` | `can inline … with cost 16` | 8 参求和仍在预算内 |
| `bigLoop` | `can inline … with cost 56` | 循环不挡内联，56 < 80 |
| `benchSmall` | `cost 186 exceeds budget 80` | 整段裸循环 benchmark，超预算 |
| `smallSum8NI` | `marked go:noinline` | 显式禁用优先级最高 |
| 含 `defer` 的函数 | `unhandled op DEFER` | 硬规则，直接拒绝 |

注意 cost 不是语句数：一条循环体语句会记好几份（近似目标指令集（ISA）的指令量估算），所以"看着不长"的函数照样可能超 80。诊断输出里 `benchSmall` 的 `cost 186 exceeds budget 80`，就是这杆秤上的读数。

### 三组实测：内联到底值多少

1. **小函数 ~1.1x**：call 有真开销，但现代乱序 CPU（OOO，乱序执行）把大部分隐藏了——快，但不神话
2. **大函数 ~1.0x**：函数体本身占满运行时间，call 占比 ≈ 0，内联救不了大函数
3. **常数函数 ~4.3x**：内联的王牌——内联后编译器把 `acc += constForty()` 折叠成 `acc = 42·n`，**整个循环被删掉**

第三档与 Quick Start 输出里的 `cfRatio: 4.28` 互相印证：省 call 只值 1.1x，数倍收益来自内联解锁的常量折叠。

### 纠正一个常见误解：循环函数也会被内联

很多教材（含本目录旧注释）说"大函数/含循环的函数体量超预算、默认不内联"。实测 go1.26.5 并非如此：`bigLoop` 的 cost 只有 **56 < 80**，诊断明说 `can inline bigLoop`。

`benchBig` 里还发生了 `inlining call to bigLoop`——内联确实发生了。

"内联救不了大函数"的结论依然成立，但原因是**函数体开销占主导**，而不是"没被内联"——输出里 1.01 的 bigRatio，正是在"已内联 vs 真调用"之间量出来的。

### 内联与逃逸/reflect：不是拒绝，而是协作

流传的说法是"参数逃逸、用 reflect（Go 的运行时反射包）的函数会被拒绝内联"，go1.26 实测（探针程序 + `-m -m`）：

- 返回堆指针的函数照样 `can inline … with cost 11`——**逃逸不挡内联**；关系是反过来的：内联之后逃逸分析在调用点统一判定，小对象更容易留在栈上
- `reflect.ValueOf` 被拒是因为**cost 145 超预算**，属于普通超限而非"reflect 特判"
- 真正的硬规则是少数语法：`defer` → `unhandled op DEFER`，以及 `//go:noinline` 显式禁用

### 命令与标记速查

| 命令/标记 | 含义 | 为什么重要 |
|---|---|---|
| `//go:noinline` | 强制该函数不被内联 | 对照实验的开关；也用于保住 profile 归属（见 [22_pprof](../22_pprof/)）、抑制二进制膨胀 |
| `-gcflags=-m` | 编译器优化诊断（单层） | 只报 `can inline` / `inlining call to` |
| `-gcflags="-m -m"` | 两层诊断 | 才会报 `cannot inline` 的完整原因 |
| `-a` | 强制全部重编 | 构建缓存命中时诊断为空，必须加它才稳定复现 |
| `cost … budget 80` | 内联成本与预算 | 判定的唯一硬门槛（defer 等硬规则除外） |

## Pitfalls & Q&A

### 踩坑清单

- **别用 `bench(fn)(...)` 泛型/函数值测内联**：测出来的差异全是噪音
  - 原因：函数值调用等价于间接调用，内联直接被掐断
  - 解法：像 `main.go` 这样给每组写裸循环，让调用点静态可见
- **`-gcflags=-m` 的输出会缓存**：第二次构建诊断为空，误以为函数没被分析
  - 原因：构建缓存命中，编译器没真正重跑
  - 解法：加 `-a` 强制全部重编
- **预算单位别数错**：以为"语句不多"必然在预算内
  - 原因：cost 是指令量级估算不是语句数，循环体一条语句记好几份
  - 解法：判断只看诊断输出，不靠目测源码长度
- **看比值不看绝对值**：拿 ns 差异对照教科书数字，对不上
  - 原因：OOO 流水线会吞掉大部分 call 成本，±15% 的运行间波动是常态
  - 解法：只比较内联 vs noinline 的比值与趋势
- **fmt 字符串里的裸 `%`**：输出出现 `%!`（如 `%!(MISSING)`）
  - 原因：fmt 把裸 `%` 当格式动词的引导符
  - 解法：图表标题写 `ns/op` 这类不含裸 `%` 的文本

### 深入问答

**Q：怎么验证一个函数有没有被内联？**
A：`go build -a -gcflags="-m -m" main.go`。报 `can inline f with cost N` 只是"够便宜"，调用点出现 `inlining call to f` 才是真的内联了（命令细节见 Quick Start 与上文速查表）。

**Q：内联明明只是"复制代码"，为什么能带来 4 倍加速？**
A：复制本身省的 call 开销有限（小函数实测 ~1.1x）。数倍加速来自内联解锁的后续优化：函数边界消失后，常量折叠能把 `acc += 42` 的整个循环折叠成 `acc = 42·n`（实测 ~4.3x）。内联是"放大器"不是"加速器"。

**Q：为什么内联不是越多越好？**
A：函数体在每个调用点复制会膨胀二进制、伤害指令缓存；内联后函数在 profile 里"消失"，热点归因变难。所以 `//go:noinline` 是正经调优工具，不是摆设。
