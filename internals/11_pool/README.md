# 11 · sync.Pool：per-P 分片、victim 缓存与 GC 的两拍清理

> `sync.Pool` 是 Go 提供的临时对象复用器，但它不是普通对象池：生命周期与 GC 深度绑定。本篇用三组可复现的实测回答：它为什么快（per-P 无锁分片）、为什么 GC 后对象不是立刻消失而是"慢一拍"清理（victim 缓存）、为什么拿它当持久缓存一定失败。实测环境 go1.26.5。

## Background

高频路径上反复 `new` 大对象，GC 次数和堆分配量会随请求量线性上涨——分配越快，GC 越忙，吞吐被拖累。直觉解法是自己写个 `map` 当对象池，把对象攒起来重复用。

自建池有两个躲不开的问题：一是并发访问要加锁，热路径上一个全局锁会把复用的收益吃掉；二是回收时机没有好答案——对象留着占内存，删了下次又得重新构造。

`sync.Pool` 把这两件事都替你处理了：性能靠 per-P（processor，Go 调度器中执行 goroutine 的资源）无锁分片，清理靠 GC 两拍淘汰。理解这两层机制，才能解释它"有时明显提速、有时对象莫名丢失"的行为。

## What

`sync.Pool` 是 Go 标准库的临时对象复用器：并发安全、热路径无锁，且对象的存活期与 GC 周期绑定——最多跨一轮 GC，之后按两拍节奏被清空。

可以把 Pool 想象成每个工位自带的零件盒：用完的零件先放回自己盒里（private 槽），放不下就摆上共享架（shared 链），别的工位缺件可以来架上拿；但和真实零件盒不同的是，库存不保证一直在——每次 GC 把当前库存整体降级为待清，第二次 GC 后全部回收，缺件时只能现造（`New` 兜底工厂）。

心智模型一句话：Pool = 一撮 per-P 无锁分片（`local[]`，每 P 一份 `poolLocal`：private 槽 + shared 链）+ victim 缓存（上一轮 GC 留下的整体备份）+ `New()` 兜底。

Get 沿着"本 P private → 偷他人 shared → victim → New()"逐级下探，越靠前越快。

## When to Use

**在高频路径复用大临时对象、给 GC 减压时**。大 buffer、临时切片这类"构造贵、用完即弃"的对象最适合；标准库自己在 `fmt` 等高频路径上也是这么用的。

**在对象可以随时重置、不携带必须保留的状态时**。复用的前提是取出来后能便宜地清理成白纸。

何时不用：

- 需要持久存活的对象（连接池、结果缓存）——对象最多跨一个 GC 周期，跨两轮一定丢。
- 对象状态复杂、重置成本高时，复用收益盖不住清理成本。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| `sync.Pool` | 无锁分片 + GC 自动回收 | 高频临时对象，可随时重置 |
| 自建 map + Mutex 池 | 全局锁，回收时机自管 | 需要精确容量与持久存活 |
| chan 池 | 固定容量，取用阻塞 | 连接池这类需要限流/等待的 |

## Quick Start

前置条件：已安装 Go（实测 go1.26.5）。

```bash
cd internals/11_pool
go run main.go          # 文本演示：同轮复用 → GC 两拍 → GC 压力对比
go run main.go -json    # 输出 JSON 快照
```

预期输出（节选，Go 1.26.5 实测）：

```text
========== 1. 同一轮：Put/Get 复用同一个对象 ==========
   Get→Put→Get 拿到同一指针: true（New 只被调了 2 次）
   连续 3 轮 Get/Put 拿到的都是同一对象 = true

========== 2. GC 的两拍：victim 缓存延迟清理 ==========
   GC×1 后 Get → 捞出旧对象（blob.a=100, 是 seed=true）
   GC×2 后 Get → 触发 New（blob.a=7, 是 seed=false）

========== 3. 复用 vs 新建：GC 次数与总分配量 ==========
   Pool 复用 3000000 轮：GC 增量 0 次
   裸 new  3000000 轮：GC 增量 19 次，期间分配 72.1 MB
```

exp3 的分配量（72.1 MB / GC 19 次）随机器与调度会小幅漂移，量级稳定。

## How It Works

### 三层结构与 Get/Put 路径

- **Get**：先摸本 P 的 `private`（无锁）；没有就去别的 P 的 `shared` 尾部"偷"；再没有就翻 victim 缓存；还空才调 `New()`。
- **Put**：本 P 的 `private` 空就放进去，否则推入本 P 的 `shared` 链头。

同一轮 GC 周期内、同一个 P 上，Get/Put 就是两次内存读写。输出第 1 段"连续 3 轮 Get/Put 拿到的都是同一对象 = true"就是证据——你在输出里看到的稳定复用，来自 private 槽的独占读写。

输出里"New 只被调了 2 次"的原因：前一次 `Get` 把对象取走后没有还回，下一次 `Get` 只能触发 `New`。对象所有权是"尽力而为"。

### GC 的两拍清理：victim 延迟一拍

标准库在每次 GC 开始时执行 `poolCleanup`（此时处于 STW——stop-the-world，暂停所有 goroutine 的阶段）做两件事：先丢掉上一轮留下的 victim，再把当前 local 整体平移成 victim。

一个池对象的完整生命周期是：Put 进 local → 第一次 GC 后还能从 victim 捞回 → 第二次 GC 才彻底消失。输出第 2 段正是这个序列：GC×1 后 Get 捞回 seed（`是 seed=true`），GC×2 后 Get 触发 New（`是 seed=false`）。

### 复用收益：GC 次数归零

exp3 同样 300 万次操作对比两条路径。Pool 复用全程 0 次 GC；裸 `new` 用 `interface{}` 装箱（把值包装进接口的堆分配）强制逃逸（变量从栈分配改为堆分配）后触发 19 次 GC、累计分配 72.1 MB（72045624 B）垃圾——即输出第 3 段的两行。

复用把 GC 的工作量几乎清零，这就是"大对象循环复用"在吞吐上的意义。

### 关键字段与概念

| 字段/概念 | 含义 | 为什么重要 |
|---|---|---|
| `local[] poolLocal` | 每 P 一份分片：private 槽 + shared 无锁链 | 热路径零锁、零 CAS，Pool 快的全部来源 |
| `private` | 本 P 独占的槽位 | Get 第一优先级，Put 优先落点 |
| `shared` | 本 P 的无锁链（其他 P 可偷尾部） | 跨 P 平衡负载，仍是有限竞争 |
| `victim` | 上一轮 local 的整体备份 | GC 后第一拍还能捞回，两拍才清空 |
| `New func() interface{}` | 池空兜底工厂 | 对象所有权是"尽力而为"，必须设 |

## Pitfalls & Q&A

坑清单：

- **victim 按 P 分块，多 P 下结果是概率性的**。现象：GC 后有时第一轮也捞不回对象。原因：goroutine 可能漂到别的 P，它的 local 里没有你的对象。解法：实验锁定 `runtime.GOMAXPROCS(1)` 才能稳定复现"第一拍捞回 seed"。
- **`runtime.NumGC()` 不存在**。现象：编译报错。原因：GC 计数在 `runtime.MemStats.NumGC` 字段里。解法：`ReadMemStats` 前后各读一次取差值。
- **编译器会把裸分配优化没了**。现象：裸 new 组 300 万轮只分配 28 KB，对比失真。原因：`b := &blob{...}` 不外泄会被栈上化。解法：用 `interface{}` 装箱（`sink = b`）强制逃逸，才能制造真实垃圾。

**Q：sync.Pool 能当连接池/缓存用吗？**
A：不能。对象生命周期与 GC 绑定，最多存活一个 GC 周期；且 Get 不保证归还顺序、内容可能随时被清。要持久语义请用带锁的真实池或 `chan` 池。

**Q：怎么量化 Pool 的收益？**
A：同一工作量对比 `MemStats.NumGC` 增量与 `TotalAlloc`（累计分配字节数）：exp3 里 300 万轮复用 GC 增量 0 次，裸 new（强制逃逸）19 次、72.1 MB 分配。
