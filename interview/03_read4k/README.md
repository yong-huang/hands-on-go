# 03 · Read4K：跨调用缓冲管理的 4K 读取管线

> 这是一道经典面试题（LeetCode 157/158 "Read N Characters"）：底层 API `Read4(buf4)` 每次最多读 4 个字符，要求在其上实现 `Read(buf, n)` 读取 n 个字符。单调用版本人人会写，多调用版本才是考点——第一次 `Read(3)` 时 `Read4` 实际读了 4 个字节，剩下的 1 个必须缓存到下次调用。本实验用可运行的 Go 程序把这条"源 → 分块填充 → 缓冲 → 逐块处理 → 计数聚合"管线完整跑一遍，把跨调用状态与边界处理变成看得见的输出。

## 1. 为什么需要它

`Read4` 是操作系统/标准库分块读的缩影：底层永远按块（比如 4096 字节的页缓冲）搬运数据，而调用方要的是任意长度的 n。两者的差额不会消失，只会堆积——如果每次调用都把没读完的字节丢掉，数据就永久丢失了。所以这道题真正考察的是：

- **跨调用状态保持**：多读的字节必须存在实例字段里，而不是函数局部变量
- **边界 EOF 处理**：读到文件尾时如何优雅停机，且不重复读、不多读
- **易错点**：缓冲区还有剩余时误调 `Read4`，导致整块数据被覆盖丢失

**心智模型一句话**：`Reader` 是夹在调用方与 `Read4` 之间的一条 4 字节mini管线——`Read4` 把数据分块灌进 `buf[4]`，`Read` 优先消费缓冲区剩余（`pos < size`），不够才再调 `Read4` 补充，最后把复制字节数 `total` 聚合返回。`buf/pos/size/eof` 四个状态全部挂在结构体上，跨调用共享。

## 4. 核心概念

### 4.1 Reader：跨调用的状态容器

```go
type Reader struct {
    buf  [4]byte // 内部缓冲区
    pos  int     // buf 中下一个要读的字节
    size int     // buf 中有效字节数（Read4 的返回值）
    eof  bool    // 文件是否读完
}
```

单调用版本（LC157）读完即弃，不需要任何字段；多调用版本（LC158）必须把 `buf/pos/size/eof` 保存在结构体里，让下一次 `Read` 接着上次的进度走。这就是两个版本的本质分界。

### 4.2 Read：先吃缓存，再补货

```go
func (r *Reader) Read(buf []byte, n int) int {
    total := 0
    for total < n {
        if r.pos < r.size { // 1. 缓冲区有剩余，直接复制
            buf[total] = r.buf[r.pos]
            r.pos++
            total++
            continue
        }
        if r.eof { // 2. 文件已读完，退出
            break
        }
        r.size = Read4(r.buf[:]) // 3. 补货
        r.pos = 0
        if r.size == 0 { // 4. 补到 0 字节 = EOF
            r.eof = true
            break
        }
    }
    return total
}
```

循环四步的顺序不能换：**必须先检查 `pos < size` 再决定是否调 `Read4`**。`Read(3)` 时 `Read4` 一次灌 4 字节，第 4 字节留在 `buf` 里等下次——这就是"少读不丢字"的关键。

### 4.3 eof 与逐次对照

`Read4` 返回 0 是文件结束的唯一证据：置 `eof = true` 后，后续所有 `Read` 直接短路返回 0，不再碰 `Read4`。测试 2 的逐次管线对照：

| 调用 | 返回 | 缓冲区动作 |
|---|---|---|
| `Read(3)` #1 | `"Hel"` | `Read4` 灌入 `"Hell"`，取 3 剩 1（`"l"` 留在 buf） |
| `Read(3)` #2 | `"lo,"` | 先吃缓存 `"l"`，再 `Read4` 灌 `"o, W"`，取 `"o,"` 剩 `"W"` |
| `Read(3)` #3 | `" Wo"` | 先吃缓存 `"W"`，再 `Read4` 补充 |
| `Read(3)` #4 | `"rld"` | 同上 |
| `Read(3)` #5 | `"! T"` | 同上，缓存链始终连续 |

## 5. 关键字段与坑清单

| 字段/语句 | 含义 | 为什么重要 |
|---|---|---|
| `buf [4]byte` | 内部块缓冲 | 存放 `Read4` 多读的残字节，跨调用不丢 |
| `pos` | buf 内读游标 | `pos < size` 判定"还有缓存可吃" |
| `size` | buf 有效字节数 | 来自 `Read4` 返回值；为 0 即 EOF 证据 |
| `eof` | 结束标志 | 置位后短路返回 0，防重复读 |

坑清单：

- **顺序颠倒丢数据**：若先调 `Read4` 再检查缓存，残字节被整块覆盖，测试 2 从第 2 次起就断流
- **忘置 eof 导致死循环**：`Read4` 返回 0 后若不 `break`，`pos == size` 恒成立，循环空转
- **`n` 超过文件长度**：靠 `size == 0 → eof → break` 兜底，返回实际字节数（实测 45），不能假设返回 n
- **值接收者陷阱**：`Read` 必须用指针接收者 `*Reader`，否则每次调用复制的都是状态的快照，缓存永远传不下去

## 7. 面试要点

**Q：多调用版本和单调用版本的本质区别是什么？**
A：单调用（LC157）读一次就结束，多读的字节可以丢弃；多调用（LC158）必须用结构体字段（`buf/pos/size/eof`）保存跨调用状态，`Read4` 多读的部分要缓存到下次，否则数据丢失。

**Q：为什么 `pos < size` 的检查必须在调 `Read4` 之前？**
A：`Read4` 是整块覆盖式写入。如果缓冲区还有剩余（`pos < size`）就去"补货"，没消费完的字节会被新块覆盖，造成静默丢字。实测测试 2 的连续性依赖这个顺序。

**Q：`Read(100)` 但文件只有 45 字节，返回什么？为什么不会多读？**
A：返回 45（实测）。循环里 `Read4` 返回 0 时置 `eof` 并 `break`，`total` 停在真实读取数；eof 之后即使再调 `Read` 也直接返回 0，不会重读。

**Q：真实系统里 `Read4` 对应什么？为什么是 4 字节/4096 字节？**
A：对应内核页缓存与标准库的 `bufio` 分块读。块大小是系统调用的摊销单位——4096 正是一个内存页；本题用 4 字节是为了让"缓存残字节"的边界在几步之内就能人肉验证。

## 8. 总结

Read4K 的全部难度都在"状态归属"上：把 `buf/pos/size/eof` 从函数作用域提升到结构体作用域，多调用版本就自然成立；再守住"先吃缓存再补货"和"返回 0 即 EOF"两条边界，管线就既不丢字也不多读。验证方法不变——`go run read4k.go` 把每次调用的返回值与缓存动向打印出来，比背结论可靠。
