# 23 · error 基础：错误就是值，哨兵 + 包装 + errors.Is

> Go 没有 try/catch：错误是普通的内置接口 `error`，随返回值一路往上传，由调用方决定处理还是忽略。这个模型简单，但有一套必须掌握的配合技——哨兵错误定义锚点、`%w` 包装保留上下文与错误链、`errors.Is` 穿透包装做判定。读完本篇你将掌握这三件套的用法、自定义错误类型的写法，以及"裸比对失效、`%v` 断链"等典型坑的成因与解法。

## Background

异常语言（Java、Python 等，用 throw/try/catch 传递失败的方式）的做法是把错误抛出去，沿调用栈向上飞，谁想处理谁 catch。它的问题有二：错误可以无声穿透多层调用，中间层"忘了处理"没有任何痕迹；错误也不在函数签名里，调用方不看实现不知道会抛什么。

Go 的取舍是**错误是值**：错误作为普通返回值，被强制出现在每个调用点的视线里，不能被无声吞掉。`if err != nil` 写得多，换来的是每个可能失败的调用点都无法被跳过——编译器还会强制你处理或显式忽略。

但"返回错误"只是第一步。上层调用者还想加上下文（"在哪一层、带什么参数错的"），同时让底层仍能识别错误类别（"是不是除零"）。这两件事要同时成立，就需要错误包装与穿透判定的组合。

## What

Go 的错误处理模型可以概括为"错误即值"：`error` 是内置接口 `type error interface { Error() string }`，任何实现这个方法的类型都能当错误用，随函数返回值逐层上传。

这套模型有三件配合技：

- 哨兵错误（sentinel error，调用双方约定用于判定的固定错误值）：包级定义的"锚点"
- `%w` 包装：`fmt.Errorf` 在原错误外加上下文、同时保留链条
- `errors.Is`：沿链条逐层比对，穿透包装找到锚点

可以把 `%w` 包装想象成转发邮件时引用原文并加批注：每转发一层加一句"在我这层发生了什么"，原始邮件始终附在最下面。但和邮件引用不同的是，这条引用链是程序可比对的——`errors.Is` 能沿链逐层找到最初的锚点值。

**心智模型一句话**：哨兵错误是调用双方约定的"判定锚点"，`%w` 包装是"加上下文但保留链条"，`errors.Is` 沿链条逐层 `Unwrap` 找锚点——三者配合，错误才能既可读又可判。

## When to Use

- 写库或公共函数时：把可判定的失败定义成哨兵错误导出（如标准库的 `io.EOF`），调用方拿它做分支决策——重试、降级还是报错。
- 在中间层转述底层错误时：每一层用 `%w` 包装再上抛，日志带上"哪一层、什么参数"，同时不丢底层判定链。
- 需要携带结构化信息时：错误码、操作名、时间这类字段放进自定义 error 类型，调用方配合 `errors.As`（从错误链中取出指定类型错误的函数）读取细节。

何时不用哨兵/包装：

- 本地一次性处理、无人需要判定的错误：`fmt.Errorf` 直接生成一次性消息即可，不必立锚点
- 包内部的实现细节错误：导出哨兵等于把它们变成 API 承诺，不该判定的就别导出
- 真正不可恢复的程序性错误：那属于 panic 的领域，不是返回错误

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 哨兵错误（包级 `errors.New`） | 固定锚点值，可跨包判定类别 | 错误类别少、调用方需要分支（如 `io.EOF`） |
| `%w` 包装 | 逐层加上下文，保留判定链 | 中间层转述底层错误 |
| 自定义 error 类型 | 携带结构化字段 | 调用方要取出错误码等细节（配合 `errors.As`） |
| 一次性 `fmt.Errorf` | 只有消息，无锚点 | 本地处理、无需判定 |

```bash
cd concepts/23_error_basics
go run main.go
```

真实输出（共 19 行，节选）：

```text
========== 1. 正常路径：err == nil ==========
10 / 4 = 2.5（err == nil，走正常分支）

========== 2. 哨兵错误 + %w 包装 + errors.Is 判定 ==========
err 本体: safeDivide(1, 0): division by zero
== 裸比对（已失效）: false
errors.Is 穿透包装（推荐）: true
→ 判定为除零：请把分母换成非零值后重试

========== 3. error 是接口：自定义类型也是 error ==========
err2 = query failed (code 404)（动态类型 *main.OpsError，实现了 Error() string）

========== 4. 错误必须被处理或显式忽略 ==========
v, _ := safeDivide(9, 3) → v = 3（err 被 _ 显式丢弃）
```

核心代码就两个声明。这段在做什么：定义哨兵错误，并在除零时用 `%w` 把它包装后返回：

```go
// ErrDivisionByZero 是哨兵错误：包级变量，调用方拿它做判定锚点
var ErrDivisionByZero = errors.New("division by zero")

// safeDivide 除零时不返回裸哨兵，而是用 %w 包装：既保留原文，又保留判定链
func safeDivide(a, b float64) (float64, error) {
	if b == 0 {
		return 0, fmt.Errorf("safeDivide(%g, %g): %w", a, b, ErrDivisionByZero)
	}
	return a / b, nil
}
```

## How It Works

### 哨兵错误：包级错误值做锚点

`var ErrDivisionByZero = errors.New("division by zero")` 定义在包级，是调用双方都认识的固定值。库函数返回它（或它的包装），调用方拿它做判定。命名惯例是 `Err` 前缀。

### `%w` 包装：上下文与链条兼得

`fmt.Errorf("safeDivide(%g, %g): %w", a, b, ErrDivisionByZero)` 返回一个**新错误**：消息带上了参数上下文，内部通过 `Unwrap()` 链接着原哨兵。

两个反面正好对应输出第 2 节的两行：

- `%v` 只拼字符串不建链，`errors.Is` 从此判不中
- 包装后的错误 `==` 裸哨兵也判不中——输出里的 `== 裸比对（已失效）: false` 就是证据

### `errors.Is`：沿链穿透比对

`errors.Is(err, ErrDivisionByZero)` 先比 `err` 本身，不等就调 `err.Unwrap()` 取下一层继续比，直到命中或链尽。所以它对"包了多少层"无感——输出里的 `errors.Is 穿透包装（推荐）: true` 就来自这条逐层比对。这是错误链体系里最常用的判定入口。

### error 只是接口

`type error interface { Error() string }`——任何类型实现这个方法就是 error。

demo 里的 `OpsError{Op, Code}` 用指针接收者实现 `Error() string`，`var err2 error = &OpsError{...}` 直接成立，`%T` 打出 `*main.OpsError`（输出第 3 节的动态类型）：

```go
// OpsError 是自定义 error 类型：error 本质是接口，实现 Error() string 即可
type OpsError struct {
	Op   string // 出错的操作名
	Code int    // 业务错误码
}

func (e *OpsError) Error() string { return fmt.Sprintf("%s failed (code %d)", e.Op, e.Code) }
```

这也是标准库 `*errors.errorString`、`*fmt.wrapError` 的共同底座。

### 关键语法速查

| 语法 | 含义 | 为什么重要 |
|---|---|---|
| `errors.New("...")` | 创建消息式错误 | 定义哨兵 / 一次性错误 |
| `fmt.Errorf("...: %w", err)` | 包装并保留错误链 | 上层加上下文的标准姿势 |
| `errors.Is(err, target)` | 沿 Unwrap 链比对 | 包装后判定的唯一可靠入口 |
| `err == ErrXxx` | 指针/值直比 | 只对未包装错误有效，包装后失效 |
| `v, _ := f()` | 显式忽略错误 | 唯一合法的"不处理"写法 |
| `Error() string` | error 接口唯一方法 | 任何类型实现即可当错误用 |

## Pitfalls & Q&A

踩坑清单，每条按"现象 → 原因 → 解法"展开：

- **包装后 `err == 哨兵` 是 `false`**。现象：判定分支进不去，走了兜底逻辑。原因：`fmt.Errorf` 返回新值，直接比值必失手。解法：改用 `errors.Is`，demo 第 2 节可复现。
- **`fmt.Errorf` 手滑写成 `%v`**。现象：下游所有 `errors.Is` 判不中。原因：错误链断在这一层，`%v` 只把消息拼进字符串。解法：需要保留判定链时永远用 `%w`。
- **接了错误却没用**。现象：`declared and not used` 编译错。原因：Go 强制错误被处理或显式忽略。解法：不处理就写 `_`（demo 第 4 节）。
- **哨兵错误变量被重新赋值**。现象：判定错乱、间歇失效。原因：锚点值变了，旧引用全部失配。解法：把它当常量对待，不要改写。
- **自定义 error 类型的接收者不一致**。现象：类型断言与 `errors.As` 判不中。原因：值接收者与返回时取地址/不取地址不统一，动态类型对不上。解法：定义时固定一种接收者形式并保持一致。

**Q：为什么 Go 用返回错误而不是异常？**

A：错误走返回值，控制流显式可见，`if err != nil` 让每个可能失败的调用点都无法被跳过；异常则允许错误无声穿透多层调用。代价是代码略啰嗦，收益是不会"忘了处理"——编译器还会强制你处理或显式 `_`。

**Q：`errors.Is` 和 `==` 到底差在哪？**

A：`==` 只比较当前值；`errors.Is` 沿 `Unwrap()` 链逐层比较，且对实现 `Is(error) bool` 的错误类型调用其自定义判定。未包装时两者等价，一旦中间有人 `%w` 包装，`==` 即失效。

**Q：哨兵错误和自定义错误类型怎么选？**

A：错误类别少、无需携带数据 → 哨兵（如 `io.EOF`）；要带结构化信息（错误码、操作名、时间）→ 自定义类型，配合 `errors.As` 取出字段。

两者可叠加：类型内部也可以 `Unwrap` 到哨兵。更长的包装链与 `errors.As` 溯源见 [24_error_chain](../24_error_chain/)。

**Q：`%w` 可以包装多个错误吗？**

A：可以。Go 1.20 起 `fmt.Errorf` 支持多个 `%w`，错误形成树而非链，`errors.Is` 会遍历整棵树逐一匹配；更早版本一层只能一个 `%w`。
