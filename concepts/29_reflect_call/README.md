# 29 · 反射动态创建与调用：reflect 不仅能看，还能造与调

> 反射（reflect，Go 标准库里在运行时读取和操作类型信息的包）最常见的用法是"读"结构体字段（见 [27_reflect_basics](../27_reflect_basics/)），它还有更主动的一面：在只有类型信息、没有任何实例的运行时，凭空 `reflect.New` 造出实例、按名字字符串 `MethodByName` 找到方法、`Call` 打包参数调用并拆包返回值——插件系统、RPC 框架与序列化库的核心机制。读完你能跑通"造实例 → 按名调方法 → 调普通函数"的完整链路，并守住防 panic 的自检纪律。

## Background

业务代码里调用方法从不需要反射：`g.Greet("Tom")` 一行就够，编译器顺带检查方法是否存在、签名是否匹配。调用目标在编译期写死，是一切的前提。

但有一类调用的目标，要到运行时才有人告诉你：插件按名字注册命令、RPC server 按方法名派发请求、测试框架按约定名执行用例。编译期根本不存在这次调用，编译器无从检查，普通的函数调用语法无从下手。

`reflect` 为此提供了"运行时函数指针"能力：类型当图纸、名字当索引、`Call` 当扳手。net/rpc、text/template 与各类依赖注入框架的派发层，底层都是这套机制。代价也由此而来——慢约一个数量级，且失去编译期检查。

## What

反射动态创建与调用，是在只有类型信息、没有实例的运行时完成三步：`reflect.New` 从类型造出实例，`MethodByName` 按名字字符串找到方法，`Call` 打包参数、执行并拆包返回值——合起来相当于把函数指针搬进了运行时。

心智模型一句话：`reflect.Type` 是图纸，`reflect.New` 照图纸造实例，`MethodByName` 用字符串当索引进方法表，`Call` 把参数与返回值统一打包成 `[]reflect.Value` 搬运——普通函数与方法走的是同一套流程。

可以把这套机制想象成"照图纸施工"：图纸（Type）画清结构，施工队照图盖出毛坯房（New），按门牌号找到负责的承包商（MethodByName），下单开工、按单验收（Call）。但和施工不同的是，单据上的每个参数都必须与图纸规格逐位匹配——个数或类型对不上，工地当场停工（panic），没有协商余地。

## When to Use

- 写插件系统时：外部注册的命令名到运行时才知道，用 `MethodByName` 按约定名（如 "Handle" 拼接命令名）找到入口并调用。
- 写 RPC 框架时：请求里带着 "Service.Method" 字符串，服务端按名字派发到 handler——net/rpc 的核心派发逻辑。
- 写模板引擎或测试框架时：`template.Execute` 要调用数据对象上的任意方法，测试框架按命名约定执行用例，调用目标都由数据决定。

何时不用：

- 签名编译期已知：直接调用，让编译器检查。反射调用慢约一个数量级，还把错误从编译期推迟到运行时。
- 类型集合可枚举：定义接口加类型断言能满足时不要上反射——断言的成本低得多。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 直接方法调用 | 编译期查签名，零额外开销 | 调用目标编译期已知 |
| 接口 + 类型断言 | 运行时一次判定，成本低 | 能力能枚举成接口方法集 |
| 代码生成 | 把动态调用搬到编译期，运行时走普通代码 | 调用图可预知但手写重复 |
| 反射调用 | 按名字调用运行时才确定的方法 | 插件、RPC 派发等真正动态的边界 |

## How It Works

### reflect.New：从类型到实例

`reflect.New(t)` 接收 `reflect.Type`，返回一个指向新分配零值的 `Value`（指针类型）。

要写字段必须先 `Elem()`（解引用指针，落到可写的本体上）：`Elem().FieldByName("Prefix").SetString("Dr. ")`。

最后 `Interface()` 把 `Value` 还原成 `any`，再用类型断言取回静态类型——`New` 给的是指针，断言目标要写 `*Greeter`。

输出第 1 段的 `动态创建: Dr. Who | 字段 = true` 正是这条链的结果：实例是 `New` 造的，`Dr. ` 前缀是 `SetString` 写进去的。

### MethodByName：字符串当索引进方法表

`v.MethodByName("Greet")` 按名字查方法，返回一个"绑定了接收者"的函数 `Value`。名字拼写错误编译器帮不上忙，所以查完先 `IsValid()` 确认存在——输出第 2 段的 `方法存在: true` 就是这道自检。

在指针值上查询能覆盖值接收者与指针接收者的完整方法集；在值上查询则只能看到值接收者方法。

### Call：参数与返回值都是 []reflect.Value

调用前把每个参数用 `reflect.ValueOf(x)` 包装进切片；`Call` 执行后返回 `[]reflect.Value`，按声明顺序拆包：`results[0].String()`、`.Int()` 等。

签名不匹配不会静默——个数或类型对不上直接 panic，所以动态调用前先 `fn.Type()` 检查 `NumIn/NumOut`（参数个数与返回值个数）。

输出第 3 段的 `签名: func(int, int) int | in = 2 | out = 1` 打印的就是这次签名检查，随后的 `add(2, 40) = 42` 是从返回切片里拆包取回的值。

### 普通函数与方法走同一套流程

`reflect.ValueOf(add)` 直接把函数转成 `Value`，后面的 `Type` 检查与 `Call` 流程和方法完全一致——普通函数只是少了接收者的特例。

`template.Execute` 调用数据上的任意方法、RPC 框架按 "Service.Method" 字符串派发到 handler，原理都止于此。输出第 4 段的 `直接调用: Dr. Watson | 与反射结果一致: true` 是同一调用的静态写法对照。

### 代价：慢约一个数量级，且失去编译期检查

反射调用要做名字查找、参数打包、接口装箱（值被拷贝进接口的数据指针）与签名校验，基准测试通常显示比直接调用慢 10 倍上下；更重要的是错误从编译期推迟到了运行时。热路径（程序反复执行的高频代码段）不要用反射调用，框架代码在初始化期做一次、缓存住 `Value` 再用是常见折中。

底层 `Value` 的内存布局与调用机制见 [../../internals/27_reflect/](../../internals/27_reflect/)。

### 关键 API 速查

| API | 含义 | 为什么重要 |
|---|---|---|
| `reflect.New(t)` | 分配零值，返回指针 Value | 从类型凭空造实例的唯一入口 |
| `ptr.Elem()` | 解引用拿到可 Set 的本体 | 不 Elem 直接 FieldByName 会 panic |
| `MethodByName(name)` | 按名字查绑定方法 | 无效名返回零 Value，用 IsValid 判断 |
| `Call(args []Value) []Value` | 调用并取回结果 | 参数必须逐个 ValueOf 包装 |
| `ValueOf(fn).Type()` | 动态读签名 | NumIn/NumOut 先检查再调用，防 panic |

## Pitfalls & Q&A

坑清单（每条均可复现）：

- **断言目标写成值类型**。现象：`reflect.New(t).Interface().(Greeter)` panic。原因：`New` 返回的是 `*Greeter` 指针。解法：断言目标写 `.(*Greeter)`。
- **在值上查指针接收者方法**。现象：`MethodByName` 拿到零 Value，`IsValid` 为 false。原因：值的方法集不含指针接收者方法。解法：在指针上查询，覆盖完整方法集。
- **参数类型逐位不匹配**。现象：`Call` 时直接 panic。原因：参数切片里的 `Value` 类型必须与签名逐位匹配（int ≠ int64）。解法：包装参数前用 `fn.Type()` 核对个数与类型。
- **返回值拆错下标或取值方法用错**。现象：拿到零值而非报错。原因：`Call` 返回值要按序拆包（`.String()`/`.Int()`），类型用错不报错。解法：对照签名核对下标与取值方法。
- **方法名未导出**。现象：`IsValid` 返回 false，查不到方法。原因：未导出方法（小写开头）不在反射方法集里。解法：反射只调导出方法。

**Q：为什么 `reflect.New` 返回指针而不直接返回值？**

指针让实例可寻址、可 `Set`。若返回值，`Elem()` 得到的是不可地址化的临时值，`FieldByName(...).SetXxx` 会直接 panic——与"从 map 取出的字段不能 Set"是同一条可寻址性规则。

**Q：`Method(i)` 和 `MethodByName` 有什么区别？什么时候用前者？**

`Method(i)` 按下标取方法，`MethodByName` 按名字取；前者适合遍历方法集（如自动注册路由），后者适合按约定名调用（如 "Handle" + 命令名拼接）。多次调用同一方法时，应把方法 `Value` 缓存起来，省掉每次的名字查找。

**Q：反射调用到底慢在哪？**

每步都有开销：名字哈希查方法表、参数逐个装箱成 `reflect.Value`（可能触发堆分配）、运行时签名校验、通过 `callReflect`（runtime 里反射调用的内部路径）走一条与编译器生成代码完全不同的慢速调用路径。

实测常见差距在 10~100 倍，热路径的正确做法是初始化期解析一次并缓存，或改用代码生成。

**Q：既然又慢又容易 panic，标准库为什么大量用它？**

慢是"每次调用"的成本，框架用它的是"每条路由/每个类型解析一次"的低频路径，随后高频执行走的仍是普通函数值。用运行时的灵活性换编译期的安全性，在框架边界是划算的交易——自己的业务代码停在类型断言（见 [26_iface_assert](../26_iface_assert/)）就够的那一层即可。
