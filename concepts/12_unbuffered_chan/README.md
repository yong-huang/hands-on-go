# 12 · 无缓冲 channel：发送与接收必须在同一瞬间握手

> 无缓冲 channel（容量为 0 的 Go 通信原语）是 Go 里最纯粹的同步原语：它不存任何值，每次发送都必须等到一个接收方就绪才能完成——两个 goroutine（Go 的并发执行单元）在那一刻"会合"（rendezvous）。读完本篇，你能跑通 ping/pong 严格交替接力，掌握"发送完成的瞬间就是接收发生的瞬间"这条保证，以及 close 与接收第二返回值的收尾写法。

## Background

有共享就要有同步。两个 goroutine 交换数据时，如果只靠"猜对方跑到哪了"，写出来的就是依赖时序的脆代码——今天能跑，换个机器、换个负载就出错。

在没有语言级同步通道之前，让两个执行流严格交替只有两条路：`time.Sleep` 猜时间间隔——对方一慢就错；或加互斥锁——锁（同一时刻只允许一个持有者的同步原语）能保证互斥，却不编排"谁先谁后"的顺序。

缺的是一种把"先后"写进语义的手段：发送方停在那一步，直到另一端真正接住，才放行下一行代码。

Go 的无缓冲 channel 把这条保证做成了语言语义：`ch <- v` 这一行不返回，直到另一端恰好有人执行 `<-ch`。"发送方阻塞到接收方就绪"不再是调用方额外保证的事，而是语言保证的事——本篇的严格 ping/pong 交替就是这条保证的直接产物。

## What

**定义**：无缓冲 channel 是容量为 0 的 channel（Go 里用于 goroutine 之间传值的通信原语）：它不存任何值，每次发送必须等到接收方就绪才能完成；发送与接收在时间上重合的那一刻称为会合（rendezvous）。阻塞（暂停执行直到条件满足）是它的默认行为。

**心智模型一句话**：无缓冲 channel 是一次"击掌"而不是一个"信箱"——两只手（send 与 recv）必须同时伸出，值在击掌瞬间直接从一方交到另一方，channel 本身不存放任何东西。

可以把无缓冲 channel 想象成击掌：一个人伸出手干等不算完成，双方手掌相触、物品交接、动作才算结束。但和现实击掌不同的是，这两只手可以相隔任意远——只要都伸向同一个 channel，运行时负责把值递过去；而且谁先到谁原地等待，不存在"扑空"。

它由三个配套件构成：发送 `serve <- i`、接收 `n, ok := <-serve`、关闭广播 `close(serve)`——三者合起来才撑得起完整的接力与收尾。

## When to Use

这份判断力在三类场景用得上：

- 需要"交接确认"的步骤编排时：上一步没被接住就不准开始下一步——流水线阶段之间的握手、严格交替的回合制逻辑（如本篇的 ping/pong）
- 用 done channel 收尾时：`close(done)` 广播结束信号、`<-done` 等待 goroutine（并发执行流）完全退出，是 Go 的惯用法
- 需要背压（下游处理不完时把压力传回上游、让上游自动等待）时：发送方停在发送上，天然形成节流

何时不用：

- 需要解耦生产消费速率、容忍突发流量：选有缓冲 channel——"发送完成"与"接收方就绪"解耦，削峰场景的对口工具
- 只想保护共享状态的读写、不关心先后编排：互斥锁更直接

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 无缓冲 channel | send 等到 recv 才完成，天然同步点 | 要交接确认、步骤编排、结束广播 |
| 有缓冲 channel | 值滑进缓冲即返回，速率解耦 | 削峰、容忍突发（见 [13_buffered_chan](../13_buffered_chan/)） |
| 互斥锁 | 保护共享状态，不编排顺序 | 只需互斥、无需交接 |

## How It Works

### 会合：send 与 recv 同时就绪才放行

`ch := make(chan int)`（容量 0）后，`ch <- v` 会阻塞，直到某个 goroutine 执行 `<-ch`；反之亦然。两者在时间上重合的那一刻，值直接从发送方栈（函数运行时的内存区域）复制到接收方栈，channel 中间不留副本。这就是"用通信来共享内存"的最小实现。

### 握手即同步点

本 demo 用两个无缓冲 chan 交替接力：`serve` 传递回合数（ping 发球），`ball` 传回确认（pong 回球）。`serve <- i` 不返回，pong 就没收到球；`<-ball` 不返回，下一轮发球就不会开始——**两个方向各是一次握手，合起来构成严格交替**。

你在输出里看到的序号 1..10 严格递增、绝不跳号，就来自这里的双重握手：每次打印之前，发球与回球都已经各完成一次"同时到场"。

### 结束：close + 接收的第二返回值

无缓冲 chan 不会自己"空"，要结束就得显式 `close(serve)`。pong 侧用 `n, ok := <-serve` 感知：`ok=false` 表示已关闭且再无值可收，于是退出并 `close(done)` 广播给 main。`<-done` 让 main 等 pong 完全退出，程序才干净结束。

### 对照：换成有缓冲就失去这层握手

`make(chan int, 1)` 的 `ch <- 42` 会立即返回——值滑进缓冲区，接收方此刻不必存在。"发送完成"与"接收方就绪"从此解耦，本 demo 的严格交替保证随之消失。

有缓冲的适用场景（削峰、解耦生产消费速率）与满/空/关闭三个状态的切换，见 [13_buffered_chan](../13_buffered_chan/)。

语法速览：

| 语法 | 含义 | 为什么重要 |
|---|---|---|
| `make(chan int)` | 无缓冲（容量 0） | send 阻塞到 recv 就绪，天然同步点 |
| `serve <- i` | 发送（阻塞） | 对端不在 `<-serve` 上等，这行就走不动 |
| `n, ok := <-serve` | 接收 + 关闭探测 | `ok=false` 表示已关闭且无值 |
| `close(serve)` | 关闭 channel | 只应由发送方关闭；关闭后可收尽剩余值 |
| `<-done` | 等待结束信号 | 配合 `close(done)` 实现 goroutine 汇合 |

## Pitfalls & Q&A

坑清单，每条按"现象 → 原因 → 解法"展开：

- **现象**：main 里先 `ch <-` 而接收方还没 `go` 出去，程序直接挂掉。**原因**：无缓冲 chan 在双方都到齐之前谁也不放行，全部 goroutine 都在等待时报 `fatal error: all goroutines are asleep`——这就是死锁（所有执行流互相等待、谁也无法推进的状态）。**解法**：先把接收方 `go` 出去，再发送。
- **现象**：panic: send on closed channel，或重复 close 报 panic（向上传播的运行时错误）。**原因**：关闭是发送方的专属动作，接收方 close 与重复 close 都不合法。**解法**：只由发送方调用一次 close。
- **现象**：从已关闭的 chan 接收，拿到的是零值而不是阻塞。**原因**：关闭后的接收立即返回零值 + `ok=false`，这是定义行为。**解法**：用第二返回值区分"真零值"与"已关闭"。
- **现象**：以为 `make(chan int, 1)` 还是无缓冲，结果交替保证失效。**原因**：无缓冲 ≠ 队列长度 1——容量 1 是有缓冲，`ch <- 1` 能立即返回。**解法**：要握手语义就用不带容量的 `make(chan T)`。
- **现象**：demo 改坏后编译不过：变量声明了没用。**原因**：未使用的变量是编译错；demo 里每个 chan（serve/ball/done）都被真实收发过。**解法**：删掉没用的 chan，或补上收发路径。

**Q：为什么无缓冲 channel 被称为"同步"channel？**

A：因为它把"数据到达"与"双方都就绪"绑成同一时刻：send 返回时，值不仅已发出，而且**已被接收**。你可以把它当作带数据的同步屏障（所有参与方到达后才一起放行的同步点）用——本篇的交替控制正是这种用法。

**Q：值在 channel 里"存"在哪儿？**

A：不存。运行时把发送方的值直接复制到接收方（必要时经 sudog——runtime 内部表示"等待中的 goroutine"的结构——临时持有），无缓冲 chan 只是会合的媒介。对比有缓冲 chan 的环形缓冲区（固定大小、首尾相接的缓冲结构），这是两者最本质的实现差异。

**Q：怎么证明 send 确实等到了 recv？**

A：把 demo 的序号打印换成发送前/发送后各打一个时间戳，会发现 `serve <- i` 完成时刻总与 pong 的收球动作衔接；若把任一端注释掉，程序直接死锁而不是"先跑一段再停"。另外要分清：给无缓冲 chan 找不到对端就发送，结果是死锁，不是排队。
