# 08 · Goroutine 泄漏检测：让泄漏在 NumGoroutine 里现形

> goroutine（Go 的并发执行单元）没有父对象等它结束：`go` 出去之后，谁也不负责回收它。泄漏的本质只有一句话——goroutine 永久阻塞在一个"再也不会就绪"的操作上，或跑在一个永不返回的循环里。本篇用 `runtime.NumGoroutine()` 当仪表盘，把三种典型泄漏态和各自的修复对照跑通，读完可以掌握一套用计数差值确认泄漏的最小方法论。

## Background

goroutine 的启动成本极低，`go f()` 一行就有一个新的执行流。代价是它完全自治：何时结束由自己决定，没有任何父对象负责等待或回收它。

这带来一种静默的失败模式：泄漏的 goroutine 不崩溃、不报错，只是让存活计数悄悄上涨、内存慢慢变多——直到服务长跑几天后 OOM（out of memory，内存耗尽）。

在缺乏观测手段时，确认"是不是漏了"只有两条重路径：

- 给服务接入 pprof（Go 自带的运行时剖析工具），在内存已经上涨之后抓 goroutine profile 看阻塞栈
- 等内存指标告警后重启，用"重启后恢复正常"间接佐证

两者都是事后动作，回答"现在是不是正在漏"要付出等待成本。而 `runtime` 包里其实一直躺着一个零依赖的计数器——`runtime.NumGoroutine()`，返回全进程存活 goroutine 总数。

围绕这个读数可以搭出最小确认闭环：先记一次操作前的读数，制造嫌疑操作，等待片刻再读一次——增量不回落，就是泄漏的最小可复现证据。

## What

**定义**：goroutine 泄漏是一种资源滞留 bug——goroutine 永久阻塞在一个"再也不会就绪"的操作上，或跑在一个永不返回的循环里；泄漏检测则是用存活计数的差值，把这种滞留变成可观测的数字。

**心智模型一句话**：goroutine 只有"返回了才算结束"一条正常出口；发送阻塞、接收阻塞、死循环三种泄漏态都卡在出口之前，而观测的手段就是泄漏前后 `runtime.NumGoroutine()` 的差值不回落。

可以把 goroutine 想象成一名没有主管的值班员：上岗（`go` 启动）不需要任何人批准，离岗只有"把手头那件事办完并返回"一条通道。但和有排班表的公司不同的是，runtime 不会替超时的值班员强制收工——它卡在一件永远不会发生的事上时，会永远占着工位。

## When to Use

这份判断力在三类场景用得上：

- 排查常驻服务"内存缓慢上涨、长跑数天后 OOM"这类慢性问题时，先用计数差值确认是不是 goroutine 泄漏，再决定要不要上 pprof 定位
- 写或 review 并发代码时，对照三种泄漏态的形态——无接收的发送、无发送且不 close 的接收、缺退出条件的循环——检查每个 `go` 出去的函数有没有保证可达的返回路径
- 在压测前后各读一次存活计数，对比差值，为服务建立并发规模与 goroutine 数量的对照关系

何时不用：

- 短命命令行工具：main 返回即进程退出，所有 goroutine 被整体丢弃，泄漏来不及造成伤害
- 只想回答"漏在哪"时：差值法只回答"有没有"，定位具体阻塞点要用 pprof 的 goroutine profile

观测方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| `NumGoroutine` 差值法 | 零依赖、只回答"有没有漏" | 第一步筛查：确认泄漏存在 |
| pprof goroutine profile（`/debug/pprof/goroutine`） | 给出每个 goroutine 的阻塞栈分布 | 差值确认泄漏后定位"漏在哪" |
| goleak 一类测试期检测（在 TestMain 里比对计数） | 自动在每个测试结束后检查新增残留 | 在单元/集成测试里防止泄漏回归 |

## How It Works

### 基线 → 观测窗口 → 差值

`runtime.NumGoroutine()` 返回全进程存活 goroutine 数。单次读数没有意义，有意义的是**差值**：

1. 操作前记基线（一次普通读数）
2. `time.Sleep(100*time.Millisecond)` 给调度器留出观测窗口——等泄漏形态稳定的时间段
3. 再读一次，增量 >0 且不再回落，就是泄漏的最小可复现证据

100ms 是演示用的经验窗口，生产里通常在压测前后各读一次做对比。你在输出第 1 段看到的"基线 goroutine 数: 1"，就是循环启动前读的那一次。

### 泄漏态一：发送阻塞

`ch := make(chan int); ch <- 1`——无缓冲 channel（容量为 0、收发必须同时就绪的管道）的发送会一直挂起，直到有接收者。接收者永远不来，goroutine 就永久停在 Gwaiting（runtime 中等待事件就绪的状态）。

修复：给缓冲 `make(chan int, 1)`（发送即完成），或保证对端存在（如 `select`——同时监听多个 channel 操作的语句——配合超时/退出信号）。输出第 1 段"+0，缓冲吸收了那次发送"就是缓冲修复的验证。

### 泄漏态二：接收阻塞

`<-make(chan int)`——无缓冲 channel 的接收同样挂起等待发送者。修复：由**发送方**负责 `close(ch)`，接收方读到零值（`v := <-ch` 得 `0`）后自然继续/退出；这也是 `for range ch` 能随 close 退出的前提。

输出第 2 段"+0，发送方 close 解除阻塞"对应这条路径。

### 泄漏态三：死循环

`for {}` 没有退出条件，goroutine 永远处于运行态，连阻塞都算不上——它一直消耗调度时间片。修复：`select` 监听 `ctx.Done()`，`cancel()` 一调用就从 `Done` 分支 `return`，计数回落。

这是 `context`（标准库里跨调用传递取消信号的类型）取消传播的标准用法，输出第 3 段的"cancel +100ms: +0"即其验证。

### API 速览

| API / 语法 | 含义 | 为什么重要 |
|---|---|---|
| `runtime.NumGoroutine()` | 当前存活 goroutine 总数 | 零依赖的泄漏仪表盘 |
| `ch <- v`（无缓冲） | 阻塞直到接收者就绪 | 无人收 = 永久挂起 |
| `<-ch`（无缓冲） | 阻塞直到发送者就绪 | 无人发且不 close = 永久挂起 |
| `close(ch)` | 广播"不会再发了" | 接收方据此退出循环/继续执行 |
| `ctx.Done()` | 取消信号 channel | 死循环/长任务的唯一体面出口 |
| `select { case <-ctx.Done(): return ... }` | 可取消的循环骨架 | 把退出条件显式化 |

## Pitfalls & Q&A

踩坑清单（均可在 demo 中复现，每条按"现象 → 原因 → 解法"展开）：

- **现象**：服务长跑数天后内存持续上涨。**原因**：泄漏的 goroutine 不会被 GC（garbage collection，自动内存回收）回收——它阻塞在活跃的 channel 引用上，channel 也随之无法回收，形成连带泄漏。**解法**：先差值确认，再按三种泄漏态逐一修复返回路径。
- **现象**：两段嫌疑代码各差值 +1，合跑却得到说不清的总差值。**原因**：`NumGoroutine` 读的是**全进程**计数，并发段多时差值互相污染。**解法**：观测窗口内别混入其他 goroutine，一次只验证一段。
- **现象**：给 channel 加了缓冲，仍出现发送阻塞。**原因**：缓冲大小 ≠ 接收能力，容量满后照样阻塞，demo 里用缓冲只是演示手段。**解法**：生产代码用 `select` 让发送与退出信号同时待命。
- **现象**：发送方不再发数据后，接收方的 goroutine 仍不退出。**原因**：`for range ch` 只在 **close** 后退出，仅"不再发送"不够——这是接收阻塞泄漏最常见的来源。**解法**：由发送方负责 `close(ch)`。
- **现象**：调用了 `cancel()`，死循环还在转。**原因**：循环里的 `default` 分支如果不检查 `ctx.Done()`，取消信号永远没机会被处理。**解法**：把 `<-ctx.Done()` 放进 `select`，并避免 `default` 分支永远抢占。

**Q：为什么泄漏的 goroutine 不能被 GC 回收？**

A：GC 判断"不可达"才回收，而阻塞中的 goroutine 栈上还引用着 channel，channel 又被彼此引用——整条引用链从"正在等待"的 goroutine 出发全是可达的。只要它没返回，这套对象就一个都释放不掉。

**Q：`NumGoroutine` 不涨就一定没泄漏吗？**

A：不一定。若泄漏的 goroutine 先崩溃退出、或泄漏与退出速率相抵，计数会持平。计数稳定增长是最强信号；定位具体漏在哪要用 pprof 的 goroutine profile（`/debug/pprof/goroutine`）看阻塞栈分布。

**Q：给 channel 加缓冲算不算根治发送泄漏？**

A：不算根治，只是消化了这一次发送。生产代码的正确姿势是 `select { case ch <- v: case <-ctx.Done(): }`——发送与退出信号同时待命，对端消失也能走人。缓冲适合"确定有人消费、只是节奏不同步"的场景。

**Q：`select{}` 空选择和 `for{}` 有什么区别？**

A：`select{}` 没有任何 case 会永久阻塞（Gwaiting，不占 CPU）；`for{}` 是忙等（一直 G-running，烧时间片）。两者都是泄漏，但死循环危害更大——它直接偷走本可用于其他 goroutine 的调度配额。

**Q：main 退出后泄漏的 goroutine 去哪了？**

A：main 返回即进程退出，所有 goroutine 被整体丢弃，没有等待、没有优雅关闭。所以 demo 里泄漏不会累积到崩溃——但在常驻服务里没有"main 退出"兜底，泄漏就是纯粹的慢性死亡。
