# 17 · Channel 信号量限流：一行 `<-tokens` 锁死放行节奏

> 服务被打挂往往不是因为算力不够，而是因为并发不设防。Go 不需要引入任何限流库：一个带缓冲的 channel 就是计数信号量，桶里每个令牌对应一个放行名额，取不到令牌的请求自然阻塞排队。本篇用 `time.Ticker` 恒速补充令牌，搭一个经典的令牌桶限流器；读完你能亲眼看到"突发 5 个、之后每 200ms 放行 1 个"的节奏，并掌握容量与速率的分工、停补与 close 的正确收尾顺序。

## Background

假设下游服务只承受得住每秒 5 个请求，而上游一口气涌来 15 个。

没有限流时，15 个请求同时打到下游——瞬时压力直接超载。常见的替代做法是给每个请求 `time.Sleep`：sleep 限的是"每个请求自己等多久"，限不住同时放行几个，15 个各自睡完仍可能一齐涌出。

真正需要的是一个"最多 N 个同时放行、之后按固定节奏补充名额"的原语。Go 的带缓冲 channel（创建时指定容量的 channel）语义恰好够用：满了发送阻塞、空了接收阻塞——容量即名额，阻塞即排队。

## What

一句话定义：channel 信号量是把带缓冲 channel 当计数信号量（限制同时持有名额数的同步原语）来用的模式：容量 N 即最大并发 N，往通道里发送一个空结构体等于放出一个名额，接收等于占用一个名额。

可以把这个限流器想象成一个容量 5 的令牌桶：启动时装满令牌（放行资格），后台计时器每 200ms 补一枚，桶满就溢出丢弃；每个请求要先摸走一枚令牌才有资格执行。但和"排队叫号机"不同的是，桶里预存的令牌允许开头一小波同时放行——突发是被显式设计出来的能力，不是缺陷。

两个参数各管一边：

- 容量管突发：预存的 5 个令牌允许瞬时放行 5 个请求
- 速率管平均：每 200ms 补 1 个，长期平均放行速率 5 个/秒
- 两个参数分开调，互不干扰

## When to Use

在做什么事的时候选它：

- 在保护承受不住高并发的下游时（数据库连接、第三方 API 配额）：容量限制同时打过去的请求数，速率控制长期节奏。
- 在做 worker 池的并发度控制时：任务开始 `<-tokens` 占名额、结束 `tokens <- struct{}{}` 还名额；容量 1 时它就退化成互斥锁。
- 在要"突发 + 恒速"混合限流时：开头允许一小波突发吃掉存量，之后的节奏由补充速率锁死。

何时不用：只想限制单次调用间隔、不在乎并发总数时，`time.Sleep` 更省事；高并发生产场景优先 `golang.org/x/time/rate`（见下方对比表）。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| `time.Sleep` | 限单次间隔，限不住并发总量 | 只需降频、不在乎同时几个 |
| channel 信号量（本篇） | 限"同时几个"，配 Ticker 兼管速率 | 标准库纯手搭、参数直观可观测 |
| `golang.org/x/sync/semaphore.Weighted` | 带权重的成熟实现，原理与本 demo 相同 | 名额有大小之分（大任务占多个） |
| `golang.org/x/time/rate` | 懒补充令牌桶，无后台 goroutine | 高并发生产限流 |

## Quick Start

前置条件：本机装有 Go，无第三方依赖。运行总时长约 3 秒。

```bash
cd concepts/17_chan_semaphore

```

请求  6 取到令牌，开始执行 @ t=     0ms
请求  3 取到令牌，开始执行 @ t=     0ms

两个关键现象：开头 5 个请求都在 t≈0ms 放行（桶是预存满的）；之后相邻放行间隔稳定在 ~200ms（拿请求 10 与请求 11 的时间戳相减即可验证），节奏被令牌严格锁死。

桶的初始化（容量 5、预存满、再启动补充协程）：

```go
	tokens := make(chan struct{}, burst) // 信号量：桶里每个令牌=1 个放行名额
	for i := 0; i < burst; i++ {         // 预存满桶令牌：允许开头一小波突发
		tokens <- struct{}{}
	}
	stop := startRefiller(tokens)
```

请求侧的全部限流逻辑（取不到令牌就阻塞在这一行）：

```go
		go func(id int) {
			defer wg.Done()
			<-tokens // 取不到令牌就阻塞在这儿——这就是限流本体，一行代码
			fmt.Printf("请求 %2d 取到令牌，开始执行 @ t=%s\n", id, elapsed())
			time.Sleep(30 * time.Millisecond) // 模拟业务耗时，不影响放行节奏
		}(i)
```

## How It Works

### buffered channel 即计数信号量

`make(chan struct{}, N)` 创建的通道最多容纳 N 个元素：发送方在"满"时阻塞，接收方在"空"时阻塞。把元素当作"名额"，就得到一个互斥/限流两用的信号量——容量 1 退化为互斥锁，容量 N 就是最大并发 N。用空结构体 `struct{}{}` 表示令牌，因为它零字节、不携带任何数据。

Quick Start 输出的开头 5 行都在 t≈0ms——那正是预存满桶的 5 个名额被瞬间领走。

### Ticker 恒速补充

`time.Ticker`（按固定间隔反复触发的计时器）每 200ms 发一次滴答；后台 goroutine（语言内置的轻量级线程）在每次滴答时尝试 `tokens <- struct{}{}`，桶满就走 `default` 丢弃。

补充速率 1000/200 = 5 个/秒，这就是限流器的长期平均放行速率；桶容量 5 决定瞬时突发上限。

补充 goroutine 的循环（核心：滴答时非阻塞地补一枚令牌，桶满就丢）：

```go
	go func() {
		defer close(done)
		for {
			select {
			case <-ticker.C:
				select {
				case tokens <- struct{}{}: // 桶满则丢弃这个令牌（等价于容量上限）
				default:
				}
			case <-stopCh:
				return
			}
		}
	}()
```

输出里第 6 个之后的请求按 ~200ms 间隔逐个放行——`t=201ms → 401ms → 601ms → 800ms` 的时间戳，就是滴答节拍本身。

### 突发与恒速的关系

桶在启动时装满 5 个令牌，所以前 5 个请求瞬间放行；突发吃光余量后，放行节奏完全由补充速率决定——每消耗 1 个令牌要等 200ms 才有新令牌。**容量管突发，速率管平均**，这两个参数分开调互不干扰。

### 收尾顺序

先 `ticker.Stop()`，再通知补充 goroutine 退出并等它真正退出，最后才 `close(tokens)`。顺序不能反：若先 close，补充 goroutine 的下一次发送就是对已关闭通道发送，直接 panic。

demo 的 stop 函数专门用 `<-done` 等待退出确认：

```go
	return func() {
		ticker.Stop()
		close(stopCh)
		<-done // 等 refiller 真正退出，之后 close tokens 才安全
		close(tokens)
	}
```

输出最后一行"全部请求执行完毕，令牌桶已关闭"出现在 `stop()` 返回之后——三步收尾全部完成。

| 语法 | 含义 | 为什么重要 |
|---|---|---|
| `make(chan struct{}, 5)` | 容量 5 的信号量 | 容量 = 最大并发/突发上限 |
| `<-tokens` | 取令牌，取不到就阻塞 | 限流逻辑的全部本体 |
| `tokens <- struct{}{}` / `default` | 非阻塞发送 | 桶满丢弃令牌，不阻塞补充协程 |
| `time.NewTicker(d)` | 恒速滴答 | 速率 = 1/d；用完必须 `Stop()` 释放 |
| `close(tokens)` | 广播"不再放行" | 只能在补充协程退出后调用 |

## Pitfalls & Q&A

坑清单（每条按"现象 → 原因 → 解法"读）：

- **现象**：收尾时先 `close(tokens)` 再停补充协程，程序 panic。**原因**：向已关闭的 channel 发送会 panic，补充协程的下一次发送正好撞上。**解法**：按"停 Ticker → 通知退出 → `<-done` 等真正退出 → close"的顺序收尾。
- **现象**：服务结束后 Ticker 还拖着 goroutine 不放。**原因**：忘写 `ticker.Stop()`——Ticker 底层定时器不会被动回收，goroutine 会被它拖住。**解法**：在收尾函数里显式 `Stop()`。
- **现象**：给每个请求 sleep 200ms"限流"，下游照样被打挂。**原因**：`time.Sleep` 限的是"每个请求自己等多久"，限不住并发总量；信号量限的是"同时放行几个"。**解法**：并发总量问题用信号量，单次间隔问题才用 sleep。
- **现象**：纠结令牌桶要不要 close。**原因**：把 close 当成了必做清理。**解法**：如果令牌桶与服务同生命周期，不 close 也没有泄漏；close 是为了让接收方能感知"终结"，有这个需求才做。
- **现象**：删掉"看着没用"的 `burst`/`rate`/`requests` 常量之一，编译不过。**原因**：Go 里未使用的变量是编译错；反过来这三个常量都被实际引用，删定义会连带破坏引用处。**解法**：保留常量与引用的对应关系。

**Q：信号量限流和 `sync.Mutex` 互斥是什么关系？**
A：互斥是容量为 1 的信号量特例。容量 N 的信号量允许 N 个持有者并发，Mutex 不行。Go 里 `golang.org/x/sync/semaphore.Weighted` 是带权重的成熟实现，原理与本 demo 相同。

**Q：桶满时为什么选丢弃令牌而不是阻塞？**
A：补充协程如果阻塞在发送上，会与取令牌的请求竞争且可能永久卡住；丢弃等价于"桶容量封顶"，这正是令牌桶语义的一部分（闲置不攒超量突发）。

**Q：为什么用 `chan struct{}` 而不是 `chan int` 或 `chan bool`？**
A：令牌不携带信息，`struct{}` 是零字节类型，通道本身不因元素类型产生额外内存；`chan int` 也能工作，只是语义上暗示"值有意义"。

**Q：这种 Ticker 补充法和 `golang.org/x/time/rate` 一样吗？**
A：语义等价（都是令牌桶），实现不同：`rate.Limiter` 是"懒补充"——每次 Reserve 时按 `时间差 × 速率` 一次性补齐，不开后台 goroutine、不受定时器精度影响。

高并发生产场景优先用它；本 demo 用 Ticker 是为了把"恒速补充"变成看得见的时间线。
