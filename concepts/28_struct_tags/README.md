# 28 · Struct Tag 解析：反引号里的元数据，运行时才拆封

> struct tag 是写在字段反引号里的字符串元数据：编译器不解释它，`reflect` 也不替你解析语义，它只是躺在 `StructField.Tag` 里的一段文本。encoding/json、validate 这些框架的"魔法"，起点都是同一个动作——运行时读出这段字符串，按自己的协议解析。读完你能复刻 json 键名映射、写出按 tag 校验的函数，并说清 `Lookup` 与 `Get` 的本质差别。

## Background

没有统一挂载点的日子里，序列化键名、校验规则只能写死在每个类型的专用函数里：`User` 一份、`Order` 一份，字段一改处处跟着改。这些信息没有地方"跟着字段走"。

痛点集中在通用框架：encoding/json、校验库、ORM（对象—关系映射，struct 与数据库表互转的框架）没法预知业务 struct 长什么样，也不能要求每个业务类型实现一堆接口——元数据缺一个统一的声明位置。

Go 没有语言级注解语法，答案是 tag：把元数据以约定格式写成字符串挂在字段上，消费方在运行时用反射（`reflect`，读取运行时类型信息的标准库包）统一解析。理解 tag 解析，就看懂了 json/validate 等框架的第一层封装；这条解析流水线用 100 行标准库代码即可跑通。

## What

struct tag 是写在字段反引号里的字符串元数据：键值对以空格分隔（`` `json:"name" validate:"required"` ``），编译器原样保存、不做任何解释，语义完全由消费方约定。

心智模型一句话：tag 解析是一条五步流水线——结构体声明 → 反射逐字段读 `Tag` → 按键名映射消费（序列化）、按规则消费（校验），最后汇成输出。上行是声明与反射读取，下分序列化/校验两条支线。

可以把 tag 想象成行李箱上挂的纸质牌：箱子（字段）不解释牌子内容，柜台（框架）按自己的规则读牌办事——快递柜读地址，酒店读房号。但和柜台审单不同的是，牌子没有任何格式校验：格式写错不会报错，只是消费方解析时静默跳过，表现为"不生效"。

## When to Use

- 写序列化库或做键名映射时：业务字段叫 `UserName`，JSON 要 `"user_name"`——键名差异交给 tag 声明，框架代码统一消费。
- 写参数校验时：把"必填""最小值"这类规则写在字段的 validate tag 上，校验器遍历字段按规则检查，不必为每个结构体手写一遍 if。
- 写 ORM 或配置绑定时：数据库列名、配置键与字段名的对应关系，一份元数据同时服务多个消费方。

何时不用：

- 单一类型、字段很少：手写序列化或校验函数更直白，还带编译期检查；tag 写错只在运行时表现为不生效，没有编译器兜底。
- 需要复杂校验逻辑（跨字段比较、依赖外部状态）：tag 只能表达声明式规则，复杂逻辑应写成普通代码。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 手写映射/校验代码 | 显式、有编译期检查 | 类型少且稳定 |
| struct tag + 反射 | 一份元数据，多消费方复用 | 通用框架的键名映射、声明式规则 |
| 实现序列化接口（如 `json.Marshaler`） | 单类型深度定制，逻辑任意 | 单个类型的复杂编解码 |

## How It Works

### tag 的读取：Lookup 与 Get

字段的 tag 存在 `reflect.StructField.Tag`（类型 `reflect.StructTag`）里。`Get(key)` 只返回值，查不到返回 `""`；`Lookup(key)` 返回 `(值, ok)`。

输出第 1 段的三个字段（写了 `"a"` / 写了空串 / 没写）给出对照：B 行 `Lookup=("", true)`、C 行 `Lookup=("", false)`，而 `Get` 两行都折叠成 `""`——判断 tag 是否存在，永远用 `Lookup`。

### json 键名映射的约定

`encoding/json` 的键名规则可以几行复刻：`Lookup("json")` 未命中或值为 `"-"` → 跳过该字段；命中则取逗号前的部分作键名（`"age,omitempty"` 的键是 `age`）；键名为空（`json:""`）退回字段名。demo 的 `keyOf` 就是这套规则。

### validate：按规则消费 tag

校验是 tag 的另一种消费方式：`Lookup("validate")` 未命中就跳过（所以 `Email` 不参与校验）。

命中后解析规则串——`required` 检查零值（`Value.IsZero`，判断值是否为该类型的零值），`min=N` 用 strconv（标准库的字符串与数值互转包）取出 N 再比较。校验函数不需要知道字段含义，只认 Kind（底层种类）与规则串。

输出第 4 段的 `FAIL Name: required 但为零值` 与 `FAIL Age: -1 < min=0`，就是两条规则各自命中的结果。

### miniMarshal：简化序列化器

只输出带 json tag 的字段，按 `Kind` 格式化后拼成 `{"key":"value",...}`。它与 `encoding/json` 的差距只在细节（嵌套、转义、omitempty），原理完全一致：读 tag → 键名映射 → 值格式化。输出第 2 段的每个键名，都来自对应字段 tag 里逗号前的部分。

### 关键语法速查

| 语法 | 含义 | 为什么重要 |
|---|---|---|
| `` `json:"name" validate:"required"` `` | 多个 tag 空格分隔，各自独立解析 | key:value 对，value 可含逗号选项 |
| `Tag.Lookup(key)` | 返回 `(值, ok)` | 唯一能区分"没写"与"空串"的手段 |
| `Tag.Get(key)` | 只返回值 | 查不到与空串都返回 `""` |
| `json:"-"` | 明确跳过该字段 | 与"没写 tag"是两个语义 |
| `json:"age,omitempty"` | 键名 + 选项 | 解析时要先按逗号切分 |

## Pitfalls & Q&A

坑清单（每条均可复现）：

- **拿 `Get` 判断存在**。现象：`f.Tag.Get("json") == ""` 被当成"没写 tag"。原因：`json:""`（写了空值）也返回 `""`，两种情况被折叠。解法：判存在用 `Lookup`，靠 ok 区分。
- **键名忘了切逗号**。现象：键名解析成 `age,omitempty`。原因：tag 值里选项跟在逗号后面。解法：取逗号前的部分作键名。
- **给未导出字段写 tag**。现象：tag 写了却不生效。原因：未导出字段（小写开头，包外不可访问）反射读不到有效值。解法：tag 只配导出字段。
- **tag 用双引号书写**。现象：tag 解析失败或读不到。原因：双引号里的 `\"` 转义破坏了 tag 的约定格式。解法：tag 字符串一律用反引号。
- **校验失败就 panic**。现象：一个字段非法让整个流程中断。原因：把校验失败当致命错误处理。解法：返回报告（或 error 切片），让调用方决定怎么处理。

**Q：为什么 tag 用反引号字符串，而不是结构化的注解语法？**

Go 刻意不给语言加注解机制——tag 就是一段普通字符串常量，编译期原样存进类型元数据，语义完全交给消费方约定。这换来了零语言成本：任何库都能定义自己的 tag 协议；代价是没有编译期检查，tag 写错只在运行时表现为"不生效"。

**Q：`Lookup` 和 `Get` 底层差别是什么？**

`Get(key)` 等价于 `v, _ := Tag.Lookup(key); return v`。`StructTag.Lookup` 按约定格式扫描字符串：跳过空格、匹配 key、校验冒号与引号配对，格式非法的片段会被跳过——所以格式错误的 tag 不会报错，只是"看不见"。

**Q：反射遍历字段解析 tag，性能如何？**

慢一个数量级以上：`TypeOf`/`Field` 有分配，tag 解析每次都重新扫描字符串。框架的标准优化是首次解析后把"字段 → 键名/规则"的映射缓存起来，`encoding/json` 内部就是这么做的。

**Q：`validate:"required"` 对 int 字段会怎样？**

本篇 demo 用 `IsZero` 统一判断，`Age=0` 也会判为"必填缺失"——这正是很多校验库要求指针类型（`*int`，nil 才算缺）的原因：零值与"没填"在值类型上无法区分，反射只能看到值。
