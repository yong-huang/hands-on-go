# 07 · 闭包陷阱：闭包捕获的是变量，不是值

> goroutine（Go 的并发执行单元）+ 循环变量是 Go 历史上最经典的并发错误：循环里启动的所有 goroutine 打印循环变量，读到的全是最后一个值。本篇用显式共享变量复现这个陷阱，讲清 Go 1.22 前后的语义差异，并跑通三种修正写法。

## Background

在循环里为每个元素启动一个 goroutine，是最常见的并发写法：5 个元素发 5 个请求、处理 5 个任务。直觉预期是每个执行流看到自己那份数据。

但在 Go 1.21 及以前，`for _, v := range xs { go func(){ use(v) }() }` 这个写法是错的：所有闭包（引用了自身外部变量的函数值）捕获的都是**同一个变量 `v`**。

goroutine 真正执行时循环大概率早已跑完，`v` 已经是最后一个元素——所有执行流读到的都是同一个最终值。

理解这个 bug 需要三个知识点：

- 闭包的捕获语义：捕获的是变量的引用，而不是那一刻的值
- `go` 语句的启动时机：只是把函数交给调度器（runtime 中决定哪个 goroutine 何时运行的组件），不立即执行
- 循环变量的作用域：整个循环共用一个变量，还是每轮一个新变量

Go 1.22 改了循环变量的语义让原生写法变安全，但"共享变量的引用会被并发读"这条规则从未变——只要变量是显式共享的，陷阱照样发生。

## What

闭包陷阱是一种并发 bug 模式：闭包捕获的是变量的引用而非值的拷贝，叠加 goroutine 延迟执行，导致多个执行流启动后读到的都是变量的同一份最终值。

**心智模型一句话**：闭包捕获的是 `&loopVar` 这个地址；循环结束时地址里的值已是 5，于是所有 goroutine 都读到 5。

可以把闭包对变量的捕获想象成"记下了储物柜的编号，而不是柜子里当时放的东西"——循环每轮往柜子里换内容，循环结束后柜子里留下最后一个元素，所有按编号取件的人都取到它。

但和手动传指针不同的是，这个捕获由编译器自动完成，代码里看不到任何取地址符号，共享因此更隐蔽。

三种修正的本质完全相同——让每个 goroutine 捕获一个**独立的存储位置**。

## When to Use

这份判断力在三类场景用得上：

- 在循环里为每个元素启动 goroutine 做并发处理（批量发请求、并发写日志、分发任务）时，要保证每个执行流拿到独立数据
- 阅读或维护 go.mod 声明低于 1.22 的老项目时，原生循环变量写法仍然是陷阱
- 在任何版本里，多个 goroutine 捕获同一个显式共享变量（struct 字段、包级变量、循环外局部变量）时，bug 照样发生

何时不用：

- 单线程场景里闭包捕获引用往往是期望行为：`defer` 记录返回前的状态、回调注册延迟求值，靠的正是"捕获变量本身"
- 只启动一个 goroutine、不涉及循环共享时，没有"多个执行流读同一变量"的问题

修正方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 参数传递 `go func(n int){}(v)` | `go` 语句求值时按值拷贝，每个 goroutine 独立副本 | 默认首选：意图最明确，vet 工具友好 |
| 循环内重赋值 `shared := v` | 每轮迭代新建变量、新地址 | 需要在循环体内先加工出一份局部值再用时 |
| shadow（变量遮蔽，内层同名声明挡住外层）`v := v` | 函数体首行遮蔽外层同名变量 | 1.22 之前兼容老版本的历史写法，新代码少用 |
| 声明 `go >= 1.22` 用原生循环变量 | 每轮迭代自动是新变量 | 新项目或模块版本允许时的零成本方案 |

## How It Works

### 陷阱：闭包捕获引用，goroutine 延迟执行

`loopVar` 在循环体外声明、循环体内重写，所有 `go func(){ use(loopVar) }()` 捕获的都是同一个 `&loopVar`。

`go` 语句只是把函数交给调度器，真正执行时 `for` 循环大概率已经结束，`loopVar == 5`——于是值 5 出现 5 次，值 1~4 出现 0 次。

你在第 1 段输出里看到的"值 5 出现 5 次"，就来自这里的共享 `&loopVar`。这是"复现 1.22 之前的世界"的写法。

### 修正 1：参数传递（推荐）

`go func(n int){ ... }(v)`——`v` 的**当前值**在 `go` 语句求值时被拷贝成参数 `n`，每个 goroutine 拿到独立副本。

拷贝发生在启动瞬间，语义最清晰，是如今最推荐的写法。第 2 段输出里"共 5 个"就是 5 次独立拷贝的结果。

### 修正 2：循环内重赋值

`shared := v` 写在循环体内：每轮迭代创建一个**新变量**、新地址，各轮闭包各捕获各的。

它展示了"陷阱的根源是作用域"——把变量挪进循环体，共享就消失了。第 3 段输出"每个值恰好出现 1 次: true"就是它的验证断言。

### 修正 3：shadow（`v := v`）

`v := v` 写在函数体首行：右边是外层循环变量，左边是遮蔽它的新局部变量，闭包捕获的是这个新 `v`。

这是 Go 1.22 之前社区通行的"防御性 shadow"写法，`go vet -loopclosure` 至今仍认识它。第 4 段输出 `1+2+3+4+5 = 15` 证明五个值都独立到位。

### 版本语义：Go 1.22 改变了什么

**自 Go 1.22 起，`for` 循环（含 `range`）的循环变量每次迭代都是新变量**，所以原生的 `for _, v := range xs { go func(){ use(v) }() }` 已经安全，经典陷阱不再复现。

这也是 demo 用显式共享的 `loopVar` 而不是原生循环变量来演示陷阱的原因。

但规则本身没变：只要多个 goroutine 捕获**同一个变量**（结构体字段、包级变量、循环外的局部变量），它们看到的仍是同一份最终值。

### 写法对照表

| 写法 | 语义 | 结果 |
|---|---|---|
| `go func(){ use(loopVar) }()` | 闭包捕获 `&loopVar` | 全部读到最终值（陷阱） |
| `go func(n int){ use(n) }(v)` | 启动时按值拷贝 | 每个拿到独立值（推荐） |
| 循环体 `shared := v` 后启动 | 每轮新变量新地址 | 每个拿到独立值 |
| 函数体 `v := v` 后使用 | shadow 遮蔽外层 | 每个拿到独立值 |
| go.mod `go >= 1.22` + 原生循环变量 | 每轮迭代都是新变量 | 原生写法已安全 |

## Pitfalls & Q&A

踩坑清单，每条按"现象 → 原因 → 解法"展开：

- **现象**：期望各值出现 1 次，实际全部读到最终值。**原因**：闭包捕获的是**变量**不是值，`use(v)` 读的是执行那一刻 `v` 存储位置的内容。**解法**：用下面三种修正之一切断共享。
- **现象**：goroutine 里打印的值和循环进度对不上。**原因**：`go` 语句不等待，循环大概率在 goroutine 开始执行前就跑完了。**解法**：在 `go` 语句求值时就把需要的值定下来（参数传递）。
- **现象**：升级到 1.22 后以为绝对安全，仍出现全部同值。**原因**：陷阱只是从"原生循环变量"退到了"显式共享变量"（struct 字段、包级变量、循环外局部变量）。**解法**：逐一审查被多个 goroutine 捕获的显式共享变量。
- **现象**：修完闭包，各值出现次数的统计又错乱。**原因**：多个 goroutine 无锁读写共享切片/map 本身也是数据竞争（多个执行流无同步地读写同一内存）。**解法**：demo 里用 `sync.Mutex`（互斥锁，同一时刻只允许一个 goroutine 持有）保护汇总，避免陷阱之外再引入竞争。
- **现象**：修正 2 中声明了外层 `shared` 又在循环内 shadow，编译失败。**原因**：未使用的变量是编译错，vet 会提示 `declared and not used`。**解法**：删掉外层声明，只保留循环内那份。

**Q：Go 1.22 改了什么？既然原生写法已安全，还学这个陷阱干什么？**

A：1.22 把 `for` 循环变量改成每次迭代创建新变量，等价于自动做了"修正 2"。但闭包捕获引用的规则没变：只要变量是被多个 goroutine **显式共享**的（struct 字段、包级变量、`loopVar` 这类循环外变量），全部读到最终值的 bug 照样发生。

版本升级消灭的是"无意识的共享"，不是"有意的共享"。

**Q：为什么参数传递是按值拷贝？如果 v 是大结构体怎么办？**

A：`go func(n T){}(v)` 中 `v` 在 `go` 语句求值时拷贝给 `n`。大结构体拷贝有开销，可以传指针 `go func(p *T){}( &v )`——注意 `&v` 若仍是共享变量同样有陷阱，前提是每次迭代 `v` 本身是新变量（1.22+ 原生即如此）。

**Q：三种修正该选哪种？**

A：选型依据见 When to Use 的对比表：优先参数传递（意图最明确、vet 友好）。看到 `v := v` 应立刻想到"这里在切断共享"。

**Q：怎么在代码里发现这个 bug？**

A：`go vet -loopclosure` 能报出老版本语义下的经典形态；`go run -race` 能暴露共享变量的数据竞争；另外第 1 段输出"值 5 出现 5 次"本身就是最直白的证据——期望"各出现 1 次"的断言失败了。

**Q：这与 WaitGroup 的等待范围有关吗？**

A：WaitGroup 是 sync 包的等待计数器，`Add` 加一、`Done` 减一、`Wait` 阻塞到归零。每段 demo 都是先循环里 `wg.Add(1)`、goroutine 里 `defer wg.Done()`、循环后 `wg.Wait()`。

若把 `Add` 放进 goroutine 内，`Wait` 可能抢先返回——这是与闭包陷阱同级别的时序错误，见 [06_goroutine_basics](../06_goroutine_basics/)。
