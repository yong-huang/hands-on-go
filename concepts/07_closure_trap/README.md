# 07 · 闭包陷阱：闭包捕获的是变量，不是值

> goroutine + 循环变量是 Go 历史上最经典的并发错误：10 个 goroutine 打印循环变量，结果全是最后一个值。根源只有一句话——**闭包捕获的是变量的引用，而不是那一刻的值**。本实验用显式共享变量复现这个陷阱（并说明 Go 1.22 前后的语义差异），再跑通三种修正。

## 1. 为什么需要它

`for _, v := range xs { go func(){ use(v) }() }` 在很多语言里是错的，在 Go 1.21 及以前也是错的：所有闭包捕获的是**同一个变量 `v`**，goroutine 真正执行时循环早已跑完，`v` 已经是最后一个元素。理解它需要三个知识点：闭包的捕获语义（引用而非拷贝）、goroutine 的启动时机（`go` 语句只是调度，不立即执行）、循环变量的作用域。Go 1.22 改了循环变量的语义让原生写法变安全，但"共享变量的引用会被并发读"这条规则从未变——只要变量是显式共享的，陷阱照样发生。

## 4. 核心概念

### 4.1 陷阱：闭包捕获引用，goroutine 延迟执行

`loopVar` 在循环体外声明、循环体内重写，所有 `go func(){ use(loopVar) }()` 捕获的都是同一个 `&loopVar`。`go` 语句只是把函数交给调度器，真正执行时 `for` 循环大概率已经结束，`loopVar == 5`——于是值 5 出现 5 次，值 1~4 出现 0 次。这是"复现 1.22 之前的世界"的写法。

### 4.2 修正 1：参数传递（推荐）

`go func(n int){ ... }(v)`——`v` 的**当前值**在 `go` 语句求值时被拷贝成参数 `n`，每个 goroutine 拿到独立副本。拷贝发生在启动瞬间，语义最清晰，是如今最推荐的写法。

### 4.3 修正 2：循环内重赋值

`shared := v` 写在循环体内：每轮迭代创建一个**新变量**、新地址，各轮闭包各捕获各的。它展示了"陷阱的根源是作用域"——把变量挪进循环体，共享就消失了。

### 4.4 修正 3：shadow（`v := v`）

`v := v` 写在函数体首行：右边是外层循环变量，左边是遮蔽它的新局部变量，闭包捕获的是这个新 `v`。这是 Go 1.22 之前社区通行的"防御性 shadow"写法，`go vet -loopclosure` 至今仍认识它。

### 4.5 版本语义：Go 1.22 改变了什么

本仓库 go.mod 声明 `go 1.26`。**自 Go 1.22 起，`for` 循环（含 `range`）的循环变量每次迭代都是新变量**，所以原生的 `for _, v := range xs { go func(){ use(v) }() }` 已经安全，经典陷阱不再复现——这也是 demo 用显式共享的 `loopVar` 而不是原生循环变量来演示陷阱的原因。但规则本身没变：只要多个 goroutine 捕获**同一个变量**（结构体字段、包级变量、循环外的局部变量），它们看到的仍是同一份最终值。

## 5. 关键字段与坑清单

| 写法 | 语义 | 结果 |
|---|---|---|
| `go func(){ use(loopVar) }()` | 闭包捕获 `&loopVar` | 全部读到最终值（陷阱） |
| `go func(n int){ use(n) }(v)` | 启动时按值拷贝 | 每个拿到独立值（推荐） |
| 循环体 `shared := v` 后启动 | 每轮新变量新地址 | 每个拿到独立值 |
| 函数体 `v := v` 后使用 | shadow 遮蔽外层 | 每个拿到独立值 |
| go.mod `go >= 1.22` + 原生循环变量 | 每轮迭代都是新变量 | 原生写法已安全 |

坑清单：

- 闭包捕获的是**变量**不是值：`use(v)` 读的是执行那一刻 `v` 存储位置的内容
- `go` 语句不等待：循环大概率在 goroutine 开始执行前就跑完了
- 1.22 之后陷阱并未消失，只是从"原生循环变量"退到了"显式共享变量"（struct 字段、包级变量、循环外局部变量）
- 多个 goroutine 无锁读写共享切片/map 本身也是数据竞争——demo 里用 `sync.Mutex` 保护汇总，避免陷阱之外再引入竞争
- 未使用的变量是编译错：修正 2 中如果声明了外层 `shared` 又在循环内 shadow，vet 会提示 `declared and not used`

## 7. 深入要点

**Q：Go 1.22 改了什么？既然原生写法已安全，还学这个陷阱干什么？**
A：1.22 把 `for` 循环变量改成每次迭代创建新变量，等价于自动做了"修正 2"。但闭包捕获引用的规则没变：只要变量是被多个 goroutine **显式共享**的（struct 字段、包级变量、`loopVar` 这类循环外变量），全部读到最终值的 bug 照样发生。版本升级消灭的是"无意识的共享"，不是"有意的共享"。

**Q：为什么参数传递是按值拷贝？如果 v 是大结构体怎么办？**
A：`go func(n T){}(v)` 中 `v` 在 `go` 语句求值时拷贝给 `n`。大结构体拷贝有开销，可以传指针 `go func(p *T){}( &v )`——注意 `&v` 若仍是共享变量同样有陷阱，前提是每次迭代 `v` 本身是新变量（1.22+ 原生即如此）。

**Q：三种修正该选哪种？**
A：优先参数传递（意图最明确、vet 友好）；循环内重赋值和 shadow 是 1.22 之前兼容老版本的等价手段，如今更多出现在历史代码里。看到 `v := v` 应条件反射地想到"这里在切断共享"。

**Q：怎么在代码里发现这个 bug？**
A：`go vet -loopclosure` 能报出老版本语义下的经典形态；`go run -race` 能暴露共享变量的数据竞争；另外第 1 段输出"值 5 出现 5 次"本身就是最直白的证据——期望"各出现 1 次"的断言失败了。

**Q：这与 WaitGroup 的等待范围有关吗？**
A：每段 demo 都是先循环里 `wg.Add(1)`、goroutine 里 `defer wg.Done()`、循环后 `wg.Wait()`。若把 `Add` 放进 goroutine 内，`Wait` 可能抢先返回——这是与闭包陷阱同级别的时序错误，见 [06_goroutine_basics](../06_goroutine_basics/)。

## 8. 总结

闭包捕获的是变量的引用，goroutine 是延迟执行的——两条规则相遇就成了 Go 最经典的并发 bug。Go 1.22 让原生循环变量免于陷阱，但"每个 goroutine 需要独立的数据"这一判断永远是你的责任：参数传递、循环内重赋值、shadow，三种修正殊途同归。
