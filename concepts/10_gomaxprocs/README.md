# 10 · GOMAXPROCS 与并行度控制：goroutine 多不代表跑得快

> 起 100 个 goroutine（Go 的并发执行单元）不等于用了 100 个核。Go 运行时用 GOMAXPROCS 决定**最多用多少个 OS 线程同时执行 goroutine**——它才是"真并行"的闸门。读完本篇，你能分清并发与并行的分界线，并知道什么场景该手动调这个值。

## Background

goroutine 是并发的结构，数量从来不是速度的保证。常见的第一反应是在 CPU 密集任务（以计算为主、几乎不等待的任务）里起几百个 goroutine，结果实测比单线程还慢——多出来的执行流只带来切换开销，没有带来算力。

另一种常见认知是"GOMAXPROCS 默认等于核数，所以不用管"。默认值确实如此，但说不清"10 个 goroutine 在单核上到底怎么跑"的人，也无法判断容器里、混部场景下该不该调。

缺口在于没有可对照的数字：并行度的效果谈起来容易，测起来需要控制变量——总工作量必须恒定，否则耗时变化说不清归因。

Go 运行时把这个问题做成了一个可测的参数：GOMAXPROCS（同时执行 Go 代码的 OS 线程——操作系统内核调度的执行单元——数上限）。本篇用同一份固定工作量、只调这一个值，把分界线实测出来。

## What

**定义**：GOMAXPROCS 是 Go 运行时的并行度上限参数，设定"同时执行 Go 代码的 OS 线程数"。它管的是并行（parallelism，多个线程真正同时占用不同核），不是并发（concurrency，多个 goroutine 交替推进的结构）——后者由 goroutine 的写法决定。

| 概念 | 回答的问题 | 由谁决定 |
|---|---|---|
| 并发（结构） | 任务怎么组织、能不能交替推进 | goroutine 的写法 |
| 并行（执行） | 有几个真的同时算 | GOMAXPROCS 与核数 |

**心智模型一句话**：任务先平分给若干 goroutine（结构），再由 GOMAXPROCS 决定几个 goroutine 能真正同时占用 CPU（执行）——上限为 1 时只有交织没有并行，接近核数才接近线性加速。

可以把 GOMAXPROCS 想象成食堂打饭的窗口数：排队的顾客（goroutine）再多，同一时刻真正被服务的数量由窗口决定。但和食堂窗口不同的是，有些"顾客"——等待网络或磁盘的 IO 型 goroutine——打到一半会主动离开窗口去等菜，把窗口让给别人；所以 IO 密集场景少量窗口也能服务大量顾客。

## When to Use

这份判断力在三类场景用得上：

- 在容器里跑 CPU 密集服务，CPU 配额小于宿主机核数时：按配额设定并行度，避免过量线程争抢（Go 1.25 起默认已尊重 cgroup——Linux 限制进程组资源用量的机制——配额）
- 与其他进程同机混部时：调小 GOMAXPROCS 给同机其他进程让出算力，或用于调试调度问题
- 做性能基准判断"加 goroutine 有没有用"时：先分清 CPU 密集还是 IO 密集，再决定动结构还是动并行度

何时不用：

- 裸机普通部署：默认值等于核数，已接近最优，手动调没有收益
- IO 密集服务：调 GOMAXPROCS 意义不大——goroutine 等待时会让出执行位，少量线程也能撑起大量 goroutine

同类手段对比：

| 手段 | 差异 | 什么时候选它 |
|---|---|---|
| 保持默认（= `NumCPU()`） | 并行度对齐核数 | 裸机部署、无配额限制 |
| `GOMAXPROCS(n)` 手动调小 | 限制同时执行的线程数 | 容器配额受限、混部让核、调试调度 |
| 增加 goroutine 数 | 只改结构、不改并行度 | IO 密集任务提高吞吐；CPU 密集无收益 |

## Quick Start

前置条件：安装 Go；跑 `python3 viz.py` 另需 Python 3 与 matplotlib（`pip3 install matplotlib`；不带 `-json` 的运行只需 Go）。

```bash

go run main.go -json    # 以 JSON 输出每次测量的原始数据
python3 viz.py          # 用真实测量数据绘制耗时对比图
```

预期输出（节选，**数值机器相关**：每次测量都有波动，你的数字一定不同）：

```text
========== GOMAXPROCS 并行度实测（CPU 密集：总工作量恒定 32 次 fib(30)） ==========
P=1      58.3 ms  加速比 1.00x  █
P=2      29.0 ms  加速比 2.01x  █
P=4      15.9 ms  加速比 3.66x  █

结论：P=1 时 goroutine 只能并发交织、不能并行，最慢；
```

读数要点：加速比指相对 P=1 耗时的倍数，它随 P 接近核数而接近线性；核少的机器上 P=8 可能不比 P=4 快甚至更慢，机制见 How It Works。结论以你自己跑出来的数字为准。

## How It Works

### G-M-P：GOMAXPROCS 到底控制什么

Go 的调度是 G-M-P 模型：goroutine（G）必须挂在逻辑处理器（P）上，P 再绑定到 OS 线程（M）执行。`runtime.GOMAXPROCS(n)` 设定 P 的数量，也就是**同时执行 Go 代码的线程数上限**。

默认值等于 `runtime.NumCPU()`（物理/逻辑核数），所以平时不用手动调；手动设小可以限制 CPU 占用（比如容器里配合配额），设大没有意义——超过核数的 P 只是排队等核。

以输出为例：P=1 一行 58.3 ms，是单个 goroutine 独做 32 次 `fib(30)` 的串行耗时；P=8 时 8 个 goroutine 各做 4 次、8 个 P 真正同时占用 8 个核，才拿到 7.11x 的加速比。

### 并发 vs 并行：分界线在哪

并发是**结构**：多个 goroutine 交替推进，上限为 1 时运行时在一个线程里快速切换它们（交织），总耗时不会比串行短。并行是**执行**：P>1 时多个线程真的同时在不同核上算。

CPU 密集任务只有拿到并行才有加速；IO 密集任务（以等待网络、磁盘为主的任务）在等待时会**让出 P**，所以少量 P 也能撑起大量 goroutine——两类任务的调优思路完全不同。输出结论段第一行"P=1 时 goroutine 只能并发交织、不能并行，最慢"，对应的就是这条分界线。

### 实验设计：恒定总工作量

总工作量固定为 32 次 `fib(30)`（纯 CPU 递归、无 IO 无锁），P 个 goroutine 平分（各做 32/P 次），WaitGroup（sync 包的等待计数器，`Wait` 阻塞到计数归零）等待全部完成后用 `time.Since` 记时。

**总工作量不随 P 变**：若每个 goroutine 都做固定次数，P 越大总工作量越大，测出来的是"更重的活花了多久"，不是加速比。计时骨架就是下表的 `go func` + `wg.Wait()` + `time.Since` 组合。

### 为什么 P 超过核数反而可能更慢

P 超过物理核数后，多个 P 共享核，不但没有额外算力，还多了调度切换与缓存争用开销；核越少越明显。此外笔记本省电模式、云主机 CPU 配额、超线程（一颗物理核呈现为多个逻辑核的技术）的"假核"都会让实测偏离线性。

API 速览：

| API / 写法 | 含义 | 为什么重要 |
|---|---|---|
| `runtime.GOMAXPROCS(n)` | 设置同时执行 Go 代码的线程数上限 | 并行度的总闸门，返回旧值 |
| `runtime.NumCPU()` | 本机逻辑核数 | GOMAXPROCS 的默认值与调优参考 |
| `n := runtime.GOMAXPROCS(0)` | 传 0 = 只查询不修改 | 探测当前并行度 |
| `go func(){...}()` + `wg.Wait()` | 平分工作量再汇合 | 测并行耗时的基本骨架 |
| `time.Since(start)` | 计时到汇合为止 | 放在 `wg.Wait()` 之后 |

## Pitfalls & Q&A

坑清单，每条按"现象 → 原因 → 解法"展开：

- **现象**：P=1 时起再多 goroutine 也不见快，反而 P=1 一档最慢。**原因**：只有交织（并发），没有并行。**解法**：要加速先确认并行度大于 1，goroutine 数量不是加速旋钮。
- **现象**：CPU 密集任务里把 goroutine 数开到远超核数，期望加速，实测更慢。**原因**：这类任务没有等待期，多出的 goroutine 只增加调度开销。**解法**：让并行度对齐核数或配额；结构层面用固定 worker 数的任务池（见 [11_worker_pool](../11_worker_pool/)）。
- **现象**：以为 `GOMAXPROCS(n)` 能限制 goroutine 总数。**原因**：它限制的是"同时执行的线程数"，不是 goroutine 数量上限——goroutine 可以成千上万。**解法**：限制并发数量用信号量或任务池等结构手段。
- **现象**：容器里线程开得比配额多，性能反而受损。**原因**：容器环境下 `NumCPU()` 读到的是宿主机核数，CPU 配额受限。**解法**：按配额调小 GOMAXPROCS（Go 1.25+ 已默认尊重 cgroup 配额）。
- **现象**：测出来的耗时异常短、加速比失真。**原因**：计时没有包住 `wg.Wait()`，测的是"派活时间"而不是"干完时间"。**解法**：`time.Since` 的终点放在汇合之后。

**Q：P=1 时 10 个 goroutine 是怎么"同时"跑的？**

A：不是同时。运行时在一个 OS 线程里快速切换它们（每个跑约 10ms 就让出），宏观上都在推进，微观上串行。这就是并发与并行的分界：并发保证"都能跑"，并行才保证"同时跑"。

**Q：为什么 CPU 密集任务的最优 goroutine 数量 ≈ 核数，而不是越多越好？**

A：CPU 密集任务没有等待期，每个 goroutine 都想占满一个核；数量超过核数只会带来上下文切换和缓存失效。IO 密集任务相反——等待时让出 P，goroutine 数可以远大于 P。
