# 05 · 结构体、方法与接口：Shape 一次遍历，两种实现

> struct 把数据组织在一起，方法给数据挂上行为，接口只认行为不认类型。没有接口，"对所有图形求面积"就要为每种图形写一个分支；有了接口，一个 `[]Shape` 循环遍历所有实现，类型甚至不需要声明"我实现了这个接口"。本篇用一份可运行的 demo 把值/指针接收者、隐式实现与多态遍历逐条跑出来。

## Background

初学者常在三处困惑：`r.Scale(2)` 能编译，但把 `r` 赋给接口后"方法不见了"；`var s Shape = c` 之前没人写过 `implements Shape`，编译器怎么知道 Circle 实现了 Shape；接口变量里到底装了什么。

换一个角度看痛点的来源。传统面向对象语言（Java、C#）里，类必须在定义处声明 `implements` 才算实现接口，方法全部挂在类上、通过类继承复用。这套显式声明换来的是"一眼看到关系"，代价是实现方必须预知接口的存在。

Go 走了另一条路：接口满足与否由类型拥有的方法决定，与任何声明无关；方法也不挂在类上，而是通过接收者（方法签名里标明"属于哪个类型"的那个参数）挂到类型上。上面三个困惑的根源，就是方法集与隐式实现这两条规则的边界。本篇把边界跑出来。

## What

一句话定义：struct 把一组字段组织成一个值类型；方法以接收者的形式挂在类型上；接口是一组方法签名的集合——某类型的方法覆盖了这组签名即自动满足它，无需声明。

心智模型一句话：接口在上方声明行为，Circle 与 Rectangle 从下方各自"长上去"（方法集覆盖即自动实现），汇入 `[]Shape` 后一次循环按动态类型（运行期才知道的具体类型，`%T` 可打印）分派——这就是 Go 的多态。

可以把接口想象成一份岗位说明书：只写职责（方法签名），谁来应聘都行。但和岗位说明书不同的是，应聘者不需要签字确认"我履行这份说明"——招聘方（编译器）逐条对照你已有的技能（方法集），全对上就算录用。

## When to Use

先说在做什么事的时候用接口：

- 在要"对一族类型做同一件事"（求面积、序列化、写日志）时：定义小接口 + 存实现集合的切片，一个循环完成多态分派。
- 在想给第三方库的类型抽象行为时：隐式实现允许你定义接口、让对方的类型自动满足，不需要改对方代码。
- 在设计包的公共 API 时：参数收接口而不是具体类型，调用方可传入任何满足者，测试时可换桩实现。

何时不用接口：只有一种实现、也预见不到第二种时，直接用具体类型更简单；过早抽接口会让调用链多一层无意义间接。

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 具体类型直接调用 | 无间接层，最直接 | 单一实现、无替换需求 |
| 接口 + 多实现 | 按方法集隐式匹配、动态分派 | 一族类型做同一件事、需要桩测试 |
| 继承（其他语言） | 关系在定义处显式声明 | Go 不提供类继承，用组合与接口替代 |

## How It Works

### struct 与方法：接收者就是"第一个参数"

`func (c Circle) Area() float64` 本质上等价于 `func Area(c Circle) float64`——接收者是函数签名的一部分。值接收者拿到副本，方法内改字段不影响原值；要修改调用者手里的数据，用指针接收者（见 `Scale`）。

输出第 1 段 `Circle Area=12.5664`：半径 2 的圆，`πr²` 与 `2πr` 恰好相等，都是只读方法，用值接收者。

### 接口的隐式实现

`Shape` 只声明三个方法签名；`Circle`、`Rectangle` 从未写过任何 "implements"。只要一个类型的方法集覆盖接口的全部方法，它就满足该接口——赋值 `var s Shape = c` 编译通过即是证明。定义（接口方）与使用（实现方）完全解耦：你可以给第三方库的类型"补"出接口实现。

输出第 2 段 `s 的动态类型是 main.Circle`：`%T` 打印出接口变量装的具体类型，证明接口里装的是"类型 + 值"而非单纯的值。

### 方法集：值类型 vs 指针类型

规则一句话：值类型 `T` 的方法集只含值接收者方法；`*T` 的方法集含两者。所以 `Rectangle` 值可以直接赋给 `Shape`（Area/Perimeter 是值接收者），但接口变量调不到 `Scale`——它属于 `*Rectangle` 的方法集。

而普通值变量 `r.Scale(2)` 能编译，是因为 `r` 可寻址，编译器自动改写成 `(&r).Scale(2)`；这个语法糖（同一语义的简写，编译器自动补全）在接口里不生效。

输出第 3 段 `Scale(2) 后 Area=48.0 (3x4=12 -> 6x8=48)`：`Scale` 是指针接收者，改的是调用者手里的 Rectangle 本身。

### 接口切片多态遍历

`[]Shape` 里的元素可以混装不同具体类型，`for` 循环里同一个 `sh.Area()` 调用按动态类型分派到各自的实现。新增三角形时循环一行不改——这是"对扩展开放"的最小形态。

输出第 4 段两行 Circle 面积 12.5664 与 3.1416 来自同一个 `Area` 调用，分别落到半径 2 与半径 1 的实例；`总面积 = 27.7080` 是三个面积之和。

### 关键语法速查

| 语法 | 含义 | 为什么重要 |
|---|---|---|
| `func (c Circle) Area()` | 值接收者，操作副本 | 只读方法首选；T 的方法集含它 |
| `func (r *Rectangle) Scale()` | 指针接收者，可改原值 | 需要修改状态时必须用它 |
| `var s Shape = c` | 隐式实现 + 装箱 | 无 implements 声明，编译器检查方法集 |
| `[]Shape{c, Rectangle{...}}` | 接口切片混装 | 同一循环多态分派 |
| `%T` 打印 `main.Circle` | 接口的动态类型 | 接口 = (动态类型, 动态值) 二元组 |

## Pitfalls & Q&A

踩坑清单（每条按"现象 → 原因 → 解法"展开）：

- 现象：同一个类型上值/指针接收者并存，接口赋值时好时坏。原因：混用接收者让方法集规则难以推理（本实验的 Rectangle 是为演示才这么写）。解法：统一接收者类型——有指针接收者就全用指针。
- 现象：`var s Shape = r`（值）后调 `s.Scale(2)` 编译错。原因：值类型的接口方法集不含 `*Rectangle` 方法。解法：改成 `var s Shape = &r` 赋值。
- 现象：给 `T` 定义了值接收者方法，`*T` 自动也拥有。原因：方法集是单向包含，`*T ⊇ T`。解法：记方向即可——反向（T 拥有 *T 的方法）不成立。
- 现象：接口变量与 nil 比较为 false，但里面装的指针是 nil。原因：接口是 (类型, 值) 二元组，装了 `(*T)(nil)` 的接口不等于 nil。解法：判空要同时检查两半（见 [26_iface_assert](../26_iface_assert/)）。

深入问答：

**Q：为什么 Go 不用 implements 声明，靠隐式实现不会更难排查吗？**
A：编译器在赋值点就报错并指出缺哪个方法（"does not implement Shape (missing Perimeter method)"），排查成本不比显式声明高。

换来的是解耦：接口使用方按需定义，类型提供方无需预知，也给已有类型（含第三方类型）留了"事后满足接口"的空间。

**Q：值接收者和指针接收者到底怎么选？**
A：默认值接收者；需要修改字段、或结构体较大且拷贝开销敏感、或含 sync 互斥量等不可拷贝字段时用指针接收者。关键是一致性——同一类型混用两种接收者会让方法集规则变得难以推理。

**Q：接口变量在内存里长什么样？**
A：一个两字结构（iface）：指向类型元数据的指针（含方法表）+ 指向数据的指针。`%T` 打印的是前半部分；这也是"动态类型"一词的来源。多态调用的分派走方法表，是运行时的一次间接寻址。

**Q：空接口 `interface{}`（`any`）和 Shape 这类接口差别在哪？**
A：`any` 方法集为空，所有类型都满足它——它放弃类型信息换取"什么都装"，取回数据要靠类型断言。Shape 这类小接口则保留行为契约，调用方可以直接 `sh.Area()`。

惯例是接口越小越好（标准库的 io.Reader 只有一个方法）。

接口的运行时表示与类型断言，见 [26_iface_assert](../26_iface_assert/)。
