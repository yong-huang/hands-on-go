# 13 · 有缓冲 Channel：异步队列的三种状态

> 有缓冲 channel（自带固定容量暂存区的 channel）是一条容量固定的传送带：没满就能塞了就走，满了发送方才被挂起。本篇用容量 3 的 channel 发送 10 条消息，打印每一次阻塞的耗时；读完你能分清它的三种状态——未满可发、满则阻塞、关闭后排空——并掌握 `len`/`cap` 观测与 `close` 语义。

## Background

Go 里 goroutine（语言内置的轻量级线程）之间用 channel 传递数据。channel 最基本的形态没有暂存区：`ch <- v` 必须等到接收方就位才能完成，`<-ch` 也必须等到数据到来——两边每次都要"碰头"。

碰头模型在"批量生产、零散消费"时撞墙。假设生产者每 20ms 产出一条、消费者每 30ms 才消化一条：用碰头模型连接，生产者每发一条都要停下来等人，整条流水线的节拍被慢的一方锁死。

Go 为此在 `make(chan T, N)` 里留了第二个参数：N 个暂存位。数据先落进暂存位，对方晚点来取也行；暂存位占满后，发送方依旧会被挂起。它换来的是节奏上的错峰，不是产能上的扩容——这个边界贯穿全篇。

## What

一句话定义：有缓冲 channel 是创建时指定固定容量的一种 channel，用来让发送方领先接收方至多 `cap` 条数据；缓冲未满时发送立即返回，缓冲满时发送方睡眠等空位。

可以把有缓冲 channel 想象成一条定长传送带：发送方把零件放上去就走，接收方从另一头取，传送带上最多同时摆 `cap` 件。但和"无限仓库"不同的是，传送带长度固定——摆满之后发送方只能原地等待，直到接收方取走一件腾出空位。

三种状态对应三种行为：

- 未满可发：`ch <- v` 立即完成，数据进缓冲
- 满则阻塞：`ch <- v` 挂起发送方，直到接收方取走一条腾出空位
- 关闭后排空：`close(ch)` 封住入口，缓冲里已有的数据照常可读

## When to Use

在做什么事的时候选它：

- 在拼接"快生产、慢消费"的流水线时（比如批量读文件喂给耗时的解析器），用缓冲吸收节奏差，让生产者不必每条都同步等人。
- 在做"一次性投递一批任务、固定几个 worker 慢慢消化"时（worker 指干活的 goroutine），容量不小于批大小，投递方就能一口气塞完再阻塞。
- 在做日志/事件收集时，用缓冲吸收突发峰值，下游短暂卡顿不至于立刻把压力反弹回上游。

何时不用：只传一个结果或一个信号时，无缓冲 channel（不带暂存区、双方必须碰头的 channel）的"发送即确认对方收到"更直接；消费长期慢于生产时，加大缓冲只是推迟阻塞，不解决问题。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 无缓冲 channel | 每次传递双方碰头，天然携带"对方已收到"信号 | 需要严格同步语义、传信号或单个结果 |
| 有缓冲 channel（本篇） | 发送方可领先接收方至多 `cap` 条 | 已知节奏错配、需要吸收突发 |
| `sync.Mutex` + 切片队列 | 长度无上限，需自己处理加锁与唤醒 | 需要动态长度或队列之外的集合语义 |

## How It Works

### len 与 cap：缓冲的即时水位

`cap(ch)` 是建好就不变的容量，`len(ch)` 是此刻排队的数据条数。发送前 `len=3/3` 意味着这次发送必然阻塞。

Quick Start 输出里的"此刻缓冲占用 len=0/3 → len=3/3"逐条递增，就是每次发送前用 `len(ch)`/`cap(ch)` 打出的实时水位；第 4 条发送前的 `len=3/3` 提前预告了那次 56ms 的等待。

`len` 只在运行时有意义：读到的瞬间值可能已变，所以它只适合观测，不能做跨 goroutine 的逻辑判断。

### 满则阻塞：背压的最小实现

缓冲满时 `ch <- v` 挂起发送方——不需要任何额外代码，阻塞本身就是"消费不过来就别再生产"的背压（backpressure，上游因下游过载而自动减速的机制）。

demo 的节奏是生产每 20ms 一条、消费每 30ms 一条，缓冲 3 只够垫 3 条，所以第 4 条起每次都要等人收——输出里第 4 条的 56ms 就是这么来的。

### close 不清空：排空后才退出

`close(ch)` 只宣告"不再有新消息"，缓冲里的存货仍可继续读。`for range ch` 会先排空剩余数据，缓冲空且已关闭才退出循环。输出末尾两行印证的正是这两条规则：

- "关闭后再读：v=0 ok=false"——排空后再读，立即返回零值（Go 里变量类型的默认值，`int` 为 0）与 `ok=false`，永不阻塞
- "对账：发完 10 条、收到 10 条，len(ch)=0"——存货已被 `for range` 全部取走

常用表达式速查：

| 表达式 | 含义 | 为什么重要 |
|---|---|---|
| `make(chan int, 3)` | 容量 3 的异步队列 | 第二个参数决定同步还是异步 |
| `len(ch)` | 当前排队条数 | 只用于观测，不能做跨 goroutine 判断 |
| `close(ch)` | 封住发送入口 | 只能由发送方关闭；重复 close 会 panic |
| `v, ok := <-ch` | ok=false 表示已关闭且排空 | 区分"值为 0"和"channel 关了" |

## Pitfalls & Q&A

坑清单（每条按"现象 → 原因 → 解法"读）：

- **现象**：向已关闭的 channel 发送，程序以 "send on closed channel" panic 退出；关闭 nil channel、重复 `close` 同样 panic。**原因**：`close` 只封入口，不会通知所有发送方停手。**解法**：只有发送方在确认不再发送后调用 `close`；多发送方要用 `sync.WaitGroup`（标准库的等待计数器：`Add` 登记一个任务、`Done` 报告完成、`Wait` 阻塞到计数归零）加一个单独的关闭 goroutine 协调。
- **现象**：消费者的 `for range ch` 永不退出，goroutine 越积越多。**原因**：忘了 `close`，`for range` 等不到"缓冲空且已关闭"的退出条件，发生 goroutine 泄漏（已启动却永远无法结束的 goroutine）。**解法**：发送方在发完后调用 `close(ch)`。
- **现象**：缓冲开得很大，程序最终还是卡住。**原因**：消费长期慢于生产，缓冲只延迟阻塞、不消除阻塞。**解法**：正视产能差本身（加消费者或减生产速度），缓冲只用来吸收短期突发。
- **现象**：用 `if len(ch) > 0` 决定是否发送/接收，偶发行为错乱。**原因**：`len` 在读到的下一刻就可能变化，观测与决策之间存在竞态（多 goroutine 同时读写同一状态导致的错序）。**解法**：`len(ch)` 只用来打印观测，收发直接依赖 channel 自身的阻塞语义。

**Q：缓冲大小怎么选？**
A：吸收已知的突发差值（如"生产一批 10 条"就选 ≥10），而不是随手设大——缓冲只是延迟背压，掩盖不了产能差。

**Q：无缓冲和有缓冲的本质区别？**
A：无缓冲的发送/接收是同步握手（双方碰头才完成，天然传递"你收到了"这个信号）；有缓冲则解耦了双方节奏，代价是失去这层同步含义。

**Q：close 应该由谁调？**
A：发送方。接收方无法知道数据是否发完，只有发送方有权宣告结束；多发送方需要额外的协调（如 `sync.WaitGroup` + 单独的关闭 goroutine）。
