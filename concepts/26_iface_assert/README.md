# 26 · 接口组合与类型断言：小接口拼大接口，运行时验明正身

> Go 的接口是隐式满足的，本篇讲清两件事：编译期用接口嵌入（把小接口拼成大接口的写法）组装 `io.ReadWriter` 这类组合接口，运行期用类型断言（从接口变量里取出具体类型值的操作）安全取值。读完你能分清单值/双值断言的适用边界，并用类型 switch 一次分派多种类型。

## Background

只用"大而全"的接口定义会丢掉 Go 接口设计的精髓：小接口才能被广泛实现。`io.Reader`（标准库里"能读"的单方法接口）只有一个方法，所以无数类型都能当 Reader 用；需要"既能读又能写"的函数若各自重新定义一遍完整方法集（一个类型拥有的全部方法），实现方就得重复劳动。

另一边的痛点在取值：拿到一个 `interface{}`（空接口，可以装任何类型值的接口）之后，怎么取回里面具体类型的值？取值形式用错——在类型可能不符时强行取出——不是编译错误，而是一次运行到一半的 panic（崩溃式的运行时错误，会中断当前调用链直至进程退出）。

Go 的应对是把这件事拆到两个时机：拼接口发生在写代码时，取值验证发生在程序运行后。本篇用 `Memory` 类型把"实现方法 → 自动满足三个接口 → 运行时分派"的完整链路演示一遍。

## What

**接口嵌入**是把若干小接口组合成大接口的写法：大接口自动拥有被嵌入接口的全部方法，`io.ReadWriter` 就是 `Reader` 与 `Writer` 的拼装。**类型断言**是运行时从接口变量里取出具体类型值的操作，失败后果由书写形式决定。

心智模型一句话：接口嵌入发生在编译期（小接口拼大接口、方法集即满足），类型断言发生在运行时（问接口变量里装的具体类型是谁）——上行是组合，下行依次走"双值断言 → 单值断言 → 类型 switch"的验证链。

可以把小接口想象成乐高积木的凸点标准：类型只要实现出符合规格的方法，就自动能拼进任何需要该规格的位置，无需任何声明。但和乐高不同的是，出厂（编译）只检查拼装方向是否合法，从成品里辨认具体积木是否对得上，要等到运行时才验证，错了当场崩坏。

## When to Use

- 写通用函数时：参数声明成 `io.Reader` 这类最小接口，文件、网络连接、`bytes.Buffer` 都能传入；需要"读写兼备"时把小接口拼成 `io.ReadWriter`，而不是另立大接口。
- 处理 `interface{}` 数据时：例如解析 `map[string]interface{}` 形态的配置或解码任意 JSON，先用双值断言确认字段的真实类型再取值，失败走 ok 分支而不是崩溃。
- 写按类型分派的逻辑时：同一个接口值可能是 string、int、bool 等多种类型，用类型 switch 把所有分支写在一处，每个分支内直接拿到具体类型。

何时不用：

- 类型编译期已知：直接用具体类型。断言只该出现在"真实类型只有运行时才知道"的边界上。
- 类型集合在编译期可枚举：Go 1.18 起的泛型（类型参数：函数签名里留类型占位，调用时才确定具体类型）能替代大部分 `interface{}` 加断言的写法，并保留编译期检查。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 双值断言 `v, ok := x.(T)` | 失败返回 ok=false 与零值，程序继续 | 类型不确定、失败属正常分支 |
| 单值断言 `v := x.(T)` | 失败直接 panic | 逻辑上必定成功（前一步刚确认过类型） |
| 类型 switch `switch v := x.(type)` | 一次判定分派多类型，分支内 v 自带具体类型 | 三种及以上类型分派 |
| 泛型类型参数 | 编译期实例化，无运行时判定 | 类型集合编译期可枚举时优先选它 |

## Quick Start

前置条件：本机已安装 Go 工具链（`go run` 可用），无第三方依赖。

```bash
cd concepts/26_iface_assert
go run main.go
```

预期输出（节选）：

```text
========== 1. 接口组合：Reader + Writer → ReadWriter ==========
rw.Read() = world | 剩余一读: hello
========== 2. 双值断言：v, ok := x.(T) ==========
x.(string) 成功: gopher （长度 6 ）
x.(int) 失败但安全: ok = false ，n = 零值 0
========== 3. 单值断言：v := x.(T)，失败会 panic ==========
尝试 x.(int)，x = 42
断言成功: v = 42
尝试 x.(int)，x = text
recover 捕获断言 panic: interface conversion: interface {} is string, not int
========== 4. 类型 switch：一次分派多种类型 ==========
类型 switch → string: "go" (len=2)
类型 switch → int: 100 (翻倍=200)
类型 switch → bool: true (取反=false)
类型 switch → 其他: float64 = 3.14
```

诚实预期：程序以退出码 0 正常结束；上面是节选——完整输出里第 1 段末尾还有一行"Memory 通过方法集自动满足…"，程序最后会自打印一段「总结」。第 3 段的断言 panic 已被 recover 拦截，进程不会崩。

核心实现只有三小段。第一段是接口嵌入的完整定义。这段在做什么：把 `Reader` 与 `Writer` 的方法集并进 `ReadWriter`，等价于标准库 `io` 包里的 `io.ReadWriter`：

```go
type ReadWriter interface {
    Reader
    Writer
}
```

第二段对照两种断言形式。这段在做什么：双值形式失败时 ok 为 false、变量取零值；单值形式失败直接 panic：

```go
s, ok := x.(string) // 双值：失败 ok=false，s 是 string 零值 ""，程序继续
v := x.(int)        // 单值：失败直接 panic: interface conversion
```

第三段是类型 switch 的骨架。这段在做什么：对同一接口值做一次类型判定，每个分支里的 `v` 自动具有对应的具体类型：

```go
switch v := x.(type) {
case string:  // 这里 v 已是 string
case int:     // 这里 v 已是 int
default:      // v 保持接口类型本身
}
```

## How It Works

### 接口嵌入：小接口拼成大接口

Quick Start 的两行定义就是全部语法。嵌入可以多层，`io.ReadWriteCloser` 就是三个小接口的拼装。方向上有条不对称规则：大接口的值可以隐式赋给小接口变量（`var r Reader = rw` 合法），反过来不行——编译器只看方法集是不是超集。

### 方法集即满足

`*Memory` 实现了 `Read` 和 `Write`，于是它同时是 `Reader`、`Writer`、`ReadWriter` 三者的实现者——Go 没有 `implements` 关键字，编译器在赋值那一刻自动检查。

代价是报错晦涩：漏实现一个方法时，错误只在赋值处出现（"does not implement ..."），不在类型定义处。

输出第 1 段的 `rw.Read() = world` 就来自这次赋值：`var rw ReadWriter = &Memory{}` 编译通过，即证明方法集满足。

### 双值断言 vs 单值断言

双值形式是防御性代码的标配；单值形式只在"逻辑上必定成功"时使用，例如前一步刚用类型 switch 确认过类型。输出第 3 段的 `recover 捕获断言 panic: ...` 就是单值形式失败的原始报错。

recover（Go 内建函数，拦截 panic 并转回正常执行，须在 defer 里调用）能救场，但那是事故处理，不是控制流；defer（注册为"函数返回前必执行"的延迟调用）在 panic 时依然执行，这是它能兜底的原因。

### 类型 switch：多类型分派的正解

一个 `switch` 覆盖所有分支，比一串 `if s, ok := x.(T); ok` 更清晰。输出第 4 段的四行"类型 switch →"就是四种 case 的实际分派结果：`float64 = 3.14` 落入 default 分支，此时 `v` 保持接口类型本身，其余分支里的 `v` 都已是具体类型。

### 关键语法速查

| 语法 | 含义 | 为什么重要 |
|---|---|---|
| `type RW interface { Reader; Writer }` | 接口嵌入 | io.ReadWriter 的拼装方式 |
| `var rw ReadWriter = &Memory{}` | 方法集自动满足 | 无 implements，赋值即检查 |
| `s, ok := x.(T)` | 双值断言 | 失败安全：ok=false、零值 |
| `v := x.(T)` | 单值断言 | 失败 panic，仅限"必定成功"场景 |
| `switch v := x.(type)` | 类型 switch | 每个分支内 v 具有具体类型 |

## Pitfalls & Q&A

坑清单（每条均可复现）：

- **单值断言失败是 panic，不是零值**。现象：程序当场中断，报 `interface conversion: interface {} is string, not int`（输出第 3 段可见原文）。原因：单值形式把类型不符当致命错误处理。解法：类型不确定处一律用双值形式，失败走 ok 分支。
- **nil 接口上断言必崩**。现象：对零值接口变量做任何断言都 panic。原因：nil 接口里没有动态类型可供比对。解法：断言前先 `if x == nil`。
- **值接收者与指针接收者的方法集不同**。现象：`Memory`（值类型）赋给含 `Write` 的接口编译失败。原因：含 `Write` 的接口只能由 `*Memory` 满足。解法：用指针赋值——本篇 `var rw ReadWriter = &Memory{}` 就是这么写的。
- **类型 switch 的多类型 case 共享不了具体类型变量**。现象：写 `case int, int64:` 后想直接用 `v` 的具体类型，`v` 却保持接口类型。原因：多类型合并时 `v` 无法具备唯一的具体类型。解法：每种类型单独一个 case。
- **接口转换方向弄反**。现象：`var r Reader = rw` 能编译，反方向直接赋值报错。原因：大接口转小接口时方法集是超集，可隐式赋值；反方向不成立。解法：小接口转大接口才需要断言。

**Q：为什么标准库全是 `io.Reader` 这种单方法小接口，而不是一个大 IO 接口？**

小接口的方法集要求低，能被最多的类型实现——文件、网络连接、`bytes.Buffer` 甚至 `strings.Reader` 都是 `io.Reader`。消费方按需组合（`ReadWriter`、`ReadWriteCloser`），接口越组合越精确，实现方却只需实现最小集。

**Q：双值断言失败时 ok=false，第一个变量是什么？**

T 的零值（输出第 2 段的 `n = 零值 0`）。双值形式因此永不 panic，但必须检查 ok 再用值——只拿值不看 ok，等于把单值断言的 panic 换成静默的逻辑错误。

**Q：类型 switch 和一串 if-ok 断言，除了写法还有什么区别？**

语义上等价，但类型 switch 对同一接口值只做一次类型判定，且分支内变量自动带具体类型；编译器还能检查 case 类型是否合法（重复 case 报错）。运行时两者都查接口的 itab（runtime 里记录"接口—具体类型"配对信息的结构，断言与分派查的就是它），性能无实质差异。

**Q：接口的动态类型与动态值是什么？断言到底在比什么？**

接口变量内部是 (动态类型, 动态值) 二元组——动态类型是装入值的具体类型，动态值是那份数据本身。断言 `x.(T)` 比的是动态类型是否与 T 相同（T 是接口时，比动态类型是否实现 T）。

这解释了两个经典坑：动态类型相同但值不同时断言照样成功；nil 指针装入接口后接口本身不等于 nil（typed-nil）。运行时表示的深入原理见 [internals](../../internals/01_slices/) 相关篇目。
