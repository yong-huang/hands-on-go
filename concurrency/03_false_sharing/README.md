# 03 · false sharing 与缓存行填充：把计数器各自关进一条缓存行

> 8 个 goroutine 各写各的计数器，逻辑上零共享，却可能互相拖慢 19 倍——只因为它们紧排在同一条缓存行里。本篇实测无填充与 64 字节填充两版实现，给出基准入档与"倍数不及格时的排查清单"。

## Background

并发程序有一个反直觉的坑：逻辑上完全独立的数据，性能上却互相纠缠。

典型的现场是分片计数器：按 user_id 取模分片，8 个 goroutine 各自累加
自己的计数器，代码 review 看不到任何共享。压测却显示吞吐量随并发数不升
反降，pprof 的时间全花在原子指令上，没有锁、没有争用、没有解释。

解释在硬件层：CPU 与内存之间不按字节搬数据，按缓存行（cache line，CPU
与内存间数据搬运的最小单位，本机 64 字节）整行搬运。核心 A 写了行内的
1 个字节，核心 B 手里这一行的副本就整行作废——哪怕 B 只关心行内另一个
毫不相干的字节。

**定义**：这种"逻辑无共享、物理同行"导致的性能损失就是伪共享（false
sharing）。解法是缓存行填充（padding）：给每个热写变量补齐到独占一行。

## What

**定义**：伪共享是一致性协议（多核间保持缓存一致的 MESI 类协议）按行
粒度工作时产生的性能现象——正确性毫无问题，纯粹是行内无关字节被连坐。

判断一个热点变量是否被伪共享，只看两件事：地址是否落在同一条 64 字节
行内；是否被不同核心同时热写。两者同时成立才有伪共享。

**心智模型**：可以把缓存行想象成合租房的房租单——一个人开空调，全屋
电费重算，室友的账单全被连坐。但和合租房不同的是，这里的"连坐"没有
商量余地：只要地址同房，写一次作废一次，与变量语义完全无关。

## When to Use

什么时候需要想到伪共享：

- 分片计数、每个 worker 的统计量、对象池的 per-P 字段这类"各写各的"热数据
- 压测发现吞吐不随核数扩展，而 profile 显示时间耗在原子指令或锁前缀上
- 阅读标准库源码：`runtime.m` 里的 per-P 统计字段就带显式填充注释

什么时候不用：

- 冷数据、只读数据、写频率低于每微秒一次的数据：填充只增加内存占用
- 一个缓存行本来就装得下的热数据组（互斥锁 state + 其元数据同行为常态）

同类方案对比：

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 64 字节填充 | 零运行时成本，多占内存 | 热写字段固定、数量少的结构 |
| 分片计数（项目 21） | 降低争用也顺带分缓存行 | 计数场景，填充与分片常配合 |
| `runtime_procPin` 局部化 | 写完全不跨核 | 标准库 per-P 结构的做法 |

前置条件：多核机器 + Go 1.19 及以上，纯标准库。


## How It Works

填充结构体的核心就三行——声明、对齐、校验：

```go
type cell struct {
	n atomic.Int64
	_ [cellSize - 8]byte // atomic.Int64 占 8 字节，凑满 64
}
```

Go 没有 `aligned(64)` 属性，填充是唯一的语言层手段。分配器只保证 8 字节
对齐，所以 `newPaddedCounters` 多分配一段、用 `unsafe.Add` 把起点推进到
第一个 64 字节边界；元素间隔恰为 64 字节，后续元素自动逐个落上边界。

你在输出里看到的"对齐校验 8/8"，校验的就是这件事——对齐失败的填充版
只会快一点点，基准结论全部作废。

**为什么 Apple Silicon 仍按 64 填充**：Apple 芯片 L1 数据缓存的行为宽度
是 64 字节，与 x86 一致，L1 层的伪共享按 64 填充即可消除。

需要注意的
细节是 Apple 在 L2 层按 128 字节成对取行（line pair），原子操作可能牵动
相邻行，因此填充能把 L1 连坐消干净，跨 cluster 的一致性流量仍会残留——
这正是实测填充版摊薄 0.33 ns/op、没到单核基线 0.56 ns 八分之一的原因。

**倍数不及格时的排查清单**：

- `GOMAXPROCS` 是否被容器限额压到低位：worker 数不足 8，行弹跳不充分
- 频率漂移：前后两版基准间隔太久，比较基准跑 `-count=5` 取中位数
- goroutine 恰好全落在共享 L2 的同 cluster：`taskset`/`GOMAXPROCS` 分档重跑
- 编译器优化掉了循环：加 sink（本项目的正确性测试断言精确计数）

## Pitfalls & Q&A

**坑 1：只加填充不查对齐。** 若基址只 8 字节对齐，第一个 cell 会横跨两条
行，效果减半。本项目用 `reflect.ValueOf(&cs[i]).Pointer()%64==0` 逐个校验。

**坑 2：`uintptr(unsafe.Pointer(p))` 算对齐被 go vet 点名。** uintptr 与
unsafe.Pointer 互转是 vet 判定的可疑模式。改用 `unsafe.Add`（1.17+ 的
认可 API）做指针推进，基址经 reflect 取出，vet 静默通过。

**坑 3：基准数字快得离谱先怀疑作弊。** 本机填充版 0.33 ns/op、单核基线
0.56 ns/op，初看低于一条原子指令的直觉成本。用独立计时程序交叉验证
（10 亿次自增 573ms，带 sink），确认 Apple 核上 L1 命中的原子自增确实
约 2.5 个时钟周期，数字是真的。

**Q：为什么不是把字段排序凑行，而是硬填充？** 排序只在布局恰好的时候
有效，任何人加一个字段就全部失效。填充把"这一行只属于谁"写进类型定义，
不依赖后人对布局的想象力。
