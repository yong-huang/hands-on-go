# 05 · mini Mutex：盲写双模式互斥锁

> 不看 src/sync/mutex.go，按自己的理解复刻一把带正常/饥饿双模式的互斥锁：CAS 复合状态字加双通道信号量，通过 `-race -count=200` 的 100 goroutine 压测后，再对照标准库逐条出差异表。

## Background

互斥锁是并发里最"日用而不自知"的原语：每天调用 Lock/Unlock，很少有人能
说清持有者睡眠时锁把状态记在哪、醒来凭什么轮到自己。

理解它的传统做法是读源码，但读过的代码留不下判断力——注释里每行都认识，
合上文档还是写不出状态机。这个仓库此前的做法是逐位拆解标准库的 state 布局，
拆解属于"读懂"，离"写对"还差一次实操检验。

盲写是补上这一步的手段：先把标准库的行为约定（快路径 CAS、自旋窗口、
1ms 饥饿阈值、交接式解锁）当作规格，凭理解写出实现并压测到绿，最后才
对照真实源码列差异表。写错的地方，就是理解与实现之间的缝。

## What

**定义**：mini Mutex 是一把零值可用的互斥锁，用单个 `atomic.Int32` 状态字
记账，慢路径靠通道信号量睡眠与唤醒，行为对齐标准库的正常/饥饿双模式。

状态字布局：bit0 是 locked（含"交接在途"的账面占用），bit2 是 starving
（所有权定向交接中），bit3 起是等待者计数。信号量是两个无缓冲通道：
nudge 递送"去重抢"的普通叫醒，handoff 递送承载所有权的交接令牌。

**心智模型**：可以把状态字想成餐厅门口的候位牌——locked 是"有桌在用"，
计数是排队人数，starving 是"本店改为叫号入座"。但和餐厅不同的是，叫号
凭证（handoff 令牌）丢了桌子就没了主人，所以投递必须签收，不允许过号作废。

## When to Use

什么时候值得手写互斥锁：

- 学习内存模型与调度交互：盲写加压测是检验理解的唯一手段
- 需要在锁内嵌自定义记账（如公平性统计）且能承担出错代价的场景
- 阅读标准库前的预热实现，读完对照差异收尾

什么时候必须用标准库：

- 一切生产代码：标准库有 runtime 信号量、TryLock、noCopy 与竞态检测钩子
- 对尾延迟敏感的服务：自定义实现的交接语义未经多年生产验证

同类实现对比：

| 实现 | 差异 | 什么时候选它 |
|---|---|---|
| sync.Mutex | runtime 信号量，63 ns/op 争用成本 | 默认选择 |
| mini Mutex（本篇） | 通道信号量，语义对齐但更慢 | 学习与实验 |
| channel 互斥（容量 1） | 语义最简，无饥饿保护 | 极小工具，非关键路径 |

## How It Works

慢路径是状态机的全部。拿到一次锁只有三种方式，对应 CAS 成功后的三种旧值：

- 旧值完全空闲：`newState |= mutexLocked`，直接占有后离队返回
- 旧值被占或交接在途：等待者计数 +1（只加首次），去通道上停车
- 旧值带 starving：所有权由 Unlock 定向交接，停车等 handoff 令牌签收

Unlock 的分岔：无排队者时清位收工；有排队者且 starving 置位时**保留
locked 位**并阻塞投递交接令牌——令牌即所有权，丢了锁就没了主人；否则
清位、记一笔欠账唤醒再尝试投递 nudge。欠账（wakeups 计数）保证叫醒
不丢：投递失败时额度留在计数里，下一个排队者销账后回去重抢。

**与标准库的差异表**（盲写后对照 Go 1.26 `internal/sync/mutex.go`）：

| # | 简化点 | 标准库做法 | 后果 |
|---|---|---|---|
| 1 | 信号量用双通道加欠账计数 | runtime 信号量（sudog 队列、queueLifo 队首入队） | 争用慢约 1.7 倍；重排队者排队更靠后 |
| 2 | 省略 woken 位 | Unlock 靠它跳过无效唤醒，且作为状态自检依据（可 throw） | 假唤醒更多（靠重抢兜底）；状态机错误无自检 |
| 3 | 自旋条件只有核数与轮数 | runtime_canSpin 另查 P 本地队列为空；doSpin 用 PAUSE 指令 | 单核或队列忙时标准库放弃自旋，mini 会白转烧 CPU |
| 4 | 交接期间保留 locked 位 | 标准库清 locked、靠 starving 位挡新到者，醒来补账加回 | 无正确性差异，状态编码不同 |
| 5 | 无 TryLock / noCopy | 标准库提供 TryLock，noCopy 让 vet 报拷贝错误 | 试锁要自己写 CAS；拷贝锁不会被 vet 点名 |
| 6 | 无 race.Acquire/Release 钩子 | 标准库显式告知 TSan 锁的先后关系 | mini 靠通道与原子操作天然可被 -race 理解，无需钩子 |

基准实测（`-count=3` 取中位数，ns/op）：

| 基准 | mini Mutex | sync.Mutex |
|---|---|---|
| 无争用 | 8.71 | 4.52 |
| 有争用（18 P） | 109.1 | 63.19 |

无争用差距来自慢路径多出的结构（欠账计数、双通道判断都在快路径之后的
分支里，主要差异是标准库快路径可内联且更短）。争用差距主要是通道调度
与 runtime 信号量的差距，差异表第 1 行。

## Pitfalls & Q&A

**坑 1：第一版盲写死锁 600 秒。** 正常唤醒重抢的 waiter 从不撤销排队
计数，计数越积越大；计数提前归零后 Unlock 停止发唤醒，最后一个停车者
睡死。修法是让计数与"还在排队的人数"严格相等，退出前必须销账。

**坑 2：假唤醒冒充所有权。** 把普通叫醒与饥饿交接混在同一个通道里，
一个排队者把承载所有权的令牌当普通假唤醒消费掉，随后自己带账停车，
锁进入"有主但主人睡着"的死局。修法是拆成双通道：所有权令牌阻塞投递、
必须签收，普通叫醒才允许欠账兜底。

**坑 3：醒来看见 starving 位就以为自己被交接。** starving 位是"某个
waiter 重排队时"置上的，读到的 goroutine 未必是交接对象，实测出现双
owner 后 unlock 报"unlock of unlocked"。所有权必须由通道令牌显式区分，
不能靠事后读状态反推。

**Q：为什么 mini 版不需要 race 钩子？** 标准库的 state 是裸 int32 加
runtime 信号量，TSan 看不懂其先后关系，必须用 race.Acquire/Release 显式
告知。

mini 版的同步全由原子操作和 channel 完成，这两类本身就在检测器的
理解范围内，200 轮零报告即是证据。
