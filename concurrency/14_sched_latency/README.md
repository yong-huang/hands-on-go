# 14 · 调度延迟测量：Runnable→Running 的 p50/p95/p99

> 本篇测"G 就绪了却跑不上"要等多久：空闲场景 p99=12µs，满载场景 p99=126.5ms，四个数量级的差距来自哪，用 runtime/metrics 官方直方图给分位数、用 go tool trace 的 sched profile 交叉验证。读完本篇能选对测量口径，并把 p99 差异归因到排队、抢占、GC 三个来源。

## Background

请求毛刺的排查里有一类最难缠的问题：CPU profile 显示不忙，p99 却周期性出现尖峰。一个常见的隐藏嫌疑是调度延迟——goroutine 已经就绪，却没有 P 可用，排队干等。

在运行时提供官方口径之前，只能靠在自己代码里打时间戳：spawn 前记一个时刻、回调第一行再记一个。它测得到自家代码的间隔，测不到"在运行队列里排了多久"，更测不到别人的 G 排了多久。

现代 Go 给出两个官方出口：runtime/metrics 的 /sched/latencies:seconds 直方图，持续累积全量调度延迟分布；runtime/trace 落盘后可用 go tool trace 生成 sched profile。本篇把两个口径放进同一实验对照读数。

## What

调度延迟（scheduling latency）定义为 G 处于 _Grunnable 状态、到被放上 P 转入 _Grunning 为止的累计时长。两个官方口径的分工：

| 口径 | 输出 | 适合 |
|---|---|---|
| /sched/latencies:seconds | 全量分布直方图 | 算 p50/p95/p99 |
| go tool trace -pprof=sched | 按调用栈聚合的样本数与延迟总和 | 均值交叉验证、按人群拆分 |

一个必须知道的细节：直方图是抽样统计——运行时源码里 gTrackingPeriod=8，
每 8 次状态迁移才跟踪 1 次。所以报表里的"样本数"约为实际迁移数的八分之一，
分位数的形状仍然有效，但不能把样本数当成 G 的个数。

可以把直方图想象成路口的抽样测速：不是每辆车都测，但测到的分布能代表车流。
但和测速不同的是，它按"第几次迁移"做等距抽样，且高延迟的迁移不会遗漏——
只要恰好落在抽样点上。

## When to Use

- **容量评估**：满载时一次典型调度迁移等多久，决定"加并发"是加吞吐还是加排队。
- **毛刺归因**：把 p99 尖峰拆到排队、抢占、GC 三个来源，而不是笼统说"调度慢"。
- **何时不用**：需要单次、确定性的微秒级读数时别用它（抽样+运行抖动），用基准测试。

| 手段 | 差异 | 什么时候选它 |
|---|---|---|
| runtime/metrics 直方图 | 零窗口成本，持续累积，1/8 抽样 | 线上随时读，分位数 |
| trace sched profile | 需录制窗口，按栈聚合 | 归因到代码位置，验均值 |
| 自打时间戳 | 只测自家间隔 | 业务侧近似估计 |

## Quick Start

需要 go 1.26，无第三方依赖。空闲与满载各测一个窗口：

```bash
go run ./14_sched_latency/
```

真实输出（具体数值每次运行不同；量级关系稳定：满载比空闲高 3~4 个数量级）：

```text
== 调度延迟测量（go1.26.5，GOMAXPROCS=18）==
  空闲     样本=  1894  p50=6µs        p95=10µs       p99=12µs
  满载     样本=  2258  p50=32.635ms   p95=109.931ms  p99=126.514ms
```

trace 交叉验证（同一程序带 -trace 录制，再取官方 sched profile）：

```bash
go run ./14_sched_latency/ -trace=sched.out
go tool trace -pprof=sched sched.out > sched.pb.gz
go tool pprof -raw sched.pb.gz
```

真实输出节选（每行 = 按栈聚合的一组：样本数与延迟总和，单位 ns）：

```text
contentions/count delay/nanoseconds
      3054   59864638: 8 9 
       157   61174655: 
         5   39931648: 17 18 
```

## How It Works

### 直方图差分

测量窗口前后各读一次 /sched/latencies:seconds，逐桶相减得到窗口内新增的分布；
算分位数时按累计计数定位桶，桶内线性插值。窗口里 spawnShort 分 40 批、每批
200 个短 G，制造约 8000 次"就绪→运行"迁移。

### 一次运行的完整读数

同一窗口的两组官方口径（数字来自同一次 -trace 运行）：

| 场景 | 样本 | p50 | p95 | p99 |
|---|---|---|---|---|
| 空闲 | 1795 | 13µs | 24µs | 29µs |
| 满载 | 2515 | 30.91ms | 109.603ms | 125.763ms |

p99 差异的三个来源，逐条对到数字上：

- **抢占**：满载下每个占 P 的 G 超 10ms 就被 sysmon 抢走、扔进全局队列重新排队
  （见 [12_preemption](../12_preemption/)），等待下一轮常要 10~100ms+
  ——直方图 25~134ms 区间的主体就是这类"被抢占后的再排队"。
- **队列排队**：短 G 与满载 G 同队竞争。trace 口径把人群拆开了：
  3054 个短 G 样本共 59.86ms，均值 19.6µs——它们多数排在 spawner 的
  本地队列快车道上（机制见 [11_work_stealing](../11_work_stealing/)）。
- **GC**：trace 里最大的单组（5 个样本、均值 8ms）与 STW/标记区间相邻。
  直方图无法归因，必须靠 trace 对照——这正是两条口径并用的原因。

### 读懂满载 p99 的口径

满载 p99=125.763ms 描述的是"满载系统里一次典型迁移的等待"，它的主体是满载 G
自身被抢占后的循环排队；新产生的短任务大多走本地队列，真实等待是 µs 级
（trace 口径的 19.6µs）。下结论前先分清问的是哪个人群。

## Pitfalls & Q&A

**把样本数当 G 数**。1/8 抽样下 8000 次迁移只记到约 2000 个样本。
要看真实迁移次数，用 trace 口径或自己计数，别用直方图计数乘系数硬猜。

**用满载分位数回答"新任务要等多久"**。直方图不分人群，满载场景的大值主体是
负载生成器自身。归因到"某类 G"，用 trace sched profile 的按栈聚合
（看得到 19.6µs 与 8ms 两个世界），或者控制负载生成器不被统计。

**把桶边界当精确值**。直方图前段以 64ns 步进、后段指数放宽，插值假设桶内
均匀分布。p50 落在细桶区可信；p99 落在宽桶区时只能当量级看。

**Q：为什么不用 trace 提取逐 G 分位数？** 官方工具链的 -pprof=sched 只输出
按栈聚合的计数与总和；/jsontrace 导出里 unblock 流事件锚定在"开始运行"时刻，
拿不到就绪起点。

第三方 reader（x/exp 的 trace 包）可解析逐 G 事件，
但本项目保持纯标准库，故分位数用 runtime/metrics（官方口径中唯一给分布的），
trace 只做均值与人群交叉验证。

**Q：runtime.Gosched 采样法是什么时候的选择？** 在没有 runtime/metrics 的
老版本上，用后台 G 循环让出并自测两次被调度的间隔，只能得到上界式的粗估计。
本机 go1.26 有官方口径，未采用该方法。
