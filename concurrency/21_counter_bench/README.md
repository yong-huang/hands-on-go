# 21 · 计数器三路基准：Mutex / atomic / 分片填充的争用扩展性实测

> 同一个"并发安全计数"用三种实现各跑一遍 1/2/4/8/16 并发五档基准：锁把核串行化的代价、单缓存行乒乓的固定成本、分片填充后的线性扩展，全部用实测数字说话，并用中位数脚本压掉基准抖动。

## Background

并发计数的老写法是 `sync.Mutex` 保护一个 int64：一个字段加一把锁，
六行代码，正确性无可指摘。代码评审也从未拦下过它——单看任何一次
加锁，成本都只有几十纳秒。

撞墙发生在扩容时：服务的某个统计计数被放大到每秒百万次调用，机器
核数越加越多，这个计数器反而成了瓶颈，而且曲线形状反直觉——加核
不提速甚至降速。

问题不在"锁太慢"，在争用（contention，多个核同时
抢同一个同步对象）：临界区把所有核排成串行队列，热点数据所在缓存
行的所有权在核间反复易手。

回答"多快会坏、哪种方案扛得住多少并发"不能靠推理，要靠基准矩阵。
本篇把三种实现放进同一套 -bench 矩阵里实测。

## What

**定义**：三实现是同一契约（并发 Add、读总数）的三档代价模型，
从"一把锁"到"无锁单变量"再到"无共享分片"。

| 实现 | 写路径 | 争用行为 |
|---|---|---|
| `MutexCounter` | Lock 后 `n++` 后 Unlock | 全部核串行化，锁的缓存行弹跳 |
| `AtomicCounter` | 一条 `atomic.Int64.Add` | 无锁，但全核写同一缓存行 |
| `ShardCounter` | 协程认领的分片上加 | 分片各自独占 64B 缓存行，零共享 |

可以把三种实现想成三间食堂的打饭窗口：mutex 是只有一个窗口排队
（队越长越慢），atomic 是一个窗口但 everyone 递同一张卡（每次都要
等卡传回来），分片是每人一个独立窗口。但和食堂不同的是，"窗口数"
由协程认领决定——认领了同一个分片，就退化回 atomic 的乒乓。

## When to Use

- 给热点统计计数（QPS、字节数、错误数）选型：先测本机的争用曲线，
  再决定要不要为它上分片
- 做基准方法论练习：-cpu 档位、-count 取中位数、ReportAllocs、
  基准不带 -race，这套流程适用于所有微基准
- 判断"要不要优化"：如果 mutex 档位曲线对本服务的调用频率足够平
  （ns/op × QPS 占核时可忽略），不必换实现

何时不用：计数不是热路径（每秒千次以下）时三实现无感差异，选
mutex 的可读性；读多写少且临界区含多条操作时，锁内批处理反而摊薄
锁成本，分片无优势。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| MutexCounter | 可读性最好，争用最差 | 冷路径、临界区含多条操作 |
| AtomicCounter | 一条原子加，常数级争用成本 | 单变量、中低频更新 |
| ShardCounter | 写端零共享，读端求和 | 热点计数、写多读少 |

## Quick Start

前置条件：go 1.26，纯标准库。运行分步演示：

```bash
go run ./21_counter_bench/
```

真实输出（第 3 步耗时每次不同，量级参考；守恒校验固定）：

```text

MutexCounter(锁+int64) / AtomicCounter(原子加) / ShardCounter(16 分片×64B 填充)。
paddedShard 实际大小 = 64 字节（固定，恰好一条缓存行）

== 第 2 步：守恒校验（8 协程 × 10000 次）==

== 第 3 步：争用快测（16 协程 × 200 万次，耗时每次不同）==
mutex  ：  1982.5 ms（    16 Mops/s）
```

权威矩阵与中位数脚本（基准不带 -race，竞争检测会扭曲临界区成本）：

```bash
go test -run '^$' -bench . -benchmem -cpu=1,2,4,8,16 -count=5 \
```

|---|---:|---:|---:|---:|---:|
| MutexCounter | 4.121 | 31.66 | 88.95 | 81.00 | 65.38 |
| AtomicCounter | 1.582 | 13.83 | 13.30 | 14.15 | 12.88 |

```bash
go test -race -count=10 ./21_counter_bench/   # ok  1.913s
```

## How It Works

矩阵的三条曲线各有形状。mutex 从 1 到 2 并发涨 7.7 倍（4.12 →
31.66ns），4 并发见顶 88.95ns——此时核间争抢完全压过加锁本身；
8 与 16 档反而回落到 65~81ns，原因是信号量队列的批处理交接把唤醒
成本摊薄了，非单调但量级不变：全程比 atomic 慢 5~7 倍。

atomic 的曲线近乎平坦（13ns 上下）：所有核轮流写同一条缓存行，
每条原子加都要等缓存行所有权到达本核，这个跨核往返是固定成本，
不随核数增长——争用上限就是"每往返一次"。

ShardCounter 随并发上升反而更快（0.79 → 0.39ns）：ns/op 是全组
摊薄值，各协程只写自己的缓存行后，增加协程纯粹是并行度增加。
16 档回升到 0.92 是因为 16 个工作协程超过物理核数，超订
（oversubscription，可运行协程多于核）引入了调度切换开销。

**结论句（以实测为准）**：本机任何并发档位 mutex 都不是最快——
"低并发下 mutex 反而最快"的直觉在 go1.26 + Apple Silicon 上不成立，
1 并发时它已比 atomic 慢 2.6 倍（无竞争的 Lock/Unlock 是两次原子
操作，atomic.Add 是一次）。

真正的分界线是 2 并发：mutex 从这里开始
崩坏，而分片从这里开始反超 atomic。

## Pitfalls & Q&A

**坑 1：基准开着 -race 跑。** 竞争检测给每次内存访问插桩，临界区
成本放大几十倍，曲线形状完全失真。规则：-race 只进测试，不进基准。

**坑 2：分片后仍按调用随机选片。** 每次 Add 换一个分片，等于把
一条缓存行的流量摊到十六条上再加一遍，本地性尽失。分片必须按
协程固定认领（协程号 → 分片），这是方案成立的前提。

**坑 3：单次基准当结论。** -count=5 取中位数是为了压掉频率漂移与
后台任务的抖动；对比两实现时差异小于 10% 应视为持平（见 mutex
8 与 16 档的回落，不应过度解读）。

**Q：填充为什么是 56 字节？** 缓存行 64B，`atomic.Int64` 占 8B，
补 56B 后 `unsafe.Sizeof` 恰为 64（TestPaddedShardFillsCacheLine
钉住这个断言）。
