# 17 · 泛型并发原语库：Chan/Pipe/Merge/Split 与三级流水线

> 用泛型把管道模式收成四个可组合组件：Chan[T]、Pipe[T,U]、Merge[T]、Split[T]，自动完成"转发 + 级联关闭"，并组装三级流水线实测各阶段吞吐。读完能按 API 表拼装流水线，并说出两个必须手写的场景边界。

## Background

手写管道时每个阶段都是同一套四件套：起 goroutine、for 循环收发、
转发进下一段、收尾关闭下游。阶段一多，这套样板重复出现在每个环节，
而且"谁负责关闭"最容易出错——漏关一处，下游全部永久阻塞。

泛型（Go 1.18 的类型参数）解决了另一半个痛点：变换阶段的输入输出
类型可以不同，不必退回 `interface{}` 加类型断言的老写法，`Pipe[int,
float64]` 这样的阶段签名让编译器替你查类型。

本篇把样板收进四个组件：通道句柄、变换、扇入、扇出，用"级联关闭"
协议保证收尾唯一，再组装成流水线验证吞吐与守恒。

## What

**定义**：一组构建在内置 channel 之上的泛型组件库，用类型参数表达
阶段的输入输出类型，用统一协议表达关闭的传播。

| 组件 | 签名要点 | 语义 |
|---|---|---|
| `Chan[T]` | `Send`/`Recv`/`Close` | 幂等关闭；panic 语义与内置一致 |
| `Pipe[In,Out]` | workers + 变换函数 | N 个 worker 共享消费；输入排空后自动关闭输出 |
| `Merge[T]` | 可变参数输入 | 每路一个转发 goroutine，全部排空后关闭输出 |
| `Split[T]` | n 个输出分支 | 严格轮转分发；某分支停消费则全停 |

可以把组件库想成流水线车间的标准工位：工位之间用传送带（channel）
连接，收班时从源头到末端逐段关闸（级联关闭）。但和车间不同的是，
"分流"工位是严格轮流投料——任何一个下游工位停手，整条线都会停。

## When to Use

- 阶段数量多、各阶段类型不同的数据流水：组件替你管理 goroutine 与关闭
- 需要扇入扇出组合（多源汇聚、多路负载均衡）：Merge/Split 一行拼装
- 同一管道要按不同类型参数复用：泛型阶段免断言、免重复实现

何时不用：

- 数据量小、就两三个阶段：直接手写 channel 更清晰，引组件反而多一层
- 需要 select 多路竞争或精细背压控制：组件只覆盖"一路进一路出"的形状
- 单纯的生产者消费者：一个 buffered channel 就够，无需任何封装

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| 手写 channel 管道 | 样板多但直白，无抽象成本 | 阶段少、数据量小 |
| 本组件库 | 级联关闭 + 类型安全组合 | 阶段多、形状规整的流水线 |
| 裸 goroutine 各自为战 | 无统一关闭协议 | 不建议，漏关即死锁 |

## Quick Start

前置条件：go 1.26，纯标准库。运行三级流水线演示：


## How It Works

级联关闭是整套库的骨架，Pipe 的收尾五行是代表：

```go
go func() {
    wg.Wait()    // 联结：所有 worker 退出（输入已排空）
    out.Close()  // 才轮到我关闭输出，下游的 Recv 这时才见 ok=false
}()
```

每个组件都遵守"联结所有发送方之后才关闭"的契约：Close 用 CAS 保证
幂等，多路同时关闭只有第一次生效。你在 Quick Start 看到的守恒数字
（200000/200000 与 Σ(x²+分支偏移) 精确相等）就依赖这条协议——任何
一段提前关闭或漏关，数值都对不上。

Split 的轮转是确定性的：第 i 个元素进分支 `i%n`，因此期望值可以
离线算出并由测试精确断言。轮转同时意味着队头阻塞：分支 1 不消费时，
分发器停在"给分支 1 送第 2 个元素"，分支 0 的后续元素全部排队等待
（TestSplitHeadOfLineBlocking 断言了这一行为）。

## Pitfalls & Q&A

**坑 1：中间转发 goroutine 忘记 Close 下游。** 演示第一版在"计速
转发"goroutine 里漏了 `brIn.Close()`，整个流水线死锁——下游全部
停在 Recv。修法：转发结束必须关闭，或直接改用 Merge 组件替你收尾。

**坑 2：用 recover 把 send-on-closed 转成 false。** 看似让 Close 永远
安全，实际并发 Send 与 Close 是使用级数据竞态，-race 直接判红
（chansend1 与 closechan 并发）。修法：保持 panic 语义，用
wg.Wait 联结后再 Close。

**坑 3：断言 panic 用字符串等号失败。** 内置的 panic 值是
runtime.plainError 而非 string，`recover() != "..."` 恒为真；先
`fmt.Sprint` 转文本再比较。

**Q：为什么 Split 是轮转而不是广播？** 两者的下游契约相反：轮转要
求每个元素恰好被一个分支处理（负载均衡），广播要求每个元素到达所有
分支（副本分发）。把两种语义混在一个 API 里，调用方无法从签名分辨
守恒关系，所以只做轮转，广播需要时另写。

**Q：与 [15_mini_channel](../15_mini_channel/) 的 Chan 是什么关系？**
那是运行时复刻，替换内置 channel 的实现；本库是内置 channel 之上的
组合层，两者层次不同，本库刻意不依赖任何自制通道。
