# 16 · select 均匀性：随机轮询起点与排序加锁的实证

> 双就绪通道跑 10^6 次 select，实测两路占比偏差远小于 5% 的验收线；再用 ABBA 场景说明 selectgo 为什么必须按 channel 地址排序加锁，并用 getrusage 量化 select+default 忙等的 CPU 代价。读完能从实现层解释 select 的三个行为。

## Background

一个 goroutine 同时伺候多条 channel 是常态：网关等任一后端回包、
事件循环等任一事件源。没有多路等待原语时，做法是每条 channel 配一个
goroutine 再汇聚到公共 channel。能工作，但"任一路就绪立刻处理"退化
成"处理完上一条才看下一条"，胶水代码随路数增长。

select 把多路等待做成一个原语，其实现 selectgo（runtime/select.go
里执行 select 语句的核心函数）有两个决定行为的设计：轮询起点随机化、
加锁前按 channel 地址排序。

前者回答"多路同时就绪听谁的"，后者回答"两个 goroutine 的 select
互等怎么办"。本篇把两者变成看得见的数字，并实测 default 的忙等代价。

## What

**定义**：select 是多路 channel 等待原语，编译器把 select 语句改写为
对 selectgo 的调用，由它完成轮询、加锁、注册与唤醒。

| 行为 | 实现机制 | 本篇实测现象 |
|---|---|---|
| 多路就绪随机选 | fastrandn 打乱轮询起点 | 10^6 次双就绪占比 ≈ 50/50 |
| 多路等待原子 | channel 按地址排序后统一加锁 | 交叉收发对 10^4 次无一互卡 |
| default 非阻塞 | 无就绪 case 立即走 default | 忙等循环占满一核 |

可以把 select 想成总机接线员同时盯几条线路。但和人工接线员不同的是：
先接哪条由掷骰子决定（长期各线路均等，单次无保证）；接听前把所有
线路一次性置忙——不存在"只占了一半线路"的中间态。

## When to Use

- 多路等待加超时：业务 channel 与取消信号一起等，谁先来处理谁
- 非阻塞试探：select+default 表达"有就做、没有就走"的低频检查
- 扇入汇聚：少量输入源合并到一条处理循环

何时不用：

- 单一数据源：直接收发，select 是多余的一层
- 高频轮询等待：select+default 忙等烧满一核（见第 4 步实测），应改
  成阻塞等待

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| select | 原子多路等待，就绪路随机均分 | 默认选择 |
| 每路一个 goroutine 汇聚 | 多一层 channel 与胶水代码 | 每路需要独立处理逻辑时 |
| select+default 轮询 | 忙等，300ms 墙钟耗 300ms CPU | 仅低频试探，禁作等待循环 |

## How It Works

selectgo 执行一次 select 语句的顺序：先把 case 的轮询次序用随机数
打乱；再按 channel 地址排序，把所有 case 的 channel 一次性全部加锁；
然后逐个查就绪，有可执行的立即执行并解锁返回。

全部不就绪且没有 default 时，把当前 goroutine 登记到每一路的等待
队列，统一解锁停车；被某路唤醒后重新加锁、从所有队列摘除、执行该路。

均匀性来自第一步：轮询起点随机，长期统计各路机会均等。10^6 次双就绪
实测占比 50.00%/50.00%，偏差 0.000%；按二项分布标准差约 0.05%，
5% 的验收线有百倍余量。

排序加锁针对的灾难可用两把容量 1 的 channel 当锁复现：g1 先 A 后 B、
g2 先 B 后 A，各自持第一把后停 1ms，两方互等第二把，实测 3 轮全部
超时（3/3）。

若 selectgo 按用户书写顺序加锁，select(a,b) 与 select(b,a) 就是这个
下场；按地址排序后全系统只有一个加锁全序，ABBA（互相持有对方需要的
锁）在结构上不可能发生。

CPU 数字来自 getrusage（内核按进程累计 CPU 时间的采样接口）：空转
300ms 消耗 300.117ms CPU，阻塞等 300ms 超时只消耗 107µs，相差约三
个数量级——阻塞的 select 把 goroutine 停在等待队列，不占任何核。

## Pitfalls & Q&A

**坑 1：for + select + default 当等待循环。** 空转烧满一核（实测
300ms 墙钟耗 300ms CPU）。解法：去掉 default 让 select 阻塞，或在
循环里加 time.Sleep 退避。

**坑 2：把均匀当公平。** 随机只保证长期均等，某一路可能连续多次落选；
对单次时序敏感的逻辑不能依赖 select 的选择结果。

**坑 3：nil channel 让某一路永久沉默。** select 里 nil channel 永不
就绪——"置 nil 禁用分支"是合法技巧，但忘了恢复赋值，该路就永远
收不到事件。

**Q：为什么排序加锁后还要"先全查再注册"两阶段？** 多路查询加登记
必须在一个临界区里才原子；查完解锁、登记延后，窗口内的唤醒会落空。
这与 [15_mini_channel](../15_mini_channel/) 的"接收者判断先于缓冲
判断"是同一不变式。

**Q：case 书写顺序影响命中概率吗？** 不影响。轮询起点随机覆盖了书写
顺序，且随机只在多路同时就绪时有意义——单路就绪时无所谓顺序。
