# 07 · mini Cond：先领票、再放锁、后入睡——一个不丢唤醒的通知列表

> 本篇徒手复刻 `sync.Cond` 与 runtime 的 notifyList 协议，用它搭一个有界阻塞队列，并复现"检查条件与 Wait 之间放锁"导致的丢失唤醒。读完本篇你能说清 Wait 内部四步的顺序为什么不可调换，以及 Cond 与 channel 各该用在什么场合。

## Background

一个 goroutine 需要等"队列非空"才能取数，等"缓冲未满"才能放数。没有条件变量时，可行做法只有轮询：循环检查条件，不满足就睡几毫秒再查。轮询能工作，代价是延迟与 CPU 的双输——睡短了空转烧核，睡长了响应慢。

把轮询改成事件驱动需要一个通知机制：条件可能被谁改变，就由谁唤醒等待者。痛点在于通知与时序的配合：如果"检查条件"和"挂起等待"是两个独立动作，通知完全可能落在两步之间——检查过的人已经决定去睡，通知却因为他还没睡着而落空。

条件变量（condition variable，让线程挂起等待某事件、被通知唤醒的同步原语）为此设计了严格的协议：等待者先登记，再放锁入睡；通知按登记顺序发放。Go runtime 的 notifyList 用票号实现这个协议，本篇用一个 `uint64` 计数器加一组通道把它复刻出来。

## What

mini Cond 是一个条件变量：调用方在持锁状态下发现条件不满足就 `Wait`（放锁挂起，醒来重新持锁），改变条件的一方用 `Signal`（唤醒一个）或 `Broadcast`（唤醒全部）通知。它由两层组成：

| 部件 | 职责 |
|---|---|
| `Cond.L` | 保护条件的锁；`Wait` 内部放掉再拿回 |
| `notifyList.wait` | 已发出的票号总数（单调递增） |
| `notifyList.notify` | 已通知的票号数；`notify == wait` 表示无人等待 |
| `notifyList.queue` | 每张未通知的票一个容量 1 的个人唤醒通道，队头票号最小 |

可以把 notifyList 想象成银行取号机：进门先取号（领票），取到号你的叫号通道就开通了；柜台按号顺序叫人（Signal），无人取号时广播直接忽略。但和叫号屏不同的是，号码一经发出不会被回收——容量 1 的通道把"先叫号、后坐下"的顺序差也接住了，这正是通知不落空的机关。

## When to Use

**多个 goroutine 等待同一个条件、条件由共享状态表达时**。典型如资源池有空位、任务队列非空、一批工作全部完成：条件与保护它的锁天然一体，`for !cond { Wait() }` 一行表达等待。

**需要精确控制"唤醒一个"时**。`Signal` 逐个放行消费者，`Broadcast` 适合状态反转类事件（关闭、刷新配置）让所有等待者自行复核。

**何时不用**：数据只需从一个 goroutine 流向另一个时，channel 更简单；一条消息只有一个接收者时，channel 的发送/接收本身就是同步。标准库文档也明确：多数简单场景用 channel 更好。

| 方案 | 差异 | 什么时候选它 |
|---|---|---|
| `sync.Cond` | 条件 + 锁 + 广播/单播通知 | 多等待者共享条件，持锁更新状态 |
| channel | 数据本身即通知 | 点对点传值、扇入扇出 |
| 轮询 | 无依赖但浪费 | 条件只能外部观察且变化极慢 |

## How It Works

`Wait` 的四步顺序是整个机制的骨架，任何一步挪动位置都会破坏正确性：

```go
func (c *Cond) Wait() {
	ch := c.notify.register() // 1. 领票：唤醒通道此刻就位
	c.L.Unlock()              // 2. 放锁：改条件的人拿得到锁
	<-ch                      // 3. 入睡；唤醒先到也被容量 1 通道接住
	c.L.Lock()                // 4. 醒来重新持锁，调用方再查条件
}
```

第 1 步为什么必须在第 2 步之前：领票就是登记。登记完成后，无论通知多快到达（甚至先于第 3 步的 `<-ch`），容量 1 的通道都能接住；若先放锁再领票，通知就可能落在"已放锁、未登记"的空窗里。

runtime 的 notifyList 用 `wait`/`notify` 两个票号达成同样效果，本篇把票号换成通道，协议不变。

`Signal` 只通知队头一张票，无人等待（`notify == wait`）则直接返回——通知不存储、不补发。Quick Start 步骤 3 打印的 `pendingWaiters=0` 就是这个现场：条件已改变、数据已入队，但通知按协议丢弃，消费者继续睡。

这与"广播会丢"不同：`Broadcast` 唤醒当前全部等待者，只是对之后才 Wait 的人同样无能为力。

醒来后必须重查条件，原因有二：一是唤醒到执行之间条件可能被其他消费者抢先消费掉；二是 mini Cond 与 runtime 都允许"唤醒一个"只保证"有人该醒了"，不保证"条件对该 goroutine 成立"。所以等待侧的标准写法是循环：

```go
q.mu.Lock()
for len(q.items) == 0 { // 不是 if：醒来后条件可能又变了
	q.notEmpty.Wait()
}
v := q.items[0]
q.mu.Unlock()
```

mini 版与 runtime notifyList 的两处简化：唤醒通道用切片队列而非 runtime 的 `sudog` 链表（无池化，等待者极多的场景多一次堆分配）；没有 `copyChecker`（复制的 `Cond` 不会被检测报错，靠 `go vet` 的 copylocks 检查兜底）。

## Pitfalls & Q&A

**检查条件与 Wait 之间放锁**。现象：生产者已投放并 Signal，消费者却永远睡下去。原因：检查完条件就放锁，通知落在"已检查、未领票"的空窗里，而 Cond 的通知不补发。解法是持锁检查、持锁 Wait——`Wait` 内部自己放锁，调用方从检查到入睡全程持锁，就没有空窗。

**把 `for` 写成 `if`**。现象：偶发地从空队列取出零值或越界。原因：醒来不等于条件成立，可能在挂起期间数据被其他消费者取走，或 `Signal` 唤醒的顺序与条件满足的顺序不一致。解法：唤醒后回到条件检查，即 `for !cond { Wait() }`。

**Q：Signal 之后修改条件，和修改条件之后 Signal，有区别吗？** 持锁调用时两者等价——锁把"改条件"与"通知"串成原子的组合。不持锁调用 `Signal` 也合法，但条件更新与通知之间会出现空窗，等待者可能错过本轮通知，下一轮条件复核才恢复，语义上类似一次延迟唤醒。

**Q：Cond 版和 channel 版队列怎么选？** 一句话：数据只是从一方流向另一方就用 channel；多个等待者要在锁保护下共用同一份可变条件，且需要"唤醒一个"的语义，才轮到 Cond。
