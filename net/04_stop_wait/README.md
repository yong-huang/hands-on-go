# 04 · 在 UDP 上手写停等协议：可靠传输的最小闭环

> UDP 丢了没人管，那就自己管：每条消息带序号，发一条等一条 ACK，超时就重发，接收端用 expected 序号去重。本篇让这套 40 行的停等协议穿越 30% 双向丢包链路——200 条消息重传 191 次、去重 75 条重复，最终零丢失、零重复交付。TCP 和 QUIC 的可靠层，都是从这颗种子长出来的。

## Background

项目 3 的结论是 UDP 保留边界但不管死活：丢、乱、重全由应用层负责。最直接的反问是：到底要补多少东西才算"可靠"？

把可靠性拆到最小，只需要三个机制：**序号**（区分新旧与重复）、**确认**（ACK 告诉发送方"这条我收到了"）、**超时重传**（ACK 没来就当丢了再发一次）。

1970 年代 ARPANET 的最初版本、今天 TCP 的核心循环，都是这三个机制的组合。它们有一个最小的可运行形态——停等协议（stop-and-wait）：发一条、等一条，发送窗口恒为 1。

停等的效率不高（每条消息都要一个往返），但正因为窗口为 1，它把可靠传输里最难的"边界情况"压缩到了肉眼可数的程度：重复怎么判？最后的 ACK 丢了谁负责？这些问题的答案会一路沿用到大窗口协议里。本篇把它写出来，在 30% 双向丢包下验收。

## What

停等协议是一种窗口为 1 的自动重传请求（ARQ，Automatic Repeat reQuest）协议：发送方每发出一条带序号的 DATA 就停下等待，收到对应 ACK 才发下一条，超时未收到则重发同一条。

一句话心智模型：**停等协议是"挂号信"——寄一封、等一张回执，回执超时就再寄一封一模一样的；收信人按信封编号拆信，编号重复的拆都不拆，只补寄回执**。

但和挂号信不同的是，回执本身也会丢：收信人明明收到了信、也寄了回执，回执在路上丢了，寄信人就会再寄一封——重复信件不是差错，而是协议的正常代价，去重机制就是为它而生的。

协议只有两种消息，帧头 5 字节（沿用项目 2 的长度前缀思想）：

| 消息 | 格式 | 语义 |
|---|---|---|
| DATA | `[0][seq 4B][payload]` | 第 seq 条消息 |
| ACK | `[1][seq 4B]` | 序号 ≤ seq 的消息我都有了 |

## When to Use

理解停等不是为了在生产里手写它，而是为了在三个真实时刻用得上它的判断力。

- **评估现成方案时**：看到 TCP 重传、QUIC 的 PTO/快速重传，能立刻对上"这就是停等的超时重传长大了的样子"
- **写真正需要自定义可靠层的时候**：游戏状态同步、固件 OTA——知道最小闭环只有 40 行，才不会一上来就拖一个 TCP 栈
- **排查"连接卡死"类故障时**：卡死的三大来源（丢包等超时、对端不在了、去重逻辑漏了）都是本篇见过的现场

何时不用：任何能直接用 TCP 的场合——内核的实现比你手写的强几个数量级；本篇的价值是把这个"强"拆解到可理解。

| 方案 | 窗口 | 效率（30% 丢包） | 什么时候选它 |
|---|---|---|---|
| 停等（本篇） | 1 | ~2.1 次发送/条，7 秒/200 条 | 教学与极慢速控制信令 |
| 滑动窗口（TCP） | 动态 | 接近链路容量 | 绝大多数场景 |
| QUIC | 流级多路 | 免队头阻塞 | 现代传输 |


诚实预期：30% 丢包场景每次约 5~8 秒（每条重传都要等 30ms 超时）；重传次数在 150~250 次间浮动——理论期望是 200×(0.3 + 0.7×0.3) ≈ 102 次，实测偏高来自重传本身也可能丢的重尾效应。

## How It Works

### 发送端：一条消息的生命周期

```go
for attempt := 0; attempt <= retries; attempt++ {
    conn.Write(encodeMsg(kindData, int32(seq), msg)) // 发 DATA(seq)
    conn.SetReadDeadline(time.Now().Add(ackTimeout)) // 30ms 内等 ACK(seq)
    n, rerr := conn.Read(buf)
    if rerr != nil { continue } // 超时 → 原样重发
    kind, ackSeq, _ := decodeMsg(buf[:n])
    if kind == kindAck && ackSeq == int32(seq) {
        ok = true // 这条消息的旅程结束
        break
    }
}
```

每一次 `Write` 之后发送方都不知道三个事实里的哪些成立：DATA 丢了、ACK 丢了、还是对端已交付只是 ACK 还在路上。

停等的答案是：不区分，统一按超时处理，重发就是了——代价是重复 DATA，而接收端正好有去重。实测 200 条消息总发送 391 次：约 102 次是首丢，其余是"重传的 ACK 又丢"引发的连锁重发。

### 接收端：expected 序号一夫当关

```go
case seq == expected:
    deliver(seq, payload) // 应用层恰好一次
    delivered++
    expected++
case seq < expected:
    dups++ // 重复 DATA：只补 ACK，不调 deliver
```

窗口为 1 的红利在这里：接收端只需要一个 `expected` 计数器。等于它才交付（恰一次语义），小于它就是重复（回个 ACK 让对方安心），大于它不可能出现（对端不发下一条就不会有未来序号）。验收断言"交付序号恰为 0..199 连续"就是把这条不变式写成了测试。

### linger：本篇最值钱的一课

开发实录：第一版接收端交付满 200 条就 `conn.Close()` 退场，发送端有约一半概率卡在最后一条消息上重试 100 次全失败。

原因链：最后一条的 **ACK 在回程被丢** → 发送方超时重发 DATA → 接收端已经退场，无人应答。修复是给接收端加 800 毫秒 linger 期——交付完不立刻走，留下来给迷路的重复 DATA 补 ACK。

这就是 TCP TIME_WAIT 由主动关闭方持有的存在理由：**先走的人要等一拍，接住对方因你的 ACK 丢失而重发的"遗言"**。在停等协议里亲手踩到它，比背八遍状态图都记得牢。

## Pitfalls & Q&A

- **接收端交付完立刻关连接**：现象是发送端卡在最后一条消息无限重传。原因与解法见上——linger 观察期是可靠协议的收尾标配，不是可选优化
- **两个方向共享一个 rand.Rand**：现象是 `-race` 报 DATA RACE。原因：NAT 两个方向的 goroutine 无锁并发掷同一个骰子。解法：每个方向独立随机源（或加锁），本项目实录
- **把 ACK 丢失当异常**：现象是看到去重计数就想"修复重复"。原因：30% 丢包下 ACK 丢失是常态（期望 ~102 次），重复 DATA 是它的影子。解法：去重计数是健康指标，非零才对
- **超时后重发用新序号**：现象是接收端收到"未来序号"直接洞穿。原因：重发的必须是同一条消息（同 seq）——序号标识的是消息内容，不是发送尝试

**Q：停等每条消息一个往返，效率到底差多少？**
A：实测 200 条 × 30ms 超时预算耗时 5~8 秒，而项目 2 的 TCP 流水线同量数据毫秒级完成。

差距的根源是"发送窗口 = 1"：链路大部分时间在空等。TCP 用滑动窗口让几十条消息同时在途，把等待重叠掉——机制没变，只是并发度上去了。

**Q：ACK 为什么设计成"累计确认"（seq ≤ 我的全收到），本篇怎么是单条确认？**
A：停等窗口为 1，两种写法完全等价。一旦窗口 >1，单条确认会让"ACK 丢一条就重传一条"退化成发一条等一条，累计确认（TCP 的 `ack = 下一个期望序号`）才能一次补认一大片——这是窗口放大时的第一个必改点。

**Q：重传超时 30ms 是怎么定的？**
A：拍脑袋的固定值。正经协议会自适应：TCP 的 RTO 基于 RTT 的指数加权移动平均（EWMA）加 4 倍偏差，Karn 算法规定重传样本不计入 RTT 测量（分不清是原件还是重传件的往返）。

固定 30ms 在 30% 丢包下工作良好，在 1ms 局域网里就是灾难性的慢。

**Q：这套东西和项目 2 的帧协议什么关系？**
A：帧协议解决"边界"，停等解决"可靠性"，正交可叠加：本篇的 DATA 帧头就是长度前缀帧的变体（类型 1B + 序号 4B）。真实协议 = 帧格式 + 可靠性机制 + 拥塞控制三层叠出来的，项目 21 的迷你 RPC 会把这三层串成完整栈。
