# 18 · protobuf wire format：手写 varint、zigzag 与 tag

> protobuf 的线格式只有三种编码原语：varint（变长整数）、zigzag（负数映射）、tag（字段头）。本篇手写全部编解码器，再用 protoc 生成的同一消息做逐字节对拍——负数、大数、嵌套三例全部一致。对拍还抓到 proto3 零值语义的一条细则：标量零值省略，但非 nil 的 message 字段恒编码（哪怕内部全零，输出 tag+长度 0）。

## Background

项目 8 的多路复用协议、项目 5 的二进制帧，都是自创格式——两端必须同步文档才能互通。gRPC 选了 protobuf 做线格式：一套跨语言、有 schema 演进纪律、编码紧凑的二进制协议。要看懂 gRPC 的每一次字节流动，先读懂 protobuf 的 wire format。

wire format 的全部数字编码建立在三种原语上。

**varint**（variable-length integer，变长整数）：每字节低 7 位承载数据、最高位标记"后面还有"，小数省字节。**zigzag**：把有符号数按 0,−1,+1,−2,+2 映射为 0,1,2,3,4——否则负数的补码全 1 会让每个负数占满 10 字节。

**tag**：每个字段前的头部，编码为 `(字段号 << 3) | wire_type`，同时声明"这是几号字段"与"载荷是什么形态"。

验证手写实现是否正确，背文档没用——**与 protoc 生成码逐字节对拍**是唯一权威判据。本篇手写一套，官方一套，三个用例逐字节比。

## What

wire format 是 protobuf 的二进制编码规则：每条消息是"tag + 载荷"的序列，tag 声明字段号与载荷形态，载荷形态共四种（varint / 64 位定长 / 长度前缀 / 32 位定长）。

一句话心智模型：**wire format 是行李托运系统——tag 是行李牌（几号行李 + 里面装的是什么类型），varint 是可伸缩的打包袋（短物件用小袋），zigzag 是把负数物件翻转成正数再打包，长度前缀是一整箱物品先报箱内件数**。

但和行李托运不同的是，同一件行李可以有多个合法打包装箱顺序（字段顺序不敏感、未知字段透传）——protobuf 的解码器按 tag 走，不依赖位置；本篇按字段号升序编码只是与 protoc 保持一致的对拍纪律。

三种原语的解剖（本篇实测）：

| 原语 | 规则 | 实测 |
|---|---|---|
| varint | 每字节 7 位数据 + 1 位续传标记 | 0→`00`、127→`7f`、128→`80 01`、MaxUint64→10 字节 |
| zigzag | `(v<<1)^(v>>63)`，负数翻正 | −1→1（1 字节）；裸 int64 −1→10 字节 |
| tag | `(field<<3)|wire_type` 按 varint | 字段号 1~15→1 字节、16~2047→2 字节 |

## When to Use

理解 wire format 在三个时刻兑现。

- **gRPC 调试与性能优化**：抓包里每个字节的偏移都能对上字段——字段号 1~15 的优化纪律（高频字段小编号）从此有依据
- **跨语言协议对齐**：排查"两个语言版本的序列化不一致"时，wire format 是仲裁标准
- **自研协议的字段设计**：tag/长度前缀/零值省略——protobuf 沉淀了 20 年的取舍都写在这套格式里

何时不用：业务代码永远不该手写 protobuf 编解码——用 protoc 生成码；本篇手写是为理解与验证，生产即退化风险。

| 方案 | 负数开销 | 字段开销 | schema |
|---|---|---|---|
| 自创二进制（项目 5） | 自己设计 | 5 字节固定头 | 手写文档 |
| protobuf | zigzag（sint）| tag 最小 1 字节 | .proto 演进纪律 |
| JSON | 文本直写 | 字段名全量重复 | 无紧凑性 |

## How It Works

### 逐字节对拍：为什么它是权威判据

对拍流程：同一消息分别走手写 `Encode()` 与官方 `proto.Marshal`，`bytes.Equal` 逐字节比。用例刻意覆盖三个编码难点——负数（考验 zigzag）、`1<<62` 与 MaxUint64（考验 varint 多字节与溢出边界）、嵌套消息（考验长度前缀计算）。

三例全等即可宣称"手写实现与 protoc 等价"——这不是巧合，是线格式规范唯一性的体现：同一消息的规范编码是唯一的（字段号升序、无冗余字节）。

### 对拍抓到的两条 proto3 语义

第一轮对拍当场抓到差异。

**差异一：标量零值省略**——官方对全零 TestMessage 的输出不含字段 1/2/3 的任何字节（proto3 的零值字段默认"不存在"）；手写版无脑编码了全部字段。**差异二：message 字段恒编码**——非 nil 的 `Inner{X:0}` 官方输出 `22 00`（tag + 长度 0），message 的"存在性"与内部值无关。

两条规则合起来就是 proto3 的完整零值语义，教科书常常只讲第一条。

### 字段号 1~15：挤进一个字节的优化纪律

tag 的编码是 `(字段号 << 3) | wire_type` 再过 varint——字段号占 4 位以上时 tag 就要多一个字节。实测：字段号 1~15 的 tag 恰好 1 字节（4 位字段号 + 3 位类型 = 7 位，塞进一个 varint 字节的数据区），16~2047 要 2 字节。

`.proto` 文件的公开优化纪律由此而来：**最高频的字段编成 1~15**。这解释了为什么流行项目的 proto 定义里第一个字段永远是"id"或"name"。

## Pitfalls & Q&A

- **给 int64/int32 用裸 varint 传负数**：现象是负数字段恒占 10 字节。原因：补码表示下负数最高位全 1，varint 要编码全部 64 位。解法：schema 里用 sint64/sint32（zigzag 编码），负数按大小占位（本篇实测 −1 只占 1 字节）
- **零值省略只对标量生效**：现象是"全零消息应该是空的"的断言失败——官方对非 nil 的 message 字段输出 `22 00`。原因：message 的存在性独立于内部值。解法：区分两类字段的存在性语义（本项目对拍实录）
- **用 proto.Int64 等 helper 赋值 proto3 字段**：现象是编译错误"cannot use *int64 as int64"。原因：proto3 生成码的标量字段是普通值类型（无显式存在性）。解法：直接赋值；要显式存在性用 optional 关键字
- **假设字段顺序敏感**：现象是自己写的解码器按位置取值。原因：wire format 按 tag 走，字段顺序无关、未知字段透传。解法：解码器永远解析 tag 再分发（本篇 ReadTag 的设计）

**Q：varint 为什么不用定长编码？**
A：分布倾斜——绝大多数整数值都很小（id、计数、枚举），varint 下 1 字节收尾；定长 8 字节对它们是 8 倍浪费。代价是 uint64 大数要 10 字节（比 8 字节多 25%），protobuf 用 fixed64 类型为"值域均匀分布"的场景留了出路——按数据分布选类型，这是所有紧凑编码的共同纪律。

**Q：zigzag 的位运算为什么自逆？**
A：`(v<<1)^(v>>63)` 把符号位从最高位搬到最低位：正数左移一位后最低位 0，负数（右移 63 全 1）最低位 1。解码 `int64(u>>1)^-int64(u&1)`：最低位 0 时算术右移即原值，最低位 1 时异或全 1 取反——两次变换共用同一对移位，数学上互为逆运算。

**Q：为什么 message 字段不像标量那样省略？**
A：存在性信息在 RPC 场景有语义（"显式设置了但为零" vs "没设置"——策略更新、部分更新都依赖它）。标量字段 proto3 用"零值即缺省"换取紧凑，message 用"出现了就编码"保留存在性；需要对标量也区分时用 optional 关键字（生成指针字段）。

**Q：这和项目 19 的 gRPC 什么关系？**
A：gRPC 的请求体就是一条 protobuf 消息，响应体也是——本篇手写的 Encode/ReadVarint 就是 gRPC 每 RPC 里跑的编码路径。项目 19 会看到 gRPC 在 protobuf 外再包一层帧（压缩标志 + 长度前缀），组成完整消息。
