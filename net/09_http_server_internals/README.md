# 09 · net/http 服务端行为学：超时参数、慢攻击与连接状态机

> 教科书说 slowloris 能打瘫 HTTP 服务，Go 上实测**不成立**——每连接一个 goroutine，没有 worker 池可占满，300 条慢连接下正常请求照样毫秒级返回。

> 但默认配置有一张隐藏账单：攻击期间 goroutine +602、堆内存涨 10 倍且永不回落。三行超时配置就是给这道无底洞封顶的——加固版曲线 604→3，一秒内全额回收。

## Background

`http.ListenAndServe` 一行就能起服务，默认配置却没有一个超时。这默认值面向"理想客户端"：请求总是快速完整、连接总是用完即走。

真实网络里最常见的对手恰是反着来的——slowloris：开几百条连接，每条把请求头拆成碎片慢慢发（每 200ms 发一个字节），服务端的协议解析永远等不到终结的空行，只能干等。

这类攻击在 Apache（线程/进程池模型）上是致命的：每条慢连接占死一个 worker，池子一空正常请求全挂。

Go 的 http.Server 结构不同——**每连接一个 goroutine**，goroutine 便宜到可以百万计，没有池可占满。那 Go 服务是不是就不用配超时了？本篇用对照实验回答：正常请求确实免疫，但 goroutine 与内存的账本会说话。

超时参数的三件套（`ReadHeaderTimeout`/`ReadTimeout`/`IdleTimeout`）各自把守一段连接生命周期，本篇用 `ConnState` 钩子（连接状态变化的回调）把这段生命周期变成可见的事件流。

## What

http.Server 的超时配置是一组按连接生命周期分段生效的截止时间：头超时管解析、读超时管整个请求、空闲超时管无请求的连接。它们共同保证"任何一条连接占用的资源都有上限"。

一句话心智模型：**无超时的服务是无限期保管行李的酒店——每位客人（连接）一间房（goroutine）+ 行李间（缓冲区），客人不退房就永不清理；三超时是退房时间表：头 500ms、整单 2s、空闲 1s，到点一律清房**。

但和酒店不同的是，Go 的酒店房间（goroutine）多到近乎无限——超时防的不是"没房间"，而是"账单失控"：一条慢连接约 50KB 内存（8KB 栈 + 读写缓冲），10 万条就是 5GB，这才是它真正的杀伤半径。

三个超时的守门位置：

| 参数 | 守护阶段 | 不设的后果 |
|---|---|---|
| ReadHeaderTimeout | 收完请求头 | slowloris 式半头连接永久驻留 |
| ReadTimeout | 整个请求（含体） | 慢请求体无限拖占连接 |
| IdleTimeout | 两个请求之间的空闲 | 客户端走后连接永不回收 |

## When to Use

这套行为学知识在三个时刻兑现价值。

- **任何 http.Server 上生产之前**：三超时是和 `go vet` 同级的必配项——默认值等于"对慢客户端无限宽容"
- **评估"我的服务会不会被慢连接打挂"时**：先看模型（Go 结构性免疫连接耗尽），再看账本（内存随连接数线性涨）
- **排查连接堆积时**：ConnState 钩子是服务端视角的连接状态机，堆积在 active 还是 idle 直接指认病因

何时不用：内网工具、只服务自己的本地服务，超时可以放宽；反向代理后面有严格超时兜底时，应用层可酌情简化。

| 配置 | 攻击期间健康 | goroutine 账本（本篇实测） | 适用 |
|---|---|---|---|
| 默认（无超时） | ✅（结构性免疫） | +602 永驻、堆 ×10 | 永不 |
| 三超时 | ✅ | 冲高后全额回落（Δ+0） | 生产 |

  事件计数：new=1 active=1 idle=1 closed=1
  一条连接的一生：new（接入）→ active（处理中）→ idle（空闲）→ closed（回收）

## How It Works

### 结构性免疫：goroutine-per-connection 的意外红利

slowloris 的杀伤模型是"占满 worker 池"，而 Go 的 http.Server 没有池——每条接入连接一个 goroutine，各自独立调度。

300 条慢连接 = 300 个阻塞在 `ReadHeader` 上的 goroutine，与正常请求的 goroutine 互不干扰。所以攻击期间 `/health` 始终毫秒级（两次实验各 4~5 次探测零失败）。这个红利不是设计者的仁慈，是调度模型的副产品；它的价签在下一步。

### 隐藏账本：永不驻留的反面

vulnerable 曲线 `604 604 604 604 604 604`——攻击开始 500ms 后冲到 604（300 服务端 goroutine + 300 攻击端 + 探测），然后纹丝不动：没有超时，这 600 个 goroutine 与约 4MB 堆内存将**永久驻留**。

把 300 换成 30000（公网僵尸），就是 12GB。这就是"结构性免疫"的隐藏账单：连接耗尽打不倒你，资源耗尽可以。三超时的意义由此从"防攻击"精确定义为"给每连接资源占用封顶"。

### ReadHeaderTimeout 的切法：曲线的悬崖

hardened 曲线 `604 3 3 3 3 3`——冲高后 500ms 内断崖回落到基线。

`ReadHeaderTimeout=500ms` 的实现是给头解析设置绝对读截止时间：慢连接的头永远读不齐，截止时间一到服务端关闭连接（closed 事件 304 次），慢连接的 goroutine 立即释放。

注意它是**绝对截止**而非空闲超时——攻击端每 200ms 发一个"吊命字节"无法续命。服务端掐断后，攻击端的下一次写收到 RST 而失败，攻击者被迫下线——goroutine 曲线因此全额回落。

## Pitfalls & Q&A

- **只用 ReadTimeout 不用 ReadHeaderTimeout**：现象是慢头连接仍长期驻留。原因：ReadTimeout 覆盖"从接入到读完请求体"全程，通常被设成很大值（如 30s）来兼容大文件上传，等于没防慢头。
  解法：ReadHeaderTimeout 单独收紧（500ms~5s），ReadTimeout 放宽到业务允许值
- **把 ConnState 当事件顺序日志**：现象是钩子里收到的状态顺序与预期不符。原因：钩子是并发回调，且 new→active 在 Accept 之前触发。解法：按状态计数（本篇做法），需要严格时序才上时间戳
- **拿塌陷结论照搬其他语言**：现象是"Go 服务不用防 slowloris"被当成普适结论。原因：免疫来自 goroutine 模型，线程池模型（Apache/nginx worker）上不成立。解法：结论绑定运行时模型，跨栈要重测
- **测试自己的攻击端泄漏**：现象是加固版实验的 goroutine 曲线停在 304 不回落。原因：攻击端 `c.Write` 的错误被忽略，对着已死连接永远空转。解法：写失败即退出（本项目实录——修复后曲线 604→3 才成立）

**Q：真生产环境还需要防 slowloris 吗？**
A：应用层三超时已让慢连接成本有限；公网入口再由 LB/CDN 挡第一波（它们有连接速率与超时策略）。

应用层要补的是**告警**：ConnState 钩子统计 active 连接数与 goroutine 数，异常爬升即报警——本篇的钩子就是告警探针的原型。

**Q：超时设多短会误伤正常用户？**
A：看慢在谁。ReadHeaderTimeout 的合法下界 = 弱网完成发送头的时间（3G 网络几秒内），500ms 偏激进、5s 偏保守，公网服务常用 2~5s；ReadTimeout 覆盖请求体上传，大文件要走分片或预签名直传，不能靠放大 ReadTimeout 解决。

**Q：IdleTimeout 和客户端连接池什么关系？**
A：两侧要配对：服务端 IdleTimeout ≥ 客户端连接池的空闲复用周期，否则池里的连接被逐个掐断，客户端下次复用即撞墙（表现为偶发 EOF）——这是项目 10 的第一课。

**Q：ConnState 的四种状态覆盖全部生命周期吗？**
A：常见路径全覆盖（new→active→idle→closed）。

两个特殊态：hijacked（handler 接管连接，如 WebSocket 升级，服务端不再管理）与处于 StateActive 的持续请求。本篇第 1 步的四态计数就是服务端连接账本的原始形态。
