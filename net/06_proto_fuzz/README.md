# 06 · 协议健壮性：畸形包矩阵与 30 秒 fuzz 靶场

> 解码器读到的每一个字节都应视为攻击者的输入。本篇把项目 5 的解码器架在靶场上：十类畸形包逐一分诊（零 panic、每类有名字），再加 30 秒 `go test -fuzz` 的 3343 万次随机轰炸——第一轮 fuzz 就抓到一个真缺陷（"合法帧+尾巴"被静默接受），修复后语料文件转为回归测试。

## Background

项目 5 给解码器装了四道闸（魔数/版本/类型/CRC），但装上不等于有效——没有验证过的防御工事只是装饰。验证有两种思路：手写畸形用例（想得到才测得到）和模糊测试（fuzzing，让程序自己喂随机输入找崩溃）。Go 1.18 把 fuzzing 做进了 `go test`，带覆盖率导航，两者正好互补。

"想得到才测得到"是手写用例的天花板：本篇矩阵里的"合法帧+1 字节尾巴"这一类攻击，第一轮设计时并没有想到——是 fuzz 机器 30 秒内找到的。反过来，fuzz 只找"让程序崩溃/违反不变式"的输入，语义级缺陷（比如长度上限设太大）它认为一切正常。手写矩阵划清语义红线，fuzz 扫荡未知角落，缺一不可。

## What

协议健壮性测试是一套"输入不可信"假设下的验证体系：畸形包矩阵覆盖已知攻击类别，fuzz 覆盖未知空间，两者共享同一套判定标准——**零 panic，且每个失败都能归类到有名字的错误上**。

一句话心智模型：**fuzz 是一个不知疲倦的破坏检测员——每秒往解码器扔一百万个随机包裹，盯着两件事：箱子有没有炸（panic），退货理由有没有超出退货手册（错误闭集）**。

但和人力检测员不同的是，它只认"炸了"这种硬信号：一个让解码器把恶意帧误当合法帧的输入，只要不触发不变式，检测员毫无反应——语义红线仍然要靠手写矩阵。

十类畸形与本篇的分诊结果（验收③的分类表）：

| 攻击类别 | 构造方式 | 解码器判定 |
|---|---|---|
| 空输入 | 零字节 | TRUNCATED |
| 短输入 | 1 字节 | TRUNCATED |
| 串线流 | `GET / HTTP/1.1` | BAD_MAGIC |
| 未来版本 | Version=9 | BAD_VERSION |
| 长度欺骗 | Length=0xFFFF | TOO_LARGE |
| 截断 | 合法帧去尾 2 字节 | TRUNCATED |
| 载荷位翻转 | 翻 1 bit | BAD_CRC |
| CRC 字段翻转 | 翻 1 bit | BAD_CRC |
| 帧后尾巴 | 合法帧+1 字节 | TRAILING（fuzz 实录新增） |
| 未知类型 | Kind=0x7F 且 CRC 合法 | BAD_KIND |

## When to Use

矩阵 + fuzz 的组合适合这些时刻。

- **解码器/解析器上线前**：任何把不可信字节变成结构化数据的代码（协议帧、JSON、图片头）都是靶场候选
- **协议版本演进时**：新类型、新字段加进来，旧的不变式要重跑——语料文件就是回归资产
- **安全评审与渗透自查**：攻击者会先打解码器；自己先打一遍是最便宜的一次渗透

何时不用：纯内存到内存的转换（自己序列化自己读）威胁模型不同，矩阵瘦身即可；跑一次就归档的内部脚本，成本高于收益。

| 手段 | 覆盖 | 盲区 |
|---|---|---|
| 畸形矩阵（手写） | 已知语义红线 | 想不到的输入形状 |
| go test -fuzz | 未知形状（覆盖率导航） | 语义缺陷（不违反不变式就无感） |
| 两者结合 | 互补 | —— |

## Quick Start

前置条件：Go 1.21+（fuzz 为 `go test` 内置）。运行：

```bash
cd net/06_proto_fuzz
go run .              # 矩阵现场 + 可恢复性分诊
go test -race .       # 矩阵回归（含 fuzz 抓到的 crasher 语料）
go test -fuzz FuzzDecodeFrame -fuzztime 30s   # 30 秒轰炸
```

`go run .` 真实输出：

## How It Works

### 三条不变式：fuzz 的"及格线"是怎么写的

```go
f.Fuzz(func(t *testing.T, data []byte) {
    frame, err := DecodeFrame(data)
    if err != nil {
        if classify(err) == "UNCLASSIFIED" { t.Errorf("错误逃出闭集") }
        return
    }
    re, _ := frame.Encode()
    if !bytes.Equal(re, data) { t.Fatalf("非规范接受") }
})
```

不变式一：**永不 panic**——panic 会被 fuzz 引擎自动记录为 crasher；不变式二：**错误分类是闭集**——失败必须落在有名字的哨兵上，`UNCLASSIFIED` 出现即解码器缺陷。

不变式三：**解码成功 ⇒ 规范重编码逐字节一致**——接受了一个输入却不能无损还原，说明解码器对"什么是合法帧"的定义有缝。

### fuzz 抓到的真缺陷：合法帧 + 1 字节尾巴

开发实录：首轮 30 秒 fuzz（11 万次/秒）即产出 crasher `NETC 01 02 00 00 |r..0`——一个完全合法的 PING 帧后面跟了一个多余字节 `0x30`，`DecodeFrame` 把它静默接受，但重编码只剩 12 字节，不变式三当场击穿。

修复是个协议设计决定：**严格解码**——整帧之后的残余字节不属于本帧，显式返回 `ErrTrailing` 拒绝。静默忽略尾巴就是给"帧+走私数据"的攻击面开门。修完之后，crasher 文件（testdata/fuzz/…）留作回归语料，每次 `go test` 都会重放它。

### 坏帧的两种可恢复性：分诊决定断不断链

CRC/类型坏帧：帧头有效 ⇒ 帧长已知 ⇒ 整帧已消费 ⇒ 拒帧后流可以继续（演示 A）。

魔数/版本坏帧：连"这一帧多长"都不可信 ⇒ 后续字节无法定位帧边界 ⇒ 只能断链重连（演示 B）。解码器把这个分诊编码进错误类型，调用方（项目 5 的服务端）据此决定 `continue` 还是断链——错误分类的价值在恢复策略上兑现。

## Pitfalls & Q&A

- **fuzz 不变式写成"必须成功"**：现象是 fuzz 启动一秒就失败——随机输入绝大多数是非法帧，"必须成功"这个断言本身错了。解法：不变式断言的是性质（不 panic、闭集、规范性），不是结果（成功）
- **删掉 testdata 里的 crasher 文件**：现象是修复后同一崩溃几周后回归。原因：crasher 文件是 fuzz 的回归语料，删了就不再重放。解法：入库保留，文件名即哈希、内容即最小复现
- **给 fuzz 目标加日志/随机数**：现象是 fuzz 变慢且结果不可复现。原因：目标必须确定性、无副作用——同一输入永远同一行为。解法：日志移到调用方，随机性由 fuzz 引擎提供
- **把"零 crasher"当安全证明**：现象是"跑了 30 秒没问题"就上生产。原因：fuzz 只找触发不变式的输入，语义漏洞（长度上限太大、类型权限混乱）不违反任何不变式。解法：fuzz + 手写矩阵 + 评审三层都在

**Q：30 秒够吗？**
A：入门够（本篇 3343 万次执行已抓到真缺陷），加固不够。惯例是 CI 里每次提交跑 15~30 秒，nightly 对关键解码器跑小时级；Go 的 fuzz 引擎会把覆盖率新字典存进缓存（cachepath），下次续跑不是从零开始。

**Q：ErrTrailing 会不会误伤合法的多帧流？**
A：不会——`DecodeFrame` 的契约是"单帧全量解码"（测试/审计用），流式场景走 `ReadFrame`：它只消费一帧，剩余字节本来就是下一帧。两条入口、两种契约，注释里写清楚，混用才是事故。

**Q："负长度"攻击为什么矩阵里没有？**
A：本协议长度字段是 uint16，不存在负值——等价攻击是"声明超长"（TOO_LARGE 已覆盖）。但如果换成 int32 长度字段，负长度会在 `make([]byte, n)` 处直接 panic。攻击面跟着类型系统走，矩阵要按自己的协议定制，不能照抄。

**Q：矩阵、fuzz 和项目 2 的粘包测试是什么关系？**
A：项目 2 验证"边界怎么切"（功能正确性），本篇验证"切错时怎么死"（健壮性）。同一个解码器，两套测试正交：功能测试用合法输入断言成功，健壮性测试用非法输入断言体面地失败。
