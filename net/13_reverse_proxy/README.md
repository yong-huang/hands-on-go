# 13 · ⛓️ 反向代理：手写迷你网关的轮询、健康检查与 XFF 链

> httputil.ReverseProxy 组装一个迷你网关：轮询在两后端间 50/50 均分（1000 请求实测各 500±5%）、后端下线后 1 秒内流量全部切到幸存者、两层网关串联后后端看到 2 项 XFF 链。

> 最大的一课藏在 XFF 里：Rewrite 模式出于防伪造默认丢弃入站 XFF，链路传递必须显式拷贝——这条被排查逼出来的行为，官方文档写在源码注释里。

## Background

服务从单体长成集群的第一步，就是在前面加一个反向代理：客户端只认识一个地址，代理把请求分发给背后的多台后端，后端故障时自动绕行。

Nginx/HAProxy 是现成答案，但理解"代理到底做了什么"最好的方式是亲手写一个——Go 标准库的 `httputil.ReverseProxy` 把传输细节全部封装，只暴露两个钩子：Rewrite（改写发往后端的请求）与 ErrorHandler（转发失败怎么办）。

钩子虽小，藏着一个反直觉的设计：**Rewrite 模式下，入站的 X-Forwarded-For 头默认被丢弃**。原因是安全——XFF 由客户端可控，无条件信任就是伪造漏洞（攻击者自带假 XFF 冒充"我是内网"）。

代价是代理链路信息也一并丢了，多级代理必须显式逐跳拷贝。本篇的三组实验里，XFF 链的修复过程（逐跳排查到源码）是含金量最高的一课。

## What

反向代理是一种服务端代理：代替后端集群对外提供服务，按负载均衡策略把请求转发给后端，并把后端的响应透传回客户端。对客户端而言它就是服务本身。

一句话心智模型：**网关是餐厅的领位员——客人只认识大门，领位员按轮桌规则（轮询）安排桌子（后端），某张桌子坏了（健康检查失败）就带去下一张；客人的排队号（XFF）由每位领位员依次登记，后厨才知道客人经历了谁**。

但和领位员不同的是，"登记排队号"在这里是个安全决策：客人自己谎报号码（伪造 XFF）时，合格的领位员应该无视客人自述、按自己看到的登记——Go 的 Rewrite 模式默认正是这么做的。

本篇网关的三个组件：

| 组件 | 实现 | 本篇实测 |
|---|---|---|
| 负载均衡 | 原子轮询游标 + 跳过拉黑后端 | 1000 请求 A/B 各 ~500（±5% 内） |
| 被动健康检查 | ErrorHandler 拉黑失败后端 1 秒 | A 下线后窗口内全量命中 B |
| XFF 传递 | 拷贝入站链 + SetXForwarded 追加本跳 | 两层网关链长 2，单层 1 |

## When to Use

自研反向代理适合"需要业务感知的转发"时刻。

- **按内容路由**：按路径/头/租户转发到不同后端池——Nginx 配置表达不了的逻辑
- **嵌入业务统计**：本篇的 X-Backend 头 + 后端命中计数——网关即观测点
- **学习与排障**：理解 ReverseProxy 后，Nginx 的 proxy_set_header、XFF 语义不再黑盒

何时不用：纯流量分发给生产服务——Nginx/云 LB 的连接管理、TLS 终止、热更新成熟度远超手写版；本篇网关是教学与特殊路由需求的形态。

| 方案 | 健康检查 | 路由逻辑 | 适用 |
|---|---|---|---|
| Nginx/云 LB | 主动+被动 | 配置化 | 生产流量入口 |
| 本篇网关 | 被动（失败拉黑） | 任意 Go 逻辑 | 业务感知路由/学习 |
| 客户端直连 | —— | —— | 单后端 |

## How It Works

### 轮询与被动健康检查的组合

选路是原子自增游标取模：`rr.Add(1) % n`，无锁且严格均分。每个后端有 `downUntil` 时间戳：ErrorHandler 转发失败（典型是拨号 connection refused）时把失败后端拉黑 1 秒；`pick` 跳过拉黑中的后端。

两个实验的关键断言：正常时 A=B≈500；A 关闭后窗口内有且仅有 1 次非 200（触发拉黑的探针），此后 hitsA 恒为 0——"被动"的含义就是健康与否由真实流量试出来，而非主动探测。

### 选路结果怎么告诉 ErrorHandler

Rewrite 选中的后端，ErrorHandler 也要知道（才拉黑得准）。Go 的 ReverseProxy 在转发失败时把**出站请求**传给 ErrorHandler。

所以本篇用 `X-Backend` 头作为载体：Rewrite 里 `pr.Out.Header.Set("X-Backend", name)`，ErrorHandler 里 `r.Header.Get("X-Backend")` 取回并按名拉黑。

（曾尝试走 request context 传递，出站请求的克隆时机让方案不稳，头载体一行收尾——实录见开发记录。）

### XFF 链：Rewrite 模式的防伪造设计

本篇最深的坑：两层网关串联，后端只看到 1 项 XFF（应 2 项）。

排查到 Go 源码才发现语义：**Rewrite 模式克隆出站请求时默认丢弃入站 XFF**（防客户端伪造），`SetXForwarded` 只在出站请求的既有 XFF 上追加——而初始是空的，于是每跳都"重写"而非"追加"。官方文档给出的修法是先拷贝再追加：

```go
// Rewrite 模式默认丢弃入站 XFF（防伪造：客户端可带假 XFF）。
// 要传递代理链，必须按官方文档先拷贝入站链，SetXForwarded 再追加本跳。
pr.Out.Header["X-Forwarded-For"] = pr.In.Header["X-Forwarded-For"]
pr.SetXForwarded() // 追加本跳客户端 IP
```

修复后两层链长 2、单层链长 1，测试固化。（对照：老式 Director 钩子默认保留入站 XFF——Rewrite 是 1.20 的新钩子，安全默认更紧。）

## Pitfalls & Q&A

- **Rewrite 模式下 XFF 链只有 1 项**：现象是多级代理后后端只见直接上游 IP。原因：Rewrite 克隆出站请求时丢弃入站 XFF（防伪造默认）。解法：Rewrite 里先 `pr.Out.Header["X-Forwarded-For"] = pr.In.Header["X-Forwarded-For"]` 再 `SetXForwarded()`（本项目实录，源码注释即文档）
- **ErrorHandler 不知道该拉黑谁**：现象是 A 挂了之后请求在 A/B 间继续 502。原因：ErrorHandler 只拿到原始入站请求，不知 Rewrite 选了谁。解法：Rewrite 把选中后端写进出站头（X-Backend），ErrorHandler 读头定位
- **负载均衡断言比例写死 50/50**：现象是 CI 偶发失败。原因：并发调度有波动。解法：断言放宽到 ±5% 且并发采样（1000 请求下标准差 ~11，5% 窗口极稳）
- **网关把 Host 头透传给后端**：现象是后端路由按 Host 匹配时全落到默认站点。原因：入站 Host 是网关地址。解法：`pr.Out.Host = b.target.Host`（本篇 Rewrite 内），与 SetURL 配合使用

**Q：被动健康检查和主动有什么区别？**
A：被动（本篇）由真实流量的失败触发拉黑——零成本，但每个故障周期至少牺牲一条请求当探针；主动（定时拨测）在流量到来前发现故障——需要拨测频率与误判的权衡。小网关被动足够，大集群两者结合：被动快速拉黑、主动负责恢复确认。

**Q：拉黑 1 秒后 A 恢复了吗？**
A：本篇 A 是真下线（listener 已关），拉黑到期后 pick 会再给它流量、再次失败、再次拉黑——每秒一个 502 探针。生产实现会加指数退避或半开探测（连续 N 次成功才完全恢复），本篇聚焦最小闭环。

**Q：XFF 链可以无限信任吗？**
A：绝对不能——XFF 是可伪造的追加式头，攻击者可自带假链。可信做法：只信任"可信代理列表内"的追加段（从右往左数，跳过自己的代理），其余视为客户端自报。这也是 Rewrite 模式默认丢链的原因：把"要不要信"的决定权交回给实现者。

**Q：这条网关离项目 21 的 RPC 框架还差什么？**
A：协议层（本篇转发 HTTP，RPC 需要转发自研帧——项目 8 的多路复用直接复用）、连接池（项目 10 的 Transport 调参平移）、以及服务发现（后端列表从配置变成动态注册）。负载均衡与健康检查两层已经就位。
