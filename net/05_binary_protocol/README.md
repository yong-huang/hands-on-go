# 05 · 二进制协议设计：魔数、版本、长度与 CRC 的四道闸

> 帧格式是网络世界的合同条款。本篇设计一个完整的二进制协议帧——魔数 NETC、版本号、消息类型、长度前缀、CRC32 尾——并让 50 条随机 DATA、一次 PING→PONG 和一帧人为损坏的比特穿越真实 TCP：坏帧被 CRC 拦下，后续好帧无缝重新同步。

## Background

项目 2 给出了三种定界方案，长度前缀胜在 O(1) 定界；项目 4 的 DATA/ACK 证明协议只需要 5 字节头就能跑。但那都是"最小可用"形态——真实的二进制协议帧还要回答四个工程问题。

这四个问题每个都有血泪史：

- 对端收到一串错位字节时（比如粘了个 HTTP 请求上来），怎么第一时间发现"这不是我的协议"？——需要**魔数**
- 新旧版本实现要能共存并明确拒绝，而不是解析出乱码——需要**版本号**
- 收到不认识的消息类型时，老实现应当拒绝而非误读——需要**类型白名单**
- 内存翻转、代理篡改、序列化 bug 造成的比特损坏，要在应用层之前拦截——需要**校验和**

没有这四道闸的协议不是不能跑，而是在第一起故障面前裸奔。本篇把它们一次装齐，并逐个验证每道闸真的会关。

## What

二进制协议帧是一种自描述的消息封装：帧头携带解释载荷所需的全部元数据（这是谁、什么版本、什么类型、多长），帧尾携带完整性证据，载荷只负责内容。

一句话心智模型：**帧头是快递面单——魔数是"本公司专用箱"、版本是"合同版本号"、类型是"货物类别"、长度是"内件数量"；CRC 是封箱章，章对不上箱就是坏的，拆都不拆**。

但和快递不同的是，二进制帧的每个字段都是**显式字节序列**，没有"默认格式"可言：长度 258 写成 `01 02`（大端）还是 `02 01`（小端），两端必须白纸黑字约定——本篇验收②就是一条手算断言。

帧格式规格（全部大端，总长 = 8 + n + 4）：

| 偏移 | 大小 | 字段 | 作用 |
|---|---|---|---|
| 0 | 4B | Magic `0x4E455443` | "NETC"，错位/串线帧的第一道闸 |
| 4 | 1B | Version = 1 | 旧实现明确拒绝，不误读 |
| 5 | 1B | Kind | 0x01 DATA / 0x02 PING / 0x03 PONG |
| 6 | 2B | Length = n | 载荷长度（大端） |
| 8 | nB | Payload | 载荷 |
| 8+n | 4B | CRC32 | 覆盖 Magic 到 Payload 全部字节 |

## When to Use

自定协议帧适合这些时刻。

- **长连接业务协议**：IM、推送、游戏——消息类型多、演进周期长，版本号与类型白名单是生命周期投资
- **二进制载荷为主**：音视频帧、序列化对象——文本协议的转义与膨胀不可接受
- **不可信网络路径**：跨公网、经代理——CRC 与长度上限让损坏与恶意输入止步于解码层

何时不用：请求-响应业务直接 HTTP/gRPC（帧、版本、校验它们都定义好了）；纯内部短距离调试通道，RESP 式文本协议更好查（项目 7 对比）。`net.TCPConn` 层面上，凡是把项目 2 的裸长度前缀直接上生产的冲动，都应升级为本篇的完整帧。

| 防护 | 裸长度前缀 | 本篇完整帧 |
|---|---|---|
| 错位/串线识别 | ❌ | ✅ 魔数 |
| 版本共存 | ❌ | ✅ Version |
| 未知消息 | 解析成乱码 | ✅ Kind 白名单 |
| 比特损坏 | ❌ | ✅ CRC32 |
| 长度欺骗 | 可加上限 | ✅ 上限 + CRC |

## Quick Start

前置条件：Go 1.21+，127.0.0.1:19551。运行：

```bash
cd net/05_binary_protocol
go run .
```

真实输出：

```text
== 第 1 步：一帧的字节长什么样（hexdump 逐字段讲解）==
  [ 0..3 ] Magic(NETC)    4e 45 54 43
  [ 4..4 ] Version        01
  [ 5..5 ] Kind           01
  [ 6..7 ] Length         00 0b
  [ 8..18] Payload        68 65 6c 6c 6f 2c 20 4e 45 54 43 = "hello, NETC"
  [19..22] CRC32          26 c6 64 9f
  总长 23 字节

== 第 2 步：100 帧往返（DATA×50 + PING→PONG + 1 帧损坏注入）==
服务端直方图：map[BAD(被CRC/类型拒绝):1 DATA:53 PING:1 PONG(客户端收到):1]
客户端发送：DATA 50 + PING 1 + 坏帧 1 + 坏帧后好帧 3
⇒ CRC 把坏帧拦在应用之外，长度前缀让后续好帧无缝重新同步。
```

测试验收（`-race` 下连跑 3 轮全绿；fuzz 的正式靶场在项目 6）：

```bash
go test -race -count=3 .
```

诚实预期：直方图里的 `DATA:53` = 50 条随机 + 3 条坏帧后的好帧；坏帧 bit-flip 的位置每次相同（代码固定翻 `payload[3]`），CRC 值每次运行相同（载荷固定 "corrupt-me"）。

## How It Works

### 解码检查的次序：从便宜到昂贵

`DecodeFrame` 的六步检查有严格次序：结构长度 → 魔数 → 版本 → 长度上限 → 截断 → CRC → 类型。

这个次序不是随意的：魔数比对是 4 字节比较，CRC 要跑完整个载荷，而"按声明长度分配内存"是最贵且最危险的一步——所以长度上限检查必须排在分配之前。

你在输出里看到的每类失败都对应一个哨兵错误（`ErrBadMagic`/`ErrBadVersion`/`ErrTooLarge`/`ErrBadCRC`/`ErrBadKind`），调用方用 `errors.Is` 分诊，项目 6 的 fuzz 将逐条轰炸它们。

### 坏帧之后为什么还能继续

CRC 拦截演示的关键细节：坏帧被拒后，**后续 3 条好帧在同一连接上正常解析**。

原因是长度前缀的自同步性质——CRC 检查失败时帧头有效、整帧字节已按 Length 精确消费完毕，流的位置正好落在下一帧开头。对比：若坏掉的是 Length 字段本身，边界就不可知了，只能断链重连。这也是解码器把 `ErrBadCRC`（可恢复）与 `ErrBadMagic`（不可恢复）分成两类错误的原因。

### 字节序：一张手算断言值多少钱

验收②断言了 258 字节载荷的帧头必须逐字节等于 `4e 45 54 43 01 01 01 02`——末两字节 `01 02` 就是 258 的大端写法（高位在前）。

若实现偷偷用了本机字节序（x86/ARM 都是小端），写出来会是 `02 01`，解码端按大端读出 513，直接洞穿。`encoding/binary.BigEndian` 显式指定加这条手算断言，字节序陷阱就永久关死在测试里。

## Pitfalls & Q&A

- **改字段不重算 CRC**：现象是想构造"未知类型"帧测试类型检查，结果报的是 CRC mismatch。原因：CRC 覆盖类型字节，改了类型必须重算校验和。本项目实录——修复后的测试恰好验证了"CRC 合法但类型未知"这条真实路径（新版对端场景）
- **CRC 放帧头而不是帧尾**：现象是不得不先算"含 CRC 字段的全帧"校验和——CRC 覆盖自身在数学上是绕圈。解法：CRC 永远放尾部，只覆盖前面的字节
- **长度上限检查晚于内存分配**：现象是畸形帧头触发大额分配。解法：`n > MaxPayload` 判断必须在 `make([]byte, n)` 之前，本项目两处（全量/流式解码）都先验后分
- **魔数与版本二选一**：现象是升级版本后旧实现解析新帧出乱码。原因：只靠魔数区分协议族，版本演进没有出口。解法：魔数定协议族、版本号定代际，二者缺一不可

**Q：CRC32 每帧 4 字节，开销值得吗？**
A：`crc32.ChecksumIEEE` 有硬件加速（SSE4.2），1GB/s 级吞吐，23 字节帧的校验耗时可忽略。

它防的是内存翻转与传输位错，不防恶意篡改（攻击者可重算 CRC）——防篡改要用 HMAC，那是项目 21 mTLS 之外的另一层，按威胁模型选。

**Q：为什么 PING/PONG 在应用层做，不用 TCP keepalive？**
A：TCP keepalive 只能证明"内核的连接还活着"，证明不了"对端应用还能处理消息"——应用死锁时 keepalive 依然全绿。

应用层 PING/PONG 穿过整个协议栈，才是端到端健康检查；本项目实测 PING→PONG 往返约 1ms（loopback）。

**Q：帧头 8 字节会不会太浪费？**
A：看载荷分布。50 字节载荷开销 16%，1000 字节只有 1.2%；真实协议还会做头压缩（QUIC 的 HPACK 同思路）。本篇用 2 字节长度 + 1 字节类型已经比 HTTP/2 的 9 字节帧头精简——浪费与否取决于最小载荷的设计，而不是头本身。

**Q：版本号怎么演进才不破坏兼容？**
A：规则三步：加字段只加在尾部（旧解码器按 Length 截断，不读不懂的部分）；改语义必须升 Version 并在握手期协商（回 PONG 带版本）；两个 Version 并存运行一个发布周期再下线旧版。本篇的 Version 检查就是"协商失败即拒绝"的最小实现。
