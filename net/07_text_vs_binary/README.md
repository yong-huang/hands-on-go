# 07 · 文本协议 vs 二进制协议：nc 直连的调试性与被淹没的解析开销

> 同一个 KV 语义做两版协议：RESP 风格文本（nc 直连手敲即调试）与 NETC 二进制帧（项目 5 同款）。实测两轮基准后得到一个反直觉结论：回环 TCP 上端到端吞吐差距不足 2%——RTT 把解析开销完全淹没；剥离网络后的纯解码基准才见真章。选型的正确依据因此不是快慢，而是可调试性与带宽。

## Background

项目 2 把消息边界从 TCP 字节流里收了回来（帧协议），项目 5 给帧装上了四道闸，项目 6 验证了它的健壮性。到了定义"命令长什么样"这一层，所有协议设计者都会在同一个岔路口停下：**命令用文本还是二进制？**

文本阵营的代表是 Redis 的 RESP：`SET key value` 一行即可，telnet 就能当客户端。二进制阵营的代表是 HTTP/2 与 protobuf：帧头紧凑、零转义、类型明确。

两个阵营的论战从 1990 年代打到今天，但双方的核心论据经常是错的——"文本慢"的论断在 RTT 面前往往站不住，"二进制可读性差"的论断也忽视了 hexdump 工具的成熟。

本篇不站队，做实验：同一 KV 语义、同一台机器、同一条回环链路，两版协议各跑一遍端到端吞吐与纯解码基准，把"网络"和"解析"两个变量拆开看。

## What

文本协议与二进制协议是应用层消息格式的两极：前者用人类可读字符定义命令与边界，后者用紧凑字节布局。对比的维度不是"谁更好"，而是四个可测属性：**解析开销、每消息字节数、可调试性、转义成本**。

一句话心智模型：**文本协议是明信片——内容直接可读，但格式受字符集约束（含 CRLF 就得转义）；二进制协议是装箱单——紧凑精确，但拆箱得靠说明书（帧格式文档）**。

但和明信片/装箱单的比喻不同的是，性能差距必须实测而不能想当然：本篇端到端基准里二进制只快了 1.7%，纯解析基准里反而各有所长（见下）——直觉里的"数量级差距"在真实网络路径上经常不存在。

两种封装的具体形态（同一 SET/GET/DEL 语义）：

| | 文本（RESP 风格） | 二进制（NETC 帧） |
|---|---|---|
| SET 请求 | `SET k v\r\n`（命令+空格+CRLF） | 帧头 8B + 载荷 `k v` + CRC 4B |
| GET 响应 | `$5\r\nalice\r\n` 或 `$-1\r\n` | 帧头 8B + 载荷 + CRC 4B |
| 调试方式 | `nc 127.0.0.1 19561` 直接手敲 | hexdump + 协议文档 |
| 含 CRLF 的值 | 必须转义（RESP 用长度行绕开） | 天然支持（长度定界） |

## When to Use

文本与二进制的选型发生在"定义新协议"的时刻，判断依据是四个属性的权重。

- **运维/协议设计期需要肉眼可读**：配置面、管理面、入门级服务——文本的 `nc` 可调试性是杀手锏（本篇第 2 步实录）
- **二进制载荷为主或带宽敏感**：音视频帧、序列化对象、跨 WAN 高频消息——零转义与紧凑头是硬需求
- **需要无脑互操作**：文本协议的解析器十行写完（bufio.Scanner），生态门槛最低

何时不用：两边都不选——直接用 HTTP/gRPC 时它们的选型已经做完；Redis 类现成中间件自带 RESP，没有理由重造。

| 维度 | 文本（RESP 风格） | 二进制（NETC 帧） | 胜者 |
|---|---|---|---|
| 端到端 ops/s（回环） | ~57.6K | ~56.2K | 平手（差 1.7%，RTT 主导） |
| 纯解析 ns/往返 | ~87 | ~98 | 文本（简单行扫描） |
| 每消息字节数 | 92B（SET+响应） | 89B（同语义） | 二进制（载荷越长差距越大） |
| 转义成本 | 需要（值含 CRLF 时） | 零 | 二进制 |
| 可调试性 | nc 手敲 | hexdump | 文本 |

## How It Works

### 为什么端到端分不出胜负：RTT 淹没一切

回环链路上一次 SET→响应往返约 35µs，其中 TCP 栈与内核路径占掉 30µs+，协议解析只贡献 0.1µs 量级。两版协议的解析差距（87 vs 98ns）被 RTT 摊薄成 1.7% 的端到端差——这就是"网络测量会掩盖协议差异"的直接证据。

推论：**判断协议快慢，先问瓶颈在哪一层**；跨 WAN 场景每消息字节数（带宽成本）反而升为主项，那是二进制的主场。

### nc 实录里每个响应的形状

`+OK`/`-ERR` 是简单状态行；`$5\r\nalice\r\n` 是 bulk string——**长度行先行**，这正是 RESP 对"值里含 CRLF"的解法：解析器按声明长度读满 5 字节即可，值内容是任意字节，转义问题被长度前缀消灭（项目 2 的思想在文本协议里的翻版）。

`$-1` 表示 nil，`:1` 是整数响应。这套前缀约定让文本协议获得了二进制式的长度定界能力，代价是比纯行协议多一次往返解析。

### 纯解析基准怎么隔离变量

`BenchmarkParseOnly` 把两协议各自的"一个完整往返"（请求+响应）预编码成字节流，基准循环里只做解析不碰 socket。这样测出的 87 vs 98ns 才是解析本身的成本。

方法论要点：**端到端基准回答"用户感知多少"，微基准回答"成本在哪"**——两个数字需要同时存在，缺了前者会高估优化收益，缺了后者会找不到优化位置。

## Pitfalls & Q&A

- **在 RTT 主导的链路上比协议解析**：现象是测出"两协议一样快"就断言协议无差别。原因：回环 RTT 35µs 是解析开销的 400 倍。解法：分两层测量（本篇双基准），并在结论里写明层次
- **文本值的 CRLF 陷阱**：现象是值里含换行时流被切断。原因：纯行协议没有转义机制。解法：用 RESP 的长度行前缀（本篇 GET 响应同款），或换二进制帧
- **基准连接共享全局 KV 锁**：现象是并发基准测出来的是锁竞争而不是协议。解法：每连接独立 KV 实例（本项目实录），把共享状态从测量路径上摘掉
- **拿回环数字外推公网行为**：现象是"文本也不慢啊"。原因：跨 WAN 带宽成本与丢包重传的比例完全不同。解法：结论只对测量环境负责，跨环境要重测

**Q：既然解析开销差距这么小，什么时候性能才成为选型理由？**
A：三个条件下二进制的解析优势才会兑现：单连接高吞吐（几十万 QPS 级，解析占比放大）、CPU 紧张的代理/网关（解析成本乘以转发倍数）、超大消息（文本解析是 O(n) 扫描，二进制长度前缀是 O(1) 定界）。

日常业务 API 的 QPS 下，永远轮不到解析开销说话。

**Q：为什么项目 2 的定界基准里分隔符最慢，这里文本反而略快？**
A：测量对象不同。项目 2 是"从字节流切出消息"（分隔符逐字节扫描吃亏）；本篇文本路径每行都是一次 `ReadString`（bufio 缓冲批量拷贝），且二进制多了 CRC32。

协议内部结构不同，同一族协议的相对快慢不能跨篇外推——这恰是"别背结论、要跑测量"的例证。

**Q：RESP 的长度行不是把文本协议变得和二进制一样了吗？**
A：定位能力确实一样了（长度定界），但保留了文本的全部可调试性——`nc` 里你看到的仍是 `+OK\r\n`、`$5\r\n`。

RESP 的聪明之处在于只在"边界"处借用二进制思想（长度前缀），"内容"仍保持明文。混合风格正是工程协议的主流形态（HTTP/1.1 的 Content-Length 同款思路）。

**Q：本篇和项目 8 的多路复用是什么关系？**
A：本篇的协议都是"一问一答"（请求发一条、响应读一条）。项目 8 引入请求 id 后，同一条连接上可以同时挂着 100 个未决请求——那时协议要新增的不是一个字段，而是一整套"响应乱序归来如何配对"的机制。
