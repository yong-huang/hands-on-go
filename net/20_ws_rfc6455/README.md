# 20 · 手写 WebSocket（RFC6455）：握手、帧、心跳与关闭握手

> 不用任何第三方 ws 库，纯标准库实现 WebSocket 服务端核心三件：Upgrade 握手（Accept key 对 RFC 示例值断言）、帧编解码（FIN/opcode/mask/三档长度，客户端帧强制掩码）、心跳与关闭握手。掩码编解码的顺序错误被逐字节对拍当场抓出——载荷写两遍，帧长直接多出一份。

## Background

WebSocket 是浏览器里唯一的全双工长连接通道：HTTP 完成握手后协议升级，连接保持，两端随时互发消息。

它解决的问题 HTTP/1.1 做不到——轮询的延迟与浪费、SSE 的单向限制。

市面上 Go 的 ws 库（gorilla/websocket、nhooyr/websocket）都很好，但本篇刻意不用。

握手的一个 base64 计算、帧头的三档长度编码、掩码的循环异或——这些 RFC6455 的核心机制每一环都足够小，亲手写一遍之后，"帧是怎么被解析的""为什么客户端帧必须掩码"就从文档知识变成肌肉记忆。

项目 11 讲过 h2 的流复用，WebSocket 是它的"前一代"答案：h1 时代的长连接方案，至今仍是浏览器实时通信的标配。

## What

WebSocket 协议是 HTTP 之上的全双工消息协议：HTTP Upgrade 请求把连接升级为双向字节流，此后按帧（frame）收发，帧头声明操作码（文本/二进制/心跳/关闭）与载荷边界。

一句话心智模型：**WebSocket 是把一通电话挂在了 HTTP 的门牌上——握手（Upgrade）是拨号接通，帧是通话里的每句话（带类型标签），Ping/Pong 是"喂，还在吗"的确认，Close 是双方说"挂了"**。

但和打电话不同的是，客户端发往服务端的每句话都要"加密"（掩码——异或一个 4 字节随机密钥），这是 RFC 防止缓存代理被旧协议实现污染的历史设计；服务端发往客户端则不需要。理解掩码方向是读懂帧格式的关键。

帧格式解剖（本篇实现）：

| 字段 | 大小 | 含义 |
|---|---|---|
| FIN + opcode | 1B | 分片结束标志 + 操作码（text/binary/ping/pong/close） |
| mask + len(7) | 1B | 掩码位 + 长度（≤125 直接放） |
| 扩展长度 | 2B/8B | 126 触发 16 位、127 触发 64 位 |
| 掩码密钥 | 4B | 仅客户端帧携带 |
| 载荷 | nB | 客户端帧已掩码 |

## When to Use

WebSocket 适合"两端都主动发消息、连接长期保持"的时刻。

- **聊天/协同编辑**：双向独立消息流，任何一端随时说话
- **实时行情/推送面板**：服务端高频推送 + 客户端低频确认/订阅变更
- **在线状态与互动**：游戏、协作白板、直播弹幕——延迟敏感的双向小消息

何时不用：单向推送（服务端→客户端）用 SSE 更简单；请求-响应语义走 HTTP/gRPC；需要跨语言强类型契约时 gRPC 的流式更系统。

| 方向 | 方案 | 复杂度 |
|---|---|---|
| 单向推送 | SSE | 极低 |
| 双向（浏览器） | WebSocket | 中（心跳/重连自管） |
| 双向+强类型 | gRPC-Web | 中高 |

```bash

go test -race -count=3 .
```

测试验收（`-race` 下连跑 3 轮全绿；真实连接 echo 实录）：

```text
    握手: HTTP/1.1 101 Switching Protocols
    握手: Sec-WebSocket-Accept: F4ZcmYPZ+l3SCEg6LN+SYcdttAo=
    echo: "hello ws"
--- PASS: TestDemoInteraction (0.20s)
```

诚实预期：Accept-Key 的值随客户端 key 变化（每连接随机）；RFC 示例 key（`dGhlIHNhbXBsZSBub25jZQ==`）对应的 Accept 值（`s3pPLMBiTxaQ9kYGzzhZRbK+xOo=`）是常量断言。

## How It Works

### 握手：一条 HTTP 请求换一条双向连接

客户端发 Upgrade 请求并携带随机 `Sec-WebSocket-Key`；服务端把 `key + 魔术串（258EAFA5-E914-47DA-95CA-C5AB0DC85B11）` 做 SHA1+base64 得到 Accept 值回执。

这个计算的意义是**证明服务端理解 WebSocket 协议**——缓存代理无法伪造回执，旧协议实现会把它当普通响应缓存（握手请求不可缓存头也在防这个）。RFC 示例断言：`dGhlIHNhbXBsZSBub25jZQ==` → `s3pPLMBiTxaQ9kYGzzhZRbK+xOo=`，本篇测试逐字符比对通过。

### 帧编解码：三档长度与掩码方向

帧头的 7 位长度是三级触发器：≤125 直接放、126 触发 2 字节 16 位扩展、127 触发 8 字节 64 位扩展。

**客户端帧必须掩码**（4 字节密钥循环异或载荷）——这是防"恶意字节流欺骗中间代理"的历史设计，服务端帧不掩码。

开发实录：第一版 `EncodeClientFrame` 先用 `EncodeFrame` 编出"含载荷的完整帧"、再追加掩码载荷——载荷在帧里出现了两遍，帧长 12 而非 10，逐字节对拍当场抓出。正确的布局是 `[头部(含 mask 位)][掩码密钥 4B][掩码后载荷]`，头部单独编码。

### 心跳与关闭：两个"说好再挂"的仪式

Ping/Pong 是保活协议：任何一端发 Ping，对端必须尽快回 Pong（载荷原样返回）——服务端超时未收到任何活动即断连（本项目 pongTimeout=2s）。

Close 帧是关闭握手：先发 Close 的一方收到对端回的 Close 帧后才断开——这不是可有可无的礼貌，是让 TCP 的四次挥手由应用层发起，避免 RST 丢数据。实测：客户端发 Close（code=1000）后收到服务端回的 Close，随后连接关闭。

## Pitfalls & Q&A

- **EncodeFrame 复用导致载荷写两遍**：现象是客户端帧长度 12（应 10）、解码载荷与原始不符。原因：EncodeFrame 返回含载荷的完整帧，再 append 掩码载荷等于载荷重复。解法：客户端帧编码单独拼头部（长度字段带 mask 位），载荷只 append 一次（本项目实录）
- **握手读掉的缓冲字节丢失**：现象是握手后第一帧解析错乱。原因：用 bufio.Reader 读握手头，但连接后续直接用 conn.Read——缓冲区里可能还压着第一帧的字节。解法：握手与数据帧共用同一个 bufio.Reader（本篇 connWrapper）
- **心跳超时设太短**：现象是正常空闲连接被服务端断开。原因：pongTimeout 小于网络往返+客户端心跳周期。解法：心跳周期 ≤ 超时的一半（本篇 2s 超时配 1s 心跳节奏的测试）
- **服务端帧也加掩码**：现象是浏览器/标准客户端解析失败。原因：RFC6455 仅强制客户端→服务端掩码，服务端帧带 mask 位属于协议违规。解法：EncodeFrame（服务端方向）不设 mask 位

**Q：为什么客户端帧必须掩码？**
A：历史安全设计：早期某些中间代理缓存了"响应内容由请求决定"的启发式，未掩码的攻击者帧可能被误当缓存响应投毒。掩码让客户端字节流不可预测，代理无法模式匹配。代价是每帧 4 字节密钥 + 一次异或——现代代理已不依赖该假设，但协议保留。

**Q：分片（fragmentation）是什么，本篇支持吗？**
A：一个大消息可拆成多个帧：第一帧 opcode=text/binary 且 FIN=0，后续帧 opcode=continuation，最后一帧 FIN=1。本篇解码层按单帧处理，分片聚合留作扩展——实现要点是按 opcode==continuation 把载荷依次 append，直到 FIN=1。

**Q：这和项目 11 的 h2 什么关系？**
A：WebSocket 从 h1 时代的补丁演化为 h2 时代的扩展（RFC8441 把 WS 跑在 h2 流上，复用连接与拥塞控制）。本篇的帧概念与 h2 的帧同源（opcode/长度/标志位），但 h2 的帧是协议内部的、用户不可见；WebSocket 帧是应用直接操作的。

**Q：生产部署还缺什么？**
A：三件：大消息的分片聚合、按消息类型的消息边界语义（text 必须是合法 UTF-8）、断线重连与消息序号。它们都是工程可靠性而非协议正确性——协议核心（握手/帧/心跳/关闭）本篇已全覆盖。
