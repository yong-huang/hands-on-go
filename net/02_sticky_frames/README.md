# 02 · 粘包拆包：TCP 是字节流，不是消息流

> 发送方写 10 次，接收方可能 1 次读完，也可能 37 次读完——Read 的边界由内核说了算。本篇先逐字节发消息让"写 10 次 ≠ 读 20 次"当场现形，再实现定长、分隔符、长度前缀三种帧解码器从同一种乱流里完整还原消息，最后用基准分出三者高下。

## Background

项目 1 里连接的两端已经能互发字节，但"发一条消息"这个动作在 TCP 里并不存在。TCP 只承诺把字节按序、可靠地送到，不承诺保留 Write 的边界——两次 Write 的内容可能被合并成一次 Read 到达（粘包），一次大 Write 也可能被拆成多次 Read（半包）。

这件事在局域网演示里常被掩盖：小消息往往一次 Read 就到，程序"碰巧"跑对了。等放到真实网络——消息大小不一、Nagle 算法攒包、中间设备分片——边界错乱的 bug 才炸出来：解析到半条消息、把两条消息当一条。这就是"粘包"一词的来历（TCP 并没有粘，是应用层的错觉）。

解法是把消息边界放回应用层：既然字节流没有边界，就由协议显式定义边界——要么约定定长，要么约定分隔符，要么在每帧前写明长度。三种方案各有代价，本篇全部实现并用同一份逐字节乱流检验。

## What

帧解码器是一种把无边界字节流切回消息序列的组件：它消费 `io.Reader`，每次吐出一条完整消息，内部缓存"已到但未齐"的字节。

一句话心智模型：**解码器是一台切香肠机——进去的是连续的肉（字节流），出来的是片（消息）；切法（定长/看分隔符/读长度头）由协议决定，与香肠怎么进货（Read 怎么到达）无关**。

但和真实香肠机不同的是，进货永远不按整片到：Read 可能一次只给半片的肉，切香肠机必须把碎肉先存着，等凑齐再切——这就是解码器内部必须有缓冲的原因。

三种切法的帧格式：

| 方案 | 帧结构 | 边界如何确定 |
|---|---|---|
| 定长 | 64 字节一帧，短消息补零 | 帧长写死在协议里 |
| 分隔符 | 消息 + `\n` | 扫描到分隔符 |
| 长度前缀 | 2 字节大端长度 + 载荷 | 帧头自报长度 |

## When to Use

需要自己定义应用层消息时，就是选帧格式的时候。

- **内部服务间高频小消息**：长度前缀是事实标准——定界 O(1)、无转义烦恼、二进制载荷友好
- **运维/调试友好优先的协议**：文本 + 分隔符（Redis 的 RESP、各类行协议），`nc` 直连就能手测
- **遥测/信标类固定结构**：定长帧解码最快、实现最短，代价是浪费补零字节

何时不用：直接用 HTTP/gRPC 时，帧格式已由它们定义，不要自己再包一层；消息天然是行文本且频率极低时，`bufio.Scanner` 一行一读就够，不必造解码器。

| 方案 | 解码开销（本篇实测） | 主要代价 | 什么时候选它 |
|---|---|---|---|
| 定长 | ~17 ns/op，1 alloc | 补零浪费带宽、长度写死 | 固定结构遥测帧 |
| 分隔符 | ~158 ns/op，4 alloc | 逐字节扫描、内容需转义 | 文本协议、可调试性优先 |
| 长度前缀 | ~27 ns/op，2 alloc | 需要"先收齐帧头" | 绝大多数二进制协议 |

## How It Works

### 半包为什么必然发生

Write 只是把字节交进内核发送缓冲区，什么时候打成一个 TCP 段发出去、对端什么时候 Read，分别由 Nagle/拥塞窗口和对端调度决定。

所以第 1 步里 47 次 1 字节 Write 到了对端变成 20 次 Read，块长 1~4 字节完全随机。推论：**任何"按 Write 边界解析"的代码都是在赌运气**，正确做法只有一个——协议显式定界。

### 长度前缀：两阶段凑帧

```go
var head [2]byte
if _, err := io.ReadFull(r, head[:]); err != nil {
    return nil, err // 帧头没到齐就先欠着，下次接着凑
}
n := binary.BigEndian.Uint16(head[:])
if int(n) > d.Max {
    return nil, ErrFrameTooLarge // 长度字段不可信，先验再分配
}
msg := make([]byte, n)
io.ReadFull(r, msg)
```

`io.ReadFull` 是解码器的灵魂原语：差一个字节就阻塞等下一个 Read，多出来的字节留给下一帧。注意顺序——**先验长度上限、再按长度分配内存**，顺序反了就是一个 65535 字节的恶意帧头骗你分配 64KB 的漏洞（项目 6 会专门 fuzz 这条路径）。

### 基准数字怎么读

分隔符解码最慢（157ns、4 allocs）：`ReadByte` 逐字节过手、`append` 因容量不足反复扩容。

长度前缀 27ns、2 allocs：帧头一次凑齐、载荷一次分配。定长 17ns、1 alloc：一次 `ReadFull` 进预分配缓冲，零扫描。

都很快——单机每秒百万帧起步，瓶颈永远在网络而非解码；选型看的是语义（转义/长度上限/带宽浪费），不是这 100ns。

## Pitfalls & Q&A

- **分隔符内容不转义**：现象是消息里恰好含 `\n` 时被切错。原因：分隔符协议要求分隔符在载荷内不出现。解法：转义（如 RESP 的 `\r\n` 配长度行）或改用长度前缀
- **长度上限缺失**：现象是收到一个声明 2GB 长度的帧头后内存暴涨。原因：先分配后验证。解法：`n > Max` 直接断链并报 ErrFrameTooLarge（本篇解码器内置，测试 TestFrameTooLarge 覆盖）
- **定长帧忘了 trim 补零**：现象是消息尾部多出 `\x00`，等值比较失败。原因：补零是传输填充不是内容。解法：读出后按实际长度截断（本篇 `trimZero`）
- **基准里把网络算进去**：现象是三种解码器差距"消失"。原因：回环网络 RTT 数十微秒，把纳秒级解码差异淹没了。解法：基准只测解码器（内存流），网络归网络

**Q：bufio.Reader 的缓冲会不会"吃掉"下一帧的字节？**
A：不会——这正是用它的原因。`bufio` 会把一次 Read 到的多帧数据留在缓冲里，解码器按需消费；帧与帧的边界在缓冲内自然衔接。手写 `conn.Read` 切帧反而容易把"多出来的字节"扔掉。

**Q：三种方案能混用吗？**
A：能，且常见：帧头用长度前缀定界、载荷内部再用分隔符分字段（HTTP/1.1 就是"头按行、体按 Content-Length"）。混用的代价是协议复杂度，设计时一次说清，别让解码器猜。

**Q：为什么不用 `bufio.Scanner`？**
A：它就是内置的分隔符解码器（`ScanLines`），还有token 化接口。但默认 64KB 上限、只认分隔符、错误处理粗糙——本篇自实现是为了把"缓冲未齐"的机制看明白，业务代码里行协议直接用 `Scanner` 没问题。

**Q：流空了但帧没凑齐，怎么区分"对端关了"和"对端慢"？**
A：`io.EOF` 出现在帧中间 = 对端半关闭且数据不完整，这是协议级损坏，应报错而非静默接受；帧边界处的 `io.EOF` 才是正常收尾。本项目解码器对两者的返回值做了区分——帧中 EOF 会原样冒泡，调用方据此断链。
