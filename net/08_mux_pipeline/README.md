# 08 · 单连接多路复用：请求 id、pending 表与队头阻塞的量化

> 一问一答的连接同一时刻只挂一个请求；多路复用让 100 个请求同时在途——每个带唯一 id，唯一的读循环按 id 把乱序归来的响应分发给等待者。本篇实现这套机制并量化它的核心收益：慢请求注入 200ms 后，99 个快请求仍毫秒级完成；停等对照里它们被逐个压后。断线瞬间，全部 in-flight 请求立即得到错误而非永久悬挂。

## Background

项目 7 的两版协议在测量里打平，但都输在同一个结构限制上：一问一答。前一响应没回来，下一个请求就不能发（或发了不敢发）——链路的往返时延（RTT）被逐次累加，100 个请求就是 100 个串行 RTT。

这个限制的工业级解法是多路复用（multiplexing）：给每个请求编上唯一 id，请求可以全部立即发出；响应按**完成顺序**（而非发出顺序）返回，客户端的读循环按 id 把它们分发给各自的等待者。

HTTP/2 的 stream、gRPC 的 RPC 编号、HTTP/1.1 的 pipeline 失败后催生的所有现代协议，核心都是这一张 pending 表。

为什么值得亲手写一遍？因为多路复用把"一问一答"里隐藏的三个新问题一次性暴露：响应乱序了怎么配对、半包的帧怎么在流里重组成完整响应、连接死了那些在途请求找谁算账。

三个问题对应三段代码，缺一段都是生产事故。

## What

单连接多路复用是一种并发请求模式：一条 TCP 连接上同时承载多个未决请求，靠请求 id 关联响应，用一张 pending 表（in-flight 请求的登记簿）完成乱序配对。

一句话心智模型：**pending 表是餐厅的取餐牌——点单时给你一个号码（seq），后厨（服务端）按完成顺序出餐，取餐口（读循环）喊号，谁点的那份谁领走；号码对不上谁的，谁就一直等（或餐厅倒闭时全员退款）**。

但和取餐牌不同的是，"响应乱序"在这里是常态而非事故：慢餐（慢请求）排在后面出，快餐不等它——这正是与停等的本质区别。

帧格式与三个实验的实测数字：

| 帧 | 格式 | 说明 |
|---|---|---|
| 请求 | `[0x01][seq 4B][len 2B][payload]` | seq 客户端分配，单调递增 |
| 响应 | `[0x02][seq 4B][len 2B][payload]` | 按完成顺序乱序返回 |

## When to Use

多路复用适合高并发、单连接、请求有快有慢的时刻。

- **同一服务的密集小请求**：数据库/缓存连接上的并发查询——复用一条 TCP 连接省掉握手与端口开销，慢查询不再拖累快查询
- **移动端到后端的长连接通道**：IM 消息、推送、心跳共用一条连接，各自独立等待
- **延迟敏感的扇出调用**：一次页面渲染并发拉 20 个后端接口，任何一个超时都不影响其余 19 个返回

何时不用：请求本身就串行（后一步依赖前一步结果）时，复用没有收益；HTTP/1.1 时代用连接池开多条连接也能绕开队头阻塞（代价是每条连接一次握手）；直接用 HTTP/2/gRPC 时，多路复用已经内建。

| 方案 | 同连接并发 | 队头阻塞 | 复杂度 |
|---|---|---|---|
| 停等（项目 4/7） | 1 | ✅ 逐个压后 | 最低 |
| 连接池（多条 TCP） | 每连接 1 | 池内互不影响 | 中（连接管理） |
| 多路复用（本篇） | N | 仅传输层（TCP 丢包）仍共享 | 高（id/乱序/半包） |

```text
== 第 1 步：100 并发请求经单连接乱序返回，按 seq 全部正确配对 ==
  配对 100/100，耗时 1ms，乱序返回 46 次

== 第 2 步：队头阻塞量化——慢请求（SLOW）注入 200ms，看快请求何时完成 ==
  多路复用：总耗时 1ms——99 个快请求毫秒级完成，SLOW 的 200ms 与它们并行
  停等对照：总耗时 4ms，最后一条请求在 4ms 才发出——被前面 99 次串行往返逐个压后
  ⇒ 若把 SLOW 换成一条大响应或网络拥塞，停等的逐个压后就是队头阻塞；
     多路复用让快慢请求共享一条连接而不共享命运（HTTP/2 的核心动机）。

== 第 3 步：断线不悬挂——关闭后 in-flight 全部立即收到 ErrClosed ==
  50 个 in-flight 请求在关闭后 0s 内全部收到 ErrClosed
```

诚实预期：演示里停等对照总耗时只比多路复用多几毫秒——因为回环 RTT 只有几十微秒，99 次"逐个压后"的代价是小倍数；把 SLOW 换成 200ms 的响应体（而非思考时间）或把 RTT 换成 20ms 的公网，倍数会立刻拉开。测试把不变式写成了断言：快请求自身往返 ≤50ms、断线后 100ms 内全部返回。

## How It Works

### pending 表：三行代码的状态机

```go
ch := make(chan muxResult, 1)
m.pending.Store(seq, ch)   // 发出前登记
// ... conn.Write(请求) ...
select {
case r := <-ch:            // 读循环喊号
case <-m.closed:           // 或餐厅倒闭
}
```

每个请求一个容量为 1 的 channel：读循环拿到响应就 `Load(seq)` 投递，等待者从 channel 取走。

容量 1 保证"响应先到、等待者后取"与"等待者已在等"两种时序都不阻塞读循环——这一点在响应乱序时是正确性的关键。删除 pending 记录的责任在接收方（取走即删），pending 表因此不会膨胀。

### 读循环：唯一的读取者，半包在这里消失

`readLoop` 是整条连接唯一的读取者，它把 `Read` 的字节累积进缓冲、按帧头声明的长度切帧——项目 2 的长度前缀在这里的变体形态。切出的每个响应帧按 seq 查表分发，乱序是天然的（表里只认号码，不认顺序）。

若用多个 goroutine 并发读同一条连接，帧会互相撕碎——"单读循环 + 分发"是多路复用客户端的铁律。

### 断线清算：Once + Range 的广播

```go
func (m *MuxClient) failAll(err error) {
	m.once.Do(func() {
		m.pending.Range(func(k, v any) bool {
			v.(chan muxResult) <- muxResult{err: ErrClosed}
			m.pending.Delete(k)
			return true
		})
		close(m.closed)
	})
}
```

连接断了，pending 表里每个未决请求都欠一个结局。

`sync.Once` 保证清算只发生一次；`Range` 遍历全部在途请求逐个投递错误；`close(m.closed)` 兜住"还没登记上表的请求"。三条路合起来构成验收③的不变式：任何 Call 要么拿到响应、要么拿到 ErrClosed，没有第三种命运。

## Pitfalls & Q&A

- **按 seq 判定"哪个是慢请求"**：现象是注入 200ms 后被拖住的请求每次不同。原因：seq 由客户端并发分配，测试的 goroutine 编号与 seq 没有对应关系。解法：注入策略按 payload 判定（本项目实录，`slowSleeper("SLOW")`）
- **把 goroutine 晚发起当成队头阻塞**：现象是某个快请求"往返 201ms"，但它根本是 201ms 时才发起。原因：测量的起点选错（实验开始 vs 自身发起）。解法：不变式按"自身往返耗时"断言，发起时刻是随机变量
- **测试自己的数据竞争**：现象是 `-race` 报测试代码 race（README 都写好了，测试挂了）。原因：多 goroutine 累加统计量无锁。解法：统计归拢到锁内或 channel，测试代码与生产代码同一标准
- **响应 channel 容量给 0**：现象是响应先到时读循环卡死在投递上，整个连接停摆。原因：无缓冲 channel 要求收发会合，而读循环是唯一读取者、不能被单个等待者绑架。解法：容量 1（本篇）或事件循环全异步化

**Q：这和项目 4 的停等协议什么关系？**
A：同一棵树的两个分叉。停等窗口=1，靠"顺序即编号"省掉了 pending 表；本篇窗口=N，就必须显式登记配对。

TCP 自己的滑动窗口是多路复用的底层形态——应用层多路复用（HTTP/2）是在 TCP 已经多路复用之上再建一层，原因正是 TCP 层的队头阻塞（丢包时整个窗口重传）：应用层的流互不等待。

**Q：seq 会不会耗尽？**
A：会，必须设计回收。本篇 int32 递增，40 亿个请求后耗尽；工业做法是耗尽后关闭连接重建（HTTP/2 的 GOAWAY 语义之一），或按"pending 表为空即可重用号段"回收。demo 忽略了它，生产实现不能。

**Q：为什么不用连接池？**
A：连接池解决"并发"，不解决"队头阻塞"——池里每条连接仍是一问一答，慢响应只是从拖 1 条变拖 1/N 条。多路复用在单连接内消除排队；两者可以叠加（池内每条连接都多路复用）。

代价对比：连接池要管理建立/销毁/健康检查，多路复用要管理 id/乱序/断线清算——复杂度都不低，选型看瓶颈在哪。

**Q：下一步把它变成 RPC 框架还缺什么？**

- 超时与取消：pending 表里加 deadline，超时主动清算
