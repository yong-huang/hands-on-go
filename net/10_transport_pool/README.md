# 10 · http.Transport 连接池：keep-alive、调参与连接泄漏

> http.Client 背后的 Transport 默认每个 host 只保留 **2 条**空闲连接——50 并发的突刺建起 50 条连接，用完即裁，只剩 2 条进池，下一波突刺重新握手。本篇实测：1000 请求下默认参数建连 494 次，把 `MaxIdleConnsPerHost` 调到 100 后只要 53 次；再实测响应体未读尽的泄漏形态——10 次请求 10 条连接，读尽后 10 次只建 1 条。

## Background

TCP 连接的建立要三次握手、销毁要四次挥手，HTTP 请求本身可能只有几十微秒——如果每个请求都新建连接，握手开销就是主要成本。HTTP/1.1 的 keep-alive 机制让一条连接可以串多个请求，而 Go 把连接的复用管理全部收进了 `http.Transport`：请求结束，连接不关闭，放回池子等下一个请求。

池子的大小由两个参数控制：`MaxIdleConns`（全局空闲上限，默认 100）与 `MaxIdleConnsPerHost`（**每个 host** 的空闲上限，默认 2）。默认值的设计取向是"客户端少占资源"——但这意味着并发突刺建起的连接几乎全部被裁撤，下一波突刺全部重新握手。

另一类问题藏在"复用的前提"里：连接能回池的条件是响应体被**完整读取**。Body 没读尽就丢弃引用，Transport 无法确认流的位置，只能把整条连接废弃重建——这就是 Go 社区常说的"连接泄漏"，它不需要忘记 Close，读一半就够。

## What

连接池是一种把 TCP 连接的生命周期与 HTTP 请求解耦的复用机制：请求结束连接归还池中，后续请求按 host 取用，空闲超时统一回收。

一句话心智模型：**Transport 是一家出租车队——MaxConnsPerHost 是车队规模上限，MaxIdleConnsPerHost 是"排队候客区"的车位数；座位满了，刚收车的司机直接下班（连接关闭），下一批乘客来了车队重新出车（重新握手）**。

但和出租车队不同的是，"乘客没下车"会让车直接报废：响应体未读完的连接 Transport 不敢复用（不知道流走到哪了），只能整条丢弃——泄漏的形态是建连数随请求数线性增长。

三个参数的守门位置：

| 参数 | 默认 | 控制什么 |
|---|---|---|
| MaxIdleConnsPerHost | 2 | 每 host 池内空闲连接数——**突刺场景的第一瓶颈** |
| MaxIdleConns | 100 | 全局空闲连接总数 |
| IdleConnTimeout | 90s | 空闲连接的保质期，到点主动关闭 |

## When to Use

调 Transport 参数发生在"客户端打后端"的所有场景。

- **微服务间高频调用**：几十个并发 worker 打同一个下游——`MaxIdleConnsPerHost` 至少等于并发 worker 数，否则握手风暴
- **网关/代理转发**：上游突刺流量经客户端放大后打到下游，池参数决定下游的建连 QPS
- **批量作业**：脚本一次性打几千请求，读尽 Body 的纪律决定它是 1 条连接还是 N 条

何时不用：低频调用（每秒几次）时池参数无关紧要；只调一次的 CLI 工具，连复用都没意义。

| 配置 | 建连次数（1000 请求/50 并发，本篇实测） | 适用 |
|---|---|---|
| 默认（IdlePerHost=2） | 494 | 低频调用 |
| IdlePerHost=100 | 53 | 并发 worker 打同一下游 |
| Body 未读尽 | 每请求 1 条（10 次→10 条） | ——（反模式） |

## Quick Start

前置条件：Go 1.21+，127.0.0.1:19591。运行：

```bash
cd net/10_transport_pool
go run .
go test -race -count=3 .
```

真实输出（建连次数随调度浮动，量级与结论固定）：

```text
== 第 1 步：默认 Transport（MaxIdleConnsPerHost=2）==
  1000 请求（50 并发）→ 服务端建连 494 次，关闭 491 次，请求数 1000
  ⇒ 50 条并发连接用完即裁，池里只留 2 条空闲——下一波突刺重新握手。

== 第 2 步：调优 Transport（MaxIdleConnsPerHost=100）==
  1000 请求（50 并发）→ 服务端建连 53 次，关闭 0 次，请求数 1000
  ⇒ 突刺建起的 50 条连接全部进池保留，后续请求零握手复用。

== 第 3 步：响应体未读尽 → 连接被弃（泄漏形态）==
  10 次未读尽的 /big 请求 → 建连 10 次、关闭 0 次（每条连接用完即弃）
  10 次读尽再关闭的同样请求 → 建连 1 次、关闭 0 次（单连接全程复用）
  ⇒ 泄漏不是忘了 Close 才叫泄漏：Body 未排干，Transport 只能弃连接重建。

== 排查工具 ==
  watch -n 1 'netstat -an | grep 19591 | grep ESTABLISHED | wc -l'
```

测试验收（`-race` 下连跑 3 轮全绿；对照组带 2ms 处理延迟保证稳态）：

```bash
go test -race -count=3 .
```

## How It Works

### 池满即裁：默认参数的突刺行为

50 个并发 worker 同时打一个 host，瞬时需要 50 条连接；请求完成后连接归还池中，池只收 2 条，其余 48 条被 `close`。下一批请求到来时池里只有 2 条可复用，其余全部重新握手。

服务端的 ConnState 计数如实记录了这个循环：494 次建连、491 次关闭——**请求只有 1000 个，握手却做了 494 次**。调优后池容量 ≥ 并发数，突刺建起的连接全部保留，53 次建连（首次 50 + 零星波动）服务全部 1000 个请求。

### 未读尽的 Body 为什么毒死连接

Transport 归还连接前必须确认"响应已读完、流的位置在响应末尾"，否则下一次请求的响应解析会从上一个响应的残留字节开始——必错。

对小于 256 字节的响应，Transport 会自动排空补救；超过则要求调用方读完。64KB 的 `/big` 不排干就丢引用，Transport 只能关闭该连接——服务端视角是"建连数线性上涨"，客户端视角是"没有任何报错"。

这类泄漏的正确排查姿势正是服务端 ConnState 计数（或 netstat 的 ESTABLISHED 条数）：**建连 QPS 与请求 QPS 出现 1:1 时，连接池已经名存实亡**。

### netstat 排查三步

```bash
# 1. 实时观察客户端到服务端的连接数（本篇端口）
watch -n 1 'netstat -an | grep 19591 | grep ESTABLISHED | wc -l'
```

排查三步：对照并发数——远大于并发 worker 数说明频繁重建中；再看服务端建连速率（ConnState 计数或访问日志的 TCP 连接标记）；最后回到客户端查 Body 排干纪律。

## Pitfalls & Q&A

- **只设 MaxIdleConns 不设 MaxIdleConnsPerHost**：现象是全局 100 的池对单 host 无效，突刺照旧握手。原因：单 host 上限被默认值 2 卡死，全局上限根本用不满。解法：两个参数成对配置，PerHost ≥ 并发 worker 数
- **基准里测出"协议无差别"（对照项目 7）**：现象是池参数调优前后 ops/s 变化不大。原因：回环 RTT 太短，握手占比低。解法：看建连次数而非 ops/s——握手成本要在公网 RTT（几十 ms）下才放大成延迟
- **`-race` 下基准对照失真**：现象是调优/默认的差距缩到 2 倍以内。原因：race 检测拖慢执行，并发在途塌缩，池裁撤频率下降。
  解法：给 handler 注入固定处理延迟，把"50 并发持续在途"变成稳态（本项目实录，`delayNs` 旋钮）
- **用 short body 测泄漏**：现象是小响应不关 Body 也不泄漏。原因：Transport 对 <256B 的响应自动排空补救。解法：泄漏复现必须用超过自动排空阈值的响应体（本篇 64KB）

**Q：MaxConnsPerHost（注意没有 Idle）要不要设？**
A：它是"在途+空闲"的总上限。不设 = 并发无上限（本篇选择）；设了 = 超出并发的请求在客户端排队等待。打下游要限流保护时它就是客户端限流旋钮——设成下游容量的安全值，而不是默认的无限。

**Q：Body 读尽但忘了 Close 会泄漏吗？**
A：不会泄漏连接——读尽后连接已回池；泄漏的是 `resp.Body` 引用的资源（若有未缓冲残余）。规范写法永远是 `io.Copy(io.Discard, resp.Body)`（排干）+ `resp.Body.Close()`（释放），两步都写。

**Q：这和项目 9 的 IdleTimeout 什么关系？**
A：一条空闲连接的生死由两边的超时竞争决定：客户端 `IdleConnTimeout` 到点客户端关，服务端 `IdleTimeout` 到点服务端关，先到先关。

配对原则：服务端 IdleTimeout ≥ 客户端 IdleConnTimeout，让客户端先知先觉地重建，避免"服务端已关、客户端复用撞墙"的偶发 EOF。

**Q：连接池的这些坑在 HTTP/2 下还存在吗？**
A：形态改变。h2 单连接多路复用（项目 11）后，`MaxIdleConnsPerHost` 管的是连接条数（通常 1 条），并发全在流上；Body 未读尽的惩罚变成"流窗口被占满"（连接级背压）而不是连接重建。

新协议解决旧坑的同时带来新坑——测量方法论不变。
